從 pixel9a_memory_analysis_v2.8.5.md 來看，異常主要集中在 Graphics PSS：116MB → 223MB（+91%），約 5 分鐘後趨於平台；Native Heap / Private Other / System 都相對穩定。這比較像 GPU/Skia/GraphicBuffer（texture 快取或 buffer queue）成長，不太像一般 Java/Native heap leak。
以 repo 實作檢視，最可疑的來源不是 MLKit 本身，而是 「用 Compose Image(bitmap = previewBitmap.asImageBitmap()) 顯示即時預覽」：
CameraScreen.kt (line 148) 每幀訂閱 previewBitmap
CameraPreview.kt (line 41) 用 Compose Image 直接畫 Bitmap
實機預覽目前走 LiveCameraSource.getPreviewStream()：LiveCameraSource.kt (line 172) 每幀把 ImageProxy → Bitmap 推給 UI（即使 ML 分析節流到 2FPS，預覽仍可能是 30FPS 的 bitmap→texture 上傳/快取，這會吃 Graphics 記憶體）
另外一個風險點：目前 CameraScreen 只有 bind，沒有對應 unbind/stop（沒有 DisposableEffect / ViewModel.onCleared() 做釋放），在「切頁/背景前景」場景可能造成 Surface/UseCase 疊加，讓 Graphics 呈現階梯上升。
修正計畫（v2.8.6 建議分階段，最小差異優先）
Phase 0（半天～1天）：先把根因證據化（A/B 實驗）
目標：用最少改動判斷 Graphics 成長到底來自「Compose bitmap 預覽」還是「ML/overlay/surface」。

A/B 開關實驗

A：保留相機 bind + ImageAnalysis，但 CameraPreview 不渲染 bitmap（只顯示黑底/文字）
B：保留 bitmap 預覽，但 關閉 guideline overlay / composition overlay
C：保留 UI，但 暫停 observePreviewForAnalysis()（CameraViewModel.kt (line 463)）只看純預覽是否還長
觀察哪一組能讓 Graphics 不再上升（或更快平台化）
加入可觀測指標（debug only）

在 LiveCameraSource 記錄：SurfaceProvider 建立/釋放次數、SurfaceTexture hashCode（看是否重複建立未釋放）
在 CameraPreview 記錄：每分鐘收到多少「不同 identity」的 Bitmap（texture churn 指標）
Phase 1（1～2天）：先解掉「離開頁面仍持有資源」的風險
目標：避免切頁/背景前景造成 Surface/UseCase 堆疊（這種最像 leak）。

在 CameraScreen.kt 加 DisposableEffect：
onDispose 時呼叫 viewModel.unbindCamera() / stopPreview()（需補齊 ViewModel/Repo API）
在 CameraViewModel 增加 override fun onCleared()：
通知 repository 做釋放（unbind、clear analyzer、必要時 BitmapPool.clear()）
在 CameraRepositoryImpl/LiveCameraSource 補齊「對外釋放入口」並確保：
LiveCameraSource.unbind() 會 unbindAll() + release previewSurface/previewSurfaceTexture（現有 LiveCameraSource.kt (line 552) 已做，但需要確保真的會被呼叫到）
Phase 2（2～4天）：根治 Graphics 成長——把「預覽顯示」從 Bitmap 改成 Surface
目標：移除「每幀 Bitmap → Compose Image → texture upload」這條最吃 Graphics 的路徑。

實機（LiveCameraSource）改用 PreviewView 顯示 Preview UseCase
UI：用 AndroidView { PreviewView(...) } 承接預覽（SurfaceTexture 由 PreviewView 管）
Data：LiveCameraSource.bindToLifecycle() 不再用自製 customSurfaceProvider，改用 UI 提供的 previewView.surfaceProvider
Bitmap stream 改為「分析用途」而非「顯示用途」（或僅 emulator 使用）
emulator 繼續保留現行 Bitmap 顯示（維持測試模式能力），用 build variant / runtime 判斷切換
這一步通常會讓 Graphics PSS 明顯下降，且更快平台化；同時 CPU 也會大幅降（少了 YUV→ARGB 轉換供 UI 顯示）。

Phase 3（備案）：若短期無法導入 PreviewView
目標：在仍用 Bitmap 顯示的前提下，降低 texture churn。

強制 UI 使用「固定少量、固定 identity」的 bitmap（例如只用 1 張或 2～3 張 ring buffer），避免隨時間產生大量不同 Bitmap 實例
CameraPreview.kt 端避免在高頻路徑建立新 wrapper/物件（可改自訂 Painter 或固定記憶體策略）
