### 2.2 研究 ML Kit 行為

**問題**: v1.3.1 測試時沒有 Logcat 日誌，僅有截圖

**研究方法**:
- 使用 WebSearch 查詢 ML Kit 官方文件
- 查詢 Stack Overflow 相關討論
- 分析 CameraX 與 ML Kit 整合最佳實踐

**關鍵發現 1: ML Kit InputImage 內部旋轉行為**

來源: Google ML Kit 官方文件
```
InputImage.fromMediaImage(mediaImage, rotationDegrees)
```

重要理解：
- ML Kit 的 `InputImage.fromMediaImage()` **內部會旋轉影像**
- 返回的 bounding box 座標**已經在旋轉後的座標系**中
- 開發者**不需要再次應用旋轉轉換**

**關鍵發現 2: Stack Overflow 討論**

來源: [Translate Firebase MLKit Bounding box coordinates](https://stackoverflow.com/questions/60425960/)

重點：
- 座標轉換僅需 scale + offset
- 對於前置鏡頭需要 X 軸鏡像處理
- 現代做法推薦使用 `MLKitAnalyzer` + `COORDINATE_SYSTEM_VIEW_REFERENCED`

**關鍵發現 3: 已知 Bug**

來源: [ML Kit Analyzer landscape mode issue](https://stackoverflow.com/questions/79568457/)

- `androidx.camera:camera-mlkit-vision:1.4.0-alpha05+` 有 landscape 座標 bug
- 建議降級至 `1.4.0-alpha04`
- 但本專案未使用 `camera-mlkit-vision` 依賴，因此不受影響

### 2.3 根本原因分析

**v1.3.1 的錯誤假設**:
```kotlin
// v1.3.1 的錯誤邏輯
when (rotationDegrees) {
    0 -> { /* 直接映射 */ }
    90 -> { /* 應用 90° 旋轉矩陣 */ }
    180 -> { /* 應用 180° 旋轉矩陣 */ }
    270 -> { /* 應用 270° 旋轉矩陣 */ }
}
```

**錯誤點**:
1. 假設 ML Kit 返回的座標在**原始未旋轉的影像空間**
2. 手動應用旋轉矩陣轉換
3. 導致「雙重旋轉」問題

**實際情況**:
1. ML Kit 已經內部旋轉影像
2. 返回的座標已經在旋轉後的空間
3. 我們只需要：
   - 判斷是否需要維度交換（90°/270°）
   - 應用 FIT_CENTER 縮放
   - 應用居中偏移

#### 2. 完全重寫 transformRect() 函數

**移除內容**:
- 所有旋轉矩陣轉換（when 語句中的 90°, 180°, 270° 分支）
- 複雜的座標旋轉計算

**保留內容**:
- 維度交換判斷（90°/270° 時 needsSwap = true）
- FIT_CENTER 縮放邏輯
- 居中偏移計算

**新的實作邏輯**:
```kotlin
private fun transformRect(
    mlKitRect: RectF,
    imageSize: Size,
    previewSize: Size,
    rotationDegrees: Int
): Rect {
    // Step 1: 判斷是否需要維度交換
    val needsSwap = rotationDegrees == 90 || rotationDegrees == 270
    val effectiveImageWidth = if (needsSwap) imageSize.height else imageSize.width
    val effectiveImageHeight = if (needsSwap) imageSize.width else imageSize.height

    // Step 2: 計算 FIT_CENTER 縮放因子
    val imageAspectRatio = effectiveImageWidth / effectiveImageHeight
    val previewAspectRatio = previewSize.width / previewSize.height
    val scale = if (imageAspectRatio > previewAspectRatio) {
        previewSize.width / effectiveImageWidth
    } else {
        previewSize.height / effectiveImageHeight
    }

    // Step 3: 計算居中偏移
    val scaledWidth = effectiveImageWidth * scale
    val scaledHeight = effectiveImageHeight * scale
    val offsetX = (previewSize.width - scaledWidth) / 2f
    val offsetY = (previewSize.height - scaledHeight) / 2f

    // Step 4: 簡單的 scale + offset 轉換（無旋轉！）
    val transformed = Rect(
        left = mlKitRect.left * scale + offsetX,
        top = mlKitRect.top * scale + offsetY,
        right = mlKitRect.right * scale + offsetX,
        bottom = mlKitRect.bottom * scale + offsetY
    )

    return transformed
}
```

**關鍵差異**:
- ❌ v1.3.1: 應用旋轉矩陣 → 雙重旋轉 → 座標錯位
- ✅ v1.3.2: 僅 scale + offset → 正確轉換

## 四、技術分析總結

### 4.1 座標系統理解

**ML Kit InputImage 行為**:
```
原始影像 (480x640, rotation=90°)
    ↓ ML Kit 內部處理
旋轉後影像 (640x480)
    ↓ ML Kit 偵測
座標已在旋轉後空間 (x: 0-640, y: 0-480)
```

**我們需要做的**:
```
ML Kit 座標 (640x480 空間)
    ↓ 維度交換判斷 (needsSwap)
有效尺寸 (effectiveWidth × effectiveHeight)
    ↓ FIT_CENTER 縮放
縮放後尺寸 + 偏移
    ↓ 映射
螢幕座標 (1080x2400 空間)
```

## 七、關鍵學習點

### 7.1 技術理解

1. **ML Kit 的內部行為**
   - InputImage 會自動旋轉影像
   - 返回的座標已在旋轉後空間
   - 不要假設座標系統，要實際測試驗證

2. **座標轉換原則**
   - 理解每個座標系的來源和方向
   - 只應用必要的轉換
   - 過度轉換會導致錯誤累積

3. **除錯方法**
   - 查閱官方文件是第一步
