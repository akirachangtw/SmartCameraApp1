# Level 1: 規劃檢視 - v2.9.0 Pixel 9a 熱節流優化

## 📋 問題背景 (What / Why / Scope)

### What - 現象描述

**已知問題**（來自 v2.8.6 測試）：
- Pixel 9a 在 v2.8.6 測試中，ImageAnalysis FPS 在 4-6 分鐘後從 25-28 降至 12-20
- Sony Xperia 同版本全程穩定 24.5-27.4 FPS
- v2.8.5 Baseline 測試確認此為 **Pixel 9a Tensor G4 裝置特性（熱節流）**
- PreviewView 顯示不受影響，維持流暢 30 FPS

**技術細節**：
```
v2.8.6 Pixel 9a FPS 時間線：
T0 (0 min):   25.5-28.9 FPS  ✅ 優秀
T2 (4 min):   15.3-21.0 FPS  ⚠️ 開始下降 (-27%)
T3 (6 min):   11.9-14.1 FPS  🔴 最低點 (-52%)
T4 (8 min):   17.7-19.3 FPS  ⬆️ 短暫回升
T5 (10 min):  11.9-16.2 FPS  ⚠️ 再次下降

Graphics Memory: 穩定 63.8 MB（Phase 2 已修復洩漏）
CPU/GPU 負載: 未測量（推測為高負載導致熱節流）
```

### Why - 為什麼需要優化

**用戶體驗影響**：
1. **AI 構圖建議延遲** - FPS 下降 52% 導致分析反應變慢
2. **長時間使用體驗不佳** - 4 分鐘後效能明顯下降
3. **裝置特定問題** - Pixel 9a 是 Google 旗艦機，用戶期望高

**商業價值**：
- Pixel 9a 是主流 Android 旗艦，市場佔有率高
- 改善效能可提升 App 評價和留存率
- 為未來 Tensor 系列裝置建立優化基準

**技術價值**：
- 探索 CameraX + ML Kit 效能最佳化
- 建立跨裝置效能調適機制
- 累積熱管理經驗

### Scope - 優化範圍

**目標版本**: v2.9.0
**預期發布時間**: TBD（需完成 L1/L2 評估）

**優化目標**：
- **主要目標**: 延長 Pixel 9a 高 FPS 運行時間（4 分鐘 → 8-10 分鐘）
- **理想目標**: 維持 FPS ≥ 20 整個使用過程
- **最低目標**: FPS 最低點從 12 提升至 18 (+50%)

**不在範圍內**：
- ❌ 改變 Phase 2 PreviewView 實作（已驗證成功）
- ❌ 降低 AI 分析精度（維持現有品質）
- ❌ 支援更多裝置類型（專注 Pixel 9a）

## 🎯 潛在優化方向（變更影響範圍）

基於 v2.8.6 測試結果和架構分析，以下是可能的優化方向：

### 方向 1: Transform 處理優化 🔥 **最高潛力**

**現狀**：
- 使用 RenderScript `ENABLE_FUSED_TRANSFORM = true`
- 每幀執行：YUV → Bitmap → Rotate/Crop → ML Kit
- CPU 密集型操作（可能是主要熱源）

**優化方案**：
1. **GPU 加速 Transform**（Vulkan/OpenGL ES）
   - 將 YUV 轉換、旋轉、裁切移至 GPU
   - 減少 CPU 負載和發熱

2. **降低 Transform 頻率**
   - 動態調整：溫度高時降至 15 FPS
   - 漸進式降頻（25 → 20 → 15）

3. **優化 RenderScript 參數**
   - 調整 Thread Pool 大小
   - 使用 Low Power 模式

**預期效果**：⭐⭐⭐⭐⭐
- CPU 負載 ↓ 30-50%
- 發熱 ↓ 顯著
- FPS 穩定性 ↑

**風險**：⚠️ 中等
- 需要大量 GPU 程式碼開發
- 可能影響其他裝置（需廣泛測試）
- RenderScript 已 Deprecated（未來遷移成本）

---

### 方向 2: ML Kit 推論優化 🔥 **中等潛力**

**現狀**：
- Face Detection: `PERFORMANCE_MODE_ACCURATE`
- 每幀完整推論（即使畫面無變化）
- 使用預設 Executor（可能與 Camera 競爭資源）

**優化方案**：
1. **動態模式切換**
   - 初期使用 `PERFORMANCE_MODE_FAST`
   - 溫度高時降級至 `PERFORMANCE_MODE_ACCURATE`

2. **智能跳幀**
   - 檢測畫面變化，無變化時重用結果
   - 溫度高時跳幀（25 FPS → 12.5 FPS）

3. **NNAPI 加速**（如果支援）
   - 啟用硬體加速（GPU/NPU）
   - 減少 CPU 負載

**預期效果**：⭐⭐⭐⭐
- CPU 負載 ↓ 20-30%
- FPS 波動 ↓
- 推論延遲 ↓（FAST 模式）

**風險**：⚠️ 低
- 模式切換可能影響 UI 一致性
- 跳幀可能降低反應速度
- NNAPI 可用性未知

---

### 方向 3: 動態效能調整 (Thermal Management) 🔥 **實用性高**

**現狀**：
- 固定 FPS 目標（30 FPS）
- 無溫度監測
- 無動態調整機制

**優化方案**：
1. **溫度監測**
   - 使用 `ThermalManager` API (Android 11+)
   - 監控 CPU/GPU 溫度狀態

2. **漸進式降頻策略**
   ```
   溫度正常 → 25 FPS（ACCURATE 模式）
   溫度偏高 → 20 FPS（FAST 模式 + 跳幀）
   溫度過高 → 15 FPS（最小化 Transform）
   ```

3. **使用者通知**
   - 溫度高時顯示提示
   - 允許使用者手動切換省電模式

**預期效果**：⭐⭐⭐⭐
- 延長高效能運行時間
- 避免極端節流（12 FPS）
- 使用者體驗可預測

**風險**：⚠️ 極低
- 實作簡單，易於回滾
- 不影響核心功能
- 使用者可控制

---

### 方向 4: Bitmap Pool 進階優化 🔥 **效益有限**

**現狀**：
- v2.8.4 已實作 BitmapPool（達成 27.2 FPS 目標）
- Graphics Memory 已從 220 MB → 64 MB

**優化方案**：
1. **更激進的 Pool 策略**
   - 減少 Pool 大小（節省記憶體）
   - 使用 RGB_565 格式（減少頻寬）

2. **Bitmap 重用頻率調整**
   - 更快速的回收策略

**預期效果**：⭐⭐
- 記憶體 ↓ 10-20 MB
- 頻寬 ↓ 略微
- FPS 影響不大

**風險**：⚠️ 低
- 效益有限（BitmapPool 已優化）
- 可能降低畫質（RGB_565）

---

### 方向 5: ImageAnalysis 設定調整 🔥 **快速嘗試**

**現狀**：
- `STRATEGY_KEEP_ONLY_LATEST`
- 解析度：Preview 相同（1080p?）
- BackpressureStrategy 預設

**優化方案**：
1. **降低 Analysis 解析度**
   - 從 1080p → 720p（ML Kit 建議）
   - 減少像素處理量 -56%

2. **調整 Backpressure 策略**
   - 測試 `STRATEGY_BLOCK_PRODUCER`

**預期效果**：⭐⭐⭐
- Transform 負載 ↓ 56%
- ML Kit 推論 ↓ 30-40%

**風險**：⚠️ 低
- 可能影響偵測精度（需測試）
- 實作簡單，易於回滾
