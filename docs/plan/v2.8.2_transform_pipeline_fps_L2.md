## 1. 可行性結論（可行 / 不可行 / 需調整）
**需調整（可行但需先釐清與收斂路徑）**

理由（工程判斷）：
- 目前瓶頸明確在 `transformBitmap()`（Canvas + Matrix + clear + drawBitmap），且時間波動 8–31ms；要達到 **≥26 FPS**，理論上必須把 Transform 平均壓到 ~10–12ms 內、尖峰大幅減少。
- 但「把旋轉/鏡像移到顯示層/CameraX」(Plan A1) 是否可行，取決於 repo 現況：**輸出 bitmap 的用途**（只顯示？還要進一步給 analyzer/AI？）以及 **UI layer** 是否能接管旋轉/鏡像且不破壞 overlay 對齊。
- 另有一個高概率的抖動來源：目前 Transform 會依旋轉後 bounding box `ceil()` 計算 out w/h，可能造成 **BitmapPool key 分裂**與 pool miss → 重新配置/GC → Transform 尖峰。此項（Plan A3）通常能以最小 diff 顯著改善抖動，優先度應高於 A1。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX Rotation / Mirror 正確性**
   - 前鏡鏡像 + rotation 的順序非常容易出錯（尤其不同 sensor orientation）。
   - 若改為顯示層處理（A1），需確保「分析結果座標系」與「顯示座標系」一致，否則 overlay 會錯位。

2. **Analyzer Thread 與背壓**
   - 目前已改 `analysisExecutor` 單一背景執行緒；若 Transform 還在 analyzer 內做，時間過長會直接降低 delivered FPS。
   - `inFlightPreviewBuffers` 的 queue release 策略若錯，可能造成：
     - buffer 過早釋放（畫面撕裂/顯示錯誤）
     - buffer 累積（記憶體上升）
     - 多執行緒競態（若下游跨執行緒使用 bitmap）

3. **BitmapPool 與記憶體/GC 抖動**
   - out size 不穩定 → pool miss → `Bitmap.createBitmap` 等級的成本（即便用 pool acquire 也會 new）→ 尖峰 20–30ms 常見。
   - `maxEntriesPerKey=4` 若 key 數量增加，總持有 bitmap 數也會上升，造成 memory 壓力。

4. **RenderScript 生命週期**
   - `unbindCamera()` 時呼叫 `renderScriptYuvConverter.destroy()` 並重置 `useRenderScript=true`，若 rebind/切前後鏡頻繁，需確保 RS 重新初始化/銷毀無 race、無 native leak。

5. **視覺正確性（透明清除/邊界裁切）**
   - `canvas.drawColor(Color.TRANSPARENT, PorterDuff.Mode.CLEAR)` 每幀 clear 可能昂貴；移除或改策略可能造成殘影。
   - 固定輸出尺寸（A3）可能引入裁切策略（centerCrop/fit），需要明確規格，避免畫面被切掉導致使用者認為「畫質/構圖變差」。

## 4. 最小差異建議（Minimal diff approach：步驟化）
以「先降抖動、再降平均耗時」排序，確保每一步都可回滾與量測。

### Step 0｜先把量測做紮實（極小 diff）
1. 在 `BitmapPool` 增加統計：
   - `acquireHit/acquireMiss/createdCount/currentKeys/currentBitmaps`
2. 在 timing log 同步印：
   - `outW/outH/degrees/mirror`
   - pool hit/miss（每 30 或 60 幀一次）

> 目的：確認尖峰是否與 pool miss / 尺寸飄動高度相關。

### Step 1｜Plan A3：固定輸出尺寸（優先，最可能改善抖動）
1. 在 `transformBitmap()` 增加「固定輸出尺寸」選項：
   - 例如固定為輸入尺寸（如 720x720）或固定為某 preset（如 analysis target size）
2. 旋轉仍用 Matrix，但不要用 `mapRect + ceil` 產生新 w/h key：
   - 改成：輸出 bitmap 固定大小，Matrix 做 center-crop 或 center-fit（需決定規格）
3. 確保 front mirror / rotation 邏輯一致（維持原順序：rotate 再 mirror 或 mirror 再 rotate，依現況驗證）

> 期待：pool key 收斂、miss 降低、Transform max 大幅下降。

### Step 2｜Plan A4：Transform 快速路徑（固定尺寸後更容易做）
1. degrees in {0,90,180,270} 的專用 fast path（避免浮點 mapRect/ceil）
2. 只在必要時 clear（例如確認每次都是 full-frame 覆蓋，則可嘗試拿掉 clear；若不能保證，至少用 `drawColor` 的成本評估）
3. `Paint(FILTER_BITMAP_FLAG)` 可改為重用單例 Paint，避免每幀 new（雖小但可降抖動）

### Step 3｜Plan A2：Analysis/overlay 降頻（若 Transform 仍偏高）
1. 若 Transform 內含 composition analysis：改為每 N 幀更新，其他幀沿用上次結果。
2. 把「分析」與「純影像 transform」拆 timing，避免誤判。

### Step 4｜Plan A1：旋轉/鏡像移出 CPU（僅在 Step1/2 不足時）
1. 先確認 bitmap 是否只用於 UI；若是，改成 UI 層做旋轉/鏡像（PreviewView / View matrix / Compose graphicsLayer）。
2. 若 bitmap 也給 analyzer：則至少讓 analyzer 使用未旋轉版本 + 座標轉換，或建立「分析用座標系」mapping（較大改動，風險升高）。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **Feature flags（建議至少兩層）**
   - `ENABLE_FIXED_TRANSFORM_SIZE`：固定輸出尺寸（對應 A3）
   - `ENABLE_FAST_TRANSFORM_PATH`：啟用 degrees 0/90/180/270 快速路徑（對應 A4）
   - （可選）`ENABLE_ANALYSIS_DECIMATION`：分析降頻（對應 A2）
   - （較大）`ENABLE_DISPLAY_SIDE_ROTATION`：旋轉/鏡像交給顯示層（對應 A1）

2. **保留舊路徑**
   - 舊 `transformBitmap()`（目前 mapRect/ceil + clear + drawBitmap）保留為 fallback。
   - 任一 flag 關閉時，回到 v2.8.2 現況行為（確保視覺正確性優先）。

3. **安全回滾驗收**
   - 關閉所有新 flag 後：
     - YUV 平均仍約 5.4ms（RS）
     - FPS 回到 19–20（可接受作為基準）
     - 無 crash、0 dropped frames（或與基準一致）

4. **降風險執行順序**
   - 先上「統計/量測」→ 再上「固定尺寸」→ 再上「快速路徑」→ 最後才考慮「移到顯示層」。
   - 每一步都要可單獨 revert（atomic commit）。
