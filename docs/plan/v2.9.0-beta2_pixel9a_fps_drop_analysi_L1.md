## 2. 背景與問題（Why / What）
### 現況摘要（來自 v2.9.0-beta2 Pixel 9a 手動 10 分鐘測試）
- **目標解析度**：480×360  
- **實際解析度（CameraX 選到）**：1080×1080  
- **YUV Converter**：RenderScript（GPU，3–5ms）→ FPS 已自 beta1 的 8–10 恢復到 ~22  
- **BitmapPool**：啟用且命中率 99%  
- **PreviewView**：已採 Native GPU rendering（v2.8.6 Phase 2 路徑）

### 核心問題
1) **Graphics 記憶體終值偏高**  
- v2.8.6：10 分鐘 ~80.5MB（相對穩）  
- v2.9.0-beta2：10 分鐘 216.1MB（且 +28.4MB 成長）  
→ 顯示「即便 FPS OK，仍存在 GPU/Graphics 佔用過高或慢漏」的風險。

2) **解析度錯配可能是主要推手**  
- 480×360 = 172,800 pixels  
- 1080×1080 = 1,166,400 pixels（約 6.75 倍）  
→ 任何與 texture / bitmap / allocation 相關的圖形資源都可能被放大，導致：  
- Graphics 常駐變大  
- 若有「未完全釋放」的週期性資源，成長速度也會被放大

3) **FPS outlier（T3 16.5）需要排除熱節流/GC/背壓等因素**  
- beta2 已加入 thermal 監控 log（LiveCameraSource）  
- 但目前報告未呈現熱狀態與 FPS 的對齊關係，需要更長測試與更完整 log 佐證。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1) **相機管線解析度不可控風險（CameraX 自選到 1080×1080）**
- 造成 Graphics/Native allocation 放大、耗電升高、溫度上升 → 長時間可能 FPS 下滑或 ANR 風險上升。

2) **慢性 Graphics Memory Leak / 緩慢累積風險**
- beta2 10 分鐘 +28.4MB（~2.8MB/min）  
- 若不收斂，40 分鐘可能 +100MB 等級，會逼近系統壓力點（尤其 Android 16 + Tensor G4 + GPU driver 行為未知）。

3) **模式切換風險（PreviewView native / fallback SurfaceTexture / 靜態圖模式）**
- `externalSurfaceProvider` 變更會觸發 rebind；若 lifecycle/重綁不乾淨，可能造成：
  - 多組 UseCase、Surface、texture 殘留（Graphics 逐步累積）
  - 短暫黑畫面/閃爍或 preview 停止

4) **效能回歸風險**
- 若改動解析度策略（或改用 ResolutionSelector / setTargetAspectRatio / setTargetRotation），可能引入：
  - FPS 不穩（背壓、轉換成本上升）
  - AI 檢測精度下降（解析度太低或裁切不符）
  - 特定裝置相容性問題（部分 HAL/相機模組不吃某些 Size）

5) **裝置差異風險（Pixel 9a 特例）**
- Pixel 9a 已有歷史：同版本在其他裝置正常但 Pixel 9a 出現記憶體問題。任何「只在 Pixel 修」的條件分支都需嚴格驗證避免碎片化。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異：先把「事實」補齊 + 延長測試）
**目標**：確認「解析度錯配」是否主因，以及 Graphics 成長是否會收斂。  
1) **加強 log/觀測（不改行為）**
- 每次 bind 時輸出：
  - target resolution（我們設定的）
  - CameraX request resolution（SurfaceProvider request.resolution）
  - ImageAnalysis 實際輸入尺寸（`imageProxy.width/height`）
- 將 thermal status、FPS、Graphics(dumpsys) 以固定週期對齊（例如每 2 分鐘一次）  

2) **延長測試到 30–60 分鐘（Pixel 9a 實機）**
- 觀察 Graphics 成長曲線是否：
  - 線性（疑似 leak）
  - 前期成長後 plateau（初始化/快取建立）
- 同時對齊：thermal 狀態變化 vs FPS outlier

**預期輸出**：足夠資訊做 go/no-go 決策（維持 beta2、修解析度、或回退 v2.8.6）。

### Plan B（仍偏最小差異：修正解析度選擇策略，避免 1080×1080）
**目標**：讓 CameraX 更接近我們期望的低成本輸入，降低 Graphics 常駐與潛在累積。  
可選路徑（依 CameraX 版本能力選擇其一）：

1) **導入 ResolutionSelector（建議優先評估）**
- 以「期望 size + 容忍的 fallback 規則」取代硬塞 `setTargetResolution`。  
- 目的：避免 CameraX fallback 到奇怪的正方形 1080×1080。

2) **改成「找最近支援的 size」再 setTargetResolution**
- 啟動時先查相機支援 size（Preview / Analysis 各自）  
- 選擇最接近 480×360（或至少 4:3 且像素量低）的 size  
- 再餵進 builder  
> 這屬於「行為改動」，需搭配 Plan A 的觀測方式驗證。

3) **若 480×360 不在支援清單：改目標為更標準的 640×480 或 720×540（視支援而定）**
- 重點是「避免大幅度 upscale / square crop」導致 GPU 成本放大。
