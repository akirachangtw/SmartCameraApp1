# Level 1 規劃摘要：v2.8.1_FPS-Memory_Issues

- 釐清並改善 **v2.8.0 Phase 1** 相較 Phase 0 出現的 **FPS 退化**（Sony XQ-BT52：28.8 → 24.0，-16.7%）。
- 釐清並控制 **Pixel 9a 記憶體成長偏高**（3 分鐘 +79MB）的原因，排除潛在洩漏或不必要的 cache / buffer 累積。

## 2) 背景與問題（Why / What）
### 已知現況（v2.8.0 Phase 1 測試結論）
- **穩定性**：已通過
  - 快速切換前後鏡 20 次：PASS（無崩潰、無 CameraControl not available）
  - 前後景切換 5 次：PASS
  - Drop rate：兩裝置皆 0%
- **效能**：
  - Sony XQ-BT52（SD690, Android 12）3 分鐘長測：
    - FPS 平均 **24.0**，相較 Phase 0 平均 **28.8**，退化 **-16.7%（超過 ±10% gate）**
    - 仍 > 20 FPS，可用但屬可見退化風險
  - Pixel 9a（Tensor G4, Android 16）3 分鐘多：
    - FPS 平均 26.6（尚可）
    - **Total PSS avg 502MB**，且 **Memory Growth +79MB**（需關注）
- 推測：Phase 1 新增的 Mutex 與 Analyzer stop 機制理論 overhead 極低，但實測仍出現 FPS 下降與記憶體成長差異，可能來自：
  - 影像分析管線的排程/背壓行為改變（例如 analyzer 未完全釋放、或 stop 後仍有 pending frame）
  - 不同 Android 版本/Runtime/GC 策略導致 PSS 成長表現差異（Pixel 9a）
  - 相機重綁定/UseCase 重建時機造成額外成本（雖長測無切換，但可能仍有 lifecycle/observer 行為）
  - 統計口徑/取樣差異或背景負載差異（需再做可重現測試控制變因）

## 4) 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線風險**：為了提升 FPS 調整 ImageAnalysis 設定（解析度、格式、backpressure）可能引入：
   - Preview/Analysis 不同步、畫面延遲或 overlay 漂移
   - 特定裝置（Sony/Pixel）相容性差異
2. **模式切換回歸風險**：動到 stop/unbind/bind 時序或 Mutex 範圍，可能讓已修復的競態問題復發（例如再次出現 CameraControl not available 或偶發黑畫面）。
3. **效能回歸風險**：
   - 為了抑制 memory growth 增加頻繁釋放/重建，反而造成 GC 壓力 → FPS 更低
   - 為了 FPS 取消某些安全檢查（stop 機制）導致過期 frame 被處理、CPU 浪費或崩潰
4. **跨版本/跨裝置差異風險**：
   - Android 16（Pixel 9a）PSS/GC 表現與 Android 12 不同，誤判為 leak 或誤用 fix
5. **度量/統計風險**：
   - FPS sample 數不同（145 vs 174）可能造成誤差；若指標口徑不一致，容易做錯決策

## 5) 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異：先「定位/歸因」再「微調」）
目標：不急著改核心管線，先把 FPS 退化與 memory growth 變成可重現、可定位的問題。

A1. 建立一致化效能測試腳本/流程（同裝置、同溫度、同背景狀態）
- Sony / Pixel 各跑 2 次：3 分鐘、10 分鐘（Pixel memory growth 必須拉長）
- 固定：亮度、網路、背景 app、螢幕刷新率設定（如可控）

A2. 增加低成本 instrumentation（不改邏輯，只加觀測）
- 每 N 秒記錄：
  - 分析 thread queue 長度/執行時間分佈（P50/P95）
  - 每幀是否 early-return（stop flag 命中次數理應接近 0，長測無 stop）
  - `ImageProxy.close()` 是否在每次 analyze 都被呼叫（避免 buffer 堆積）
- 記錄記憶體：
  - Java heap（Runtime / Debug.getMemoryInfo）
  - Native（Debug.getNativeHeapAllocatedSize）
  - PSS（dumpsys meminfo 定期取樣）

A3. 微調（在能證明瓶頸後才做）
- 若瓶頸在分析端：
  - 降低不必要的 per-frame allocation（例如避免每幀 new ByteArray/Bitmap/Mat/Tensor）
  - 確認 analyzer stop 後是否仍保留大型物件引用（導致 GC 無法回收）
- 若瓶頸在 CameraX 設定（推測）：
  - 檢查 ImageAnalysis backpressure 是否為 `KEEP_ONLY_LATEST`（或等效），避免堆積導致 latency 與 memory 成長
  - 檢查 target resolution / output format 是否導致轉換成本增加

### Plan B（回復部分行為以驗證來源：可快速二分法）
目標：用 feature flag / build variant 做 A/B 測試，快速判斷 FPS 退化與 memory growth 是否來自 Phase 1 變更。

B1. Feature flag：停用 stop 機制（僅供內測）
- 保留 Mutex（穩定性關鍵）
- 觀察 FPS 是否回到 ~Phase 0
- 風險：可能再次處理過期 frame → 僅限測試版

B2. Feature flag：保留 stop 機制，但縮小/調整其使用點（最小改動）
- 例如只在「unbind 前」強制 stop，平時 analyze 不做 check（或改用更低干擾方案）
- 目的：驗證「每幀 check」是否真的與 FPS 退化相關（雖理論上很小，但以數據說話）

B3. Pixel 9a memory growth 專用：做 10–15 分鐘 soak test + 強制截圖/旋轉/切背景情境
- 判斷是「短期 cache 上升後趨平」還是「線性成長（疑似 leak）」。
