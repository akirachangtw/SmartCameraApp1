# Level 1 規劃摘要｜v2.8.1_Performance_Issues

## 1. 目標（Goal）
- **阻止 v2.8.1 的嚴重效能回歸進入發布線**，在 Sony XQ-BT52（SD690）上把預覽分析 FPS 從 **16.4 FPS** 拉回至少 **≥ 24 FPS（Phase 1 水準）**，並以 **≥ 26 FPS** 為目標。
- 釐清回歸主因（Executor/BitmapPool/Bitmap 轉換/旋轉繪製/執行緒競爭），用**最小差異**方式修正。
- 同步修正 **Memory Growth** 從 **+37MB** 回落至 Phase 1 的 **+8MB 等級**（或至少顯著降低且可解釋）。

---

## 2. 背景與問題（Why / What）
### 背景
- v2.8.1 針對即時預覽管線做兩個主要調整：
  1) **Analyzer 改用 `newSingleThreadExecutor()`**（從 MainExecutor 移出 UI Thread）
  2) 引入 **BitmapPool** 與 **inFlightPreviewBuffers**（重用 Bitmap/IntArray，降低 per-frame allocation）

### 問題（實機觀察）
- 在 Sony XQ-BT52（SD690）3 分鐘測試中出現**關鍵回歸**：
  - FPS Avg：Phase 1 **24.0 → v2.8.1 16.4（-31.7%）**
  - FPS Min：**7.1**（明顯卡頓）
  - Memory Growth：Phase 1 **+8MB → v2.8.1 +37MB（+29MB，4.6 倍）**
  - Drop Rate：0%（代表管線仍在跑，但「跑得很慢且不穩」）

### 初步判讀
- 回歸不像是單純「YUV→RGB 算法」造成（Phase 1 已可達 24 FPS），更像是：
  - **執行緒排程/優先權/競爭**造成 analyzer 時序不穩
  - 或 v2.8.1 新增的 **Canvas/Matrix transform + pool 重用策略**導致額外成本或 GC/記憶體碎片問題
  - 或實際測試版本/程式碼路徑**未生效**（測試中未看到預期 log）

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線排程風險（高）**  
   Analyzer 改到 background single thread 後，可能與同 app 背景任務競爭、或被系統調度影響，造成 FPS 大幅波動（7–25）。
2. **效能回歸風險（高）**  
   `transformBitmap()` 走 Canvas 繪製與清空（`drawColor(CLEAR)`）每幀產生額外負擔；若再加上 `setPixels()`，等於每幀做兩次大面積記憶體操作。
3. **記憶體成長/碎片化風險（中高）**  
   pool 若 hit rate 不高，會同時保留多組 WxH 的 Bitmap/IntArray；再加上 in-flight buffer 延遲釋放，可能造成成長曲線惡化（+37MB）。
4. **模式切換/鏡頭切換風險（中）**  
   使用自建 executor 若未在 stop/release 時 shutdown，可能造成 thread/leak；或切換時 buffer 未完整釋放導致占用累積。
5. **測試版本不一致風險（中）**  
   測試中未見 v2.8.1 關鍵 log，存在「跑到舊邏輯或不同 build」的可能，導致判斷失準。
6. **回滾困難風險（低~中）**  
   v2.8.1 同時引入 executor + pool + transform 重寫，若沒有 feature flag，回退需要動到多處，易引入新錯誤。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（優先，最小差異、最快止血）：回到 Phase 1 穩定組合
**目標**：先把 FPS 拉回來，確保可發布；再談優化。  
- A1. **回滾 analyzer executor**：`imageAnalysis.setAnalyzer(ContextCompat.getMainExecutor(context), ...)`
- A2. **暫停 BitmapPool + transformBitmap 新路徑**
  - 回到 Phase 1 的 bitmap 產生與旋轉流程（或至少停用 pool/Canvas transform）
- A3. **保留必要的計時/Log**（用於下一輪定位，不影響行為）

> 適用情境：需要快速恢復體驗、阻止回歸擴散（建議作為 v2.8.1 hotfix/或直接不發 v2.8.1）。

### Plan B（定位導向，仍維持最小差異但做 A/B 拆分）：用對照實驗找主因
**目標**：確認是 Executor 還是 BitmapPool/transform 導致回歸，避免盲改。  
- B1. **實驗矩陣（一次只改一件事）**
  - Test A：**保留 BitmapPool + transform**，但 **改回 MainExecutor**
  - Test B：**移除 BitmapPool/transform（回到 Phase 1）**，但 **保留 background executor**
  - Test C：Phase 1 baseline（兩者都不用）
- B2. **加上分段耗時埋點**（YUV、setPixels、transform、analyzer）
- B3. 依結果決定後續：
  - 若 executor 是主因：改用 CameraX 建議 executor/提升 thread priority/避免與其他工作競爭
  - 若 transform/pool 是主因：優先砍掉 Canvas transform 或改成更低成本策略（例如直接在 analyzer 使用 YUV、或減少拷貝次數）
