# v2.9.5_Camera-Quality-Orientation｜Level 1 規劃摘要

## 1. 目標（Goal）
1. 修復 **後置鏡頭橫向拍照方向錯誤**（SmartCamera 產出照片與內建相機相比旋轉/方向不一致）。
2. 改善 **APP 預覽畫面解析度/清晰度過差**（避免使用者誤以為無法對焦）。
3. 提升 **SmartCamera 拍照清晰度**，使其接近內建相機的成像品質（在同樣光線/焦距條件下差距縮小）。

---

## 2. 背景與問題（Why / What）
### 已觀察到的症狀（來自使用者補充）
- **方向問題**：後置鏡頭「橫向拍照」方向錯誤。  
  - 比對檔案：`@tmp\v2.9.5_Testing\Smartcamera橫向_074.jpg` vs `@tmp\v2.9.5_Testing\內建相機橫向_DSC_2747.JPG`
- **預覽解析度很差**：`@tmp\v2.9.5_Testing\LiveScreen-000444.png` 顯示預覽顆粒/糊，懷疑是否「無法對焦」導致。
- **照片清晰度偏低**：SmartCamera 拍照成品明顯不如內建相機。

### 初步技術推測（待驗證）
1. **方向錯誤**常見成因（CameraX）  
   - `ImageCapture` 儲存 JPEG 的 EXIF orientation 設定/寫入不一致，或是「App 端自行旋轉」與「EXIF」重複/漏做。
   - `targetRotation` 未隨 UI 旋轉更新（特別是橫向拍照時）。
   - Preview / Analysis / Capture 三條 use case 的 rotation 設定不一致。
2. **預覽解析度差**不一定是對焦問題，更像是：
   - PreviewView 顯示被迫用較低解析度（或被縮放放大造成糊）。
   - 為了效能/記憶體（Pixel9a 等）引入的「動態解析度選擇/限制」導致 Preview 解析度過低。
   - Preview 的 `scaleType` / 版面裁切造成看起來「失焦」。
3. **拍照清晰度低**常見成因：
   - 實際拍照使用的 capture 尺寸過小（例如沿用 analysis 的 640x480/800x600 等）。
   - `ImageCapture` 使用 `CAPTURE_MODE_MINIMIZE_LATENCY`、或缺乏 AE/AF 收斂等待，導致快門時機太早（相機尚未完成對焦/曝光）。
   - 與內建相機相比缺少：HDR/夜景/多幀融合等（此為「期望落差」，但我們仍可把基礎對焦/解析度/旋轉先做到位）。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **Rotation 修正造成回歸**：修橫向後，直向或前鏡頭方向可能反而錯（Preview/Analysis/Capture 三路徑需一致）。
2. **解析度提升造成效能/記憶體回歸**：提高 Preview / Capture 尺寸可能導致：
   - FPS 下滑
   - Graphics 記憶體上升（尤其 Pixel 9a 先前有敏感案例）
3. **模式切換風險**（Live / Static / Debug）：
   - 若 StaticImageSource 或 fallback path 沒有同等 rotation/resize 策略，可能導致「模擬器正常、實機翻車」或相反。
4. **裝置差異**：
   - 不同 OEM 對 CameraX resolution negotiation、EXIF orientation、AF behavior 差異大。
5. **對焦流程介入風險**：
   - 增加 AF/AE 收斂等待可能提升清晰度，但也可能增加 shutter latency、影響 UX 或造成某些裝置卡住（需要 timeout）。

## 5. 建議方案（Plan A / Plan B：最小差異優先）

### Plan A（最小差異，先止血：方向一致 + 預覽品質釐清）
1. **統一 rotation 設定**（優先）  
   - 將 Preview / ImageAnalysis / ImageCapture（若有）都設定同一個 `targetRotation`，並在 UI 旋轉變更時更新。  
   - 目標：橫向拍照的 JPEG 與內建相機方向一致（至少 EXIF/顯示一致）。
2. **增加「實際輸出尺寸/rotation」診斷 log / overlay（Debug only）**  
   - 顯示 Preview resolution、Analysis resolution、Capture resolution（若有）、以及 rotation 值。  
   - 目的：快速判定預覽糊是「低解析度放大」還是「AF 失敗」。
3. **確認 PreviewView 顯示策略**（不改演算法，只避免看起來糊）
   - 檢查 `PreviewView.ScaleType`（FILL_CENTER / FIT_CENTER 等）與 Compose 版面比例，避免把低解析度畫面硬放大到滿版。
4. **先把「預覽糊」與「拍照糊」分流處理**
   - 預覽糊：先確認是否 resolution negotiation 或 UI scaling 問題。
   - 拍照糊：先確認拍照是否用到低尺寸或低品質設定。

> Plan A 目標是：**先讓方向正確 + 找出清晰度落差的主因是解析度/對焦/後處理哪一類。**

---

### Plan B（品質導向：提升拍照品質與對焦成功率，但控制風險）
1. **拍照 use case 與分析 use case 分離目標**
   - Analysis 仍可用 640x480/800x600 以保效能。
   - ImageCapture 改用更高 capture 尺寸（例如 12MP/Full sensor ratio 的合適尺寸），避免拿 analysis 尺寸去存 JPEG。
2. **ImageCapture 設定調整（若目前為 latency 優先）**
   - 視產品需求評估 `CAPTURE_MODE_MAXIMIZE_QUALITY`（或至少不要極端壓縮/低品質路徑）。
3. **加入拍照前 AF/AE 收斂（帶 timeout）**
   - 拍照前觸發一次 focus/metering（或 tap-to-focus 預設在中心點），等待短時間收斂或超時就拍。
4. **提供設定開關（Debug/Settings）**
   - 「高畫質拍照（較慢）」/「低延遲（較快）」切換，方便驗證與回歸控制。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### A. 功能驗證（方向）
1. **實機必測**（模擬器不可靠）：至少 2 台（例如 Pixel + Sony）
2. 測試情境：
   - 後鏡頭：直向拍照、橫向拍照
   - 前鏡頭：直向拍照、橫向拍照
3. 驗收方式：
   - 與內建相機同場景拍攝對照
   - 檢查：相簿顯示方向、EXIF orientation（可用工具/程式 log）

### B. 預覽品質驗證（釐清解析度 vs 對焦）
1. 啟用 Debug overlay/log，記錄：
   - Preview resolution、Analysis resolution、device/model、PreviewView scaleType
2. 產出證據：
   - 螢幕截圖（Preview 畫面）+ log（顯示實際 resolution）
3. 判準：
   - 若 Preview resolution 明顯偏低且被放大，屬「解析度/縮放問題」
   - 若 resolution 正常但仍糊，再看 AF 是否工作（可再加 AF 狀態 log）

### C. 拍照清晰度驗證
1. 同一場景：SmartCamera vs 內建相機各拍 3 張（避免手震/偶發對焦）
2. 對比：
   - 解析度（像素尺寸）
   - 細節（100% crop）
   - 噪點/塗抹感（可能來自壓縮或降噪）
3. 若導入 Plan B（AF/AE 等待），記錄拍照耗時（shutter latency）。

### D. 效能指標（避免回歸）
- FPS（維持既有目標範圍，例如 25-30，依裝置）
- Graphics memory（沿用先前監控方式；至少 3-10 分鐘穩定性）
- 重大指標：解析度調整後是否造成 Pixel 類裝置記憶體再度成長

## 7. 回滾策略（Rollback）
1. **以功能旗標/設定開關包住高風險改動**
   - 例如：高畫質拍照、AF/AE 收斂等待、capture size 提升
2. **保持 Plan A 的改動可獨立回滾**
   - rotation 統一若導致前鏡頭回歸，可快速 revert commit 或加裝置條件分支
3. **以 atomic commits 切分**
   - commit 1：診斷/overlay/log（可保留）
   - commit 2：rotation 修復
   - commit 3：capture quality / AF 流程（可選配、可回滾）
