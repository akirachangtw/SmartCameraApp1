理由：
- 目前已知 **target 480×360 → actual 1080×1080**，高度懷疑是 Graphics 偏高與成長的主要放大器，但仍缺少「CameraX 實際 negotiated size」與「支援 size 清單」等關鍵事實。
- beta2 的 FPS 已回到可用範圍（~22），因此短期不建議直接大改相機管線；優先做 **最小差異的觀測補強 + 長時測試** 才能避免誤修與回歸。
- 若確認 Pixel 9a 無法選到接近期望尺寸（或 CameraX 因為 setTargetResolution 行為而落到 1080×1080），才進入 Plan B（ResolutionSelector/尺寸挑選策略）。

## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
1) **CameraX 綁定時實際選用的 Preview / ImageAnalysis 尺寸不一致**（或其中之一被拉到 1080×1080）。  
- 需用 log 驗證：`SurfaceRequest.resolution`（Preview）、`ImageProxy.width/height`（Analysis）。

2) **480×360 可能不在 Pixel 9a 某鏡頭（或特定 format）支援清單**，導致 CameraX fallback 到更「方便」的 square size（1080×1080）。  
- 需用 Camera2Interop 或 CameraX 的可用 API 查 supported sizes 驗證。

3) **Graphics memory 成長可能不是 leak，而是前期快取/pipe warm-up**（例如 PreviewView/SurfaceTexture/GL texture pool 初始化）。  
- 需 30–60 分鐘曲線判定是否 plateau。

4) **rebind 行為可能造成多組 Surface/UseCase 殘留**（尤其 `setPreviewSurfaceProvider()` 觸發 `bindToLifecycle()` 重跑）。  
- 需檢查：是否先 `unbindAll()`、舊 surface 是否 release、rebind 頻率是否過高（Compose recomposition / lifecycle）。

5) **RenderScript YUV conversion（GPU）路徑在 Pixel 9a 穩定可用**（beta2 已顯示 3–5ms），但仍可能造成額外 graphics/alloc。  
- 需用 log/trace 確認 allocation 是否每次建立、是否可重用。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1) **CameraX 解析度策略調整風險（Preview + ImageAnalysis）**
- `setTargetResolution()` 在不同裝置/相機 HAL 行為不一，可能導致：
  - 畫面裁切比例錯誤、旋轉錯誤
  - Analysis size 與 Preview size mismatch，增加 transform 成本或額外 buffer

2) **PreviewView 外接 SurfaceProvider + fallback SurfaceTexture 的模式切換**
- 外部 provider 設定/清除若導致頻繁 rebind，可能引入：
  - Graphics 慢性累積（多個 surface/texture 未釋放）
  - 黑屏/閃爍/preview 停止

3) **Thread / Backpressure / Analyzer 節流互動**
- Pixel 9a throttle=500ms（2 FPS）對 AI 端有利，但 Preview 端 FPS 下降不應由此直接造成；若發現 FPS 波動，需排除：
  - Analyzer thread 擁塞、YUV convert 阻塞、或 GC 尖峰

4) **權限/生命周期**
- `bindToLifecycle()` 在 lifecycleOwner 變更、App background/foreground、螢幕旋轉時，是否有完整釋放與重綁流程（尤其 external surface）。

## 4. 最小差異建議（Minimal diff approach：步驟化）
> 目標：先讓「事實可被量化」，避免直接改解析度策略造成回歸。

### Step 0（只補 log，不改行為）
1) **在 Preview SurfaceProvider request 時記錄 negotiated 尺寸**
- external provider（PreviewView）通常看不到 request；但 fallback provider 已有 `request.resolution` log。  
- 建議：不論 external/fallback，都在 bind 後額外印出 Preview UseCase / CameraInfo 可取得的資訊（若可）。

2) **在 ImageAnalysis analyzer 第一幀/每 N 幀記錄 `imageProxy.width/height`**
- 這是最直接的「Analysis 實際輸入尺寸」。

3) **每次 bind/rebind 輸出唯一序號 + UseCase/Surface 狀態**
- 例如：bindCount、externalSurfaceProvider 是否存在、是否呼叫 unbindAll。

4) **對齊效能採樣**
- 同一條 log 裡同時帶：FPS、thermal、(native/java/total)、以及（若可）graphics dumpsys 採樣點 timestamp（或由 script 外部採）。

### Step 1（延長測試，不改碼或只改 script）
- Pixel 9a 30–60 分鐘測試，觀察 Graphics 是否 plateau。
- 同步記錄 thermal 變化與 FPS outlier 是否對齊。

### Step 2（若確認 1080×1080 是主因，再做最小行為改動）
優先序：
1) **改用 ResolutionSelector（若專案 CameraX 版本支援）**：以「期望尺寸 + fallback 規則」避免 square fallback。  
2) 否則採 **Camera2Interop 查 supported size → 選最近 size → setTargetResolution(closest)**。  
3) 若 480×360 不可得，改成 **640×480（4:3）** 或其他更標準低成本尺寸（以支援清單為準）。

### Step 3（鎖住 rebind 風險）
- 對 `setPreviewSurfaceProvider()` 增加「相同 provider 不重綁」判斷（identity 比較）。
- 對 rebind 做 debounce（例如 300–500ms 內只允許一次），避免 Compose 抖動造成多次 bind。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1) **版本回滾基線**
- 若 30–60 分鐘仍呈線性成長且短期無把握：回退 **v2.8.6**（已知 Graphics ~80MB/10min 且穩）。

2) **功能旗標**
- 保留 / 新增旗標（擇一或兩者）：
  - `USE_PREVIEWVIEW_DISPLAY`（既有）確保可切回 bitmap preview（debug/診斷用）
  - 新增 `USE_RESOLUTION_SELECTOR`（或 `FIX_PIXEL9A_RESOLUTION_SELECTION`）讓解析度策略可快速關閉

3) **安全護欄**
- `setPreviewSurfaceProvider()`：
  - 若 provider identity 未變，不觸發 rebind
  - rebind 需 debounce，避免短時間連續觸發
- bind 流程務必：
  - 先 `unbindAll()`（或確保等價釋放流程）
  - 紀錄每次 bind 的 usecase 組合與序號，便於定位「多綁」問題

4) **逐步上線策略**
- 先在 Pixel 9a 開啟解析度修正（若不得不做 device-specific），但需：
  - 明確註記原因（CameraX 選到 square size）
  - 在至少 1 台非 Pixel 裝置驗證不受影響
  - 後續再嘗試擴大到全裝置共用策略（避免碎片化長期負擔）
