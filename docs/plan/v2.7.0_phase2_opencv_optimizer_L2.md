## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **ImageProxy lifecycle / memory leak**
   - 新路徑若直接使用 `imageProxy.planes[0].buffer` 建 Mat，必須確保在 `imageProxy.close()` 前完成處理或做安全拷貝。
   - 常見風險：buffer 被重用、導致 Mat 內容錯亂或偶發 crash。

2. **stride / pixelStride / rowStride 造成 Mat 影像扭曲**
   - Y plane 常見 `rowStride != width`，不能直接 `Mat(height, width, CV_8UC1, buffer)` 當作緊密資料。
   - 需處理：
     - 逐行 copy 到連續 buffer
     - 或用 ROI/step 建 Mat（OpenCV Java Mat step 支援有限，需實測 API 可行性）

3. **Rotation / Mirror / viewport crop**
   - CameraX 顯示的 preview 可能經過旋轉與裁切；偵測用影像與 UI overlay 需一致。
   - 若目前是先轉 Bitmap 再套 rotation，改走 Y plane 可能會漏掉同等的旋轉處理，導致線位置不對。

4. **模式切換（Live/Static/Debug）與 UseCase bind/unbind**
   - 若要加 feature flag 或新增 converter，必須避免：
     - analyzer 重複註冊
     - thread executor 未關閉
     - use case 切換 race condition（導致 CameraControl not available / preview freeze）

5. **Threading / performance jitter**
   - conversion 改成 copy row 可能降低延遲但增加 CPU；需在低階機確認 P95。
   - Bitmap allocation 目前可能造成 GC outlier；新路徑要避免每幀 allocate（改用 buffer pool）。

6. **權限 / 相機重啟**
   - 低階裝置在切到背景再回前景，ImageAnalysis 可能重建；新路徑需保證初始化 idempotent。

## 4. 最小差異建議（Minimal diff approach：步驟化）
> 目標：先讓 v2.7.0 能「量得準、控得住、可降載、可釋出判斷」；v2.8.0 再以 feature flag 安全導入新路徑。

### Phase A：v2.7.0 最小差異（不改資料流）
1. **把 perf 拆段並標準化**
   - 統一輸出欄位：`frameId, device, android, conversionMs, opencvMs, totalMs, linesCount, samplingIntervalMs, paramsPreset, sceneTag`
2. **補足統計：Avg / P95 / outlier rate**
   - 最少在 debug log/檔案輸出：60 samples summary（每台裝置）。
3. **加入 runtime 降載保護（先做「降頻」）**
   - 若滑動窗口（例如最近 30 次）：
     - Avg > 120ms 或 P95 > 180ms → 分析頻率降到 7 FPS（或 5 FPS）
     - 恢復條件：Avg < 100ms 且 P95 < 150ms 持續 N 秒
4. **參數降載（可選、第二順位）**
   - 仍超標時才啟用：`MAX_LINES` 降、`HOUGH_THRESHOLD` 升（但要防線品質回歸）
5. **裝置 tier 決策落盤**
   - 用同一套測試場景與參數 preset，輸出表格讓 PM 做 release gate。

### Phase B：v2.8.0 可行性 Spike（feature flag、新舊雙路徑）
1. **新增 converter：ImageProxy → Gray Mat（Y plane）**
   - 先做「安全版本」：row-by-row copy 到連續 ByteArray，再建 Mat（確保正確性）
2. **在 analyzer 引入 feature flag 切換**
   - `useDirectYPlane = true/false`（預設 false）
3. **處理 rotation**
   - 先以「與舊路徑對齊」為準：同樣的 rotation/scale pipeline，確保 overlay 對齊。
4. **對照測試**
   - 同一帧（或同一段場景）新舊路徑 linesCount/line endpoints 差異 + totalMs 差異。
