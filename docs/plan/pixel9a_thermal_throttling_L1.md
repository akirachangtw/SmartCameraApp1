# Level 1: 規劃檢視 - Pixel 9a FPS 波動調查

## 📋 問題背景 (What / Why / Scope)

### What - 問題描述

**現象**：Pixel 9a 在 v2.8.6 測試中，ImageAnalysis FPS 在 4-6 分鐘後顯著下降至 20 以下

**時間線模式**：
```
T0 (0-2 min):  25.5 ~ 28.9 FPS  ✅ 優秀
T1 (2-4 min):  23.6 ~ 26.0 FPS  ✅ 良好
T2 (4 min):    15.3 ~ 21.0 FPS  ⚠️ 開始下降
T3 (6 min):    11.9 ~ 14.1 FPS  ❌ 最低點 (-52%)
T4 (8 min):    17.7 ~ 19.3 FPS  ⬆️ 短暫回升
T5 (10 min):   11.9 ~ 16.2 FPS  ⚠️ 再次下降
```

**對照組（Sony Xperia）**：
```
T0-T5 (0-10 min): 24.5 ~ 27.4 FPS  ✅ 完全穩定（波動僅 2.9 FPS）
```

---

### Why - 調查動機

#### 主要目標
確認 FPS 下降是否為 **Phase 2 PreviewView 遷移引入的新問題**

#### 次要目標
1. 識別 FPS 下降的根本原因（熱節流 vs 程式碼問題）
2. 評估對 v2.8.6 發布的影響
3. 提供緩解或優化方案

#### 商業考量
- **Phase 2 主要目標已達成**：Graphics 記憶體洩漏修復 -70%
- **使用者體驗風險**：如果 FPS 下降影響 AI 偵測品質，可能降低產品滿意度
- **發布決策依據**：需要明確證據判斷是否應暫緩發布

---

### Scope - 調查範圍

#### In Scope ✅
1. **v2.8.5 vs v2.8.6 對照實驗**（確認 Phase 2 是否引入問題）
2. **裝置溫度與頻率監測**（驗證熱節流假設）
3. **散熱對照實驗**（主動散熱下 FPS 是否穩定）
4. **效能數據分析**（CPU/GPU/Memory 使用率）
5. **可行性評估**（緩解方案的技術與時程可行性）

#### Out of Scope ❌
1. Sony Xperia 深入調查（已驗證穩定，優先度低）
2. 其他裝置測試（Samsung/Xiaomi/等）
3. v2.9.0 長期優化實作（本次僅規劃）
4. ML Kit 模型替換或重構（超出本次範圍）

## ⚠️ 潛在風險（至少 1-3 項）

### 風險 1：Phase 2 引入額外 GPU 負載 🔴 **高風險**

**描述**：PreviewView 可能增加 GPU 紋理處理負載，導致 Tensor G4 更快達到熱節流閾值

**證據**：
- ✅ v2.8.6 Graphics 記憶體雖穩定，但 GPU 可能仍在處理 PreviewView 紋理
- ⚠️ Pixel 9a 初始 Graphics 75.9 MB（比 Sony 34.6 MB 高 119%）
- ❌ 尚未進行 v2.8.5 對照測試確認

**影響**：
- 如果確認為 Phase 2 引入 → **暫緩發布，需優化**
- 使用者抱怨「相機變慢」→ 負面評價

**緩解策略**：
- 立即執行 v2.8.5 Baseline 測試（30 分鐘）
- 如果 v2.8.5 也有問題 → 排除 Phase 2 責任

---

### 風險 2：Tensor G4 熱節流特性 🟡 **中風險**

**描述**：Pixel 9a 散熱設計不佳，長時間相機運作必然觸發熱節流

**證據**：
- ✅ FPS 下降時間點（4-6 分鐘）符合典型 SoC 升溫曲線
- ✅ T4 出現短暫回升（散熱後頻率恢復）
- ✅ Sony Xperia 無此問題（不同晶片/散熱設計）

**影響**：
- 如果確認為裝置限制 → v2.8.6 可以發布，但需文件說明
- 長期需考慮「效能模式」切換（高效能 vs 省電）

**緩解策略**：
- 溫度/頻率監測驗證
- 在文件中說明已知限制
- v2.9.0 提供低功耗模式

---

### 風險 3：Transform 瓶頸放大效應 🟢 **低風險**

**描述**：既有的 Transform 瓶頸（25-62 ms）在 CPU 降頻後被放大

**證據**：
- ✅ Transform 已知為效能瓶頸
- ⚠️ 但為何 v2.8.4 在 Sony 上 FPS 25+？（使用者提到）
- ❓ 需要確認 v2.8.4 vs v2.8.6 Transform 實作是否有差異

**影響**：
- 優化 Transform 可提升所有裝置 FPS
- 但不影響 v2.8.6 發布決策（既有問題）

**緩解策略**：
- 規劃 v2.9.0 Transform GPU 加速
- 考慮降低 ImageAnalysis 解析度

---

## 📊 調查策略

### 三階段驗證計畫

#### 階段 1：排除 Phase 2 責任（最高優先度）⭐

**目標**：確認 v2.8.5 是否也有同樣 FPS 下降模式

**實驗設計**：
```
Test A: v2.8.5 Baseline（無 PreviewView）
- 裝置：Pixel 9a
- 時長：10 分鐘
- 監測：FPS（每 2 分鐘採樣）
- 環境：與 v2.8.6 相同（室內、固定光源）

預期結果：
- 如果 v2.8.5 FPS 穩定 25+ → Phase 2 有問題 ❌
- 如果 v2.8.5 也下降至 12-20 → 裝置特性 ✅
```

**時程**：30 分鐘（立即執行）

**成功標準**：
- ✅ 獲得明確的 FPS 曲線數據
- ✅ 確認 Phase 2 是否引入新問題

---

#### 階段 2：驗證熱節流假設（次要優先度）

**目標**：使用系統指標確認 CPU/GPU 降頻

**實驗設計**：
```
Test B: 溫度與頻率監測
- 工具：adb shell + thermal_zone + cpufreq
- 監測項目：
  1. CPU 溫度（/sys/class/thermal/thermal_zone*/temp）
  2. CPU 頻率（/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq）
  3. FPS（SmartCameraAnalyzer logs）
- 時長：10 分鐘
- 採樣：每 30 秒

預期結果：
- 溫度上升 → CPU 頻率下降 → FPS 下降（三者同步變化）
```

**時程**：1 小時（編寫監測腳本 + 測試）

**成功標準**：
- ✅ 繪製溫度/頻率/FPS 三條曲線
- ✅ 確認三者相關性

---

#### 階段 3：散熱對照實驗（驗證性）

**目標**：主動散熱下 FPS 是否維持高位

**實驗設計**：
```
Test C1: 正常散熱（對照組）
- 條件：室溫環境，自然散熱
- 預期：FPS 下降至 12-20

Test C2: 主動散熱（實驗組）
- 條件：風扇或冰袋輔助散熱
- 預期：如果是熱節流，FPS 應保持 25+

Test C3: 降低負載（實驗組）
- 條件：降低 ImageAnalysis 解析度至 720p
- 預期：發熱減少，FPS 應穩定
```

**時程**：2 小時（3 組實驗 × 10 分鐘 + 間隔冷卻）

**成功標準**：
- ✅ Test C2 FPS 穩定 → 確認熱節流
- ✅ Test C3 FPS 穩定 → 確認負載過高
