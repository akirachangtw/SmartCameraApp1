# v2.9.6-Phase1-Review-Issues（Level 1 規劃摘要）

## 1. 目標（Goal）
- 修復 v2.9.6-phase1（Build 52）在 **照片儲存後缺少 EXIF Orientation** 的問題，確保相簿/第三方 App 能正確判斷照片方向。
- 釐清並修復 **橫向旋轉時預覽畫面旋轉不正確（疑似多轉/轉錯 90°）** 的問題，確保 Live 預覽與拍照方向一致。
- 在不破壞既有 CameraX 管線（Preview / ImageAnalysis / ImageCapture）與即時推論效能前提下，完成最小差異修補並可驗證。

## 2. 背景與問題（Why / What）
依 2026-01-19 Pixel 9a（Android 16）實機測試報告：

1) **OrientationEventListener 初始化與觸發機制已通過**
- 關鍵 log 完整出現：camera bind、sensor orientation=90°、initial rotation、listener enabled、targetRotation set。
- 手動旋轉可觸發 `Orientation changed` 與 `ImageCapture targetRotation updated`。

2) **照片方向測試失敗：EXIF Orientation 為 None**
- 三種拍攝方向（Portrait / Landscape Left / Landscape Right）輸出 JPEG 均無 EXIF Orientation。
- 根因指向 `CameraRepositoryImpl.saveBitmapToMediaStore()`：使用 `bitmap.compress()` 寫檔，**不會自動寫入 EXIF tags**（尤其是 Orientation）。

3) **額外問題：橫向旋轉時預覽畫面不正確**
- Portrait → Landscape Right 時，預覽畫面看起來被向右旋轉 90°（使用者視覺上「轉錯方向/多轉」）。
- 初步懷疑點：`LiveCameraSource.transformBitmap()` 的旋轉邏輯與 `imageProxy.imageInfo.rotationDegrees`、Activity 鎖定 Portrait 的交互影響。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1) **相機管線一致性風險**
- 若只修 EXIF 但不修預覽旋轉，可能造成「預覽看起來不正確但照片在相簿是正的」或反之，導致使用者困惑。
- 旋轉值來源（OrientationEventListener / Display rotation / ImageProxy rotationDegrees）若混用，容易出現雙重旋轉。

2) **模式切換風險（Live / Static / Debug 等，推測）**
- 若專案有多模式共用同一套儲存/轉換流程，EXIF 寫入可能影響其他輸出（例如 debug dump、靜態圖片模式）。
- 若不同 pipeline（ImageCapture vs Bitmap-based snapshot）並存，僅修其中一條會造成行為不一致。

3) **效能回歸風險**
- 寫入 EXIF 需要額外 I/O（讀回檔案或 reopen fd），若在主執行緒或高頻觸發可能造成卡頓。
- transformBitmap 若調整旋轉/矩陣運算，可能影響每幀處理成本（FPS / CPU / 記憶體）。

4) **裝置相容性風險**
- Android 版本與廠牌對 MediaStore + ExifInterface 的支援細節不同（file path vs fd / uri）。
- EXIF 寫入若處理不當，可能造成部分裝置照片無法開啟或 metadata 損毀（低機率但高影響）。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異、優先）— 先補齊 EXIF Orientation
**目標**：不大改相機管線，僅在「寫檔成功後」補寫 EXIF Orientation。

- 作法概念：
  1. `saveBitmapToMediaStore()` 寫入 JPEG 後，取得輸出目的地（FileDescriptor 或實際檔案路徑/可 reopen 的 Uri）。
  2. 使用 `ExifInterface` 將 Orientation tag 寫入。
  3. Orientation 值來源：**明確定義**由哪個 rotation 值換算（例如 ImageCapture 的 targetRotation、或當下 deviceRotation），避免和預覽/分析的 rotation 混亂。
- 需要補的資料流（報告已指出）：
  - 從 `LiveCameraSource` 或拍照流程把「當下 rotation」傳到 repository 儲存層。
- 最小 diff 原則：
  - 不改 ImageCapture pipeline（先維持現有 bitmap 輸出）。
  - 不立即重構成「直接用 ImageCapture OutputFileOptions」除非必要。

### Plan B（若 Plan A 在 MediaStore/Uri 上寫 EXIF 不穩）— 改用 CameraX 原生拍檔或調整輸出策略
**目標**：避免 bitmap.compress 造成 metadata 遺失，改成更「相機原生」的輸出方式。

- 方向（擇一或組合）：
  1. 直接使用 CameraX `ImageCapture.takePicture(OutputFileOptions...)` 產出 JPEG（通常會包含必要 metadata 或由 CameraX 處理方向）。
  2. 若仍需 bitmap（例如套濾鏡/疊圖），則：
     - 先存檔，再用 ExifInterface 以 fd 寫入；
     - 或改成輸出到 app 私有檔再搬移到 MediaStore（確保可寫 EXIF），最後 copy/insert。
- 代價：
  - 變更範圍較大，且可能牽動拍照延遲、成功率、相容性驗證。

> 預覽旋轉問題建議先「定位後再修」，避免在同一個變更中混入兩個高風險旋轉邏輯調整；但可並行開兩個 issue/task。

## 7. 回滾策略（Rollback）
- 將 EXIF 寫入變更保持為**單點改動**（集中在 `saveBitmapToMediaStore()` 或其 wrapper），可用 feature flag 或簡單條件開關（例如僅對 JPEG 生效）。
- 若發現部分機型寫 EXIF 失敗或導致照片損毀：
  - 立即回滾到僅 `bitmap.compress()` 的版本（功能退化但可用）。
  - 同步保留 log：寫 EXIF 成功/失敗原因（例外類型、uri/fd 取得方式）。
- 預覽旋轉修正若導致 overlay/推論錯位：
  - 回滾 transformBitmap 旋轉部分，並把修正轉為只影響 Preview 顯示層（若架構允許）。
