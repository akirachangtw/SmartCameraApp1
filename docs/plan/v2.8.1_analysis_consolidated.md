```

   （而非 Executors.newSingleThreadExecutor）

2. YUV Optimization: 整數運算取代浮點運算
   R = Y + ((359 * (V-128)) >> 8)  // 避免 1.402 * float

3. Memory: Double Buffering（2-3 個固定 Bitmap）
   （而非通用 Pool）
```

#### 預期效果
- YUV 轉換加速 2-3x（整數運算 + LUT）
- 避免 generic executor 的排程問題（HandlerThread）
- 記憶體增長 < 10MB（固定 buffer）

### 🟡 Phase B: 修正階段（依 Phase A 結果選擇）

#### B-1: YUV 轉換優化（若 YUV > 30ms）

**建立 `YuvConverter.kt`**:
```kotlin
class YuvConverter {
    // 預計算查找表（避免每幀重複計算）
    private val rLut = IntArray(256) { v -> (359 * (v - 128)) shr 8 }
    private val gLut = IntArray(256) { v ->
        val u = v - 128
        (-88 * u) shr 8  // -0.344 * u
    }
    private val bLut = IntArray(256) { v -> (454 * (v - 128)) shr 8 }

    private val pixels = IntArray(640 * 480)  // 重用 buffer

    fun convert(image: ImageProxy): IntArray {
        val yPlane = image.planes[0]
        val uPlane = image.planes[1]
        val vPlane = image.planes[2]

        // ... 使用整數運算 + LUT ...

        for (y in 0 until height) {
            for (x in 0 until width) {
                val yValue = yBuffer.get(...).toInt() and 0xFF
                val uValue = uBuffer.get(...).toInt() and 0xFF
                val vValue = vBuffer.get(...).toInt() and 0xFF

                val r = (yValue + rLut[vValue]).coerceIn(0, 255)
                val g = (yValue + gLut[uValue] - ((182 * (vValue-128)) shr 8)).coerceIn(0, 255)
                val b = (yValue + bLut[uValue]).coerceIn(0, 255)

                pixels[idx++] = (0xFF shl 24) or (r shl 16) or (g shl 8) or b
            }
        }
        return pixels
    }
}
```

#### B-3: Pool 策略調整（若 hit rate < 50%）

**改用 Double Buffering**:
```kotlin
class DoubleBuffer {
    private val buffers = Array(3) {
        BitmapBuffer(
            bitmap = Bitmap.createBitmap(640, 480, ARGB_8888),
            pixels = IntArray(640 * 480)
        )
    }
    private var currentIndex = 0

    fun acquire(): BitmapBuffer {
        val buffer = buffers[currentIndex]
        currentIndex = (currentIndex + 1) % 3
        return buffer
    }

    // 不需要 release，固定 3 個 buffer 輪流使用
}
```

**預期效果**: Memory growth 從 +37MB → < 5MB

#### B-4: Executor 優先權調整（若 priority 不足）

**使用 `HandlerThread`**:
```kotlin
private val analysisThread = HandlerThread(
    "CameraBg",
    Process.THREAD_PRIORITY_DISPLAY  // 高於一般背景，低於 UI

private val analysisHandler = Handler(analysisThread.looper)

// CameraX 支援 Handler-based executor
private val analysisExecutor = Executor { runnable ->
    analysisHandler.post(runnable)
}
```

## 8. 關鍵決策點

### Q1: 是否完全捨棄 Generic Pool？
**建議**: ✅ **是**
**理由**:
- Double Buffer 更簡單、可預測
- Pool hit rate < 50% 證明動態池無效
- 記憶體開銷固定（3 × 1.2MB = 3.6MB）

### Q2: 是否必須使用整數 YUV 算法？
**建議**: ✅ **是**
**理由**:
- 浮點運算在 mid-range SoC 上特別慢
- 2-3x 加速是最大效益來源
- 顏色準確度損失 < 1%（可接受）

### Q3: 是否需要 HandlerThread？
**建議**: 🟡 **視 Phase A 結果而定**
**理由**:
- 若 YUV + Double Buffer 已達 24 FPS → 不需要
- 若仍有波動 → 需要 DISPLAY priority
