# v2.7.0 Phase 2｜OpenCV + 引導線（Guideline）— Level 2 可行性檢視備忘錄

## 1. 可行性結論（可行 / 不可行 / 需調整）
**需調整（Conditional feasible）**  

原因：  
- 「CameraX Preview + ImageAnalysis + OpenCV + UI Overlay 對齊」在 Android 上**可行**且常見；但成敗高度取決於 repo 既有的：  
  1) CameraX 管線綁定/重綁定與模式切換架構（Live/Static/Debug）  
  2) PreviewView 的 `ScaleType` 與裁切行為（crop/letterbox）  
  3) frame rotation/mirror 的單一座標映射（SSOT）是否存在  
  4) OpenCV 依賴導入方式（AAR/SDK vs NDK）與影像格式轉換策略  
- 若目前專案的 analyzer/AI pipeline 已經很吃 CPU，OpenCV 需採 **降解析度/降頻/KEEP_ONLY_LATEST** 才能避免 FPS 回歸。

## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
以下假設需由 Claude Code 讀 repo/跑 log 後確認，否則方案可能要改：

1. **CameraX 架構假設**
   - Live 模式使用 `PreviewView + Preview + ImageAnalysis`（或 CameraController 等封裝）。
   - Static/Debug 模式不是同一條 frame source，或至少具備「停用 analyzer」能力。

2. **PreviewView 顯示假設**
   - PreviewView 可能使用 `FILL_CENTER`（常見）造成裁切；overlay 若用螢幕座標直接畫，很容易與 analysis buffer 不一致。
   - 前鏡頭預覽可能是鏡像（常見），但 analyzer 取得的 frame **未必**鏡像，需要明確規則。

3. **OpenCV 導入假設**
   - 專案可接受新增 OpenCV 依賴（建議先走 `org.opencv:opencv-android` 或官方 AAR），且不會與既有 NDK/ABI 產生衝突。
   - build variant（emulator/device）對 ABI 設定一致，不會造成「模擬器可編、實機缺 .so」。

4. **效能基準假設**
   - 目前 Live pipeline 仍能維持可接受 FPS（例如 24–30fps）。若 baseline 已接近瓶頸，OpenCV 只能做極輕量或必須降頻。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **Preview / Analysis 對齊（最高風險）**
   - PreviewView scale/crop 導致：OpenCV 偵測 ROI（以 buffer 座標）映射到 overlay（以 view 座標）錯位。
   - rotation、sensor orientation、display rotation、前鏡頭 mirror 規則不一致。

2. **ImageAnalysis 背壓與併發**
   - 若使用 `STRATEGY_BLOCK_PRODUCER` 或 analyzer 太重，會造成 camera pipeline 堵塞、preview 卡頓。
   - 若同時跑 AI inference + OpenCV（甚至兩個 analyzer），可能出現 thread contention / backlog。

3. **Mat/Bitmap 配置與記憶體**
   - 每幀 new Mat/Bitmap/ByteArray 導致 GC 抖動、長時間 memory 成長。
   - YUV→RGB 轉換方式選錯（用 Bitmap + Canvas 或 RenderScript 過時路線）造成 CPU 飆高。

4. **模式切換與生命週期**
   - Live → Static → Live 重綁定時：analyzer thread 未停乾淨、OpenCV 初始化重複、overlay state 未 reset。
   - onPause/onResume 之後 CameraX 重新 bind，導致 transform 資訊失效。

5. **權限/裝置差異**
   - 實機 crop region / rotation metadata 差異、HAL 行為不同造成「模擬器正常、實機跑位」。

## 4. 最小差異建議（Minimal diff approach：步驟化）
目標：先穩定「顯示與管線」，再接 OpenCV，最後才做「結果驅動的 guideline」。

### Step 0｜鎖定 Feature Flag（先做，確保可回滾）
- 新增旗標（BuildConfig / remote config / local setting）：
  - `enableGuidelineOverlay`
  - `enableOpenCvAnalysis`
  - `enableOpenCvGuidelineBinding`（結果綁定，可獨立關）

### Step 1｜Guideline Overlay 先純 UI（不吃 analyzer）
- 新增 `GuidelineOverlayView` 疊在 PreviewView 上（或 Compose Canvas）。
- 先用「view 座標」畫固定比例（例如中心框/九宮格/水平線）。
- 驗證旋轉、切鏡頭、切模式都能顯示且不閃爍。

### Step 2｜建立單一座標映射（SSOT Transform）
- 建立 `FrameToViewTransform`（或同等 utility），輸入：
  - `imageWidth/height`
  - `rotationDegrees`
  - `isFrontCamera`
  - `previewViewWidth/height`
  - `previewViewScaleType`（FILL/FIT）
- 輸出可用於：
  - `mapPoint(bufferPoint)->viewPoint`
  - `mapRect(bufferRect)->viewRect`
- 先用假資料（例如 bufferRect = 中央 50%）映射後畫到 overlay，確定對齊。

### Step 3｜最小 OpenCV Analyzer 接入（只做輕量、只量測）
- ImageAnalysis 設定：
  - `setBackpressureStrategy(STRATEGY_KEEP_ONLY_LATEST)`
  - `setOutputImageFormat(OUTPUT_IMAGE_FORMAT_YUV_420_888)`（或 repo 既定）
  - `setTargetResolution(例如 640x480 或 1280x720)` 視效能調整
- Analyzer：
  - 僅取得 frame + timestamp + rotation，做最小轉換（必要才轉 RGBA/Mat）
  - 記錄耗時（每 30fps 統計平均、P95）
  - 確保 `image.close()` 在 finally

### Step 4｜OpenCV 結果輸出（事件化），Overlay 訂閱顯示
- 定義 `GuidelineResult`（包含 rect/points/confidence/timestamp）
- Analyzer 透過 `StateFlow/SharedFlow` 發佈結果
- Overlay 只吃結果 + transform 映射，不直接碰 Mat/Bitmap

### Step 5｜效能不足時的降載策略（預先內建）
- 降頻：每 N 帧分析一次（N=2~5）
- 降解析度：analysis 固定低解析
- 專用執行緒：OpenCV 放到 `HandlerThread` 或 `Executors.newSingleThreadExecutor()`

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **功能旗標三段式回滾（建議）**
   - `enableGuidelineOverlay=false`：完全關閉 overlay（回到 v2.6.x 視覺）
   - `enableOpenCvAnalysis=false`：保留 overlay，但不跑 OpenCV（止血效能）
   - `enableOpenCvGuidelineBinding=false`：OpenCV 可跑但不驅動 UI（便於 A/B 測與 debug）

2. **安全降載預設**
   - 預設 `KEEP_ONLY_LATEST`
   - 預設低解析度（例如 VGA/720p 擇一）
   - 預設降頻（每 2~3 帧跑一次），再視需求開回全速

3. **資源釋放與生命週期保護**
   - analyzer/executor 在 unbind / mode switch 必須 stop/shutdown（或可重用單例但要有 clear 狀態）
   - OpenCV 初始化集中在單一入口，避免多次 init 或頁面重建重複載入

4. **對齊風險隔離**
   - 未完成座標映射 SSOT 前，禁止把 OpenCV ROI 直接畫到 overlay（避免「看似能用但其實錯位」）
