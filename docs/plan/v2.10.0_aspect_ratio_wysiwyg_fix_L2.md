## 1. 可行性結論（可行 / 不可行 / 需調整）
**需調整（Plan A 可行，但必須加入可靠 fallback 與座標系驗證）**

- **(1) 1:1 用 ResolutionSelector + 固定 1920×1920**：在 CameraX 1.3.x 技術上可做，但「固定單一尺寸」在不同裝置/鏡頭組合的支援度不保證；若無 fallback，可能造成 **bind 失敗、選到非預期尺寸、或 WYSIWYG 再次破功**。建議改成「**正方形優先 + 固定尺寸作為優先項**」並記錄實際選到的 resolution。
- **(2) ViewPort.setScaleType(ViewPort.FIT)**：可行，且符合 root cause（避免預設 FILL_CENTER 的額外裁切）。但會改變 **Preview letterbox/顯示區域**，以及可能影響 **Preview ↔ Analysis ↔ Overlay** 的座標映射；必須做 overlay 對齊驗證與必要修正（通常是使用 `PreviewView` 的 transform API/座標轉換，而非手算）。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
### A. CameraX UseCase 綁定與相容性
- **固定 1920×1920** 可能導致：
  - `bindToLifecycle` 直接丟例外（IllegalArgumentException/IllegalStateException，視 API 使用而定）
  - 或 selector fallback 到「你沒預期」的尺寸（變成 1440×1080 等），造成 Capture/Preview/Analysis 不一致
- **Preview / ImageCapture / ImageAnalysis selector 不一致** → WYSIWYG 必破（尤其 1:1 與 16:9 切換時）

### B. ViewPort.FIT 對座標系/裁切鏈的影響
- FIT 會引入 **letterbox（黑邊或留白）**，導致：
  - 你原本以「填滿」假設寫的 overlay 映射會偏移
  - 觸控對焦點位（tap-to-focus）若用 view 座標手算轉 sensor，可能不再準
- 若專案同時有 **analysis cropping / target rotation / mirroring（前鏡頭）**，FIT 會放大錯位的可視化程度

### C. 模式切換/生命週期
- 4:3 ↔ 16:9 ↔ 1:1 反覆 rebind：
  - 黑屏/閃爍、zoom/reset、AF/AE metering 需重設
  - 多執行緒競態：UI state 更新與 CameraProvider 綁定在不同 dispatcher/executor，可能產生「舊 use case 還沒 unbind，新 use case 已 bind」的短暫錯亂

### D. Optical Flow / ML Kit / FPS 回歸
- 1:1 解析度若提升像素量，可能增加：
  - YUV->RGB、tensor 前處理成本
  - ML Kit Face Detection latency（特別是高解析或未縮放）
  - Optical Flow tracking cost（點數/金字塔層級與解析度關聯）
- 若 analysis 解析度跟 preview/capture 綁一起提升，整體 FPS 風險更高

### E. 權限/實作模式（PreviewView）
- `USE_PREVIEWVIEW_DISPLAY=true` 改變渲染路徑（Surface/Texture），若有歷史 graphics memory issue，要回看是否曾針對特定模式做 workaround。

## 4. 最小差異建議（Minimal diff approach：步驟化）
> 目標：**先修 16:9 FOV（低風險）→ 再修 1:1（需 fallback）→ 最後補 overlay 校正**。每步可獨立回滾。

### Step 0｜先加觀測 log（不改行為）
- 在 bind 成功後統一 log：
  - Preview / Capture / Analysis 的 **attached resolution**
  - ViewPort scaleType / aspect ratio / rotation
  - （若可）`cropRect` 或 OutputTransform 資訊
- 目的：建立「改前/改後」對照，並快速定位 WYSIWYG 不一致原因。

### Step 1｜只改 ViewPort：明確設為 FIT（修 16:9 FOV）
- 在建立 `ViewPort.Builder` 時加：
  - `setScaleType(ViewPort.FIT)`
- 不改 selector、不改 1:1。
- 驗證 16:9 FOV 改善、overlay 是否出現偏移（先觀察，不急著修）。

### Step 2｜1:1 改為「正方形優先 selector」，1920×1920 僅作優先選項
- 不建議「只鎖死 1920×1920」；建議策略順序：
  1) 若 device 支援正方形輸出 → 選最大正方形（或最接近 1:1）  
  2) 若不支援正方形 → 選高解析 4:3（或 sensor native）+ **用一致的 ViewPort/裁切規則** 保證 Preview/Capture WYSIWYG  
- 落地方式（概念層級）：
  - 統一 Preview/ImageCapture（必要時含 Analysis）使用同一套 `ResolutionSelector` 或同一套「比例策略」
  - 1:1 模式下避免再走 `toCameraXAspectRatio()` fallback 4:3 造成 capture 比例漂移

### Step 3｜Overlay/座標系修正（若 FIT 或 1:1 導致錯位）
- 優先使用 CameraX/PreviewView 提供的 transform/座標轉換（如果 repo 已有工具就沿用）
- 將 overlay 的資料流改成：
  - **Analysis result（image space）→ mapping（透過 OutputTransform / CoordinateTransform）→ PreviewView space → Compose Canvas**
- 若 repo 目前是手算 normalized mapping，FIT 引入 letterbox 後通常要補「content rect」概念。

### Step 4｜只在必要時調整 Analysis 解析度（避免效能回歸）
- 允許 Analysis 用較低解析度（例如 1280×720 或 device 建議值），但要確保座標映射正確  
- 若你們目前要求 analysis 與 preview 同解析度以求簡化，則需重新評估 FPS/溫度。
