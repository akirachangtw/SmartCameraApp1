# v2.8.1 FPS & Memory 可行性分析報告

## 1. 綜述 (Executive Summary)

經由程式碼靜態分析，針對 `v2.8.1_fps-memory_issues_L2.md` 提出的假設進行了逐項驗證。

**結論：可行，但發現更根本的效能瓶頸。**

Sony 設備上的 FPS 退化主因極大機率並非 Phase 1 的邏輯改動，而是 `LiveCameraSource.kt` 中的 `Analyzer` 執行緒配置錯誤，導致繁重的 YUV 轉 Bitmap 運算直接阻塞了 Main Thread（UI 執行緒）。

Pixel 9a 的記憶體增長則證實與高頻率的 Bitmap 記憶體分配（Per-frame allocation）有關。

---

## 2. 關鍵假設驗證 (Assumptions Verification)

| 項目 | 假設內容 | 驗證結果 | 詳情 |
| :--- | :--- | :--- | :--- |
| **1** | **ImageProxy.close() 是否每幀執行** | **✅ 符合** | `LiveCameraSource`, `SmartCameraAnalyzer`, `GuidelineAnalyzer` 均已使用 `try/finally` 確保 close。 |
| **2** | **Backpressure 設定** | **✅ 符合** | `LiveCameraSource` 使用 `STRATEGY_KEEP_ONLY_LATEST`，無佇列堆積風險。 |

| **6** | **FPS 統計口徑** | **✅ 符合** | Phase 0/1 使用相同邏輯，但因 Main Thread 被阻塞，導致任何額外負載都會直接反映在 FPS 上。 |

## 3. 嚴重風險發現 (Critical Findings)

### 🔴 1. Live Camera Source 阻塞 UI Thread (FPS Killer)
在 `LiveCameraSource.kt` 中：

```kotlin
// LiveCameraSource.kt:191
imageAnalysis.setAnalyzer(
    ContextCompat.getMainExecutor(context), // ❌ 錯誤：使用 MainExecutor
    analyzer
)
```
`analyzer` 內部執行了高成本運算：
1.  `imageProxy.toBitmap()`：YUV 轉 RGB 運算（CPU bound）。
2.  `rotateBitmap()`：矩陣運算與點陣圖複製。

**影響**：這些運算直接在 Android 主執行緒（UI Thread）上執行。即使單幀耗時僅 10-15ms，加上 UI 繪製與其他邏輯，極易導致掉幀（Jank）。這是 Sony 手機 FPS 低落的根本原因。

### 🟠 2. 每幀記憶體分配 (Memory Growth Source)
`LiveCameraSource.kt` 的 `toBitmap()` 擴充函式：
```kotlin
// LiveCameraSource.kt
val bitmap = Bitmap.createBitmap(...) // 每幀分配
val pixels = IntArray(...) // 每幀分配
```
若有旋轉，`rotateBitmap` 會再 `createBitmap` 一次。


**影響**：
-   30 FPS 下，每秒產生 ~60-100MB 的垃圾物件（視解析度而定）。
-   雖然 GC 能回收，但在 Pixel 9a 等較新設備上，高頻 GC 可能導致 PSS 指標呈現線性增長（Delayed reclamation）或 CPU 使用率上升導致過熱降頻。

### 🟡 3. 重複的 Analyzer 配置
-   `LiveCameraSource` 已經在轉換 Bitmap 並送出 Flow。
-   `CameraRepositoryImpl` 卻又另外嘗試綁定 `SmartCameraAnalyzer` 到 `LifecycleCameraController`。
-   雖然因 `ProcessCameraProvider` 搶佔了相機資源，`CameraRepositoryImpl` 的綁定可能無效（Dead logic），但這增加了架構混亂與潛在的資源競爭風險。

## 4. 建議修正方案 (Recommended Actions)

### Phase 2.8.1 Performance Fix Plan

#### Step 1: 修正執行緒問題 (High Priority)
將 `LiveCameraSource` 的 Analyzer 移至背景執行緒執行。
-   使用 `Executors.newSingleThreadExecutor()` 或 `Dispatchers.Default` 對應的 Executor。
-   確保送出 Bitmap 到 Flow 時切回適當的 Scope 或保持在背景供 ViewModel 處理。

#### Step 2: 導入 Bitmap Pool (Medium Priority)
實作 Bitmap 重用機制，避免每幀重新分配。
-   使用 `Wait-free Object Pool` 或雙緩衝（Double Buffering）機制。
-   僅在解析度變更時重新分配。

#### Step 3: 清理架構 (Low Priority)
-   確認 `SmartCameraAnalyzer` 在 `CameraRepositoryImpl` 中的初始化邏輯是否必要，若多餘應移除，統一由 `ViewModel` 訂閱 `previewBitmap` 進行分析（目前已部分實作，需完全遷移）。

3.  **授權進行 Step 2 (Bitmap Reuse)**：解決 Memory Growth 問題。
