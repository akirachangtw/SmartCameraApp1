# v2.7.0 Phase 2｜OpenCV + 引導線（Guideline）— Level 1 規劃摘要  
主題：`v2.7.0_Phase2_OpenCV_Guideline`

---

## 1. 目標（Goal）
- 在 **v2.7.0 Phase 2** 導入 **OpenCV**（用於即時影像處理/分析），並在 **CameraX 預覽畫面上疊加「引導線（guideline）」**。
- 確保在 **Live 即時模式** 下：
  - 引導線穩定顯示、與畫面對齊（旋轉/鏡像/裁切一致）
  - OpenCV 分析不造成明顯 **FPS 下滑、延遲增加、或記憶體飆升**
  - 模式切換（Live / Static / Debug）不回歸（特別是相機生命週期與重綁定）

## 2. 背景與問題（Why / What）
- Phase 2 需求屬於「即時影像 + 影像處理 + UI 疊加」的組合，通常會同時牽動：
  - CameraX Preview / ImageAnalysis 的資料流
  - 影像格式轉換（YUV ↔ RGB）、旋轉與鏡像處理
  - OpenCV Mat 建立/釋放與效能最佳化
  - UI overlay 對齊（View 座標 vs sensor buffer）
- 目前使用者補充描述為：「**v2.7.0 Phase 2 OpenCV + 引導線**」；尚未提供明確錯誤訊息或現況行為，但依專案脈絡（CameraX + AI 即時）推測主要挑戰是：
  - **對齊問題**：引導線位置與實際預覽內容不一致（尤其前鏡頭鏡像、不同裝置 crop/scale、裝置旋轉）
  - **效能問題**：OpenCV 造成 frame drop、analysis backlog、GC 抖動
  - **模式切換回歸**：切回 Live 後 analysis/overlay 狀態未恢復或相機管線重建不完全

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線風險（CameraX / Preview / ImageAnalysis）**
   - ImageAnalysis 設定不當（解析度過高、背壓策略錯）導致 preview 卡頓或分析延遲累積。
   - 在綁定/重綁定時（切鏡頭、切模式）OpenCV pipeline 或 overlay 未同步重置，造成狀態錯亂或 crash。

2. **座標對齊風險（Rotation / Mirror / Crop / Scale）**
   - PreviewView 的 `ScaleType`（FILL_CENTER / FIT_CENTER 等）與 analysis buffer 的實際裁切區不同，導致 guideline 與目標區域錯位。
   - 前鏡頭鏡像處理未一致：preview 是鏡像但 analysis 或 overlay 沒鏡像（或相反）。

3. **效能回歸（FPS / CPU / Memory / GC）**
   - 每幀建立/釋放大量 Mat/Bitmap 造成 GC 抖動。
   - 色彩空間轉換成本過高（YUV→RGB）導致 CPU 飆高、FPS 下降。
   - 若 AI 推論與 OpenCV 同時跑，可能造成併發資源競爭（thread contention）。

4. **模式切換風險（Live / Static / Debug）**
   - Static 模式若重用同一套 overlay/analysis 管線，可能出現「沒有 camera frame 但仍在跑 analyzer」或反之。
   - 切回 Live 後 guideline 顯示狀態、參數（例如比例、中心點）未恢復。

5. **裝置差異風險（Emulator vs Real Device）**
   - 模擬器通常不具代表性：實機的 camera HAL、crop region、rotation metadata 可能不同，造成實機才錯位/掉幀。

## 5. 建議方案（Plan A / Plan B：最小差異優先）

### Plan A（最小差異、先把「引導線 overlay」與「OpenCV 分析」解耦）
1. **先做純 UI 引導線 overlay（不依賴 OpenCV 結果）**
   - 新增一個 `GuidelineOverlayView`（或 Compose overlay）疊在 PreviewView 上。
   - 引導線以「螢幕座標」繪製，先確保：
     - 旋轉/全螢幕/不同解析度下外觀正確
     - 前後鏡頭切換時（鏡像）視覺符合預期（即使只是 UI）

2. **OpenCV 先以「只讀分析」方式接入 ImageAnalysis**
   - Analyzer 先做最小工作：取到 frame、完成必要旋轉/鏡像校正後就 return（或計時 log），先量測效能基準。
   - 背壓策略：優先 `STRATEGY_KEEP_ONLY_LATEST`，並限制分析解析度（例如 640x480 / 720p，視需求）。

3. **建立「座標映射」單一來源（SSOT）**
   - 定義一個 mapping（例如 `FrameToViewTransform`）統一處理：
     - buffer rotation
     - mirroring
     - crop/scale 到 PreviewView 顯示區
   - 後續 OpenCV 偵測出的 ROI/點位，都透過此 mapping 轉成 overlay 座標，避免各處各算各的。

> 優點：最小改動、先把 UI 與管線穩定性搞定，再疊 OpenCV 結果，降低回歸風險。

---

### Plan B（若引導線必須跟 OpenCV 結果強耦合，採「事件輸出」設計降低耦合）
1. OpenCV Analyzer 輸出結構化結果（例如 `GuidelineResult(roiRect, points, confidence, timestamp)`）
2. UI overlay 只訂閱結果（Flow/LiveData/StateFlow），不直接接觸 Mat/Bitmap
3. 若效能不足：
   - 降頻：每 N 帧分析一次（例如 3~5 帧）
   - 降解析度：analysis 用低解析，overlay 仍以 preview 尺寸顯示（靠 transform 映射）
   - 將 OpenCV 放到專用 Dispatcher/HandlerThread，避免阻塞主執行緒與 CameraX callback

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）

### 功能驗證
- 引導線顯示：
  - 進入 Live：引導線立即顯示、無閃爍
  - 旋轉（直/橫）：引導線位置與比例合理（不變形或跑位）
  - 前後鏡頭切換：鏡像邏輯符合預期（不左右顛倒或漂移）
- 模式切換：
  - Live → Static → Live：引導線與分析（若有）能恢復，不 crash、不殘留舊狀態
  - Debug 模式（若有）：不影響 Live 行為

### 效能驗證（建議定量門檻）
- FPS：Live 預覽穩定（例如目標 24~30fps，至少不要明顯掉到 10~15fps）
- 延遲：analysis 結果 timestamp 與顯示差距可接受（例如 < 200ms，依產品需求調整）
- CPU：長時間（3~5 分鐘）運行不持續飆高
- Memory/GC：無持續成長（避免 Mat/Bitmap leak），GC 不頻繁尖峰

### 測試矩陣（最少集合）
- 模擬器：基本流程跑通（僅做 smoke test）
- 實機（必做）：至少 1 台主力測試機
  - 測：進 Live、切鏡頭、旋轉、縮放（若有）、模式切換、背景回前台（onPause/onResume）

## 7. 回滾策略（Rollback）
- 以 feature flag / build variant 控制（擇一或並行）：
  1. **開關 OpenCV 分析**：保留引導線 UI，但停用 OpenCV pipeline（快速止血效能問題）
  2. **開關引導線 overlay**：保留既有 CameraX + AI 流程，必要時完全關閉 overlay（避免 UI 對齊造成誤導）
- 實作層面建議：
  - OpenCV 初始化與 analyzer 註冊集中在單一入口，方便一鍵停用
  - 保持 atomic commit：先上 UI overlay、再上 OpenCV analyzer、最後才做結果綁定（每一步可獨立回退）
