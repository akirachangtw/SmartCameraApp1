## 1. 可行性結論（可行 / 不可行 / 需調整）
**可行，但需調整。**

原因摘要：
- 方向（rotation / EXIF）與預覽糊（Preview negotiation / UI scaling）通常可用 **CameraX 標準修正**與 **診斷資訊補齊**在不大改架構下解掉。
- 但本專案已有「**動態解析度選擇 / Pixel 記憶體敏感**」歷史包袱，且目前已導入 `CameraInputSource` / PreviewView 雙路徑，代表：
  - **提高解析度或改動 binding 順序**可能觸發回歸（FPS/Graphics memory）。
  - 「拍照清晰度」若要追近內建相機，純靠簡單參數可能有限；建議先把 **capture 真正用的尺寸/模式**釐清，再決定是否導入 Plan B（AF/AE 收斂等待、MAXIMIZE_QUALITY、capture size 提升）。

## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
以下假設若不成立，需改策略或先補實作：

1. **專案確實有 ImageCapture 拍照 use case**
   - 若目前其實是「截 preview / 截 bitmap」存檔，則「清晰度低」的主因會直接指向 **analysis/preview 解析度過低**或 **縮放裁切**。
2. **JPEG 儲存流程是否有自行旋轉或重寫 EXIF**
   - 需要確認：是否有 `Bitmap.rotate()`、或儲存前把 bitmap 旋轉後再寫檔，導致與 EXIF 旋轉重複/相反。

   - 需要確認：是否有 `DisplayManager` / `OrientationEventListener` / `LocalConfiguration` 驅動的 rotation 更新，且同時套用到 Preview/Analysis/Capture。
4. **PreviewView 目前使用的 scaleType / implementationMode**
   - 預覽糊可能是 PreviewView 在某些裝置上走了低品質路徑（TextureView/SurfaceView 切換）或被 UI 放大。
5. **目前 LiveCameraSource 的解析度選擇策略**
   - repo 看起來已有「裝置偵測 + 解析度過濾」：需要確認 Preview 與 Analysis 是否被迫共用同一組 targetResolution，導致 preview 被鎖到 640x480/800x600 而 UI 又放大成滿版。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX UseCase 綁定與重新綁定（bind/unbind）順序**
   - 任何加入/調整 ImageCapture 或改變 resolution selector 都可能改變 CameraX negotiation，導致：
     - 實際輸出尺寸改變（甚至回到 1080x1080 類 fallback）
     - Graphics memory / buffer 數量上升
2. **Preview / Analysis / Capture rotation 不一致**
   - 常見回歸：修好後鏡頭橫向後，前鏡頭或直向反而錯；或分析結果方向正確但存檔錯（反之亦然）。
3. **PreviewView 顯示路徑（PreviewView vs Compose Bitmap）雙路徑回歸**
   - 專案已做 PreviewView migration 以修 Graphics memory；任何「為了拍照品質」改回 bitmap 顯示或改動 SurfaceProvider，都可能重燃舊問題。
4. **模式切換（Live / StaticImageSource / Debug）行為分歧**
   - Static 模式常常沒有真實 rotation/EXIF 行為，容易出現「模擬器正常、實機翻車」。
5. **Thread/Executor 與拍照前對焦等待**
   - 導入 AF/AE 收斂等待若做在 UI thread，可能造成卡頓；
   - 若等待無 timeout，某些裝置可能「永遠不回 callback」。
6. **權限 / MediaStore / 檔案寫入**
   - 若要讀 EXIF 或寫入 EXIF，可能牽涉 SAF/MediaStore URI 寫入流程差異（Android 10+）。

## 4. 最小差異建議（Minimal diff approach：步驟化）
以「先止血 + 先定位」為主，避免一開始就拉高解析度或大改 binding。

### Step 0｜先做診斷（Debug only，低風險）
1. 在 Preview 畫面加 Debug overlay（或 log）顯示：
   - device/model、鏡頭（front/back）
   - `PreviewView.width/height`、`PreviewView.scaleType`、`implementationMode`
   - **實際 Preview resolution**（從 `PreviewView.getSurfaceProvider` 或 `StreamState`/usecase attached 後的資訊；若無法直接拿到，用 `SurfaceRequest` 或 use case log）
   - **Analysis resolution**（從 `ImageProxy.width/height` 第一幀 log）
   - **Capture 設定**：是否存在 ImageCapture、其 targetRotation、captureMode、targetResolution/selector
2. 存檔後立即 log 該張 JPEG：
   - 實際像素尺寸、EXIF orientation（若能讀到）
   - （若有自行旋轉）記錄旋轉角度與是否寫 EXIF

> 目的：快速把「預覽糊」拆成：低解析度 negotiation / UI 放大 / 真失焦。

### Step 1｜Rotation 一致性修復（仍屬最小 diff）
3. 建立「單一 rotation 真實來源」：以 Activity Display rotation 為準（`display?.rotation`）。
4. 在 rotation 變更時（或 `onResume`、或 Compose side effect）更新：
   - `preview.targetRotation = rotation`
   - `imageAnalysis.targetRotation = rotation`
   - `imageCapture.targetRotation = rotation`（若存在）
5. 禁止雙重旋轉：
   - 若 JPEG 依靠 EXIF orientation：App 不要再把 bitmap 旋轉後存檔。
   - 若 App 必須輸出「已旋轉到正向」的 bitmap：那就把 EXIF orientation 固定為 NORMAL（或不寫），避免相簿再旋一次。

### Step 2｜預覽清晰度（只調顯示策略，不動演算法/解析度上限）
6. 檢查 `PreviewView.ScaleType` 與 Compose 容器比例：
   - 避免把 4:3 preview 硬撐成 16:9 滿版再被放大裁切（視覺上像糊）
   - 優先用一致比例容器（例如固定 4:3 box）做 A/B 對照
7. 若確定 Preview negotiation 真的太低，再進入 Step 3；否則不要碰解析度策略。

### Step 3｜拍照品質（僅在確認目前 capture 尺寸/模式不合理後）
8. 若目前「存檔來源是 analysis bitmap」：先導入真正 ImageCapture（或提高 capture size）才有機會接近內建相機。
9. 若已使用 ImageCapture，但 captureMode 是 MINIMIZE_LATENCY：
   - 先做可切換（Debug flag）：MAXIMIZE_QUALITY
10. 加入拍照前 AF/AE metering（**帶 timeout**，例如 500–800ms）作為可選開關，避免 UX 變慢不可控。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **功能旗標分層包住（強烈建議）**
   - `FLAG_DEBUG_CAMERA_OVERLAY`：只影響顯示/診斷，可常駐 Debug
   - `FLAG_CAMERA_ROTATION_UNIFY`：rotation 修復可獨立開關（必要時針對裝置/OEM 做條件分支）
   - `FLAG_CAPTURE_MAX_QUALITY`：CAPTURE_MODE_MAXIMIZE_QUALITY 開關
   - `FLAG_CAPTURE_AF_AE_CONVERGE`：拍照前 AF/AE 收斂等待開關（含 timeout 設定）
   - `FLAG_CAPTURE_HIGH_RESOLUTION`：capture size 提升（高風險，務必可回滾）
2. **Atomic commits 切分（對應回滾粒度）**
   - Commit A：overlay/log（永遠可保留）
   - Commit B：rotation 統一（可快速 revert）
   - Commit C：PreviewView scale/layout 調整（可 revert）
   - Commit D：ImageCapture 品質/對焦流程（高風險最後做）
3. **裝置條件保護（針對 Pixel 記憶體敏感）**
   - 若 Step 3 涉及高解析度或額外 buffer：先只對非 Pixel/非問題裝置啟用，或反過來只對特定裝置 A/B。
4. **避免改動 PreviewView migration 的核心路徑**
   - 任何「為了更清晰預覽」都不應回到 Compose 每幀 bitmap 顯示；預覽清晰度優先透過 negotiation/scaleType/layout 解。
