## 1. 可行性結論（可行 / 不可行 / 需調整）
**結論：需調整（可行但需補齊設計細節與落地順序）**

理由（對 Claude Code 的決策點）：
- 以 **Camera2 characteristics 查詢輸出尺寸** 來判斷 `800x600` 支援度，技術上可行且跨品牌穩定。
- 但 repo 目前已在進行 **PreviewView migration / 模式切換（Live vs Static）/ Pixel 9a mitigation** 等高風險變更；動態解析度檢測若插入錯誤時機，容易引發：
  - 權限未授予的 `SecurityException`
  - 與 CameraX `ResolutionSelector` / UseCase 綁定流程衝突
  - 初始化時序造成黑屏或重綁定抖動
- 因此建議先以 **最小 diff** 方式落地：把檢測封裝成「只讀快取 → 必要時檢測 → 回傳 target Size」，並在「權限已授予、且 camera bind 前」執行一次即可。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **權限時機（高風險）**
   - `CameraManager.getCameraCharacteristics()` 在未授權時可能 `SecurityException`（尤其在部分 OEM）。
   - 風險放大點：若 detector 在 App cold start / ViewModel init 就跑，會直接 crash。

2. **CameraX 綁定流程衝突（高風險）**
   - 若目前 CameraX 已採 `ResolutionSelector` 或 `QualitySelector`，硬塞 `setTargetResolution` 可能無效或造成 fallback 到非預期尺寸。
   - PreviewView migration 已引入新的 Preview UseCase 連接 surface provider（見 git diff）。解析度決策若改動 UseCase builder，容易影響黑屏率。

3. **多 UseCase 尺寸一致性（中高風險）**
   - Preview / ImageAnalysis / ImageCapture 若各自選到不同 aspect ratio 或 size，可能導致：
     - bind 失敗（IllegalArgumentException / UnsupportedOperation）
     - 預覽裁切與分析座標對不上（composition/guideline overlay 誤差）
   - 需確認目前 overlay/分析是用 previewBitmap 尺寸或 PreviewView 尺寸做 mapping。

4. **模式切換（Live vs Static / debug flags）（中風險）**
   - repo 目前已存在 `supportsNativePreview()`、bitmap fallback、A/B flags。  
   - detector 應只在 Live 實機模式跑，且不要污染 emulator 的行為（避免造成初始化流程卡住）。

5. **Thread / Coroutine / 首次啟動 UX（中風險）**
   - detector 若在 Main thread 做大量查詢可能造成掉幀或卡頓（雖預估 ~50ms，但低階機 + 多鏡頭仍可能放大）。
   - 需用 IO dispatcher，並保證「偵測未完成也能走 fallback」。

## 4. 最小差異建議（Minimal diff approach：步驟化）
**目標：先做到「可安全上線、可回滾、行為可觀測」，再逐步移除品牌策略。**

### Step 0（前置盤點，不改行為）
- 全 repo 搜尋解析度設定點：
  - `setTargetResolution`
  - `ResolutionSelector`
  - `QualitySelector`
  - `TARGET_RESOLUTION`
  - `selectDeviceOptimalResolution`
- 確定「唯一入口」與各 UseCase 的決策鏈。

### Step 1（新增 Detector + Cache，但先不接主流程）
- 新增 `CameraCapabilityDetector`：
  - 只做一件事：回傳 `supports800x600(Boolean)` + `recommendedSize(Size)`（800x600 else 640x480）
  - cache schema 先極簡：`target_width/target_height/app_version/model/manufacturer/sdk`
  - 加上 `cache_version`（避免未來 schema 變更無法辨識）
- 加入 `Result` 包裝與 exception 捕捉，**任何失敗都不要 throw**（回傳 fallback）。

### Step 2（把 Detector 接到「解析度選擇函式」但保持 fallback）
- 在 `LiveCameraSource.selectDeviceOptimalResolution()`（或同等函式）最前面：
  1) 讀 cache 命中 → 使用  
  2) cache miss →（可選）同步輕量檢測或回傳預設，並在背景寫 cache  
  3) 任何例外 → 回 `640x480`
- 先不要動到 CameraScreen/VM 的初始化流程（避免把風險擴散到 UI/權限流程）。

### Step 3（在「權限已授予」後做一次 detectAndCache）
- 在 ViewModel / UI permission granted 後呼叫：
  - `if (liveMode && !cached) detectAndCacheCapabilities()`
- 需加「只跑一次」鎖（in-flight job / mutex）避免多次重入。

### Step 4（移除品牌策略）
- 確認 detector 命中率/成功率穩定後，才刪 Pixel/Sony 策略分支。
- 刪除前保留 feature flag（見第 7 節），可一鍵切回舊邏輯。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **Feature Flag（強烈建議）**
   - `BuildConfig.ENABLE_DYNAMIC_RESOLUTION_DETECTION`（或 remote config）
   - 關閉時：完全走舊 `selectDeviceOptimalResolution()` 內的既有邏輯（即使品牌策略尚未移除，也能保命）

2. **Cache schema versioning**
   - `cache_version = 1`
   - 未來改欄位時 bump version → 舊 cache 直接視為 miss

3. **Fail-closed 行為**
   - detector 任意例外 → 回傳「不支援 800x600」→ 使用 `640x480`
   - 絕不因 detector 失敗阻擋相機初始化（避免首次啟動卡死）

4. **In-flight guard（避免重入）**
   - 使用 `Mutex` 或 `AtomicBoolean` 確保同一時間只有一個 detect job
   - UI 重組 / 多次進入 CameraScreen 不會觸發多次查詢

5. **可觀測性（logs + metrics）**
   - log：`cache_hit/cache_miss/detect_success/detect_fail/fallback_used` + 耗時
   - 若有 Crashlytics：記錄非致命錯誤（detector fail）以追真實失敗率
