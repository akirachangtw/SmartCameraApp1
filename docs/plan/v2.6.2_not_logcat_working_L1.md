# v2.6.2_not_Logcat_working｜Level 1 規劃摘要

## 1. 目標（Goal）
- 讓團隊能**穩定收集到 APP 相關 Logcat 日誌**（包含即時相機/CameraX/HDR 流程的關鍵 log），避免 `adb logcat -d` 出現**斷斷續續空白輸出**或漏 log。
- 建立一套**可重複、可交接**的日誌收集方式（指令/過濾條件/權限與裝置設定檢查），讓後續實機問題（如 HDR、CameraControl not available、模式切換）可被追蹤。

---

## 2. 背景與問題（Why / What）
### 現象（依使用者即時觀察）
- 執行 `adb logcat -d` 時，輸出會**斷斷續續出現空白段落**，偶爾才夾雜 APP 日誌。
- 造成問題定位困難：無法可靠取得完整 log（特別是相機生命週期、UseCase rebind、權限、曝光補償/HDR 等 log）。

### 初步推測原因（尚未驗證，需後續確認）
- **Log buffer/讀取行為**：`-d` 為 dump 既有 buffer，可能因 buffer 被清掉、過小、或被其他工具讀取/輪替導致看起來「空白/斷續」。
- **Android 版本/權限限制**：Android 13+ 對部分 log 與讀取行為更嚴格；若期待讀到非自己 app 的 log（system/camera service）可能受限。
- **裝置端 logd / buffer 配置**：buffer 太小、頻繁覆蓋（相機/ML pipeline 會大量輸出）。
- **指令/環境問題**：Windows shell/編碼、管線（pipe）造成看似空白；或同時有 Android Studio Logcat / 其他 adb client 在讀取造成干擾（機率較低但需排除）。
- **APP 本身 log tag/filter 不一致**：若只看特定 tag，但實際 log 使用 Timber/Log 混雜，或 release/Proguard/最小化影響（依 buildType 而定）。

## 3. 影響範圍（Scope：模組/檔案/功能層級；若未知請以推測標註）
### 直接影響
- **Debug/診斷流程**：無法在 issue 發生時保留完整證據，降低修復效率與可信度。
- **相機管線相關問題追查**：CameraX 綁定/重綁、模式切換（Live/Static）、HDR 曝光補償、CameraControl 可用性等，若無 log 會很難判斷是 lifecycle、threading 還是 device-specific。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **診斷風險（P0）**：log 無法穩定取得，導致「看似修好但實機未證實」的決策風險升高。
2. **相機管線風險（P1）**：CameraX 在實機上常見 timing/lifecycle 差異（bind/rebind、surface、analyzer attach），沒有 log 會難以定位 race condition。
3. **模式切換風險（P1）**：Live/Static 切換後若出現 `CameraControl not available` 或 HDR 失效，需依 log 判斷是否因 rebind 後未重套設定；log 缺失會讓問題被誤判為「偶發」。
4. **效能回歸風險（P2）**：為了「補 log」而提高 log 量/頻率，可能造成：
   - 影像分析 thread 被阻塞（尤其在每幀 log）
   - buffer 更快被洗掉，反而更難收集有效資訊
5. **工具流程風險（P2）**：若團隊各自用不同指令/過濾條件，會產生不可比對的 log（交接困難）。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異、優先採用）：建立「穩定可重現」的 logcat 收集指令與操作規範
- **改用即時串流收集**取代 `adb logcat -d` 作為主要手段：  
  - 用 `adb logcat -c` 先清空，再用不帶 `-d` 的串流方式輸出到檔案（避免 dump 時機與 buffer 輪替造成斷續）。
- **收斂 filter**：以 app package / PID / tag 為主，避免被大量系統 log 淹沒。
- **標準化 SOP**：固定「清 buffer → 啟動 app → 重現 → 停止收集」。
- **最小程式碼改動（可選）**：只補 1–2 個「關鍵事件 log」確保能用 tag/prefix 搜尋（例如 `APP_TRACE`），避免 per-frame log。

> 交付物：一份 `docs/workflow/logcat_collection_sop.md`（或更新既有 `LOGCAT_ISSUE_HANDOFF.md`），搭配 1 個腳本（bat/ps1 擇一）統一入口。

### Plan B（備援方案）：若裝置/系統限制導致 logcat 不可靠，改用 App 內部落盤
- 在 debug variant 加入「檔案 logger」（例如 Timber tree 寫入 app-specific storage），在 UI/快捷鍵導出 zip。
- 優點：不依賴 adb/logd；缺點：需額外實作、注意隱私與容量控管。
- 適用條件：若確認是 Android 版本/裝置策略導致 logcat 取得不全或不穩。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### 核心驗證目標
- 可在一次重現流程中取得「連續且完整」的 log 檔，且能明確包含 APP 關鍵 tag/訊息。

### 驗證步驟（建議）
1. **實機優先**（因問題多半與裝置/ADB/版本相關）  
   - 清 buffer → 開始串流收集 → 啟動 app → 重現 → 停止 → 檢查檔案是否連續、有時間戳、含 APP log。
2. **模擬器對照**  
   - 同樣流程跑一次，確認是否只有實機異常（用於判斷裝置端限制 vs 指令/腳本問題）。
3. **效能指標（避免新回歸）**
   - 收集期間 app 是否出現明顯掉幀/卡頓（主觀 + basic FPS/Frame drops 若已有工具）
   - log 檔大小成長速度是否可接受（例如 1 分鐘不應爆量到數百 MB）

### 驗證通過條件（Definition of Done）
- 在 3 次連續測試中，log 檔皆可讀、無大量空白段落、可搜尋到至少以下事件（範例）：
  - App 啟動/進入相機頁
  - Live/Static 模式切換
  - CameraX bind/rebind（若有打點）
  - HDR enable/disable 呼叫與結果
