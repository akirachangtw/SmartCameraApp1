# Plan: Aspect Ratio & Zoom Fix Proposal (v2.9.9)

## 1. Analysis Summary (現狀分析)
The current implementation suffers from two main issues identified in `docs/plan/v2.9.9-preview_zoom_aspect_ratio.md`:
1.  **Preview Zoom (FOV Issue)**: The preview feels zoomed in (1.6x) because `CameraPreview` uses `ScaleType.FILL_CENTER` (Center Crop) to display a 4:3 image on a ~20:9 screen. This crops ~36% of the horizontal field of view.
2.  **Aspect Ratio Limitation**: While recent code changes (v2.10.0 Phase A) force 16:9 to mitigate the zoom effect (by using more vertical sensor area relative to screen width), this forces a crop and doesn't offer the full 4:3 sensor readout expected in a "Professional" camera app.

## 2. Best Feasible Solution (最佳建議可行方案)

To provide a professional experience similar to Pixel Camera, we propose the following **three-part solution**:

### Phase 1: Dynamic Aspect Ratio Architecture (核心架構)
Transition from hardcoded resolution selection to a dynamic `UseCaseGroup` approach.
-   **Why**: `UseCaseGroup` with `ViewPort` is the official CameraX API for ensuring WYSIWYG (What You See Is What You Get) across different aspect ratios (4:3, 16:9, 1:1). It handles cropping automatically for both Preview and Capture.
-   **Status**: Currently `LiveCameraSource` binds use cases individually. Refactoring to `UseCaseGroup` is straightforward and robust.

### Phase 2: Aspect Ratio Strategy (長寬比策略)
Implement three modes:
1.  **4:3 (Standard/Sensor Full)**:
    *   **Preview Behavior**: Uses entire sensor.
    *   **Display**: `FIT_CENTER`. On a 20:9 screen, this will show black bars (pillarboxing). **Crucial**: This completely solves the "Zoomed In" feeling by showing the full FOV.
    *   *Alternative*: `FILL_CENTER` (Current behavior) -> Zoomed in. User must be able to choose `FIT_CENTER` behavior or it should be default for 4:3.
2.  **16:9 (Wide/Screen Match)**:
    *   **Preview Behavior**: Crops top/bottom of sensor.
    *   **Display**: `FILL_CENTER` (or `FIT_CENTER` if screen is taller than 16:9). Fills most of the screen.
3.  **1:1 (Square)**:
    *   **Preview Behavior**: Crops to square.
    *   **Display**: `FIT_CENTER` (Square with large black bars).
    *   *Implementation*: CameraX doesn't have `RATIO_1_1`. We use `RATIO_4_3` with a `ViewPort` set to 1:1 aspect ratio.

### Phase 3: UI Implementation (介面實作)
-   Add **Aspect Ratio Toggle Button** (icon cycler: 4:3 -> 16:9 -> 1:1).
-   Update `CameraPreview` to respect the requested aspect ratio.

## 3. Implementation Plan (執行計畫)

### Step 1: Add Aspect Ratio State & Enum
Create `CameraAspectRatio` enum and manage it in `CameraViewModel`.

### Step 2: Refactor `LiveCameraSource.bindToLifecycle`
Modify to accept `aspectRatio: CameraAspectRatio`. Use `UseCaseGroup` to bind.

```kotlin
// Pseudo-code for ViewPort logic
val aspectRatio = when (cameraAspectRatio) {
    CameraAspectRatio.RATIO_4_3 -> Rational(4, 3)
    CameraAspectRatio.RATIO_16_9 -> Rational(16, 9)
    CameraAspectRatio.RATIO_1_1 -> Rational(1, 1)
}

val viewPort = ViewPort.Builder(aspectRatio, rotation).setScaleType(ViewPort.FILL_CENTER).build()

val useCaseGroup = UseCaseGroup.Builder()
    .addUseCase(preview)
    .addUseCase(imageAnalysis)
    .addUseCase(imageCapture)
    .setViewPort(viewPort)
    .build()

cameraProvider.bindToLifecycle(lifecycleOwner, cameraSelector, useCaseGroup)
```

### Step 3: Update `CameraPreview` ScaleType
Change `PreviewView.ScaleType` to `FIT_CENTER` to ensure the entire `ViewPort` content is visible without further scaling artifacts, effectively letting CameraX handle the "Crop" via ViewPort and `PreviewView` just displays the result.
*Note*: If we use `UseCaseGroup` + `ViewPort`, the Preview use case outputs the *cropped* stream. `FIT_CENTER` ensures we see that whole stream.

## 4. Expected Results (預期成果)
-   **4:3**: Full sensor view, black bars on sides. No "Artificial Zoom".
-   **16:9**: Wide view, fills screen (slight top/bottom crop of sensor).
-   **1:1**: Square view.
-   **WYSIWYG**: Captured photos match Preview exactly in all modes.
