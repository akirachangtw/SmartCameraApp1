# Level 1 規劃摘要：v2.7.0_phase2_opencv_optimizer

## 2. 背景與問題（Why / What）
### Why（為什麼要做）
- 即時導引線 overlay 的使用者體感主要取決於「每次分析延遲」與「尾端延遲（P95/P99）」；單看平均值不足以決定是否可釋出。
- 目前 v2.7.0 Sprint 5 已透過 OpenCV 參數最佳化（Canny/Hough 相關）得到明顯提升，但仍需要：
  - **跨 SoC / Android 版本 / 記憶體頻寬差異** 的驗證
  - 決策 v2.7.0 是否可 release，以及 v2.8.0 是否必須投入「繞過 Bitmap 轉換」等架構級優化

### What（目前觀察到什麼）
- **Pixel 9a（Tensor G4 / Android 16）已達成 v2.7.0 acceptance**：Avg 90.7ms、P95 146ms（PASS）。
- **Sony XQ-BT52（Snapdragon 690 / Android 12）接近但未達標**：Avg 113.9ms、P95 157ms（CLOSE）。
- Root cause：兩機種共同的主要瓶頸仍是 **Camera pipeline（YUV→Bitmap→Mat）約 70–80ms，占總耗時 70%+**；OpenCV 本體差異反而只解釋了約 20% 的總提升。
- 因此 v2.7.0 可以釋出（以中高階為主），但若要廣泛覆蓋中低階，**v2.8.0 Priority 2（Bypass Bitmap conversion / 直接吃 ImageProxy）是關鍵。**

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線瓶頸風險（核心）**
   - 目前耗時大宗在 YUV→Bitmap→Mat，若裝置廠商對 YUV/RGB 轉換實作差、或記憶體頻寬更低，可能直接跌破 10 FPS 體感。
2. **模式切換風險（Live/Static/Debug）**
   - LiveCameraSource 的資源釋放/重建（CameraControl、UseCase bind/unbind、ImageAnalysis analyzer lifecycle）若與效能修正交錯，容易引發：
     - CameraControl not available
     - Analyzer 重複註冊 / memory leak
     - Preview 黑畫面或 freeze
3. **效能回歸風險（參數與場景敏感）**
   - OpenCV 參數在「室內幾何線」表現佳，不代表在低光、動態模糊、高噪點場景仍能維持同等時間與品質。
   - 調高 HOUGH_THRESHOLD / MIN_LINE_LENGTH 可能讓速度變快但線品質變差，造成 UX 回歸（線少、抖動、錯誤線）。
4. **尾端延遲（P95/P99）與 outlier 風險**
   - Pixel 9a 仍有 >150ms outlier；若某些裝置更常發生 GC、bitmap allocation 抖動，P95 會惡化。
5. **版本/ABI 差異風險**
   - Android 12 vs 16、不同 GPU/ISP、不同 camera HAL 對 CameraX pipeline 行為差異，可能造成「同參數不同結果」。
6. **量測方法風險**
   - 若只量 OpenCV 段落而未涵蓋 conversion/buffer 管理，可能低估實際延遲；或 sampling 週期造成 aliasing（100ms interval 導致某些尖峰被漏採/被放大）。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（v2.7.0：最小差異、以可釋出為導向）
1. **維持 Sprint 5 OpenCV 最佳化參數**作為 v2.7.0 預設（已證實 Pixel 9a PASS、Sony CLOSE）。
2. **明確設定裝置 tier 與產品說明**
   - Recommended：Snapdragon 7+ Gen 2 / Tensor G4 等級以上
   - Minimum：Snapdragon 690（可用但略 lag）
3. **增加 runtime 自我保護（低風險小改）**
   - 若偵測到平均 > 120ms 或 P95 > 180ms（可用滑動窗口估算），自動降載：
     - 降低分析頻率（例如 10 FPS → 7 FPS）
     - 或降低 MAX_LINES、提高 HOUGH_THRESHOLD（以換取穩定）
4. **完善效能量測與 log schema**
   - 統一輸出：frameId、conversion、opencv、total、linesCount、scene tag
   - 方便 v2.8.0 做 A/B 比較與回歸檢測

### Plan B（v2.8.0：Priority 2，必要時的架構級優化）
1. **繞過 Bitmap conversion：直接由 ImageProxy 取得 Gray Mat**
   - 目標：Camera pipeline 70–80ms → ~8–10ms（依估算可將 Pixel 9a 降到 ~29ms、Sony ~44ms）
2. **建立雙路徑（feature flag）**
   - 新路徑：ImageProxy → direct Mat（Y plane）→ OpenCV
   - 舊路徑保留：Bitmap.toGrayMat（便於回滾與裝置相容性處理）
3. **處理旋轉、stride/pixelStride、ROI 等細節**
   - 避免因灰階 plane stride 導致 Mat 解讀錯誤、影像扭曲，造成誤檢/漏檢或 crash

## 7. 回滾策略（Rollback）
- v2.7.0：
  - 若釋出後在特定裝置出現明顯 lag 或 P95 飆高：
    1) 透過 remote config / build flag 降載（降低分析頻率、降低 MAX_LINES、提高 threshold）
    2) 回退到上一版「較保守但穩定」的 OpenCV 參數組合（保留參數 preset）
- v2.8.0（若導入 Plan B）：
  - 以 feature flag 控制新舊 pipeline
  - 出現相容性問題時可即刻切回 Bitmap 路徑（不影響主流程）
