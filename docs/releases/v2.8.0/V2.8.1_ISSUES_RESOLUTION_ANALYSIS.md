## 🔍 問題詳細分析

### 🔴 問題 1: UI Thread 阻塞 (FPS Killer)

#### 原始問題描述 (v2.8.1 報告)

**位置**: `LiveCameraSource.kt:191`

```kotlin
// ❌ 錯誤配置 (假設的問題)
imageAnalysis.setAnalyzer(
    ContextCompat.getMainExecutor(context), // 阻塞 UI Thread
    analyzer
)
```

**影響**:
- YUV→RGB 轉換 (CPU bound) 在主執行緒執行
- 每幀 10-15ms 運算阻塞 UI
- 導致 Sony XQ-BT52 FPS 降至 24 (vs Phase 0 的 28.8)

#### 實際解決方案 (v2.8.2+)

**位置**: `LiveCameraSource.kt:138-140, 311`

```kotlin
// ✅ 正確配置 (實際實作)
private val analysisExecutor = Executors.newSingleThreadExecutor { runnable ->
    Thread(runnable, "LiveCameraSourceAnalyzer").apply { isDaemon = true }
}

// 使用背景執行緒
imageAnalysis.setAnalyzer(
    analysisExecutor, // 專用背景執行緒
    analyzer
)
```

**改進點**:
1. ✅ 使用 `SingleThreadExecutor` 替代 `MainExecutor`
2. ✅ 命名執行緒為 "LiveCameraSourceAnalyzer" (便於除錯)
3. ✅ 設定為 Daemon thread (避免 leak)

**驗證結果**:
- v2.8.4: FPS 27.2 (良好光線) > v2.8.0 Phase 1: 24.0 ✅
- UI thread 不再阻塞
- YUV 轉換完全在背景執行

**狀態**: ✅ **已完全解決**

### 🟠 問題 2: 每幀記憶體分配 (Memory Growth Source)

#### 原始問題描述 (v2.8.1 報告)

**位置**: `LiveCameraSource.kt` (v2.8.0 版本)

```kotlin
// ❌ 每幀分配 (舊版本)
val bitmap = Bitmap.createBitmap(...) // 每幀分配
val pixels = IntArray(...) // 每幀分配

// 若旋轉,再分配一次
rotateBitmap() // 又一次 createBitmap()
```

**影響**:
- 30 FPS 下,每秒產生 60-100MB 垃圾物件
- Pixel 9a Memory Growth: +79MB over 3 minutes
- 高頻 GC 導致 CPU 使用率上升

#### 解決方案 Phase 1: BitmapPool 引入 (v2.8.1/v2.8.2)

**位置**: `LiveCameraSource.kt:143-144, 189`

```kotlin
// ✅ v2.8.1: 引入 BitmapPool
private val bitmapPool = BitmapPool(maxEntriesPerKey = 4)
private val inFlightPreviewBuffers = ArrayDeque<BitmapPool.BitmapBuffer>(4)

// 使用 Pool 獲取 Bitmap
val rawBuffer = bitmapPool.acquire(
    imageProxy.width,
    imageProxy.height,
    Bitmap.Config.ARGB_8888
)
```

**位置**: `BitmapPool.kt` (新增檔案)

```kotlin
class BitmapPool(private val maxEntriesPerKey: Int = 2) {
    private val pools = mutableMapOf<PoolKey, ArrayDeque<BitmapBuffer>>()

    fun acquire(width: Int, height: Int, config: Bitmap.Config): BitmapBuffer {
        // 重用現有 Bitmap 或建立新的
    }

    fun release(buffer: BitmapBuffer) {
        // 歸還 Bitmap 至 Pool
    }
}
```

**改進點**:
1. ✅ Bitmap 重用機制 (避免每幀分配)
2. ✅ 使用 `ArrayDeque` 管理 in-flight buffers
3. ✅ 自動記憶體管理 (hits/misses 統計)

#### 解決方案 Phase 2: Transform 優化 (v2.8.3)

**位置**: `LiveCameraSource.kt:650-723` (v2.8.3)

```kotlin
// ✅ v2.8.3: Paint 物件重用
private val transformPaint = Paint(Paint.FILTER_BITMAP_FLAG).apply {
    isAntiAlias = false
    isDither = false
}

private fun transformBitmap(...): BitmapPool.BitmapBuffer {
    val out = bitmapPool.acquire(outWidth, outHeight, Bitmap.Config.ARGB_8888)
    // 重用 Canvas 與 Paint
}
```

**改進點**:
1. ✅ Paint 物件重用 (避免每幀分配)
2. ✅ 禁用不必要的 antiAlias/dither (效能優化)

#### 解決方案 Phase 3: BitmapPool Key Explosion 修復 (v2.8.4)

**位置**: `LiveCameraSource.kt:650-723` (v2.8.4)

```kotlin
// ✅ v2.8.4 Quick Win: 固定整數尺寸 (消除 key explosion)
val (outWidth, outHeight) = when (degrees) {
    90, 270 -> srcHeight to srcWidth  // Swap for portrait
    else -> srcWidth to srcHeight      // Keep for landscape
}
```

**關鍵發現**:
- 舊版使用 `ceil(mapRect())` → 浮點誤差 → 721, 719, 722 等不同尺寸
- Pool keys 從 2 爆增至 10+
- Hit rate 降至 <50%

**修復後**:
- Pool keys: 10+ → **1** ✅
- Hit rate: <50% → **99%** ✅
- 完全消除記憶體分配浪費

**驗證結果** (v2.8.4):
- BitmapPool hit rate: 99% (所有測試樣本一致)
- Pool keys: 1 (720x720 固定尺寸)
- Memory growth: 顯著降低

**狀態**: ✅ **已完全解決** (三階段優化)

### 🟡 問題 3: 重複的 Analyzer 配置 (架構混亂)

#### 原始問題描述 (v2.8.1 報告)

**描述**:
- `LiveCameraSource` 已經在轉換 Bitmap 並送出 Flow
- `CameraRepositoryImpl` 卻又嘗試綁定 `SmartCameraAnalyzer` 到 `LifecycleCameraController`
- 因 `ProcessCameraProvider` 搶佔資源,Repository 的綁定可能無效 (Dead logic)

**影響**:
- 架構混亂,增加維護困難度
- 潛在的資源競爭風險

#### 實際狀態 (v2.8.4)

**檢視 CameraRepositoryImpl**:
- Repository 仍保留 `SmartCameraAnalyzer` 初始化
- 但主要分析邏輯已移至 ViewModel (通過 `previewBitmap` Flow)
- Repository 的 analyzer 綁定可能確實為 dead code

**評估**:
- 不影響 v2.8.4 FPS 目標達成
- 屬於架構清理項目,非效能瓶頸
- 可列入未來重構清單

**狀態**: ⚠️ **可接受的架構問題** (非阻塞項)

## 🎯 v2.8.1 報告建議的執行狀態

### Step 1: 修正執行緒問題 (High Priority)

**原始建議**:
> 將 `LiveCameraSource` 的 Analyzer 移至背景執行緒執行。使用 `Executors.newSingleThreadExecutor()` 或 `Dispatchers.Default`。

**執行狀態**: ✅ **已完成** (v2.8.2)
- 實作: `Executors.newSingleThreadExecutor()` with named thread
- 位置: `LiveCameraSource.kt:138-140`
- 驗證: FPS 提升至 27.2

### Step 2: 導入 Bitmap Pool (Medium Priority)

**原始建議**:
> 實作 Bitmap 重用機制,避免每幀重新分配。使用 Wait-free Object Pool 或雙緩衝機制。

**執行狀態**: ✅ **已完成** (v2.8.1/v2.8.3/v2.8.4)
- Phase 1 (v2.8.1): BitmapPool 基礎實作
- Phase 2 (v2.8.3): Transform Paint 重用
- Phase 3 (v2.8.4): BitmapPool Key Explosion 修復
- 驗證: Pool hit rate 99%

### Step 3: 清理架構 (Low Priority)

**原始建議**:
> 確認 `SmartCameraAnalyzer` 在 `CameraRepositoryImpl` 中的初始化邏輯是否必要。

**執行狀態**: ⚠️ **部分完成**
- 主要分析邏輯已移至 ViewModel
- Repository 的 analyzer 可能為 dead code
- 不影響 FPS 目標,可列入未來重構
