## 🚨 Root Cause Analysis

### Hypotheses

#### ❓ H1: YUV 轉換效能問題
**描述**: 直接 YUV→RGB 轉換可能比原始 JPEG decode 更慢
**證據**:
- ❌ 無法解釋為何 FPS 比 Phase 1 **更低**（Phase 1 也使用相同 YUV 轉換）
- ❌ Phase 1 已證明 YUV 轉換可達 24.0 FPS

**可能性**: 🟢 **低** (5%)

#### ❓ H2: BitmapPool 同步開銷
**描述**: `acquire()` / `release()` 操作可能引入延遲
**證據**:
- ✅ BitmapPool 使用 `mutableMapOf` + `ArrayDeque`（非執行緒安全，但單執行緒使用）
- ❌ 無鎖設計，理論上開銷極低（< 1μs）
- ⚠️ 需驗證 `ArrayDeque.removeFirstOrNull()` 在空 pool 時的效能

**可能性**: 🟡 **中低** (20%)

#### ❓ H3: Bitmap.setPixels() 效能
**描述**: 每幀呼叫 `bitmap.setPixels()` 寫入 pixel 資料可能很慢
**證據**:
- ✅ `setPixels()` 是 native call，涉及 JNI 開銷
- ✅ 每幀寫入 640x480x4 = ~1.2MB 資料
- ⚠️ 但 Phase 1 也使用相同方法，為何 v2.8.1 更慢？

**可能性**: 🟡 **中** (30%)

#### ❓ H4: Executor 配置問題
**描述**: 單執行緒 background executor 可能與其他背景任務競爭
**證據**:
- ✅ Phase 1 使用 `MainExecutor`（有優先權保證）
- ✅ v2.8.1 使用 `newSingleThreadExecutor()`（預設優先權 `NORM_PRIORITY`）
- ⚠️ 設定了 `NORM_PRIORITY + 1`，理論上應優於 UI thread
- ❌ 但實際 FPS 反而更低

**可能性**: 🟡 **中高** (40%)

#### ❓ H5: Bitmap 重用導致記憶體碎片化
**描述**: 重用 Bitmap 可能導致記憶體配置效率下降
**證據**:
- ✅ Memory growth +37MB（比 Phase 1 的 +8MB 高 4.6 倍）
- ✅ 可能是 pool 中的 Bitmap 無法被 GC 回收
- ⚠️ 但 `maxEntriesPerKey = 4` 應限制 pool 大小

**可能性**: 🟡 **中** (25%)

#### ❓ H6: In-Flight Buffer 延遲釋放
**描述**: `inFlightPreviewBuffers` 保留 3 幀可能延遲記憶體釋放
**證據**:
- ✅ 最多保留 3 個 `BitmapBuffer`（每個 ~1.2MB）
- ✅ 640x480 Bitmap + IntArray = ~1.2MB × 3 = 3.6MB
- ❌ 無法解釋 +37MB 的增長（遠超 3.6MB）

**可能性**: 🟢 **低** (10%)

## 🔬 Recommended Investigation Steps

### Step 1: 驗證 v2.8.1 程式碼是否生效 (Priority: HIGH)

**問題**: 測試中未見 BitmapPool 或 analysisExecutor 的 Log
**行動**:
1. 在 `LiveCameraSource` 加入 Log：
   ```kotlin
   Log.i(TAG, "v2.8.1: Using analysisExecutor (${Thread.currentThread().name})")
   Log.i(TAG, "v2.8.1: BitmapPool acquired buffer (${buffer.bitmap.width}x${buffer.bitmap.height})")
   ```
2. 重新建置並測試
3. 確認 Log 中出現上述訊息

**預期結果**: 若無 Log，代表可能使用了錯誤的 build variant 或程式碼未編譯

---

### Step 2: 效能剖析 (Priority: HIGH)

**問題**: 不清楚 FPS 下降的具體瓶頸位置
**行動**:
1. 使用 Android Profiler 記錄 CPU 使用率
2. 加入計時 Log：
   ```kotlin
   val start = System.nanoTime()
   val buffer = imageProxy.toBitmap(bitmapPool)
   val yuvTime = (System.nanoTime() - start) / 1_000_000.0

   val rotateStart = System.nanoTime()
   val output = rotateBitmap(...)
   val rotateTime = (System.nanoTime() - rotateStart) / 1_000_000.0

   Log.d(TAG, "Timing: YUV=$yuvTime ms, Rotate=$rotateTime ms")
   ```
3. 分析各階段耗時

**預期結果**: 找出 > 30ms 的瓶頸操作

---

### Step 3: 對照實驗 (Priority: MEDIUM)

**問題**: 無法確定是 Executor 還是 BitmapPool 導致問題
**行動**:
1. **測試 A**: 保留 BitmapPool，恢復 MainExecutor
2. **測試 B**: 移除 BitmapPool，保留 background executor
3. **測試 C**: Phase 1 baseline（兩者都不用）
4. 對比 FPS 結果

**預期結果**:
- 若 A > B > C：BitmapPool 是主因
- 若 B > A > C：Executor 是主因
- 若 C > A, B：兩者都是問題

---

### Step 4: BitmapPool 效能驗證 (Priority: MEDIUM)

**問題**: Pool 操作可能有隱藏開銷
**行動**:
1. 記錄 pool hit/miss 率：
   ```kotlin
   fun acquire(...): BitmapBuffer {
       val buffer = deque.removeFirstOrNull()
       if (buffer != null) {
           hits++
           Log.v(TAG, "BitmapPool HIT (hit rate: ${hits*100/(hits+misses)}%)")
       } else {
           misses++
           Log.v(TAG, "BitmapPool MISS")
       }
       return buffer ?: create(...)
   }
   ```
2. 分析 hit rate（預期 > 90%）

**預期結果**: 若 hit rate < 50%，代表 pool 未有效重用

## 🎯 Conclusion

### Status: ❌ **v2.8.1 FAILED - Critical Regression**

v2.8.1 的優化**適得其反**，導致：
1. **FPS 下降 31.7%**（24.0 → 16.4）
2. **記憶體增長 4.6 倍**（+8MB → +37MB）
3. **使用者體驗嚴重退化**（最低 7.1 FPS，明顯卡頓）

### Recommendation

**不建議發布 v2.8.1**，需緊急回滾至 Phase 1 或進行以下修正：

#### Option 1: 回滾至 Phase 1 (Safe)
- 移除 BitmapPool
- 恢復 MainExecutor
- 發布 v2.8.0 Phase 1 作為穩定版本

#### Option 2: 漸進式優化 (Risky)
- 僅保留 Executor 修正，移除 BitmapPool
- 或僅保留 BitmapPool，恢復 MainExecutor
- 進行 A/B 測試確定瓶頸

#### Option 3: 完全重寫 (Time-consuming)
- 使用 RenderScript 或 GPU 加速 YUV 轉換
- 考慮 Hardware Bitmap（`Bitmap.Config.HARDWARE`）
- 需 1-2 週開發時間
