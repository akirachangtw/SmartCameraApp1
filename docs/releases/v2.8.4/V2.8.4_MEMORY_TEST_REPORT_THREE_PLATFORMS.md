# v2.8.4 Memory Test Report - Three Platform Comparison

**測試日期**: 2026-01-09
**測試版本**: v2.8.4 (versionCode 43)
**測試時長**: 10 分鐘 (每 30 秒採樣一次)
**測試條件**: Live Mode, 良好光線條件

## 執行摘要

### 🎯 主要發現

**v2.8.4 程式碼品質**: ✅ **驗證通過**
- Pixel 9a 模擬器 (Android 16): ✅ 記憶體穩定
- Sony XQ-BT52 實機 (Android 12): ✅ 記憶體穩定
- BitmapPool 優化在所有平台都有效 (99% hit rate)

**Pixel 9a 實機異常**: ❌ **嚴重問題**
- 記憶體持續成長 +210.85 MB / 10 分鐘
- **僅影響 Pixel 9a 實機**,相同 Android 16 的模擬器正常
- 推測為硬體/驅動層問題,非 v2.8.4 程式碼問題

### 💡 關鍵結論

1. **這不是 Android 16 的問題** - 模擬器 (Android 16) 測試正常
2. **這不是 v2.8.4 程式碼問題** - 模擬器和 Sony 都正常
3. **這是 Pixel 9a 實機特有問題** - 可能是 CameraX HAL、Tensor G4 驅動或 ML Kit TPU 實作問題

## 根本原因分析

### ✅ 已排除的可能原因

1. **Android 16 系統問題** ❌
   - 證據: Pixel 9a 模擬器 (Android 16) 測試正常
   - 結論: 不是 Android 16 的通用問題

2. **v2.8.4 程式碼記憶體洩漏** ❌
   - 證據: 模擬器和 Sony 都正常,BitmapPool 99% hit rate
   - 結論: v2.8.4 程式碼品質良好

3. **BitmapPool 問題** ❌
   - 證據: 所有平台都 99% hit rate, Pool Keys = 1
   - 結論: BitmapPool 優化成功

4. **Java Heap 洩漏** ❌
   - 證據: 所有平台 Java Heap 都下降 (Pixel: -7.11 MB)
   - 結論: Java 層記憶體管理正常

### ⚠️ 可疑的根本原因

**Pixel 9a 實機 Native 層記憶體洩漏** (硬體/驅動層):

#### 假設 1: CameraX Hardware Abstraction Layer (HAL) 問題 🎯 **最可能**

**證據**:
- Native Heap 異常成長 (+14.71 MB)
- 僅發生在 Pixel 9a 實機 (有實體相機硬體)
- 模擬器 (虛擬相機) 正常

**可能原因**:
- Pixel 9a 的相機 HAL 實作有記憶體洩漏
- CameraX Preview/ImageAnalysis 在 Tensor G4 上的 buffer 管理問題
- Camera2 Native pipeline 在 Pixel 驅動中累積 buffer

**驗證方法**:
```
1. 使用 Android Profiler Native Memory 分析
2. 檢查 libcamera_client.so, libcameraservice.so allocation
3. 對比 Pixel 8, Pixel 9 Pro 是否有相同問題
```

#### 假設 2: ML Kit TPU 加速記憶體累積 🎯 **次要可能**

**證據**:
- Tensor G4 有專用 TPU (模擬器無)
- ML Kit 人臉偵測在 Pixel 可能使用 TPU 加速
- Native Heap 成長符合持續 ML 推理的特徵

**可能原因**:
- ML Kit 在 TPU 模式下的 tensor buffer 未釋放
- EdgeTPU runtime 的記憶體管理問題
- TFLite delegate for TPU 的洩漏

**驗證方法**:
```
1. 暫時停用 ML Kit 人臉偵測,觀察記憶體
2. 強制使用 CPU 模式 (DELEGATE_CPU)
3. 檢查 libtflite_*.so allocation
```

#### 假設 3: Graphics Buffer / Surface 管理問題 🎯 **可能**

**證據**:
- Camera preview 使用 SurfaceTexture
- Compose UI 使用 GPU rendering
- Tensor G4 的 Mali GPU (模擬器用軟體渲染)

**可能原因**:
- Pixel 的 GPU 驅動在 Surface/SurfaceTexture 管理上有問題
- GraphicBuffer 在 Mali GPU 上未正確釋放
- Vulkan/OpenGL ES 渲染 buffer 累積

**驗證方法**:
```
1. 使用 dumpsys SurfaceFlinger 檢查 buffer usage
2. 分析 libGLESv2.so, libvulkan.so allocation
3. 測試純 Camera preview (無 Compose overlay)
```

#### 假設 4: Jetpack Compose + Hardware Rendering 交互問題 🎯 **較不可能**

**證據**:
- 使用 Jetpack Compose for UI
- Camera preview overlay 實時更新
- 模擬器也用 Compose 但正常

**可能原因**:
- Compose 在 Pixel 硬體加速下的 recomposition 累積記憶體
- AndroidView (Camera preview) 與 Compose 的互動問題

**驗證方法**:
```
1. 移除 Compose overlay,純 Camera preview
2. 檢查 Compose runtime allocation
```

## 結論

### ✅ 成功驗證

1. **v2.8.4 程式碼品質優秀**
   - Pixel 9a 模擬器 (Android 16): ✅ 記憶體穩定
   - Sony XQ-BT52 (Android 12): ✅ 記憶體穩定
   - BitmapPool 優化有效: 99% hit rate on all platforms

2. **這不是系統級問題**
   - Android 16 本身沒問題 (模擬器驗證)
   - Android 12 也沒問題 (Sony 驗證)

3. **這不是應用層洩漏**
   - Java Heap 正常 (所有平台都下降)
   - Kotlin Coroutine, Flow, Compose 都正常

### ❌ 發現的問題

**Pixel 9a 實機特有的 Native 層記憶體洩漏**

**問題特徵**:
- 僅影響 Pixel 9a 實機
- 記憶體持續線性成長 (+20.67 MB/min)
- 10 分鐘累積 +210.85 MB
- Native Heap 異常成長 (+14.71 MB vs 模擬器 +1.34 MB)

**可能根因** (按可能性排序):
1. 🎯 **CameraX HAL 層洩漏** (最可能) - Pixel 9a 相機驅動問題
2. 🎯 **ML Kit TPU 加速** (次要) - Tensor G4 TPU runtime 問題
3. 🎯 **Graphics Buffer 管理** (可能) - Mali GPU 驅動問題
4. 🎯 **Hardware Rendering** (較不可能) - Compose + GPU 交互問題
