## 執行摘要

### 問題確認 ✅

**Pixel 9a 實機特有記憶體洩漏**:
- **症狀**: +210.85 MB / 10 分鐘 (+20.67 MB/min)
- **Native Heap 異常**: +14.71 MB (vs 模擬器 +1.34 MB)
- **已排除**: Android 16 系統問題、v2.8.4 程式碼問題、BitmapPool 問題
- **推測根因**: CameraX HAL / Tensor G4 TPU / Mali GPU 驅動問題

## 方案 A: Pixel 9a Memory Mitigation (快速緩解)

### 📋 提議變更

#### 1. SmartCameraAnalyzer.kt - 降低 ML 分析頻率
```kotlin
// 將 THROTTLE_INTERVAL_MS 從 100ms 提升到 500ms (僅 Pixel 9a)
val THROTTLE_INTERVAL_MS = if (Build.MODEL == "Pixel 9a") 500L else 100L
```

**理由**:
- 減少 ML Kit TPU 呼叫頻率
- 降低 Tensor buffer 累積風險
- 對使用者體驗影響較小 (2fps vs 10fps AI 分析)

**風險**: 低 - 僅影響 AI 分析延遲,不影響相機預覽

#### 2. LiveCameraSource.kt - 降低相機解析度
```kotlin
// Pixel 9a 強制使用 480x480 (從 720x720)
val targetResolution = if (Build.MODEL == "Pixel 9a") {
    Size(480, 480)
} else {
    Size(720, 720)
}
```

**理由**:
- 減少 ImageAnalysis buffer 大小
- 降低 Native Heap 壓力
- 480x480 足夠用於 AI 分析

**風險**: 低-中 - 可能影響 AI 偵測精度,但測試報告顯示仍可接受

#### 3. CameraViewModel.kt - 使用者警告
```kotlin
// Pixel 9a 顯示一次性警告
init {
    if (Build.MODEL == "Pixel 9a") {
        viewModelScope.launch {
            _uiEvents.send(CameraUiEvent.ShowWarning(
                "此裝置可能遇到記憶體問題,建議定期重啟 App"
            ))
        }
    }
}
```

**理由**:
- 提供使用者透明資訊
- 降低使用者預期
- 避免 App 突然被系統殺掉的負面體驗

**風險**: 極低 - 僅顯示訊息,不影響功能

### ✅ 可行性分析

#### 優點
1. **最小差異原則** ✅
   - 僅 3 處修改,程式碼變動 < 50 行
   - 使用裝置檢測,不影響其他裝置
   - 可快速回滾 (移除 `if (Build.MODEL == "Pixel 9a")`)

2. **快速實作** ✅
   - 預估 1-2 天完成
   - 無需架構調整
   - 不涉及新增檔案或複雜邏輯

3. **測試簡單** ✅
   - 手動驗證: Pixel 9a 顯示警告 + 降頻/降解析度
   - 回歸測試: 模擬器/Sony 不受影響
   - 記憶體測試: 使用現有 `pixel_memory_test.ps1`

4. **風險可控** ✅
   - 所有改動都有裝置檢測保護
   - 不修改核心相機管線
   - 不影響 BitmapPool、RenderScript 等已驗證模組

#### 缺點
1. **治標不治本** ⚠️
   - 無法解決根本的 Native 層洩漏
   - 僅降低成長速率,不能完全消除

2. **Pixel 9a 體驗降級** ⚠️
   - AI 分析延遲 5 倍 (100ms → 500ms)
   - 解析度降低 55% (720² → 480²)
   - 使用者可能察覺 AI 反應變慢

3. **維護負擔** ⚠️
   - 增加裝置特定邏輯
   - 未來需追蹤 Pixel 更新/修復

### 📊 預期效果

根據測試報告推估:

| 指標 | 當前 (v2.8.4) | 預期 (Mitigation) | 改善 |
|------|--------------|------------------|------|
| **記憶體成長 (10 min)** | +210.85 MB | +80-100 MB | **-52-62%** |
| **Growth Rate** | +20.67 MB/min | +8-10 MB/min | **-51-61%** |
| **Native Heap** | +14.71 MB | +6-8 MB | **-45-59%** |
| **AI 分析頻率** | 10 fps | 2 fps | -80% |
| **解析度** | 720x720 | 480x480 | -55% |

**評估依據**:
- 降低解析度 55% → buffer 大小減少 55% → 預期記憶體降低 30-40%
- 降低 ML 頻率 80% → TPU 呼叫減少 80% → 預期記憶體降低 15-20%
- 綜合效果: 預期記憶體成長降至 80-100 MB / 10 min

## 方案 B: Pixel 9a Memory Issue Plan (完整診斷)

### 📋 提議變更 (4 階段)

#### 階段一: 深度診斷與監控強化 (1-2 天)

**1.1 Native Memory Profiler 分析**
- 使用 Android Studio Memory Profiler
- 識別 top allocator (libcamera*, libtflite*, libGLES*)
- 產出: Native allocation 熱點報告

**可行性**: ✅ 高
- Android Studio 內建工具
- 不需程式碼修改
- 產出直接可用於判斷根因

**1.2 Component Isolation Testing**
- 測試 1: 停用 ML Kit (註解 `observePreviewForAnalysis()`)
- 測試 2: 停用 RenderScript (`useRenderScript = false`)
- 測試 3: 降低解析度 (720 → 480)
- 測試 4: 停用 OpenCV (`observePreviewForGuidelineAnalysis()`)

**可行性**: ✅ 高
- 僅需暫時註解程式碼
- 每個測試約 15-30 分鐘
- 可精確定位洩漏來源

**1.3 增強記憶體監控日誌**
```kotlin
// 在 LiveCameraSource.kt 增強 FPS 報告區塊
if (Build.MODEL == "Pixel 9a") {
    Log.d(TAG, """
        Memory Stats:
        - Native Heap: ${Debug.getNativeHeapAllocatedSize() / 1024 / 1024} MB
        - Graphics: ${memoryInfo.getMemoryStat("summary.graphics")} KB
        - PSS: ${Debug.getPss()} KB
    """)
}
```

**可行性**: ✅ 高
- 程式碼變動 < 20 行
- 使用 Android Debug API
- 輸出至 Logcat,易於分析

#### 階段二: 裝置特定緩解措施 (2-3 天)

**2.1 建立裝置檢測機制**
```kotlin
// 新增 DeviceConfig.kt
object DeviceConfig {
    val isPixel9a: Boolean
        get() = Build.MODEL.contains("Pixel 9a", ignoreCase = true) &&
                Build.VERSION.SDK_INT >= 36

```

**可行性**: ✅ 高
- 新增單一檔案
- 清晰的關注點分離
- 易於測試和維護

**2.2 Pixel 9a 專用相機配置**
- ImageAnalysis: 640x640, STRATEGY_BLOCK_PRODUCER, 150ms 間隔
- RenderScript: 停用 (`useRenderScript = false`)

**可行性**: ✅ 高
- 類似方案 A 的修改
- 更保守的配置 (BLOCK_PRODUCER)
- 風險可控

**2.3 ML Kit 配置優化**
```kotlin
// MLKitDetector.kt
val faceDetectorOptions = if (DeviceConfig.isPixel9a) {
    FaceDetectorOptions.Builder()
        .setPerformanceMode(PERFORMANCE_MODE_FAST)

        .setClassificationMode(CLASSIFICATION_MODE_NONE)
        // 不啟用 tracking

    // 原配置

```

**可行性**: ⚠️ 中
- ML Kit API 支援
- 可能影響偵測品質
- 需額外測試驗證

**2.4 定期資源釋放機制**
```kotlin
// CameraViewModel.kt - Pixel 9a 專用
viewModelScope.launch {
    while (isActive) {
        delay(5.minutes)
        if (DeviceConfig.isPixel9a) {
            System.gc()  // 觸發 GC
        }
    }
}

viewModelScope.launch {
    while (isActive) {
        delay(10.minutes)
        if (DeviceConfig.isPixel9a) {
            rebindCameraPipeline()  // 重建 pipeline
        }
    }
}
```

**可行性**: ⚠️ 中-低
- **風險**: `System.gc()` 不保證執行,可能無效
- **風險**: 重建 pipeline 會造成 1-2 秒黑屏
- **風險**: 可能引入新的記憶體問題或競態條件
- 建議: 僅作為最後手段

## 風險評估與緩解

### 高風險項目

#### 1. 方案 A 無法充分緩解記憶體問題 🔴

**風險**: 降頻/降解析度後,記憶體仍成長 > 100 MB / 10 min

**機率**: 中 (30%)

**緩解措施**:
- 預備方案: 進一步降低解析度到 360x360
- 或增加 throttle 到 1000ms (1 fps AI)
- 最壞情況: 停用 Pixel 9a 的 AI 功能

#### 2. Pixel 9a 使用者體驗顯著降級 🟡

**風險**: AI 反應變慢,使用者抱怨

**機率**: 高 (60%)

**緩解措施**:
- 清晰的警告訊息,設定使用者預期
- 提供「效能模式」開關,允許使用者選擇
- 在設定中說明原因 (硬體限制)

#### 3. 官方長期不修復 🟡

**風險**: Google 不認為是 bug,或優先級低

**機率**: 中-高 (50%)

**緩解措施**:
- 方案 A 作為永久 workaround
- 未來 Pixel 10 發布後重新測試
- 考慮降低 Pixel 9a 的支援等級

### 低風險項目

#### 4. 影響其他裝置 🟢

**風險**: 裝置檢測錯誤,影響非 Pixel 9a 裝置

**機率**: 極低 (<5%)

**緩解措施**:
- 嚴格的裝置檢測邏輯 (`Build.MODEL == "Pixel 9a"`)
- 完整的回歸測試
- 快速回滾機制 (移除 if 判斷)
