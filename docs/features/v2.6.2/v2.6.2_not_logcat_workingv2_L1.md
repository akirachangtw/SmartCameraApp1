以下為針對「enableHDR/disableHDR、Repository Delegation」在 Pixel 9a（Android 16） 與 XQ-BT52（Android 11） 實機驗測差異的 Level 1（L1）彙整（依附件 logcat 觀察歸納）。
1) 問題背景（What / Why）
目標
確認 HDR 開關（enableHDR/disableHDR）與「Repository Delegation（委派）」在不同 Android 版本與裝置上，是否呈現 行為差異 / 不一致 / 無效，並初步拆解影響範圍與風險。
目前觀察到的核心現象（摘要）
Pixel 9a / Android 16
App 內部有明確的 HDR 狀態切換鏈路，且出現「委派 HDR enable/disable 給 CameraInputSource」的紀錄。
HDR 啟用時伴隨 曝光補償（exposure compensation）調整與「HDR mode changed」訊息。
Sony XQ-BT52 / Android 11
多次出現「Auto HDR skipped - manual mode active: 關閉」；並可見系統層 log 顯示 hdr_enable false（持續為 false）。
未觀察到 Pixel 上那種「Delegating HDR enable/disable to CameraInputSource」或同等語意的 App 層委派鏈路紀錄（可能與 build/log tag、或相機管線差異相關）。
2) 裝置差異拆解（Evidence → Interpretation）
A. Pixel 9a（Android 16）logcat 重點訊號
HDR 關閉流程：
Delegating HDR disable to CameraInputSource
HDR disabled: exposure compensation reset to 0
Auto HDR deactivated
HDR 開啟流程：
Delegating HDR enable to CameraInputSource
HDR enabled: exposure compensation set to 1 (range: -24..24)
HDR mode: ON - Force enabled
HDR mode changed: 開啟
L1 解讀：
此裝置上 HDR 開關行為「看起來」是由 Repository（或上層控制點）呼叫後，委派到 CameraInputSource 實際落地，且會伴隨曝光補償等參數調整；推論 HDR 功能在該機型/版本上至少具備可控性與可觀測性。
B. Sony XQ-BT52（Android 11）logcat 重點訊號
反覆出現：
Auto HDR skipped - manual mode active: 關閉
系統/裝置層訊號：
update_backlight_locked: ... hdr_enable false（多次重複）
L1 解讀：
此裝置上 HDR 可能被「手動模式關閉」條件長期壓制，導致 Auto HDR 直接被 skip；同時裝置層 hdr_enable false 也暗示 HDR 不會被打開（或必須透過不同 API/模式才能開）。因此 HDR 開關在該機型/版本上可能呈現 無效 / 被短路 / 被降級 的結果。
3) 影響範圍（Scope）
依你專案技術棧與 MVVM 分層，L1 先把影響面拆到「功能 × 模組 × 層級」：
功能面
HDR 開/關（含 Auto HDR、Force HDR）
曝光補償（Exposure Compensation）與其重置/恢復策略
可能連動：動態範圍（Dynamic Range）、色調映射/預覽渲染（若後續導入 V3.0 Shader 路線）
模組面（建議對應責任歸屬）
Data 層：CameraInputSource / CameraX + Camera2 interop（HDR 是否透過 Extensions 或 Camera2 Request 落地）
Repository 層：CameraRepository 的 HDR toggle 與「delegation」邏輯（是否依裝置/版本分流）
ViewModel 層：HDR UI state、模式切換（Auto/Manual）、與裝置能力檢測結果的狀態管理
UI 層（Compose）：HDR toggle 的可用性（enabled/disabled）、提示文案（例如「此裝置不支援/已被手動模式關閉」）
專案藍圖中 HDR/Tone Mapping 屬後續高風險路線（V3.0），建議把「HDR 開關一致性」視為先決相容性議題。

4) 風險清單（至少 1–3 項；此處列較完整）
版本/裝置相容性風險（高）
同一套 HDR toggle API/流程在 Android 16 可運作，但在 Android 11 可能被「manual mode active」或裝置層能力限制直接短路，造成使用者體驗不一致（UI 顯示可開但實際無效）。
狀態機風險（高）
Pixel 顯示 HDR enable/disable 會改動曝光補償；若 Sony 端 HDR 實際未啟用，但 UI/狀態仍以「已啟用」呈現，會造成 狀態漂移（UI state ≠ 實際 camera state），進而影響後續 AE/AF/畫面亮度。
委派鏈路不透明（中-高）
Pixel 有清楚「Delegating … to CameraInputSource」訊息；Sony 缺乏同等觀測點（可能是 log tag、build variant、或管線根本不同）。缺乏觀測會使除錯成本上升、回歸風險變高。
功能降級策略缺口（中）
若未建立「HDR capability 檢測 + UI 灰階 + 提示」的降級策略，低版本或特定機型將反覆踩雷；也會妨礙後續導入 Shader/HDR 預覽時的裝置分級策略。
測試覆蓋風險（中）
HDR 屬相機/裝置高度碎片化領域，若只在單一高版本機型驗證，容易在其他機型翻車（與你既有工作流的「實機差異」警示一致）。

5) L1 結論（先不下 L2 判定）
「看起來與版本/裝置高度關聯」的證據充足：Pixel 9a（Android 16）能觀察到完整 HDR 委派與狀態切換；Sony（Android 11）則反覆被「manual mode active: 關閉」跳過，且裝置層長期 hdr_enable false。
目前 L1 建議將此議題登錄為：
「HDR Toggle 與 Delegation 在不同 Android 版本/機型行為不一致」，並標記為 需要 Level 2 可行性/相容性評估（API/能力檢測、降級策略、效能與狀態一致性）。
