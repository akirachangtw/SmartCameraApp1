> 目的：針對「`adb logcat -d` 斷續/空白、漏收 APP 關鍵相機流程 log」建立**可落地、可重複、可交接**的收集方案；並判斷是否需要導入 App 內部落盤 logger 作為備援。

## 1. 可行性結論（可行 / 不可行 / 需調整）

**結論：可行（建議採用 Plan A 為主，Plan B 為備援；但需調整為「串流收集」並統一腳本入口）**

- 以工具/SOP 層級解決（改用 `adb logcat` 串流、先清 buffer、以 PID/package/tag 過濾、固定時間戳格式）在大多數裝置與 OS 版本上**可行且最小差異**。
- 若確認是 Android 13+ 權限/廠商策略造成（尤其期望讀取 system/camera service log），則需**調整期待範圍**：以「自己 app log + 必要時 App 內落盤」為主要證據來源。
- repo 現況已存在多個收集/過濾腳本（`diagnose_logcat.bat`, `get_hdr_log.bat`, `collect_hdr_logcat.ps1`, `filter_hdr_log.ps1` 等），目前問題高機率是「入口分裂 + 使用 dump(-d) + filter 不一致」，因此需要 **整併與標準化**。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）

1. **CameraX 模式切換 / rebind timing（P1）**  
   - v2.6.2 牽涉 HDR exposure compensation 在 rebind 後重套（`pendingExposureIndex`）。  
   - 若 log 收不到 bind/rebind、analyzer reattach、exposure set 的順序，會無法判斷 race condition。
2. **ImageAnalysis 高頻 log 造成 buffer 快速洗掉（P1）**  
   - 若 analyzer per-frame 有 log，會讓 log buffer 被覆寫，導致「抓不到關鍵事件」。需確認 analyzer 內是否有高頻輸出。
3. **Android 13+ 權限限制（P0-P1，視需求）**  
   - `READ_LOGS` 非一般可用；只能可靠讀到自身 app log + 部分 system。  
   - 若團隊期待抓到 Camera service / HAL 層 log，需調整策略（bugreport/廠商工具/內部落盤）。
4. **多腳本/多 filter 造成證據不可比（P2）**  
   - 現在 repo 內腳本與輸出檔大量存在，顯示流程已分岐；若不統一入口，後續 HDR/CameraControl issue 會繼續難以比對。
5. **效能風險（P2）**  
   - 為補 log 提高輸出量可能影響相機 pipeline（CPU/IO），特別是 Plan B 落盤需節流與容量上限。

## 4. 最小差異建議（Minimal diff approach：步驟化）

> 以「先工具化與 SOP」，最後才動 App code；且先解決「可穩定拿到 app log」這個最低門檻。

### Step 0｜先定義「要抓什麼」的最低集合（不改 code）
- 最低要能抓到：App 啟動、進入相機頁、Live/Static 切換、CameraX bind/rebind、HDR enable/disable（v2.6.2 已有 log）。
- 先盤點 tag：`CameraRepositoryImpl`, `LiveCameraSource`, `StaticImageSource`, `CameraInputSource`（以及任何既有 `Timber` tag/prefix）。

### Step 1｜停用 `-d` 作為主流程，改「串流收集」
- 改 SOP：`adb logcat -c` → 開始串流到檔案 → 重現 → Ctrl+C 停止。
- 統一輸出格式：`-v threadtime`（含時間與 thread，有利排查 rebind/race）。
- 建議把 `-b main -b system -b crash` 明確列出（視需求），避免只抓 default 造成漏 log。

### Step 2｜以 PID/package 收斂，而不是靠人工捲 log
- 啟動後取 PID：`adb shell pidof <package>`  
- 過濾方式優先順序：
  1) `--pid=<pid>`（若 adb 版本支援）  
  2) `logcat | findstr <package>`（Windows）/ `grep`（Unix）  
  3) tag filters（`TAG:V *:S`）作第二層

### Step 3｜整併腳本入口（只留 1 個對外命令）
- 建議新增或指定單一入口腳本，例如：`tools/logcat/collect_app_logcat.ps1`（PowerShell 為主，Windows 友善），並在 `diagnose_logcat.bat` 內改成呼叫它。
- 既有 `collect_hdr_logcat.ps1` / `get_hdr_log.bat` / `filter_hdr_log.ps1` 若功能重疊，改成：
  - `collect`：只負責收集（串流、清 buffer、時間戳檔名、pid filter）
  - `filter`：只負責後處理（HDR/CameraX tag 匯總）

### Step 4（可選、最小 code diff）｜補一個「可全域搜尋」的關鍵事件 prefix
- 僅在關鍵 lifecycle 點補 3~6 行 log（禁止 per-frame），例如統一 prefix：`APP_TRACE_CAMERA`  
- 目標是讓 filter 不必猜 tag/Timber 來源。

### Step 5（備援 Plan B）｜若 Step 1-3 仍不穩，才加 debug 落盤 logger
- 僅 debug variant 開啟；加節流、容量上限、導出 zip（手動觸發）。
- 這是「系統層 log 拿不到」時的保險。
