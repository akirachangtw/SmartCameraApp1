## 2) 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
1. **v2.8.1 的 analyzer 確實使用了 `analysisExecutor`**（而非仍走 `MainExecutor` 或 analyzer 根本沒 attach）。
2. **BitmapPool 的 acquire/release 有被呼叫**，且 hit rate 足夠高（預期 > 90%），否則 pool 反而造成更多配置/碎片。
3. `ImageProxy.toBitmap(pool)` 的 YUV→RGB 迴圈與 `ByteBuffer.get(index)` 使用方式在該裝置上不會造成極端慢路徑（需用 timing log/trace 驗證）。
4. `transformBitmap()` 使用 `Canvas.drawBitmap()` + `Matrix` 的路徑沒有引入額外昂貴成本（例如每幀額外配置、GPU/Skia 同步、或隱性 format conversion）。
5. Flow/Channel 的消費端（下游 UI/AI analyzer）沒有在 v2.8.1 之後變慢，導致背壓或 blocking，使 FPS 波動。
6. `inFlightPreviewBuffers` 的保留策略沒有造成 Bitmap 長期持有，間接讓記憶體成長與 GC 壓力上升（需看 pool size、in-flight queue、以及是否有漏 release）。

## 3) 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
### CameraX / ImageAnalysis
- `imageAnalysis.setAnalyzer(executor, analyzer)`：切 executor 會改變排程、優先權、與與 CameraX internal thread 的互動；**單執行緒 executor 若被其他工作阻塞**，會讓 analyzer 延遲，造成 FPS 大幅波動。
- analyzer 生命週期：`startPreview()` / `stopPreview()` / rebind 時 `setAnalyzer()` 與 `clearAnalyzer()` 的時序，可能造成 analyzer 未重新掛上或掛上多次。

### Thread / Executor
- `Executors.newSingleThreadExecutor` 預設 thread priority、daemon、以及可能與系統 background 限制互動（Android 13 對背景執行緒有更多限制/競爭）。
- 若 analyzer 內部再切 coroutine/dispatcher，可能出現 **跨 executor 競爭或同步等待**。

### Bitmap/Canvas/Matrix 路徑
- `Canvas(out.bitmap)` + `drawColor(CLEAR)` + `drawBitmap(...)` 每幀做一次：可能觸發 Skia pipeline 成本，或造成額外 memory bandwidth 壓力。
- `Bitmap.setPixels()` 每幀寫入 ~1.2MB（VGA ARGB），再加上旋轉/鏡像可能等於 **雙倍拷貝**。

### 模式切換 / 資源釋放
- `stopPreview()` 只 release `inFlightPreviewBuffers`，但 **analysisExecutor 未 shutdown**（長期 thread 存活可能影響資源與排程；雖然不一定造成 FPS，但屬高風險累積）。
- `bitmapPool` 若是全域常駐，且 key/size 變動（旋轉後尺寸不同）會造成 pool 內多種尺寸殘留，增加常駐記憶體。

### 權限（低風險但需確認）
- Camera 權限本身不是回歸主因，但若 v2.8.1 引入更多 log/trace 或 debug 設定，可能影響效能測試一致性。

## 4) 最小差異建議（Minimal diff approach：步驟化）
> 原則：先「確認程式碼生效 + 分段計時」，再做 A/B。每一步都要能在同一支裝置、同樣 3 分鐘測試下比較。

### Step 0 — 先加「唯一識別」與路徑確認（最小 diff）
1. 在 `LiveCameraSource` analyzer 進入點印出一次性 log（例如每 120 frames 印一次），內容需包含：
   - version tag：`v2.8.1`
   - thread name / priority
   - executor 類型（Main vs background）
   - 是否走 pool (`toBitmap(pool)` vs legacy)
2. 確保 log 在 `deviceDebug` 可見（Timber/Logcat filter）。

### Step 1 — 加入分段 timing（YUV / setPixels / transform / trySend）
- 只加 `System.nanoTime()` 差值、每 N 幀輸出一次彙總（避免 log 本身造成回歸）。
- 目標：找出是否某段 > 30ms（對 30fps budget 來說已超標）。

### Step 2 — 做 3 組 A/B（用旗標或簡單常數開關）
A. `BitmapPool ON` + `MainExecutor`  
B. `BitmapPool OFF` + `analysisExecutor`  
C. `BitmapPool OFF` + `MainExecutor`（Phase1 對照）

> 建議用 build-time 常數或簡單 runtime flag（例如 `BuildConfig.DEBUG` 下可切），但**務必保持最小改動且可回滾**。

### Step 3 — 若定位在 transform 成本，先做「不旋轉版本」對照
- 暫時繞過 `transformBitmap()`（rotationDegrees=0 / mirror=false 直接 output raw）做一輪測試，確認是否 Canvas/Matrix 是主因。

### Step 4 — 若定位在 executor 排程，調整 thread priority（可選）
- 先只做觀測：log thread priority、CPU 使用率、是否長時間 runnable 堆積。
- 若要改：用 `Process.setThreadPriority(Process.THREAD_PRIORITY_DISPLAY)` 或較保守的 `THREAD_PRIORITY_MORE_FAVORABLE`（仍需 A/B）。
