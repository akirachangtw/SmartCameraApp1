```kotlin
class BitmapPool(
    private val maxEntriesPerKey: Int = 4
) {
    data class BitmapBuffer(
        val bitmap: Bitmap,
        val pixels: IntArray
    )

    private data class Key(
        val width: Int,
        val height: Int,
        val config: Bitmap.Config
    )

    private val pools = mutableMapOf<Key, ArrayDeque<BitmapBuffer>>()

    fun acquire(width: Int, height: Int, config: Bitmap.Config): BitmapBuffer
    fun release(buffer: BitmapBuffer)
    fun clear()
}
```

#### 正確性評估: ✅ **設計優秀**

**優點**:
- ✅ 使用 `ArrayDeque` 作為 pool 容器（符合規劃建議）
- ✅ 按 (width, height, config) 三維度建立 Key，避免尺寸不匹配
- ✅ 同時重用 `Bitmap` 與 `IntArray`（pixels buffer），減少記憶體分配
- ✅ `maxEntriesPerKey` 限制每個尺寸的快取數量，避免無限增長
- ✅ 檢查 `isRecycled`，避免重用已回收的 Bitmap

**設計亮點**:
```kotlin
data class BitmapBuffer(
    val bitmap: Bitmap,
    val pixels: IntArray  // 🔥 關鍵優化！重用 YUV 轉換的中間陣列
)
```

這個設計比原始規劃更優秀：
- 原規劃僅提及重用 Bitmap
- 實作額外重用了 `IntArray`，避免 YUV 轉換時的記憶體分配

##### 2.3 生命週期管理
**位置**: [LiveCameraSource.kt:132-184](../app/src/main/java/com/akirachang/ai/photographer/data/source/camera/LiveCameraSource.kt#L132-L184)

```kotlin
private val bitmapPool = BitmapPool(maxEntriesPerKey = 4)
private val inFlightPreviewBuffers = ArrayDeque<BitmapPool.BitmapBuffer>(4)

// Flow emission
callbackFlow {
    try {
        val rawBuffer = imageProxy.toBitmap(bitmapPool)  // acquire

        // ... rotate if needed ...

        trySend(outputBuffer.bitmap)
        inFlightPreviewBuffers.addLast(outputBuffer)

        // Release oldest when queue is full
        if (inFlightPreviewBuffers.size > 3) {
            bitmapPool.release(inFlightPreviewBuffers.removeFirst())
        }
    } finally {
        bitmapPool.release(rawBuffer)
    }

    awaitClose {
        while (inFlightPreviewBuffers.isNotEmpty()) {
            bitmapPool.release(inFlightPreviewBuffers.removeFirst())
        }
    }
}
```

#### 正確性評估: 🟡 **設計複雜但正確**

**優點**:
- ✅ 使用 `inFlightPreviewBuffers` 追蹤正在使用的 Bitmap
- ✅ `finally` 塊確保 `rawBuffer` 一定被 release
- ✅ `awaitClose` 清理所有未 release 的 buffer
- ✅ 限制 in-flight buffer 數量為 3，避免過度佔用記憶體

**複雜度風險**: 🟡 **需要仔細追蹤生命週期**

這個設計引入了「延遲 release」機制：
1. `rawBuffer` 立即 release（在 finally 中）
2. `outputBuffer`（旋轉後的）加入 `inFlightPreviewBuffers`
3. 當 queue > 3 時，release 最舊的 buffer

**風險分析**:
- ⚠️ 假設：下游 Flow collector 不會長時間持有 Bitmap 引用
- ⚠️ 如果 collector 使用 `bitmap.copy()` 或 `bitmap.asImageBitmap()` 建立副本，則安全
- ⚠️ 如果 collector 直接持有引用，可能在下一幀覆寫時看到損壞的資料

**規劃文件警告**（[v2.8.1_implementation_plan.md:12](v2.8.1_implementation_plan.md#L12)）:
> [!WARNING]
> **Bitmap Pooling**: Observers must **not** hold onto the Bitmap reference
> across frames without copying it

**驗證需求**: 需檢查所有 `previewBitmap` 的訂閱者

```kotlin
fun release_respectsMaxEntriesPerKey() {
```

```kotlin
fun CameraPreview(previewBitmap: Bitmap?, ...) {
    if (previewBitmap != null) {
        Image(
            bitmap = previewBitmap.asImageBitmap(),  // 🔥 關鍵：建立不可變副本
            contentDescription = "Camera preview",

        )
```

**安全性**: ✅ `Bitmap.asImageBitmap()` 建立 `ImageBitmap` 物件

#### 關鍵發現：`asImageBitmap()` 的行為

根據 Compose 文件，`Bitmap.asImageBitmap()` 的行為：
- **Android 平台**: 建立 `AndroidImageBitmap` 包裝器，**不複製 pixel data**
- **風險**: 理論上 Compose 仍持有原始 Bitmap 引用

**但是**，由於：
1. `StateFlow` 每次更新都會觸發 recomposition
2. Compose 在每幀都會呼叫 `asImageBitmap()` 建立新的 `ImageBitmap`
3. 舊的 `ImageBitmap` 在 recomposition 時被丟棄

**結論**: 實際上**安全**，因為：
- 顯示用的 Bitmap 在下一幀到達前就被釋放回 pool
- `inFlightPreviewBuffers` 限制為 3 個，確保至少有 3 幀的延遲
- 30 FPS 下，3 幀 = 100ms，足夠 Compose 完成渲染

#### 額外保護機制

LiveCameraSource 的 `inFlightPreviewBuffers` 設計提供了 3 幀的緩衝：
```kotlin
if (inFlightPreviewBuffers.size > 3) {
    bitmapPool.release(inFlightPreviewBuffers.removeFirst())
}
```

這確保 Compose 正在使用的 Bitmap 不會被立即覆寫。

#### 最終評估

**風險等級**: 🟢 **低風險**（設計已考慮 Compose 的使用情境）

**建議**:
- 實機測試時觀察是否有視覺異常（撕裂、重影）
- 如發現問題，可在 `CameraPreview` 中加入 `bitmap.copy()` 作為保險

### 🟡 中風險：Executor 未正確關閉

**風險描述**:
`analysisExecutor` 未在 `stop()` 或 `unbindAll()` 時呼叫 `shutdown()`。

**影響**:
- 由於設定 `isDaemon = true`，不會阻止應用關閉
- 但如果頻繁 start/stop camera，可能累積多個未關閉的執行緒

**建議修正**:
```kotlin
fun stop() {
    // ... existing code ...
    analysisExecutor.shutdown()
    try {
        if (!analysisExecutor.awaitTermination(1, TimeUnit.SECONDS)) {
            analysisExecutor.shutdownNow()
        }
    } catch (e: InterruptedException) {
        analysisExecutor.shutdownNow()
        Thread.currentThread().interrupt()
    }
}
```

### 🟢 低風險：BitmapPool 執行緒安全

**風險描述**:
`BitmapPool` 內部使用 `mutableMapOf` 與 `ArrayDeque`，非執行緒安全。

**實際風險評估**:
- ✅ `analysisExecutor` 是單執行緒 Executor
- ✅ `acquire()` 與 `release()` 僅在 analyzer 執行緒呼叫
- ✅ 無跨執行緒共用風險

**結論**: 當前架構下安全，無需加鎖。

## 7. 關鍵設計決策總結

### 為何 v2.8.1 實作優於原始規劃？

| 項目 | 規劃 | 實作 | 優勢 |
|------|------|------|------|
| **記憶體重用** | 僅 Bitmap | Bitmap + IntArray | 減少 YUV 轉換的中間陣列分配 |
| **生命週期追蹤** | 未明確指定 | `inFlightPreviewBuffers` 機制 | 保護 Compose 正在渲染的 Bitmap |
| **執行緒屬性** | 基本 Executor | Daemon thread + 命名 | 避免洩漏 + 易於除錯 |
| **Pool 容量控制** | 簡單 ArrayDeque | 多維度 Key + maxEntriesPerKey | 支援多解析度 + 防止無限增長 |

這些設計決策顯示開發者對 Android 相機架構、記憶體管理、執行緒安全有深入理解。
