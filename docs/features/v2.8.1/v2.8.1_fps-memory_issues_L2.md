## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
請 Claude Code 以「必須能從程式碼或 log 證實」為準逐項驗證：

1. **ImageProxy.close() 每幀必定執行**
   - 假設：目前 analyze() 中無論成功/失敗/early-return 都有 close。
   - 若未 close：會造成 buffer 堆積 → FPS 降 + memory/PSS 成長。

2. **ImageAnalysis backpressure strategy 設定合理**
   - 假設：使用 `STRATEGY_KEEP_ONLY_LATEST`（或等效）避免佇列堆積。
   - 若是 `BLOCK_PRODUCER` 或 queue depth 偏大：可能造成 latency、PSS 上升、FPS 下降。

3. **Analyzer stop 機制未引入「額外工作」或「額外分配」**
   - 假設：stop flag check 是純 boolean/atomic check，沒有 per-frame lock/同步重負載。
   - 若 stop 伴隨 synchronized/mutex 或複雜狀態機：可能拉低 FPS。

4. **Phase 1 的 Mutex 範圍只包住切換/重綁定，不影響每幀分析**
   - 假設：Mutex 不會被 analyze path 取得。
   - 若 analyzer/overlay 路徑也會進入 Mutex：FPS 可被拖慢。

5. **Pixel 9a 的 memory growth 可能是 cache warm-up 或 native allocation**
   - 假設：成長會趨平；或是 native heap / bitmap / NN runtime cache 增加。
   - 需用分項指標（Java heap / native heap / PSS）拆解，不可只看 PSS。

6. **FPS 統計口徑一致**
   - 假設：Phase 0/Phase 1 使用同一個 FPS 計算方式與 sample window。
   - 若統計方式不同：可能是量測偏差，不是效能真退化。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX UseCase 重綁定與時序**
   - bind/unbind、setAnalyzer/clearAnalyzer、stop/unbind 的順序若被動到，可能回到舊的競態問題（CameraControl not available / 黑畫面）。

2. **ImageAnalysis 的 thread/executor 與背壓**
   - 若 analyzer executor 與 UI / Preview 共用資源，或 executor 是單執行緒且被阻塞，會引發 FPS 掉落。
   - 背壓策略不當會造成 frame 排隊 → latency 變大、記憶體上升。

3. **Analyzer 內部資源管理（Bitmap/ByteArray/Tensor/Mat/native）**
   - per-frame allocation 或未釋放 native buffer，會在 Pixel 9a 顯著反映成 PSS 成長。
   - 任何 overlay bitmap cache、YUV->RGB 轉換 buffer、Tensor input buffer 都是高風險。

4. **stop 機制與 pending frames**
   - stop 後仍可能收到 frame callback；若 early-return 但漏 close，或仍做昂貴轉換，會造成「看似停止但仍在燒 CPU/memory」。

5. **Lifecycle / 前後景**
   - onPause/onResume 對 camera provider、executor、analyzer 的釋放不完整，會造成 memory growth 或重複註冊 observer/listener。

6. **權限/相機重啟**
   - 若有 permission re-check 或 process death restore 行為，可能導致重綁定額外開銷（雖長測未切換也可能被觸發）。

## 4. 最小差異建議（Minimal diff approach：步驟化）
以「先觀測再動刀」為原則，並保護 Phase 1 穩定性修復。

### Step 0｜先做 A/A 量測一致化（不改邏輯）
- 確認 Phase 0 vs Phase 1：同一支測試流程、同一 FPS 計算口徑、同樣的 sample window。
- Sony/Pixel 各跑 3 分鐘 *2 次；Pixel 再跑 10–15 分鐘 soak。

### Step 1｜只加 instrumentation（邏輯零改動）
- 在 analyzer pipeline 加以下計數/時間：
  - 每幀 analyze 耗時（P50/P95）
  - `ImageProxy.close()` 執行次數 vs analyze call 次數（必須 1:1）
  - early-return（stop flag hit）次數（長測理論上趨近 0）
  - frame in-flight（若有 queue/atomic counter）
- 每 N 秒 log 一次 memory：
  - Java heap used/max
  - Native heap allocated
  -（選配）Debug.MemoryInfo / PSS（或透過腳本 dumpsys）

### Step 2｜Repo 確認後才做「微調」且一個變因一次
依 repo 現況選擇最小改動點（必須能證明改善）：
- 若發現 ImageProxy.close 非 1:1：先修 close 保證（try/finally）。
- 若 backpressure 非 KEEP_ONLY_LATEST：改為 KEEP_ONLY_LATEST（並以 flag 控制）。
- 若 per-frame allocation 明顯：導入 reuse buffer（ByteArray/Bitmap/Tensor input）但避免造成長期持有巨物。
- 若 stop check 在每幀做重同步：改為更輕量（例如 volatile/atomic + 避免 lock），或只在必要節點檢查（但要用 A/B flag 驗證）。

### Step 3｜二分法 A/B（只在需要快速歸因時）
- Feature flag：
  - `disableAnalyzerStopForPerfTest`（僅 internal）
  - `stopCheckMode = PER_FRAME / ONLY_BEFORE_UNBIND`
- 目的：快速判斷 FPS 退化是否與 stop 機制相關（而非 CameraX config / allocation）。

3. **優先回滾「效能調參」，不回滾穩定性修復**
