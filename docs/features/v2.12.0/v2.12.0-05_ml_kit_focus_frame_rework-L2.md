# v2.12.0-05 — ML Kit Focus Frame Rework（L2：技術可行性與實作細節）

## 1. 審查目的與範圍
針對 L1 提出的 ML Kit 對焦框與目標選擇的重構方案進行嚴格的技術審查。L1 目標解決三大 Bug：
* **Bug A**: 對焦框總是正方形。
* **Bug B**: 尺寸被 ML Kit 不停重置。
* **Bug C**: 後鏡頭人物對焦時錯誤選擇背景物體。

本 L2 規格書將專注於「協程併發 (Concurrency)」、「效能影響 (Performance)」、「邊界情況 (Edge Cases)」與「具體實作細節」。

## 2. 邊界場景 (Edge Cases) 與修正策略

### 2.1 目標判定「乒乓效應」 (Bug C 修復帶來的風險)
**風險描述**：
L1 提出 `Face-first policy` (有臉就強制放棄 Objects)。若遇到「人臉局部遮擋」或「轉頭」的場景，ML Kit 的 `faces` 陣列可能在 0 與 1 之間高頻切換。
如果採用剛性的 `faces.isNotEmpty() ? face : object`，即使原本追著人，一沒看到臉就會瞬間把焦點轉移給背景，下一幀看到人臉又瞬間轉回，造成嚴重的 UI 抖動 (Target Ping-pong)。

**解決方案：引入目標滯留期 (Temporal Hysteresis / Grace Period)**
不該立刻降級！當系統當前鎖定的是 `Face` 類型目標，若忽然偵測不到 Face (但仍有 Object)，應保持「等待」一段短時間，只有超過時間閾值後才允許降級成 Object。

```kotlin
// Pseudocode for SalientTargetSelector
class SalientTargetSelector {
    private var lastFaceSeenTsMs = 0L
    private val FACE_DROP_GRACE_PERIOD_MS = 500L
    private var currentTrackingType: TargetType = TargetType.NONE

    fun chooseTarget(faces: List<Face>, objects: List<DetectedObject>): Target? {
        val now = SystemClock.elapsedRealtime()
        
        // Face-first selection
        if (faces.isNotEmpty()) {
            lastFaceSeenTsMs = now
            currentTrackingType = TargetType.FACE
            return getBestFaceTarget(faces) // 優先使用 eyePositions
        }
        
        // 若剛剛還看到臉，保留滯留期，拒絕立刻跳到 Object
        if (currentTrackingType == TargetType.FACE && (now - lastFaceSeenTsMs < FACE_DROP_GRACE_PERIOD_MS)) {
             return null // 略過更新，讓 UI 與 AF 在原地保持 (或由 AF State Machine 自動判定)
        }
        
        // Grace period expired, or no face been seen recently. Fallback to object.
        if (objects.isNotEmpty()) {
            currentTrackingType = TargetType.OBJECT
            return getBestObjectTarget(objects)
        }
        
        return null
    }
}
```

### 2.2 手動對焦 (User Tap) 的絕對優先權介入
**風險描述**：若使用者點選背景物件 (User Tap)，這時畫面剛好有人臉走入，L1 的 `Face-first` 可能會自動把焦點強制拉到人臉，這是不符合「手動對焦最大」的 UX 單例。

**解決方案：明確鎖定 (Mutex / Lock) 與權重**
整合上一階段 L1 設計 (`AfTriggerThrottleController`)，`SalientTargetSelector` 也需要讀取目前的 Focus Source 狀態。這意味著 AF State Machine 若處於由 `USER_TAP` 發起的 `FOCUSING` 或 `LOCKED` 期間，`SalientTargetSelector` 必須完全靜默，直接 return null 以防止 UI 被覆蓋。

## 3. 效能影響與狀態防抖 (Performance Implications)

### 3.1 渲染層更新壓榨 (Thread Safety & UI Thrashing)
ML Kit 辨識結果(透過 ImageAnalysis)運作在獨立背景執行緒。若每次 ML Kit 回傳直接去變更 `CameraState` 中的 `focusFrameWidthPx` 與 `focusFrameHeightPx` 勢必會觸發高頻的 Compose Recomposition (重新計算)。

**解決方案：`FocusFrameSpec` 結構化打包與頻率限制 (Debounce)**
不要使用兩個分離的 Float 變數，必須組合成單一的 `FocusFrameSpec` 進行一次性 `StateFlow` 更新。同時，只有變化超過 `epsPx` 閾值 (長寬任一變動 > 5%) 結合時間截流 (~30FPS 速率限制) 時才推播更新給 UI。

```kotlin
data class FocusFrameSpec(val center: Offset, val size: Size)

// Flow 更新端
mlKitFlow.map { targets -> 
     val newSpec = mapToSpec(targets)
     // 限制 1: 變動容忍值
     if (isDifferenceSignificant(currentSpec, newSpec, epsilon = 0.05f)) {
         currentSpec = newSpec
     }
     currentSpec
}
.sample(32) // 限制 2: Rate limit to ~30Hz (每 32ms 最多發送一次)
```

### 3.2 FocusIndicator 獨立兩軸動畫 (`animateDpAsState` 調整)
L1 雖然提出 X 和 Y 軸分不同變數 `animateDpAsState`，但預設的 spring 動畫可能在「正方形快速拉長為長寬差異極大的長方形」時，產生非等比例變形，視覺上會「扭曲」。

**解決方案：AnimationSpec 微調**
建議使用較阻尼(DampingRatio)與剛度(Stiffness)適中的 `spring`，並且確保寬度跟高度使用相同的 `AnimationSpec`。
```kotlin
val animSpec = spring<Dp>(
    dampingRatio = Spring.DampingRatioNoBouncy, 
    stiffness = Spring.StiffnessMedium
)
val animatedWidth by animateDpAsState(targetValue = targetWidth, animationSpec = animSpec)
val animatedHeight by animateDpAsState(targetValue = targetHeight, animationSpec = animSpec)
Canvas {
    val rectSize = Size(animatedWidth.toPx(), animatedHeight.toPx())
    // 繪製與原本相同，但需依照自定義矩形尺寸進行半角(brackets)計算
}
```

## 4. Camera HAL 交互安全性
在 L1 提到將自動觸發 `startFocusAndMetering()`。因為這裡涉及座標的轉換 (TargetGeometryMapper)。
**相容性警告**：
* 必須確保 `TargetGeometryMapper` 的產出不僅傳遞給 UI (螢幕座標)，還要正確傳到 `MeteringPointFactory` 作為與底層 HAL (如 Sony HAL) 溝通的介面點。
* 由於後鏡頭尺寸被放大(Bug C 問題來源之一)，HAL 控制如果接收到「長方形」Focus Area 在某些 OEM Rom 其實沒有作用（舊 Camera2 API 只取中心），但為了保證對焦熱區，如果 API 允許傳入長方形權重 (Region)，我們應將 W/H 同步計算進去再傳給 HAL，提高 Sony/Samsung 的 PDAF 準確率。

## 5. 測試策略深入 (Testability)

為了確保 L1/L2 覆蓋上述風險，推薦以下具體的測試案例：

### 5.1 整合與單元測試
1. **Mock Ping-Pong Test:** 
   連續灌入 `{Face(score:0.6), Object(score:0.9)}` -> `{Object(score:0.9)}` -> `{Face(score:0.3)}` 的快速資料流，斷言 `SalientTargetSelector` 在中間那幀並**沒有**發出改變 Focus 點的事件 (藉由滯留期阻擋)。
2. **User Tap Lockout Test:**
   先模擬送出 `UserTap` 點擊事件，接著高頻送入高分 `Face` 偵測物件，斷言 `FocusIndicator` 強制停留在 `UserTap` 的坐標長達幾秒 (直至冷卻或是 Timeout 到期)。
3. **Rotation & Mirror Test:**
   假造前鏡頭分析結果 (ImageProxy rotation=270, isFront=true)，斷言 `TargetGeometryMapper` 計算出的 `Size(W, H)` 在轉譯成屏幕座標系後，長寬依然正確應對裝置真實的縱向或橫向顯示。
