# v2.12.0-07 — Native Camera Experience Replication（L2：技術可行性與架構審查）

本文件基於 L1 的高階架構規劃（UI 解耦、人臉智能對焦、物件追蹤），進行深度的技術可行性審查、效能評估、邊界條件考量以及具體的 API 建議，確保整個系統具備可實作性與穩定性。

---

## 1. 核心解法 A：UI 解耦與坐標平滑化 (UI Decoupling & Smoothing)

### 1.1 技術可行性與 API 選擇 (Technical Feasibility & API)
*   **API 選擇：** 
    *   **座標映射 (Mapping)：** 必須強烈依賴 CameraX `ImageProxy.imageInfo.rotationDegrees` 以及 `PreviewView.OutputTransform`。
    *   **平滑演算法 (Smoother)：** 建議採用**指數移動平均 (Exponential Moving Average, EMA)** 或 **1 Euro Filter** 來對原本高頻跳動的 Bounding Box 做濾波處理。這兩者都可以用純 Kotlin 輕量實作，放在 `FocusUiSmoother` 組件中。

### 1.2 效能與資源 (Performance & Resource)
*   UI 動畫解耦將 Compose Recomposition 頻率限制在螢幕刷新率之內，反而能拯救被 ML Kit 回呼壓垮的 UI Thread。
*   **建議：** 引入 `StateFlow.sample(16L)` 確保 Compose 端最多以 ~60FPS 接收坐標更新。

### 1.3 實作細節與邊界情況 (Edge Cases)
*   **前鏡頭固定對焦 (Fixed-Focus) 偵測：** 
    這是 L1 沒提到但極度重要的相容性地雷。許多低階裝置的**前鏡頭是固定焦距的 (Fixed Focus)**。
    *   **解決方案：** 在 `CameraControlAdapter` 初始化時，透過 Camera2Interop `CameraCharacteristics.LENS_INFO_MINIMUM_FOCUS_DISTANCE` 檢查。如果為 `0.0f` 代表是 Fixed Focus 鏡頭。此時架構應切斷 `FocusOrchestrator` 到 `CameraControlAdapter` 的 `startFocusAndMetering` 呼叫，僅保留 `UI UI Layer` 畫對焦框的能力，避免拋出不支援的例外或浪費時間。

### 1.4 UI/UX 考量 (UI/UX)
*   **狀態分層展示：** 儘管框的移動平滑了，但「相機是否真的已經完成實體對焦」需要獨立指示。當底層 `FocusMeteringResult.isFocusSuccessful` 為 true 時，`CameraUiState` 應送出一個信號，讓平滑移動中的框瞬間從白色變為綠色。

## 2. 核心解法 B：人臉智能對焦與防抖 (Smart Face Tracking)

### 2.1 技術可行性與 API 選擇 (Technical Feasibility & API)
*   **API 選擇：** 
    *   **ML Kit Face Detection：** 使用 `FaceDetectorOptions.Builder().setPerformanceMode(FaceDetectorOptions.PERFORMANCE_MODE_FAST)` 以確保低延遲的框獲取，不需要精準的五官特徵 (Landmarks) 即可完成對焦操作。
    *   **相機 API：** 使用 `SurfaceOrientedMeteringPointFactory` 將追蹤到且平滑後的 `stableFaceTarget` 重投影回相機 Sensor 座標準備出圖。

### 2.2 效能與資源 (Performance & Resource)
*   ML Kit 每秒跑 60 幀會導致嚴重耗電與 CPU Throttling。
*   **策略 (Frame Rate Throttling)：**
    *   透過 CameraX 的 `ImageAnalysis.Builder().setBackpressureStrategy(STRATEGY_KEEP_ONLY_LATEST)` 是基本。
    *   更進階：在 `FrameDispatcher` 實作 Token Bucket (權杖桶) 演算法，將傳遞給 `FaceDetector` 的分析頻率壓制在 **15 FPS ~ 30 FPS**，而 UI 端依然依靠 Tracking / Smoother 預測出 60FPS。

### 2.3 實作細節與邊界情況 (Edge Cases)
*   **多人臉場景 (Multiple Faces)：** L1 未詳細說明多張人臉時的目標選取。
    *   **解決方案：** 預設策略應選擇「BBox 面積最大」或是「最靠近中心點」的 Face。若使用者點擊了旁邊的小臉 (`USER_TAP`)，則將該臉的 ID 暫存入 `FaceFocusPolicy` 成為強勢鎖定目標，忽略最大臉原則。
*   **相機低光環境 (Low-Light Jitter)：** 低光下圖像噪點極多，ML Kit 給出的 Face Bbox 會瘋狂抖動，導致 `movementTolerancePx` 一直被突破，引發無意義的持續掃描。
    *   **解決方案：** 結合 `ImageProxy` 簡單取樣 Luma (亮度)。若環境極暗，動態將 `movementTolerancePx` 調大（容忍度變高），並增加 `lockHoldMs` 冷卻時間。

## 3. 核心解法 C：物件精準追蹤 (AI-driven Object Tracking)

### 3.1 技術可行性與 API 選擇 (Technical Feasibility & API)
*   **API 選擇：** 
    *   **ML Kit Object Detection & Tracking：** 這邊必須開啟 `ObjectDetectorOptions.STREAM_MODE`，這能讓 ML Kit 產生跨影格穩定的 `trackingId`，這是 `TargetTracker` 能夠運作的唯一基石。
    *   不建議自建 Optical Flow（如 OpenCV），對於 Android APP 開銷與包體太大，依賴 ML Kit 內建的 Tracker 即可滿足 80% 需求。

### 3.2 效能與資源 (Performance & Resource)
*   Object Detection 往往比 Face Detection 負載稍重。
*   **策略 (Background Threading)：** 將 `ObjectDetector.process()` 放入一個隔離的專屬單執行緒 `Executors.newSingleThreadExecutor()` 中，避免阻塞其他相機管線。

### 3.3 實作細節與邊界情況 (Edge Cases)
*   **追蹤丟失的過渡期 (Model Initialization / Lost Targets)：** 
    若物體因快速移動被手指短暫遮擋，`trackingId` 可能會消失幾幀後以新的 ID 出現。
    *   **解決方案：** 在 `TargetStateStore` 實作 **TTL (Time to Live) Grace Period (大約 400ms - 500ms)**。如果目標連續 500ms 沒被 detector 報備，才宣告丟失 (丟棄 Target) 並將 UI 回歸 `Scanning` 狀態。在此 500ms 內，維持舊框並等待網路重新捕捉。

### 3.4 UI/UX 考量 (UI/UX)
*   **動態 BBox 縮放展示：** L1 提到「跟著物件變形的方框」。這個 Compose 的 Rect 大小漸變，可以配合先前提到的 `FocusUiSmoother`，讓長寬 (`width/height`) 的變化具備彈簧特效 (`spring animation`)。物件靠近鏡頭變大時，框能 Q 彈的撐開，營造出媲美 iOS 原生相機的物件鎖定體驗。

## 總結改進建議 (Refining Recommendations)

1.  **分離 Fixed/Auto Focus 邏輯**：這是最容易被忽略的硬體地雷，請優先實作 `CameraCharacteristics` 探測。
2.  **建立偵測頻率與渲染頻率雙軌制**：Detector 跑低頻 (15FPS)，UI 與 Tracker 透過補幀平滑跑高頻 (60FPS)，是兼顧效能與順暢度的唯一解法。
3.  **依賴 ML Kit 的 Streaming Mode**：對於 Object Tracking，絕對要開啟 streaming mode 以獲取 ID，這比單純算幾何重疊度 (IoU) 來追蹤穩定非常多。
