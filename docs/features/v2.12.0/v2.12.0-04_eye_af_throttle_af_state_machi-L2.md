# v2.12.0-04 — Eye-AF 動態節流 + 4-way AF 狀態機（L2：技術可行性與實作細節）

## 1. 目的與概述
本文件基於 L1 高階方案，詳細檢視 Eye-AF 動態節流與 4 路 (4-way) AF 狀態機的技術可行性。重點在於定義具體的狀態轉換邏輯、動態節流的參數與計算方式、潛在副作用評估，以及核心組件的虛擬碼與架構圖，確保解決方案在技術上可行且能有效優化效能。

---

## 2. 4-way AF 狀態機 (AF State Machine) 詳細設計

狀態機是整個對焦管理的單一可信來源 (Single Source of Truth)，透過 `StateFlow` 或類似的響應式機制廣播當前狀態。

### 2.1 狀態定義與進入/退出條件

| 狀態 (State) | 定義 | 進入條件 (Entry) | 退出條件 (Exit) |
|---|---|---|---|
| **IDLE** | 系統空閒，無進行中的 AF 動作，未鎖定任何目標。 | 1. 初始啟動狀態。 <br> 2. 從 `LOCKED` 狀態超時或失去目標。 <br> 3. 從 `FAILED` 狀態過渡 (Cooldown 結束)。 | 收到合法的 `FocusRequest` 且節流閘道允許，轉換為 `FOCUSING`。 |
| **FOCUSING** | 已呼叫 `startFocusAndMetering()`，正在等待 HAL 的結果。 | 收到並許可執行 `FocusRequest`。 | 1. 收到 HAL 成功回報 (轉 `LOCKED`)。<br> 2. 收到 HAL 失敗回報 (轉 `FAILED`)。 <br> 3. `withTimeout` 觸發 (轉 `FAILED`)。 <br> 4. 被新的 User Tap 強行中斷 (轉新的 `FOCUSING`)。 |
| **LOCKED** | 對焦成功，並將焦點鎖定在當前目標位置。 | 在 `FOCUSING` 期間收到 HAL 成功回報。 | 1. 目標位移超過 `rescanThresholdPx` 且節流允許 (轉 `FOCUSING`)。 <br> 2. 目標消失達指定時間 (轉 `IDLE`)。<br> 3. User Tap 產生新焦點 (轉 `FOCUSING`)。 |
| **FAILED** | 對焦動作失敗 (HAL 拒絕、回報失敗、引發異常或 Timeout)。 | 1. `FOCUSING` 階段 HAL 回報失敗。 <br> 2. `FOCUSING` 發生超過 `FOCUS_TIMEOUT_MS` 的 Timeout。 <br> 3. 呼叫 HAL 發生 Exception。 | Backoff/Cooldown 時間結束，自動回到 `IDLE` 等待下一次機會，或直接由新的合法請求進入 `FOCUSING`。 |

### 2.2 `withTimeout` 與協程實作細節

為防止 `FOCUSING` 狀態卡死，我們利用 Kotlin Coroutines 的 `withTimeout` 實作防呆機制。

```kotlin
// AF State Machine 狀態封裝
sealed class AfState {
    object Idle : AfState()
    data class Focusing(val request: FocusRequest, val startTimestamp: Long) : AfState()
    data class Locked(val request: FocusRequest, val lockedTimestamp: Long) : AfState()
    data class Failed(val request: FocusRequest, val reason: FailReason, val failCount: Int) : AfState()
}

enum class FailReason { TIMEOUT, HAL_FAILED, EXCEPTION }

// FOCUSING 實作協程 (Pseudocode)
suspend fun executeFocusRequest(req: FocusRequest): AfOutcome = mutex.withLock {
    if (!throttleController.shouldTrigger(req, currentState)) {
        return AfOutcome.Skipped("THROTTLED")
    }
    
    _afState.value = AfState.Focusing(req, SystemClock.elapsedRealtime())
    
    return try {
        // 設定 TIMEOUT 避免 HAL 卡死 (例如設定為 3000ms - 4000ms)
        val result = withTimeout(FOCUS_TIMEOUT_MS) {
            cameraControl.startFocusAndMetering(req.toAction()).await()
        }
        
        if (result.isFocusSuccessful) {
            _afState.value = AfState.Locked(req, SystemClock.elapsedRealtime())
            throttleController.onSuccess()
            AfOutcome.Success
        } else {
            handleFailure(req, FailReason.HAL_FAILED)
            AfOutcome.Failure("HAL_FAILED")
        }
    } catch (e: TimeoutCancellationException) {
        cameraControl.cancelFocusAndMetering()
        handleFailure(req, FailReason.TIMEOUT)
        AfOutcome.Failure("TIMEOUT")
    } catch (e: Exception) {
        cameraControl.cancelFocusAndMetering()
        handleFailure(req, FailReason.EXCEPTION)
        AfOutcome.Failure("EXCEPTION")
    }
}

private fun handleFailure(req: FocusRequest, reason: FailReason) {
    val previousFailCount = (_afState.value as? AfState.Failed)?.failCount ?: 0
    _afState.value = AfState.Failed(req, reason, previousFailCount + 1)
    throttleController.onFailure(previousFailCount + 1)
}
```

## 3. 動態節流機制 (Dynamic Throttling Logic)

在 Eye-AF 成功(`LOCKED`)後接管觸發頻率的控制。

### 3.1 具體參數與閾值 (Parameters & Thresholds)

- **`stableThresholdPx` (穩定判定閾值)**: 預設 $3\% \times \text{螢幕寬度}$ (例如 1080p 螢幕為 ~32px)。小於此值即認定目標靜止。
- **`rescanThresholdPx` (重掃觸發閾值)**: 預設 $5\% \times \text{螢幕寬度}$ (例如 ~54px)。大於此值且節流過期才允許重掃。與 `stableThresholdPx` 之間形成 Hysteresis 緩衝區，避免抖動。
- **`preLockThrottleMs` (未鎖定節流)**: 預設 `1500ms`。目標首度出現尚未鎖定時的嘗試頻率。
- **`postLockCooldownMs` (鎖定後標準冷卻)**: 預設 `5000ms`。若目標維持在穩定區間內，絕對不發起新的 Focus (即硬性節流時間)。
- **`movingCooldownMs` (移動中冷卻)**: 預設 `2000ms`。若目標位移超過 `rescanThresholdPx`，允許縮短冷卻時間以快速重抓。
- **`backoffBaseMs` (失敗退避基準)**: 預設 `2000ms`。發生失敗時的重新嘗試間隔，隨著連續失敗次數指數增加(`backoffBaseMs * 2^(failCount-1)`)，最高限制為 `8000ms`。

### 3.2 節流判定邏輯 (Pseudocode)

```kotlin
class AfTriggerThrottleController {
    private var lastTriggerTimeMs = 0L
    private var nextAllowedTimeMs = 0L
    private var isArmed = false // true 代表曾成功進入過 LOCKED
    
    fun onSuccess() {
        isArmed = true
        // 成功後，重置下次允許觸發時間為標準鎖定後冷卻
        nextAllowedTimeMs = SystemClock.elapsedRealtime() + postLockCooldownMs
    }
    
    fun onFailure(failCount: Int) {
        val backoff = min(backoffBaseMs * 2.0.pow(failCount - 1).toLong(), 8000L)
        nextAllowedTimeMs = SystemClock.elapsedRealtime() + backoff
    }
    
    fun shouldTrigger(req: FocusRequest, currentState: AfState): Boolean {
        val now = SystemClock.elapsedRealtime()
        
        // 1. User Tap 擁有絕對優先權，強制略過所有 Throttle
        if (req.source == FocusSource.USER_TAP) {
            nextAllowedTimeMs = now + postLockCooldownMs
            return true
        }
        
        // 2. 狀態閘道檢驗
        if (currentState is AfState.Focusing) return false // 正在對焦中不干擾
        
        // 3. 穩定性/位移判定
        val deltaPx = stabilityTracker.getDeltaPx(req.point)
        val isMoving = deltaPx > rescanThresholdPx
        
        // 動態調整 Next Allowed Time
        if (isArmed && isMoving && currentState is AfState.Locked) {
             // 目標移動時，若當前等待時間還很長，將它縮短至可接受的 movingCooldownMs
             val potentialMoveTime = currentState.lockedTimestamp + movingCooldownMs
             nextAllowedTimeMs = min(nextAllowedTimeMs, max(now, potentialMoveTime))
        }

        // 4. 時間閘道檢驗
        if (now < nextAllowedTimeMs) {
            // 還在冷卻期
            return false
        }
        
        // 5. 對於未 Armed 且從 IDLE 第一次嘗試，運用 base throttle
        if (!isArmed && currentState is AfState.Idle && (now - lastTriggerTimeMs < preLockThrottleMs)) {
            return false
        }
        
        lastTriggerTimeMs = now
        return true
    }
}
```

## 4. 副作用與風險評估 (Side Effects & Risks)

### 4.1 對 AF 準確度 (Accuracy) 的影響
- **正面**: 避免了在已經對焦準確且被攝者未大幅移動時，頻繁送出新的 `startFocusAndMetering` 導致鏡頭 "呼吸" 或稍微失焦。
- **負面/風險**: 若 `rescanThresholdPx` 設定過大，或 `postLockCooldownMs` 設定過長，可能在被攝者微小前後移動 (Z軸位移不一定反映在 X/Y 螢幕座標大位移) 時，景深變化導致眼部脫焦，而系統卻因為「節流未解鎖」而拒絕補焦。
- **緩解策略**: 需針對大光圈/微距場景作調參，可能需引入 Z 軸深度預估(若有)或允許一定程度的微調重掃。

### 4.2 對延遲 (Latency) 的影響
- **正面**: 減少了不必要的 HAL 調用，降低了相機管線阻塞機率，使得 UI frame rate 及 ML Kit 推理更加平滑。
- **負面/風險**: `FOCUS_TIMEOUT_MS` 若設定過長 (例如大於 5 秒)，在暗光或本身就難以對焦的環境下，會使系統被卡在 `FOCUSING` 狀態過久，進而延遲到備用對焦模式的啟用或阻礙使用者的手動干預。
- **緩解策略**: 將 `FOCUS_TIMEOUT_MS` 設定為 3~4 秒以內，且確保 `User Tap` 能無條件覆蓋 (cancel and override) 當前的 `FOCUSING`。

### 4.3 資源消耗 (Resource Consumption)
- 預期能 **大幅降低** 馬達功耗與 CPU 繁忙程度。
- `withTimeout` 牽涉協程的取消與重新排程，但其開銷與 HAL 頻繁 AF Scan 相比微乎其微。

## 5. 架構與 HAL/API 修改需求

### 5.1 內部 API 擴充
現行 CameraX 的 `startFocusAndMetering` 回傳 `ListenableFuture<FocusMeteringResult>`，足以滿足基本的 success/failure 判定。
但為了應對邊緣案例，建議引入 **Camera2 Interop** 作為進階判定:
- 需要監聽 Capture Request 狀態：`CaptureResult.CONTROL_AF_STATE`。
- 若 `startFocusAndMetering` 沒有在合理時間內回報，但發現 `CONTROL_AF_STATE` 轉為 `CONTROL_AF_STATE_FOCUSED_LOCKED` 或 `CONTROL_AF_STATE_NOT_FOCUSED_LOCKED`，可作為備援提前結束 `FOCUSING` 狀態。

### 5.2 HAL 介面影響
- 無直接修改底層 HAL (Hardware Abstraction Layer) 之需，本層級方案為 Framework/App 端的軟體封裝控制。
- 但我們**依賴** `cameraControl.cancelFocusAndMetering()` 能夠確實終止設備端正在進行的 Scan 動作。對於部分不支援明確 Cancel 行為的舊裝置，可能會導致 Timeout 重設後，下次發出的 Request 直接被丟棄。
