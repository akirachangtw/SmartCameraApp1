# v2.12.0-06 — Camera AF UI Debug & Fix（L2：技術可行性與實作規格）

本文件基於 L1 的概念性規劃，針對 Camera AF 在不同場景下的三大 UI 顯示與對焦行為問題，進行詳細的 L2 可行性評估。針對每個假設提供具體的 Camera API 調用、配置參數修改建議、需改動的程式碼段落，以及潛在的技術平衡與挑戰。

---

## 問題 1：Front camera 對焦框固定小 / 消失過快

### 假設 1.1: UI fading 與 job cancellation 交互導致提早消失
*   **相關 API (Methods/Classes)**：
    *   Jetpack Compose: `Animatable<Float, AnimationVector1D>`, `animateFloatAsState`.
    *   Kotlin Coroutines: `Job.cancel()`, `delay()`.
*   **具體參數/配置調優**：
    *   將 UI 的漸隱動畫 (fading) 從底層的 AF `Job` 中解耦。當 `isFocusing` 狀態被新的對焦請求中斷 (cancel) 時，UI 端不應立即將 `alpha` 設為 `0f` 或清除 `focusPoint`。
    *   引入 UI 端的 `gracePeriodMs` (例如 `500ms`)，狀態翻轉後等待此時間再執行淡出動畫。
*   **需檢視/修改的程式碼區段**：
    *   `FocusIndicator.kt`：檢視 Compose 狀態訂閱邏輯，尤其是與 `isFocusing` 或 `focusIndicatorFading` 連動的部分。
    *   `CameraState.kt`：確認清空 `focusPoint = null` 的時機點是否過於激進。
*   **挑戰與取捨 (Trade-offs)**：
    *   若 UI 顯示時間與底層 HAL 實際在掃描的時間脫鉤太久，使用者可能會誤以為已經對焦成功，而實際上底層的任務已經被取消。需要拿捏 `gracePeriodMs` 的長度。

### 假設 1.2: Locked/cooldown 期間框尺寸被凍結導致固定小
*   **相關 API (Methods/Classes)**：
    *   Kotlin Flow: `MutableStateFlow.update()`.
*   **具體參數/配置調優**：
    *   修改 Throttle 邏輯，區分「是否阻擋 HAL 調用 (`shouldTriggerAF`)」與「是否阻擋 UI 更新 (`shouldUpdateUI`)」。
    *   當處於 `AfState == LOCKED` 且位於冷卻期 (Cooldown) 期間，仍然允許 `CameraState.focusFrameWidthPx` 與 `heightPx` 接收並更新較大的 bbox 數據，僅攔截對 CameraX 的 `startFocusAndMetering`。
*   **需檢視/修改的程式碼區段**：
    *   `EyeAfCoordinator.kt`：分流資料走向，將座標系更新與 AF 觸發解耦。
    *   `AfTriggerThrottleController.kt`。
*   **挑戰與取捨 (Trade-offs)**：
    *   UI 框持續隨著人臉變大變小，但相機卻沒有真正進行物理對焦（因為處於冷卻），極近拍時可能導致框對準了目標但畫面是模糊的。

### 假設 1.3: Clamp 上限過小導致截斷
*   **相關 API (Methods/Classes)**：
    *   Kotlin: `Float.coerceIn(min, max)`, `Float.coerceAtMost(max)`.
    *   Android DisplayMetrics (獲取螢幕寬高)。
*   **具體參數/配置調優**：
    *   現有邏輯可能將 `max` 硬編碼為 `120.dp` 轉為 pixels。應改為動態上限，例如 `screenWidth * 0.8f` 和 `screenHeight * 0.8f`。
*   **需檢視/修改的程式碼區段**：
    *   `TargetGeometryMapper.kt`：計算 screen-space size 時的 clamp 邊界定義。
*   **挑戰與取捨 (Trade-offs)**：
    *   如果最大值設定過大，在極近距離前鏡頭自拍時，對焦框可能大到貼齊螢幕邊緣，失去「Indicator (指示器)」的視覺意義。

## 問題 2：Rear camera（Face）永遠無法對焦成功 / 一直對焦中

### 假設 2.1: AF action 配置不完整（FLAG_AE 缺失）
*   **相關 API (Methods/Classes)**：
    *   CameraX: `FocusMeteringAction`, `FocusMeteringAction.Builder`, `FocusMeteringAction.FLAG_AF`, `FocusMeteringAction.FLAG_AE`.
*   **具體參數/配置調優**：
    *   將創建 `FocusMeteringAction` 時使用的 Flag 從單一的 `FLAG_AF` 變更為包含測光的 `FLAG_AF | FLAG_AE`。
    *   配置範例：`FocusMeteringAction.Builder(point, FocusMeteringAction.FLAG_AF or FocusMeteringAction.FLAG_AE).build()`。
*   **需檢視/修改的程式碼區段**：
    *   `AfHalAdapter.kt` 或 `CameraRepository.kt` 中負責建構 action 並呼叫 `cameraControl.startFocusAndMetering(action)` 的函式。
*   **挑戰與取捨 (Trade-offs)**：
    *   強迫綁定 AE 會導致每次對焦都進行曝光權重重算。在明暗對比強烈的環境連續觸發對焦時，可能會引起預覽畫面的亮度閃爍 (Flickering)。如果 APP 支援使用者手動曝光補償 (EV)，要小心此動作是否會重置參數。

### 假設 2.2: Timeout 與 autoCancel 不對齊
*   **相關 API (Methods/Classes)**：
    *   CameraX: `FocusMeteringAction.Builder.setAutoCancelDuration(long, TimeUnit)`.
    *   Kotlin Coroutines: `withTimeout(timeMillis)`.
*   **具體參數/配置調優**：
    *   上層協程的 timeout 必須嚴格大於 CameraX 底層設定的 `autoCancelDuration`，避免 `withTimeout` 先拋出例外，將狀態標示為異常 (Exception/Failed) 並觸發無謂的 backoff。
    *   配置設定：確保 `autoCancelDuration = 4000L` 且上層 `withTimeout(4500L)`。
*   **需檢視/修改的程式碼區段**：
    *   `AfStateMachine.kt` (負責 Coroutines `withTimeout`) 與 `AfHalAdapter.kt` (設定 `autoCancelDuration`)。
*   **挑戰與取捨 (Trade-offs)**：
    *   如果在暗光環境下 HAL 真的卡住，拉長 timeout 代表需要等更久才能轉入 `FAILED` 並執行備用邏輯，導致使用者覺得相機反應遲鈍。

### 假設 2.3: HAL 回報語義差異導致 isFocusSuccessful 判定嚴苛
*   **相關 API (Methods/Classes)**：
    *   CameraX: `FocusMeteringResult.isFocusSuccessful`.
    *   Camera2Interop: `Camera2CameraControl`, `CaptureRequest.CONTROL_AF_MODE`, `CaptureCallback`.
*   **具體參數/配置調優**：
    *   如果在特定設備上 `isFocusSuccessful` 等待 `FOCUSED_LOCKED` 失敗，可透過 `Camera2CameraInfo.from(cameraInfo).getCameraCharacteristic(...)` 獲取硬體支援層級，然後利用 Interop 監聽更鬆散的 `PASSIVE_FOCUSED` 狀態做為對焦完成的 backup 指示。
*   **需檢視/修改的程式碼區段**：
    *   `AfHalAdapter.kt` 需擴充 Camera2Interop 的監聽器 (Callback) 實作。
*   **挑戰與取捨 (Trade-offs)**：
    *   引入 Camera2Interop 會破壞 CameraX 的高度封裝性。不同 OEM 手機針對 `PASSIVE_FOCUSED` 的實作穩定性不一，可能引入更多裝置相容性 Bug。建議僅做為黑名單裝置 (Blacklist) 的 Workaround。

## 問題 3：Rear camera（Object）對焦框固定小正方形 / 框不到物件

### 假設 3.1: bbox rotation/mapping 錯誤
*   **相關 API (Methods/Classes)**：
    *   CameraX: `CoordinateTransform`, `OutputTransform`, `SurfaceRequest.getResolution()`.
    *   Android Graphics: `Matrix.mapRect(RectF)`.
*   **具體參數/配置調優**：
    *   驗證 ML Kit `DetectedObject.boundingBox` 的產出時不應該手動乘算角度。
    *   應利用 CameraX 提供給 ImageAnalysis 的 `ImageProxy.imageInfo.rotationDegrees`，將 bbox 矩陣經過相對應的 `Matrix.postRotate()`，再經過 `OutputTransform` 映射到 `PreviewView` 座標系。
*   **需檢視/修改的程式碼區段**：
    *   `TargetGeometryMapper.kt`。必須確保傳入此模組的轉換矩陣包含了 Device Rotation 與 Sensor Orientation 的修正。
*   **挑戰與取捨 (Trade-offs)**：
    *   手勢方向與解析度轉換矩陣計算複雜度高；尤其在 16:9 裁剪模式下，Letterboxing/Pillarboxing (黑邊填補) 會導致 `PreviewView` 與實際 `ImageProxy` 高寬比不一致。需依賴 `ScaleType.FILL_CENTER` 或對等設定精確計算 offset。

### 假設 3.2: object bbox 天生偏小 + scale factor 不足
*   **相關 API (Methods/Classes)**：
    *   基本數學計算：`RectF.inset()`, 依寬高比例的 `scale`.
*   **具體參數/配置調優**：
    *   動態給定不同類型的 Scale Factor。對於 Face 使用 `1.2f`，對於 Object 可提高到 `1.5f ~ 2.0f`。
*   **需檢視/修改的程式碼區段**：
    *   `TargetGeometryMapper.kt` 裡針對不同 `TargetType` 的映射判定。
*   **挑戰與取捨 (Trade-offs)**：
    *   過度放大 (Scale up) 會讓對焦框溢出顯示邊界。縮放必須以目標中心為原點，並限制邊緣不得超出整個螢幕。

### 假設 3.3: UI clamp 破壞比例/退化成方框
*   **相關 API (Methods/Classes)**：
    *   Kotlin Math: 計算比例 (`aspectRatio = width / height`)。
*   **具體參數/配置調優**：
    *   不能單獨去 clamp `width` 和 `height` (例如 `w.coerceIn(...)` 然後 `h.coerceIn(...)`)。如果一個極扁長 (10:2) 的矩形，獨立 Clamp 最小值 (如 24) 可能會變成 24:24 正方形。
    *   **正確實作**：先判斷哪一個維度超過了上下限，將其截斷，然後根據原始 `aspectRatio` (長寬比) 回推另一個維度的長度，確保矩形不會意外被擠壓成正方形。
*   **需檢視/修改的程式碼區段**：
    *   `TargetGeometryMapper.kt` 最後輸出 `FocusFrameWidthPx` 與 `FocusFrameHeightPx` 之前的幾何運算式。
*   **挑戰與取捨 (Trade-offs)**：
    *   計算邏輯增加浮點運算的複雜度，但是在極少數極端比例物件(如一條長繩子)出現時，能夠真正發揮「矩形對焦框」的效果。
