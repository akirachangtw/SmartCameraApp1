# v2.12.0 — Sony 16:9 低 FPS（L2：具體檢測與實作技術指南）

## 目標
將 L1 的高階策略轉化為具體的技術檢測步驟與工具操作指南，協助工程團隊深入剖析 Sony 設備在 16:9 相機模式下 FPS 嚴重下降（< 20 FPS）的根本原因，並提供明確的實作驗證手法。

---

## 1. 檢測環境與設備資訊收集 (System & Device Info)

**目的**：精確記錄硬體、作業系統與相關韌體版本，以確認是否為特定硬體、驅動程式的問題，或是與最近的系統更新有關。

**詳細操作與工具**：
- **設備層級資訊擷取**：
  建議全程透過 ADB (Android Debug Bridge) 確認實際版本，請在終端機執行：
  ```bash
  adb shell getprop ro.product.model          # 取得精確的裝置型號 (例如：SO-52A)
  adb shell getprop ro.product.manufacturer   # 確認製造商 (應為 Sony)
  adb shell getprop ro.build.version.release  # Android OS 版本
  adb shell getprop ro.build.version.security_patch # 安全性修補程式層級
  adb shell getprop ro.build.display.id       # 詳細的韌體/組建版本號碼
  ```
- **App 相關資訊**：
  若想檢查目前安裝的應用程式 versionName，可使用：
  ```bash
  adb shell dumpsys package <your.app.package.name> | grep versionName
  ```
- **相機 HAL 支援的 Stream Configurations (Camera2 API)**：
  透過程式碼爬取，或者使用第三方 App (如 Camera2 Probe)，重點比對 Sony HAL 宣稱支援的 `ImageFormat.YUV_420_888` 解析度清單。

## 2. 深入收集效能指標與系統日誌 (Performance Metrics & Logging)

**目的**：量化管線中各個邏輯節點的耗時，確認瓶頸是否在解析度暴增、格式轉換（YUV 轉 RGB）或記憶體拷貝/旋轉。

**詳細操作與工具**：

### A. 影像解析度與協商結果監控 (CameraX ImageProxy)
在現有的 `ImageAnalysis.Analyzer` 實作中，攔截 `analyze(image: ImageProxy)` 並印出日誌：
```kotlin
override fun analyze(image: ImageProxy) {
    Log.d("CameraPerf", "Image format: ${image.format}, Size: ${image.width} x ${image.height}")
    // ... 後續處理邏輯 ...
}
```
*📌 判斷準則：比對 4:3 與 16:9 模式，若 16:9 的 `width` x `height` 高達 1920x1080，而 4:3 只有 640x480 或 800x600，則強烈支持主要假設 (PH)。*

### B. 時間戳與分段耗時分析 (Profiling Pipeline Sections)
利用 `SystemClock.elapsedRealtimeNanos()` 更精確地量測每幀 (per-frame) 的處理耗時：
```kotlin
override fun analyze(image: ImageProxy) {
    val t0 = SystemClock.elapsedRealtimeNanos()
    
    // 1. YUV 轉換為 RGB/Bitmap 的成本
    val bitmap = image.toBitmap() // 或是自訂的 YUV to RGB 轉換
    val t1 = SystemClock.elapsedRealtimeNanos()
    
    // 2. 矩陣旋轉與縮放成本 (Rotation/Crop)
    val rotatedBitmap = rotateBitmap(bitmap, image.imageInfo.rotationDegrees)
    val t2 = SystemClock.elapsedRealtimeNanos()
    
    // 3. 機器學習 / 電腦視覺推論成本 (ML Inference)
    runMlInference(rotatedBitmap)
    val t3 = SystemClock.elapsedRealtimeNanos()
    
    Log.d("CameraPerf", """
        Timing (ms):
        YUV -> Bitmap : ${(t1 - t0) / 1_000_000f}
        Rotate/Crop   : ${(t2 - t1) / 1_000_000f}
        ML Inference  : ${(t3 - t2) / 1_000_000f}
        Total Analysis: ${(t3 - t0) / 1_000_000f}
    """.trimIndent())
    
    image.close()
}
```
*📌 判斷準則：如果總耗時超過 50ms（此為 20 FPS 的臨界值），且最大瓶頸發生在 `YUV -> Bitmap` 及 `Rotate` 階段，則證明 CPU 端被大尺寸影像拖滿。*

### C. 系統層級與底層工具觀測 (System-level Tracing)
- **相機服務狀態配置 (dumpsys media.camera)**：
  當相機驅動運作中，檢查相機服務實際被請求的串流組態（Stream Configurations）：
  ```bash
  adb shell dumpsys media.camera
  ```
  搜尋 `StreamConfigurationMap` 與 `active clients`，觀察 HAL 如何對應 CameraX 的請求。
  
- **Perfetto / Systrace**：
  若需深入分析 CPU 調度或是 Buffer Queue 壅塞情形：
  ```bash
  adb shell perfetto -o /data/misc/perfetto-traces/sony_camera.perfetto-trace -t 10s sched freq idle am wm gfx view binder_driver hal dalvik camera res memory
  adb pull /data/misc/perfetto-traces/sony_camera.perfetto-trace
  ```
  將 Trace 匯入 [ui.perfetto.dev](https://ui.perfetto.dev/)，觀察 `App UI Thread`、`CameraX Analysis Thread` 及 `android.hardware.camera.provider` 的 CPU 時間佔比，尋找是否發生嚴重 Buffer 阻塞 (Backpressure)。

## 3. 硬體溫控與背景負載排除 (Thermal & Throttling)

**目的**：排除系統因晶片過熱而觸發降頻所造成的 FPS 低落。

**詳細操作與工具**：
- **Thermal Service 狀態對比**：
  請在「冷機啟動 (Cold Start)」的前 60 秒內進行基準量測，確保設備無高溫餘熱。
  ```bash
  adb shell dumpsys thermalservice
  adb shell dumpsys battery
  ```
  *📌 判斷準則：若 `mThrottlingStatus` 處於 `NONE` (0) 狀態或無明顯節流行為，但 FPS 在啟動的第一分鐘內就低於 20，則明確排除溫控 (Thermal) 降頻干擾。*

## 4. 最小化實驗設計與解決方案實作 (Experiments & Mitigation)

為了拆解複雜的流程，開發團隊應逐一實作以下獨立實驗來驗證，並確認最佳的修復路徑。

### 實驗一：強制限制 ImageAnalysis 解析度 (驗證 H1 / PH - 首選解法)
**操作手段**：透過 CameraX 的 API，為 `ImageAnalysis` 強制指定一個兼具 16:9 比例且較低的解析度上限（例如 640x360 或 1280x720 以內），把推論的尺寸拉下來，並維持 Preview 尺寸不變。

**程式碼實作參考**：
```kotlin
// 1. 建立 ResolutionSelector 以限制尺寸
val resolutionSelector = ResolutionSelector.Builder()
    .setResolutionStrategy(
        ResolutionStrategy(
            Size(640, 360), // 目標解析度 (16:9 低配版)
            ResolutionStrategy.FALLBACK_RULE_CLOSEST_LOWER // 允許向下尋找鄰近尺寸
        )
    )
    .build()

// 2. 套用至 ImageAnalysis 機制上
val imageAnalysis = ImageAnalysis.Builder()
    .setResolutionSelector(resolutionSelector)
    // 確保使用非阻塞策略，避免舊幀壅塞 (Backpressure)
    .setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)
    .build()
```
*✅ 成功準則：若重新編譯套用後，`Analyze` 日誌確實顯示拿到 `640x360` 尺寸的影像，且 FPS 直接爬升回 24~30 穩定水平，則此案可正式結案並作為最終修復方案。*

### 實驗二：移除分析端額外負載 (驗證 H4)
**操作手段**：保留原有 16:9 設定，但在 Analyzer 中完全跳過所有 Bitmap 轉換與 ML 推論。

**程式碼實作參考**：
```kotlin
override fun analyze(image: ImageProxy) {
    // 不做任何 YUV 或圖片運算，單純測量 CameraX 給圖的頻率
    image.close() 
}
```
*✅ 判斷準則：如果 FPS 大幅恢復正常，代表相機底層 HAL 給圖速度是 OK 的，瓶頸全因為 App 這端轉換耗時。若 FPS 依然低落（< 20），代表瓶頸發生在相機 HAL 內部產生 / 輸出 16:9 影像時已經掉圖。*

### 實驗三：優化旋轉與轉換成本 (驗證 H2 / 替代方案)
**操作手段**：若確認是轉換 `toBitmap()` 及 `Rotate` 太慢，但又不希望降低偵測解析度解析度。
- **解法建議**：
  1. 改用 RenderScript 或 Vulkan/OpenGL shaders 進行 YUV 到 RGB 的底層轉換。
  2. 若後端對接的是 ML Kit 或自訂模型，嘗試**不對 Image Buffer 實體旋轉**，而是將 `rotationDegrees` 標籤與 Metadata 交給 ML API 內部處理，或是將推論取得的 Bounding Box 結果利用反轉矩陣回到正確的螢幕顯示座標系。
