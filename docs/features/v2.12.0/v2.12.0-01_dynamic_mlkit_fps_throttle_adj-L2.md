# v2.12.0-01 — 動態 ML Kit FPS Throttle（L2：具體技術實作與可行性評估）

## 1. 目標摘要
將 L1 動態 ML Kit FPS Throttle 的架構方案，深化為可進入開發階段的軟體實作設計。本文重點在於評估資料擷取的精準度、選擇抗抖動且低負載的限流控制演算法、探討高/低階裝置影響與邊界情況（冷啟動、突波），並定義具體需使用的 Android API。

---

## 2. ML Kit 處理時間的測量與取樣 (Measurement & Sampling)

### 2.1 精確測量方法 (Precision Measurement)
為了提供極為精準的次微秒級與無時鐘回調干擾的測量：
- **API 選擇**：統一使用 `SystemClock.elapsedRealtimeNanos()`。絕對不要使用 `System.currentTimeMillis()` 以避免使用者調整系統時間或網路校時產生的突變。
- **擷取與計算錨點**：
  需要在非同步 API 的起點與對應的 Callback 來擷取 `start` 與 `end`：
  ```kotlin
  val startT = SystemClock.elapsedRealtimeNanos()
  mlPocessor.process(inputImage)
      .addOnCompleteListener { task ->
          val endT = SystemClock.elapsedRealtimeNanos()
          val processingTimeMs = (endT - startT) / 1_000_000f
          throttleController.reportMlTime(processingTimeMs)
          inputImage.close() // 確保資源必然釋放
      }
  ```

### 2.2 取樣與聚合策略 (Sampling Strategy)
基於 per-frame 計算的 CPU 負載考量，不應在每次測量時執行昂貴的陣列排序。
- **推薦方案：EWMA (指數加權移動平均 Exponentially Weighted Moving Average)**
  - **優勢**：時間複雜度 $O(1)$，記憶體佔用極低 (僅需一個變數記錄前值)，且具備良好的「平滑」防抖效果。
  - **數學公式**：$E_t = \alpha \cdot T_{current} + (1 - \alpha) \cdot E_{t-1}$
  - **參數與實作建議**：$\alpha$ (平滑係數) 設為 `0.2`~`0.3`。這能對突波做出一定程度的退避反應，同時不致引起 Interval 上下劇烈震盪。為了達到類似 P95 的絕對安全保守值，最終可用公式 `Safe_Interval = EWMA * Safety_Factor (約 1.25)` 來推導。
- **次要方案：Ring Buffer 排序取 P95**
  - 使用長度為 10~30 的 Ring Buffer 來推導真正的第 95 百分位數，對於少數跳針不敏感，但每次需進行 `Insertion Sort` 或 `Quick Select`，在極高頻率下存在無謂的 Overhead。結論：第一階段**建議採用 EWMA**。

## 3. 動態限流調整演算法 (Dynamic Throttle Algorithm)

不建議使用傳統的 PID 控制器 (Proportional-Integral-Derivative)。PID 更適合連續型物理系統，而 Camera 分析系統為離散非線性事件，參數 $(K_p, K_i, K_d)$ 整定困難，且容易造成 Overshoot (限流值震盪縮放)。

本案應採用 **自適應平均步進控制 (Adaptive Averaging with Step Limits)**：

### 控制邏輯
1. **防抖死區 (Deadband/Hysteresis)**：
   計算出理想的 `Base Target = EWMA_Time * 1.25 + Preprocess_Time` 後，與目前的 `current_interval` 做比較。若差異幅度 `< 10%`，**不進行任何修改**，以防止閘門開啟頻率不斷抖動。
2. **最低目標頻率保障 (Target Limit)**：
   `Final Target = max(Base Target, 100ms)` (假設最高目標是 10 FPS 分析)。
3. **步長限制 (Rate Limiting / Slew Rate)**：
   單次更新的最大跳躍幅度應受到限制。例如，即使目標要增加 200ms，我們在一幀中最多只允許調整平滑步長 `+50ms` 或 `-20ms`（下降/升頻慢，上升/退避快，以保證穩定與安全）。

## 4. 各裝置階層與模型影響評估 (Implications for Tiers & Models)

- **高階設備（具備 TPU / 頂規 GPU，例如 Pixel 9 / Samsung S24）**：
  - **特徵**：單次推論極其快速（可能僅需 15~25ms）。
  - **結果**：EWMA 計算所得的 `Base Target` 落在 30ms 左右，因此控制器會持續咬合在最低的安全限制 `100ms`（10 FPS），維持高頻且平穩。效能無浪費且分析即時。
- **中低階設備（僅依賴 CPU，例如一般中階 Android 機型）**：
  - **特徵**：單次推論耗時動輒 150ms ~ 350ms。
  - **結果**：控制器將自動適應並將 Interval 擴張至推論耗時之上的水平（例如 250ms ~ 450ms，即 2~4 FPS）。大幅度避免推論堆疊造成的 Main/Render Thread 阻塞與過熱當機，能保證預覽 FPS 的順暢，只是 Analyzer 反應較不即時（符合硬體物理限制）。
- **模型複雜度的無縫過渡**：
  不同型態的分析（例如切換 Face Detection 到 Pose Detection）。因為機制純看底層耗時，因此切換昂貴模型時會無縫自動降頻，無需任何人為撰寫 `if (model == pose) interval = 500` 的 Hardcode。

## 5. 潛在挑戰與緩解機制 (Challenges & Mitigation)

### 5.1 冷啟動效能衝擊 (Cold Start Performance)
- **挑戰**：ML 模型載入或是冷啟動的第一幀，耗時可能暴增到 1000ms+。若將第一幀寫入 EWMA，會導致系統在後續 3~5 秒內被不必要的拉長到超低頻操作。
- **緩解 (Warm-up Filter)**：
  - **忽略極端異常值 (Outlier Dismissal)**：設立 Warm-up 階段。前 3 次分析無論耗時多少均**不納入** EWMA，並在這 3 次強迫使用一個適中的預設值（例如 `200ms`）。

### 5.2 突然的負載尖峰 (Sudden Workload Spikes)
- **挑戰**：畫面瞬間從空無一人變為出現 10 張臉，處理耗時在下一幀翻了三倍。
- **緩解 (Fast Backoff)**：
  - 繞過 EWMA 平滑器與 Deadband。當單次硬體測量 `T_current > current_interval * 1.5` 時，直接觸發「緊急退避 (Panic Backoff)」，立刻調升 `current_interval = T_current * 1.2`，以防止接下來幾幀造成嚴重積壓。

### 5.3 ML 處理與渲染 (Rendering) 同步問題
- **挑戰**：當推論時間變得很具波動性，UI/Overlay 的 Bounding box 在畫面上可能無法貼合移動中的物件。這也是 Throttle 的一個副作用。
- **緩解**：必須要實作出 **Timestamp-based Synchronization**。將送進去分析的 Image `Timestamp` 或是相機視角的 `Matrix / ROI` 做記錄，當 ML 吐出結果時，對比目前最新的 Preview 畫面 Timestamp 來做位置插補或廢棄失效且過時的疊影。

## 6. 需求 API 與 SDKs 清單

要在架構中實作上述方案，需依賴以下關鍵 Android API 與相機特性：

1. **時間精準量測**：`android.os.SystemClock.elapsedRealtimeNanos()`
2. **CameraX Frame 丟棄機制**：
   確保 `ImageAnalysis.Builder` 配置了 `STRATEGY_KEEP_ONLY_LATEST`，讓閘門直接擋掉太快的 Frame 而不會塞爆 Camera Queue。
3. **安全跨執行緒鎖定**：
   使用 `java.util.concurrent.atomic.AtomicLong` 來儲存和比較 `next_allowed_time_ms` 以及 `ewma_value`。確保 Throttle Gate 判斷能在高併發與輕量級鎖定的狀況下工作。
4. **系統次級訊號擷取 (Secondary Signals)**：
   - 溫度控制：`PowerManager.getCurrentThermalStatus()` (支援 Android 10 (API 29+))。
   - 記憶體壓力：`ActivityManager.getMemoryInfo()`，判斷是否處於低記憶體並乘加 Backoff 係數。
