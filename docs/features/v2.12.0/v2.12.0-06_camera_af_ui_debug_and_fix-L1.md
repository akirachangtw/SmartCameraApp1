# v2.12.0-06 — Camera AF UI Debug & Fix（L1：概念性規劃與初步假設）

## 一、已知問題（From Traycer/L0）

1. **Front camera**：對焦框尺寸固定偏小、或顯示很快淡出/消失（使用者感知「沒有持續追蹤」）。
2. **Rear camera（Face）**：人臉場景「一直對焦中」或反覆失敗，難以進入對焦成功（logs 偶見 `AF_FAILED` / `isFocusSuccessful=false`）。
3. **Rear camera（Object）**：物件對焦框固定小正方形或框不到物件（framing 不正確）。

## 二、裝置/系統脈絡（Context & Assumptions）

> L1 屬於概念規劃；以下是「先驗假設」用於切分問題領域與排查順序，L2 會以 log/實機結果驗證。

- App：Android CameraX + Jetpack Compose + ML Kit（faces + objects），自訂 `FocusIndicator`。
- AF：透過 `CameraX CameraControl.startFocusAndMetering()`；上層有 `AfStateMachine`（4-state）與 `AfTriggerThrottleController`（節流/退避）。
- 鏡頭：前/後鏡頭切換；可能存在 mirror（前鏡頭）與 rotation（90/270）座標系差異。
- 目標：以「最小跨層改動」修正行為，不做大規模重構（例如全面改 Camera2）。

---

## 三、潛在問題領域切分（Problem Domains）

為了避免把所有症狀都歸咎於單一層，先把可能責任區分為四類（可同時成立）：

1. **UI/Compose 渲染層**
   - `FocusIndicator` 的大小 clamp、寬高比例、淡出 timing、與 state 更新頻率造成的視覺錯覺（例如「框變小/消失」其實是 alpha/fading 或 state 被覆寫）。
2. **AF 策略/狀態機層（Algorithm / State Management）**
   - `autoFocusOnSalientTarget()` 的 target selection、frame 尺寸更新策略、以及 `AfStateMachine`/throttle 對 UI 與 HAL 觸發時機的影響。
3. **Camera API 使用/配置（CameraX / FocusMeteringAction）**
   - `FLAG_AF` vs `FLAG_AF|FLAG_AE`、timeout 與 autoCancel 的對齊、以及不同 HAL 對結果回報的差異（導致後鏡頭人臉「永遠不成功」）。
4. **座標與幾何映射（Coordinate / Geometry Mapping）**
   - ML Kit bbox（image-space）到 screen-space 的 mapping（rotation/mirror/preview scale/letterbox），影響「框不在目標上」與「框大小不對」。

## 四、逐問題：最可能的子系統 + 3 個核心假設（每題最多 3 個）

### 問題 1：Front camera 對焦框固定小 / 消失過快

**最可能子系統**
- 主要：UI/Compose（fading/clamp/動畫）＋ AF 策略（Locked/cooldown 期間是否更新框）
- 次要：鏡頭切換時的狀態殘留（throttle/armed state）

**Hypotheses（最多 3）**
1. **UI fading 與 job cancellation 交互**：對焦成功後觸發 dwell fade（alpha/stroke 變化），但 focus job 被後續自動對焦 cancel，導致 `focusPoint` 或顯示條件提早變成 null/不顯示 → 看起來「消失過快」。
2. **Locked/cooldown 期間框尺寸被凍結**：`AfState=LOCKED` 時停止更新 frame size/position（或只更新 position 不更新 size），前鏡頭大臉仍顯示小框 → 看起來「固定小」。
3. **Clamp 上限過小**：`coerceIn(min,max)` 的 max 對前鏡頭近距離人臉不足，導致永遠被截斷到較小尺寸。

**診斷步驟（高階）**
- 觀測 UI state：每 500ms log 一次 `focusPoint`, `focusFrameW/H`, `focusIndicatorFading`, `afState`, `isFocusing`。
- 觀測動畫/淡出：確認「消失」是否來自 alpha 降低、`focusPoint` 被清空、或 composable 被條件渲染關掉。
- 鏡頭切換測試：切到前鏡頭後立即 reset throttle/state（只用於 diagnosis），確認是否消除「固定小/凍結」。

**解法方向（高階）**
- 把「顯示生命週期」與「對焦 coroutine」解耦：fading 不應因新 request cancel 而中斷到不顯示。
- Locked 期間允許有限度更新（例如：若位移超過門檻仍更新 size/pos），或把 cooldown 的凍結策略改成「只抑制 HAL 觸發，不凍結 UI」。
- clamp 改為「依螢幕比例的 max」或等比縮放（避免近拍被截斷成小框）。

### 問題 2：Rear camera（Face）永遠無法對焦成功 / 一直對焦中

**最可能子系統**
- 主要：Camera API 使用/配置（FocusMeteringAction flags, timeout, autoCancel）
- 次要：AF 策略（timeout 太短、失敗分類錯誤導致 backoff 過重）

**Hypotheses（最多 3）**
1. **AF action 配置不完整（FLAG_AE 缺失）**：某些後鏡頭 HAL 需要 AE 參與才能收斂；只用 `FLAG_AF` 可能導致 `isFocusSuccessful` 長期為 false。
2. **Timeout 與 autoCancel 不對齊**：上層 `withTimeout` 早於 CameraX autoCancel 觸發，導致「永遠在失敗循環」；或把 autoCancel 視為 FAILED，觸發指數退避，讓重試越來越慢。
3. **HAL 回報語義差異**：HAL/CameraX 在人臉場景不一定回報 `isFocusSuccessful=true`（但可能已達到可用焦平面），需要額外訊號（例如 AF_STATE）或更寬鬆的成功判定。

**診斷步驟（高階）**
- 把一次 focus action 的 timeline 打出來：start ts、回呼 ts、成功布林、exception/取消原因、實際耗時、當前 flags（AF/AE）。
- 對照兩個時間：`FOCUS_TIMEOUT_MS` vs `autoCancelDuration`（CameraX）是否一致。
- A/B：在後鏡頭人臉場景加上 `FLAG_AE`（或條件式加）比較成功率與耗時。

**解法方向（高階）**
- 統一 timeout 策略：上層 timeout ≥ CameraX autoCancel + buffer；並把「autoCancel/cancelled」分類為可重試的 IDLE，而非 FAILED/backoff。
- 對後鏡頭人臉採用更健壯的 action flags（至少 AF|AE），必要時引入可選的 AF_STATE 觀測作 backup 判定。

### 問題 3：Rear camera（Object）對焦框固定小正方形 / 框不到物件

**最可能子系統**
- 主要：座標/幾何映射（rotation/mirror/preview scaling）＋ UI 尺寸策略（scale factor / clamp）
- 次要：ML Kit object bbox 品質（天生偏小/抖動）

**Hypotheses（最多 3）**
1. **bbox rotation/mapping 錯誤**：object bbox 在 90/270 rotation 下仍在 sensor-native 坐標，未被正確旋轉後再 mapping → 轉到 screen 後尺寸/位置失真。
2. **object bbox 天生偏小 + scale factor 不足**：即使 mapping 正確，ML Kit object detection 的 bbox 可能比 face 小很多，乘以固定 1.5x 仍偏小 → 看起來「固定小」。
3. **UI clamp 破壞比例/退化成方框**：若以單一 size 或不當的 `coerceIn` 分別截斷寬高，可能造成比例被破壞、視覺退化成接近正方形。

**診斷步驟（高階）**
- 同時 log：image-space bbox（L,T,R,B）、rotationDegrees、screen-space corners、最後渲染 size（W/H）。
- 在 overlay 上把「ML Kit bbox（screen-space）」與「FocusIndicator frame」同時畫出來，快速判斷是 mapping 還是 UI clamp/scale 問題。
- A/B：提高 object scale factor（或改為依面積動態 scale）檢查是否立即改善可見性。

**解法方向（高階）**
- 收斂 mapping：把 rotation/mirror/letterbox 的處理集中在單一 `CoordinateTransformer`/mapper，並以 corners mapping 驗證正確性。
- object 尺寸策略改為「類型分流」：face 與 object 使用不同 scale factor / min size；並採用等比縮放的 clamp（保持 W:H）。

---

## 五、跨問題的通用排查順序（快速收斂）

1. **先補可觀測性（Observability first）**：把 focus action 與 UI frame 的關鍵欄位打點（一次就能縮小 50% 不確定性）。
2. **再分離「UI 問題」與「API/HAL 問題」**：用 overlay 對照 bbox 與 UI frame（幾何），再看 focus action timeline（行為）。
3. **最後做最小修正**：優先修「配置/分類」類（flags、timeout、cancel vs fail），再修「渲染/比例」類（clamp、scale、fading），避免跨層連動。
