# v2.12.0 — Sony 16:9 低 FPS（L1：假設與量測計畫）

## 目標與輸出

- **目標**：釐清 Sony 裝置在 **16:9** 影像分析（ImageAnalysis）時 FPS 明顯降低（< 20 FPS）的最可能原因，並提出可重現、可驗證的診斷流程與解法方向。
- **L1 輸出**：
  - 優先排序的 **可能原因（Hypotheses）**
  - 對應的 **驗證策略（Measurements / Experiments）**
  - 一個要先驗證的 **主要假設（Primary hypothesis）**
  - 若主要假設成立，對應的 **解決策略（Mitigation / Fix direction）**

> 參考：L0 既有分析指出 Sony HAL 在 16:9、未限制尺寸時，可能偏好給出 1920×1080，導致 CPU 端 YUV→Bitmap + 旋轉成本過高而掉 FPS。

---

## 優先排序：最可能原因（Hypotheses）

### H1（最高機率）：16:9 時 HAL 選到過高解析度（例如 1920×1080）造成 CPU pipeline 超載

- **現象解讀**：同一支手機 4:3 正常、16:9 變慢，最常見是「**輸入影像尺寸變大**」→ 每幀轉換與處理時間暴增。
- **推論**：在沒有 ResolutionStrategy/size cap 的情況下，Sony Camera HAL 對 16:9 `ImageAnalysis` 輸出選到 1080p；4:3 則落到較低解析度（例如 640×480 / 800×600）。

### H2：旋轉／裁切／格式轉換路徑在 16:9 觸發較重的處理（Transform 或 Copy 次數增加）

- 例如：16:9 對應到不同的 rotation / crop / scale 造成額外 buffer copy、Bitmap rotate 成本上升。

### H3：CameraX 針對 16:9 的 use case 組合協商（Preview + ImageAnalysis + ImageCapture）導致 backpressure 或 buffer queue 壅塞

- 可能以 `ImageAnalysis` 為主導的協商在 Sony 裝置上更容易落到高解析度、或造成 stall。

### H4：ML/Analyzer（例如 ML Kit）在 16:9 下輸入更大，導致推論更慢（次要）

- 若 Analyzer 本身節流（throttle）或耗時隨解析度成倍增加，會反映在整體 FPS。

### H5：溫控／省電策略（thermal / power mode）或背景負載（最低優先）

- 若冷啟動第一分鐘即長期 < 20 FPS，通常不是 thermal；但仍需排除。

---

## 主要假設（Primary Hypothesis to Test First）

**PH：Sony 裝置在 16:9 模式下，`ImageAnalysis` 被 HAL 協商為 1920×1080（或其他高解析度），導致 `getPreviewStream()` 的 YUV→Bitmap + transform/rotate 每幀耗時超過 50ms（20 FPS 門檻），因此 FPS 掉到 < 20。**

若此假設成立，最直接的解法是：**對 `ImageAnalysis` 設定解析度上限（例如 ≤ 640×480 或最接近的較低 16:9 尺寸）**，讓 Preview 仍可維持高畫質，但 analysis pipeline 保持可即時。

---

## 驗證策略（Measurements / Experiments）

### 1) 先確認版本與近期變更（軟體/驅動/韌體）

**目的**：確認是否為近期更新導致回歸、或是否有裝置端已知問題/修補。

- **App/Library**
  - SmartCameraApp 版本（v2.12.0 分支/commit）、build variant（debug/release）
  - CameraX artifacts 版本（camera-core / camera-camera2 / camera-lifecycle / camera-view 等）
- **OS/裝置**
  - Android 版本、Security patch level
  - Sony 裝置型號（精確型號）與相機相關韌體（如有可查）
- **近期更新**
  - 是否剛升級 Android 系統 / Sony 韌體
  - 是否剛升級 CameraX/Compose/Kotlin/AGP（若與 CameraX 綁定流程相關）

**判斷點**：若同一裝置「更新前正常、更新後變差」，優先比對版本差異與已知 issue。

### 2) 在 16:9 影片/預覽擷取時收集關鍵效能指標與系統日誌

**目的**：把「FPS 掉」具體化成「哪一段 pipeline 慢」與「輸入尺寸是否暴增」。

建議在 Sony 裝置上做兩組測試（4:3 vs 16:9），每組至少 60 秒、冷啟動優先：

- **影像尺寸與協商結果**
  - 取 `ImageProxy.width × height`（或 CameraX UseCase 設定尺寸）在開始時記錄一次
  - 若可行，同步記錄 Preview/Analysis 各自拿到的 target size
- **每幀耗時（建議以現有 timing log 為主）**
  - YUV→Bitmap（或 YUV→RGB）耗時
  - transform/rotate 耗時
  - Analyzer（ML/後處理）耗時
  - 實際 FPS（可以 1s window 計算、或利用既有 log）
- **系統層級**
  - `logcat`：CameraX / camera2 / vendor camera log（搜尋 `CameraX`, `camera2`, `StreamConfigurationMap`, `configureStreams` 等）
  - `dumpsys media.camera`（如流程允許）：相機使用狀態/clients
  - 溫度與頻率（可選）：`dumpsys thermalservice` / `dumpsys battery`（用來排除 thermal）

**判斷點（支持 PH）**：
  - 16:9 的 `ImageProxy` 尺寸顯著大於 4:3（例如 1920×1080 vs 640×480）
  - 16:9 的 YUV/transform 每幀耗時大幅上升（例如從 ~5–10ms 變成 ~60–80ms）

### 3) 針對 16:9 的已知問題/韌體更新/裝置最佳化檢查

**目的**：避免重造輪子；確認是否有 Sony 機型對 CameraX + 16:9 有已知協商/性能問題。

- 查詢方向（內部/外部）：
  - Sony 機型是否對特定 stream combination（Preview+Analysis+Capture）在 16:9 有限制
  - CameraX 官方 issue / release note：是否提到特定 OEM（Sony）在特定 aspect ratio 會選高解析度或掉帧
  - 是否存在建議的 **ResolutionSelector/ResolutionStrategy** 配置（analysis 限制尺寸、preview 保持畫質）
- 若 Sony 有相機韌體更新：確認更新說明是否提到 camera performance / stability

**判斷點**：若存在官方/社群已知 issue，優先按建議配置驗證（通常也是設定 analysis cap）。

### 4) 最小化實驗：只改一個變因來驗證 PH

**實驗 E1（優先）**：對 `ImageAnalysis` 套用解析度上限（cap）或目標解析度（例如 ≤ 640×480）

- **預期**：16:9 下 `ImageProxy` 會落到較低解析度（可能是 640×360 / 640×480 等），FPS 恢復 > 20。
- **成功準則**：
  - 16:9 FPS > 20 且穩定
  - YUV/transform 耗時下降到可接受範圍
  - Preview 畫質不受影響（如 Preview 獨立 selector）

**實驗 E2（排除 H4）**：暫時停用/大幅節流 Analyzer（ML）

- **預期**：若 FPS 幾乎不變，表示瓶頸在前段（YUV/transform/尺寸）；若 FPS 明顯改善，表示 Analyzer 也需降解析度或改 pipeline。

**實驗 E3（排除 H5）**：冷啟動前 60 秒 vs 之後比較

- **預期**：若從一開始就 < 20 FPS，thermal 不是主因。

---

## 解決方案方向（若 PH 成立）

- **策略 S1（首選）**：`ImageAnalysis` 使用獨立 `ResolutionSelector` / `ResolutionStrategy`，限制最大尺寸（例如 ≤ 640×480 或接近的 16:9 低解析度），Preview/ImageCapture 維持原有高畫質策略。
- **策略 S2**：減少每幀成本
  - 盡可能避免 Bitmap rotate（改以 shader/矩陣、或在下游以 metadata 處理 rotation）
  - 降低 color conversion 成本（例如 RenderScript 替代方案、GPU path、或只取 ROI）
- **策略 S3**：針對 Sony 機型套用 device-specific optimization（若僅 Sony 受影響）
