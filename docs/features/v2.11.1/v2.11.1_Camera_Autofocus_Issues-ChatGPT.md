整體判斷：你現在遇到的 5 個現象大多不是「單一功能壞掉」，而是座標系統/視窗裁切（ViewPort + PreviewView FIT_CENTER letterbox）沒有被當成單一真相，導致：

視覺 Overlay（格線/對焦框）用的是「全螢幕座標」
偵測（ML Kit / optical flow）用的是「ImageAnalysis/Bitmap 座標」
對焦測光（FocusMeteringAction）又用「SurfaceOrientedMeteringPointFactory 的 viewWidth/viewHeight」
三者沒有一致 mapping，就會出現：格線超出預覽、對焦框不貼合物件、追蹤飄移、Eye-AF/Smart Focus 看起來像沒作用或永遠在對焦中。
以下分題分析、最佳方案與風險：

1) Eye‑AF 無自動對焦（前後鏡頭都沒有）
根因高機率

Eye landmark 有抓到（專案已開 LANDMARK_MODE_ALL），但眼睛座標屬於影像座標，目前並沒有嚴謹轉換到 PreviewView 顯示區。
對焦動作使用 SurfaceOrientedMeteringPointFactory(viewWidth, viewHeight)，在你目前採用 PreviewView.ScaleType.FIT_CENTER + ViewPort.FIT 時，畫面存在黑邊(letterbox)，點位到感光元件的映射容易偏掉或落到無效區，造成對焦失敗/無感。
Eye‑AF 即便在追蹤時更新了對焦點（UI 位置），也不等於持續驅動硬體 AF；如果只做「框跟著跑」但沒有按節奏重新 metering，使用者會感覺「沒有自動對焦」。
最佳建議方案

以 PreviewView 為真相：改成使用 PreviewView.meteringPointFactory（或 CameraX 的 view transform API）產生 MeteringPoint，避免自己猜 FIT/CROP 幾何。
建立一個統一的座標轉換層：Image(Analysis/Bitmap) ↔ Preview(contentRect)，並且要支援 FIT_CENTER 的 letterbox（非 CENTER_CROP）。
Eye‑AF 變成「可控頻率」的持續 metering：例如 2–5Hz 或在 eye 位置位移超過門檻才觸發，避免每幀呼叫造成抖動與功耗。
主要風險

OEM 相機行為差異：有些前鏡頭固定焦/不支援 AF，需先做 capability 檢測與降級（退回臉框中心或不觸發 AF）。
太頻繁 metering 會造成「拉風箱/抽動」與耗電上升；必須節流 + 門檻控制。
2) Smart Subject Focus 狀態機制失效（框固定、一直對焦中、無淡化）
根因高機率

對焦框大小目前是常數（例如固定 48dp），自然不會隨物件大小變化。
fade（Alpha 1.0→0.4）目前只在「非 tracking」分支才會走；一旦 Smart Focus/自動追蹤把你帶進 tracking 模式，邏輯就會維持 alpha=1.0，看起來像「一直在對焦中 / 沒進入 dwell」。
若對焦 future 未完成或失敗頻繁（常見於座標不準），focusSuccess 無法變成 true，UI 也會一直呈現「對焦中」。
最佳建議方案

把 focusOnPoint() 拆成兩條路徑：manualFocus()（會覆蓋 auto）與 autoFocus()（不更新 lastManualTapTime，不強制進 tracking，或明確定義 auto 是否自動啟追蹤）。
明確狀態機：IDLE → FOCUSING → SUCCESS(hold) → DWELL(fade to 0.4) → TRACKING(optional)，用 timestamp/timeout 驅動，避免「靠 if/else 拼湊」。
加入對焦 timeout（例如 1500–2500ms）：超時就結束 focusing，避免 UI 永久卡在 focusing。
對焦框大小：把「目前追蹤目標 bounding box（已映射到 preview）」存到 state，FocusIndicator 用該尺寸（再做 min/max/平滑）。
主要風險

狀態機改動會影響既有 UX（例如何時顯示括號、何時淡化）；需要與設計稿/期望行為對齊並寫回歸測試/錄影驗收腳本。
引入 bounding box 動態尺寸後，若座標 mapping 未先修好，反而會更抖更亂（所以必須先修 mapping）。
3) 三分格線超出預覽範圍（切 1:1 / 4:3 / 16:9）
根因幾乎確定

Preview 是 FIT_CENTER（有黑邊），但 GridOverlay/GuidelineOverlay/... 都 fillMaxSize() 畫在整個螢幕 Box 上，所以線會畫到黑邊區域，看起來「超出預覽」。
最佳建議方案

建立 PreviewViewportContainer：先在 Compose 計算「實際預覽內容矩形 contentRect」（依螢幕大小 + 目標 aspect ratio + FIT），讓PreviewView 與所有 overlays 都只在這個 rect 裡繪製（其餘區域是黑邊背景）。
同時把 touch（tap/long-press）座標也限定/轉換到 contentRect，避免點黑邊也觸發對焦。
主要風險

版面結構會動到 CameraScreen 的 layout；需要測：旋轉、不同螢幕比例、瀏海/手勢列 insets。
若未同步修正「點擊座標→對焦點」的轉換，會造成點到內容但實際 metering 偏移。
4) 未看到雙層結構（外層角落括號 + 內層實線四邊形）
根因

目前的 FocusIndicator 是「同一個方框 +（條件式）角落括號」，不是「外括號框一層、內實線框一層」的兩個尺寸/兩種語意。
最佳建議方案

把繪製拆成兩個 geometry：
外層：只畫角落括號（尺寸略大，代表追蹤目標範圍）
內層：畫實線四邊形（尺寸略小，代表實際對焦/測光區）
內外尺寸來源：以「目標 bounding box」推導（再加 padding），並做平滑（lerp）避免跳動。
主要風險

Canvas 畫更多元素，低端機可能掉幀；需做節流/只在尺寸或位置變動超過門檻才重繪（或降低 glow）。
5) 對焦追蹤效果差，容易偏移定點
根因高機率

座標 mapping 假設錯誤：專案現有 CoordinateMapper 是以 CENTER_CROP 幾何設計，但你現在是 FIT_CENTER + letterbox，所以 optical flow / 目標點回投到 preview 時會系統性偏移與漂移。
tracking 更新只改 UI 點位，不一定同步驅動對焦/測光；再加上抖動、遮擋、ID 變更，就更容易飄。
最佳建議方案

先修 mapping：讓 mapper 支援 FIT_CENTER（含 offsetX/offsetY 的黑邊），並處理前鏡頭 mirror。
再修追蹤穩定性：
加低通濾波/Kalman（位置、尺寸）；
加 reacquire：追蹤丟失或品質低就回到「重新鎖定臉/物件」；
optical flow 定期用 ML Kit 重新播種（避免長時間漂移）。
主要風險

濾波太強會造成延遲感；太弱則抖動。需要調參與不同場景測試（走動、人臉近距離、低光）。
最佳落地路線（建議優先順序）
P0：統一座標系/viewport（必做）：先把 contentRect 算對、overlay/touch 對齊 preview；修正 FIT_CENTER 的 mapping。
P1：對焦 metering 正確化：改用 PreviewView 的 meteringPointFactory（或等價 transform），Eye‑AF/Smart Focus 才會真的對到地方。
P2：狀態機 + 視覺規格：補 dwell/fade、雙層框、尺寸隨物件變化；加 timeout 防卡死。
P3：追蹤品質：濾波 + reacquire + 節流
