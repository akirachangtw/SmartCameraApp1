# Level 1 規劃摘要｜lk_tracking_stability

## 1. 目標（Goal）
提升 Optical Flow（LK）追蹤的穩定性與可診斷性，降低「點位漂移、RANSAC 誤判、追蹤突然 LOST」的發生率，並確保在不同相機管線來源（CameraX ImageAnalysis vs Bitmap pipeline）與不同裝置行為差異下，追蹤座標與影像尺寸一致、可預期。

---

## 2. 背景與問題（Why / What）
目前 LK 追蹤不穩定的主要訊號與根因推測如下（依現況 diff）：

- **LK 點位品質污染**：僅用 `status=1` 判斷有效點，未過濾 `error` 過高的追蹤點，導致錯誤匹配點混入位移統計（median / RANSAC-like outlier filter），使得「整體一致運動」被誤判成 outlier 或導致 median 偏移，最後觸發 LOST。
- **影像尺寸來源不一致 / 競態**（特別是實機差異）：
  - `trackFromBitmap()` 可能先設定 `imageWidth/Height`（例如 ~720px）；
  - CameraX `analyze()` 影像實際解析度可能是 `ImageProxy` 的 1920×1920（1:1 mode）；
  - 若不同 pipeline 的尺寸/座標系混用，會造成 tracking 初始化或更新時的座標落差，進而增加 LOST、out-of-bounds 等問題。
- **實機 vs 模擬器行為差異**（從註解推測）：某些裝置（例 Pixel 9a）可能發生 ImageAnalysis 不跑或觸發條件不同，導致「只能依賴 bitmap pipeline」；這會讓「依賴 analyze pipeline 尺寸」的設計失效。
- **診斷不足**：追蹤 LOST 的原因（越界/品質太低/距離過大/有效點數為零）若沒有明確 log，很難定位是參數問題、座標系問題、或管線沒有跑。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線風險（ImageAnalysis vs Bitmap pipeline）**
   - 若 `analyze()` 在部分裝置不觸發，任何依賴 `ImageProxy` 尺寸或 analyze 初始化的流程會失效。
   - pending track 套用時機若與 pipeline 實際啟動順序不一致，可能導致「追蹤永遠不啟動」或「用錯尺寸啟動」。

2. **模式切換/座標系風險（preview coords vs image coords）**
   - `startOpticalFlowTrackingImageCoords()` 走 bypass CoordinateMapper，若呼叫端提供的其實是 preview space，會造成啟動點錯位（進而快速 LOST）。
   - 1:1 mode、旋轉、鏡像（前鏡頭）等情境下，座標系若未完整定義，仍可能出現邊界越界與漂移。

3. **效能回歸風險**
   - LK 增加 error filter（每點判斷）成本低，但 log（尤其 `Log.v` 每 frame）可能造成 FPS 抖動或大量 log。
   - 若誤設 `MAX_LK_ERROR` 過低，會導致有效點數不足、追蹤更容易 LOST（穩定性反而下降）。

4. **行為回歸風險（過濾造成敏感度改變）**
   - 在低光/高噪環境，LK error 可能普遍偏高，導致 filter 把大多點踢掉，降低追蹤能力。
   - 「distance / quality」門檻若偏嚴，可能把原本可接受的追蹤判定為 LOST。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異、延續現有方向）
1. **LK 點位品質過濾**：維持 `status==1 && error < MAX_LK_ERROR`，但需要：
   - 將 `MAX_LK_ERROR` 設計為可調參（config 或 build flag），避免硬編碼造成不同裝置表現分歧。
   - 補充「有效點數下限」策略（例如少於 N 點時降級策略），避免一律 LOST。

2. **尺寸/座標系單一事實來源（SSOT）**
   - 明確定義「Image coords」到底對應哪個尺寸：`bitmap.width/height` 或 `ImageProxy.width/height`。
   - 將「追蹤啟動」統一以同一套 image space 尺寸啟動（目前偏向 bitmap 即 image space）。
   - 保留 `analyzeImageWidth/Height` 作為診斷/未來修正用，但避免當下流程混用兩套尺寸。

3. **診斷 log 收斂**
   - 保留 LOST 關鍵原因 log（Info 等級可接受），但將每 frame 的 `Log.v` 受控（例如 debug build 才開，或加節流）。

### Plan B（更保守的 fallback，降低裝置差異風險）
1. **完全以 bitmap pipeline 作為 tracking pipeline**
   - 若確認某些機型 ImageAnalysis 不穩，則將 tracking 更新與尺寸全部綁定 bitmap pipeline（已接近現況），ImageAnalysis 只負責 ML 或可選功能。
2. **加入「追蹤初始化握手」**
   - 只有在已知取得「本次追蹤所用影像尺寸」後才允許 startTracking。
   - pending track 需要設定超時/重試或狀態提示，避免長期 pending 造成使用者誤解。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### 功能正確性
- **實機（必測）**
  - Pixel 系列（至少包含目前提到的 Pixel 9a 或同級）：
    - 1:1 模式下點選啟動追蹤，觀察是否能穩定跟隨 5–10 秒。
    - 快速移動/遮擋/重新出現，確認不會立刻 LOST 或漂移到錯位。
  - 另一台非 Pixel（Samsung/小米任一）交叉驗證裝置差異。

- **模擬器（次要）**
  - 主要驗 UI 流程與不 crash；tracking 表現模擬器參考價值有限。

### 診斷與指標
- Log 檢查（建議在 debug build）
  - LK error filter 通過率（passed/total）
  - LOST 原因分類（out-of-bounds / quality / distance / 0 valid points）
- 效能
  - FPS（預覽 + tracking 開啟/關閉）
  - CPU 使用率（特別是 log 量大時）
  - 每秒 LOST 次數（或平均追蹤存活時間）

## 7. 回滾策略（Rollback）
- 提供可快速回滾的開關或 commit 邊界：
  1. 回滾 LK error filter（恢復只看 status）或改成「僅記錄 error，不過濾」。
  2. 回滾 SmartCameraAnalyzer 的 pending image-coord 套用邏輯（恢復舊版 CoordinateMapper 路徑）。
  3. 將新增的詳細 log 降級或移除（避免效能回歸）。
- 建議以 atomic commits 分拆：  
  - Commit 1：純診斷 log（可安全回滾）  
  - Commit 2：LK error filter（行為變更）  
  - Commit 3：pipeline 尺寸/座標修正（高風險）
