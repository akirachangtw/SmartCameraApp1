## 2. Fix A — lockAEAF 停止 Optical Flow

### 2.1 實作方案

```kotlin
// v2.11.2 fix Bug A: Stop Optical Flow BEFORE state update
val wasOpticalFlowTracking = _state.value.trackedPointActive
if (wasOpticalFlowTracking) {
    cameraRepository.stopOpticalFlowTracking()   // SmartCameraAnalyzer.isTracking=false
    Log.i(TAG, "Optical flow tracking stopped for AE/AF lock")
}

// 單一原子 update：清除所有 tracking + 設定 lock state
_state.update {
    it.copy(
        trackedObjectId = null,       // ML Kit tracking
        trackedObjectType = null,
        trackedPointActive = false,   // ← 關鍵：OF callback 不再更新 focusPoint
        trackedPointLost = false,
        focusIndicatorFading = false, // 重置 dwell fade
        focusPoint = Pair(x, y),     // B 點（此後不被 OF 覆蓋）
        isFocusing = true,
        focusSuccess = null,
        lockPoint = Pair(x, y),
        isAEAFLocked = false
    )
}
```

| 項目 | 狀態 | 說明 |

| `trackedPointActive` in CameraState | ✅ 已存在 | 直接更新 |
| `observePreviewForOpticalFlow()` 守衛 | ✅ 已有 `if (trackedPointActive)` | 設 false 後自動停止 |

## 3. Fix B — 移除 isFocusSuccessful Gate

### 3.1 CameraX API 行為確認

CameraX 的 `startFocusAndMetering()` 執行 AE/AF metering，**lock 在呼叫時即套用**，與 `isFocusSuccessful` 無關：
- `isFocusSuccessful=true`：AF 在 timeout 內收斂至最佳焦距
- `isFocusSuccessful=false`：AF 未完全收斂（暗景、移動主體、焦距邊界等），**但 lock 已套用**
- 驗證：`cancelFocusAndMetering()` 在 `isFocusSuccessful=false` 後仍可解鎖 → 鎖定確實有效

### 3.2 修改方案

```kotlin
// 修改位置: LiveCameraSource.lockAEAF():714-722
// Before:
if (result.isFocusSuccessful) {
    continuation.resume(Result.success(Unit))
} else {
    continuation.resume(Result.failure(Exception("AE/AF lock failed")))
}

// After:
// v2.11.2: Lock is applied regardless of AF convergence quality.
// isFocusSuccessful indicates AF convergence, not lock status.
Log.i(TAG, "[v2.11.2] AE/AF lock applied at ($x,$y), isFocusSuccessful=${result.isFocusSuccessful}, factory=${if (previewView != null) "PreviewView" else "SurfaceOriented"}")
continuation.resume(Result.success(Unit))
```

### 3.3 各場景行為對比

| 場景 | 舊行為 | 新行為 |
|------|--------|--------|
| AF 收斂成功 | ✅ success → 動畫 + 黃框 | ✅ 相同 |
| AF 未收斂（暗景/移動） | ❌ failure → 無動畫無黃框 | ✅ success → 動畫 + 黃框 |
| `future.get()` exception | ❌ failure（catch 捕捉） | ❌ failure（不受影響）|
| 相機未初始化 | ❌ failure | ❌ failure（不受影響）|

**可行性**: ✅ **可行，極低風險** — 單行改動，exception 路徑完整保留

## 4. Fix C — Optical Flow 追蹤參數（保守改善）

### 4.1 歷史脈絡

**v2.9.9 已實作**（`v2.9.9_Day1-2_improve-optical-flow-tracking_Traycer.md`）：
- 多點 LK + RANSAC 追蹤（`goodFeaturesToTrack` + 中位數聚合）
- `maxFeaturePoints=30`, `redetectionInterval=15`, `ransacDistanceThreshold=0.5`

**v2.9.9 ChatGPT P0-P4 建議**（`v2.9.9_Day1-2_improve-optical-flow-tracking-v2_ChatGPT.md`）：

| 優先 | 方案 | 說明 | v2.11.2 處理 |
|------|------|------|-------------|
| P0 | Bitmap→ImageProxy Y-plane 高頻管線 | 追蹤 FPS 提升，大動作 LOST 大幅減少 | ❌ 延後至 v2.12.0（架構變更） |
| P1 | 縮小/自適應 ROI | featureROISize 降低，防背景特徵混入 | ⚡ 部分採用（redetectionInterval 動態化） |
| P2 | matchTemplate drift correction | 定期拉回漂移 | ❌ 已存在但停用，延後 |
| P3 | 大動作抗性（maxLevel, FB check） | 減少跳點 | ❌ 延後 |
| P4 | 座標/旋轉一致性 | CoordinateMapper rotation | ❌ v2.12.0 計劃 |

### 4.2 v2.11.2 採用範圍（最小修改）

**redetectionInterval: 15 → 5**

| 指標 | 舊值（15幀/1s） | 新值（5幀/333ms） |
|------|--------------|---------------|
| 點集補充週期 | 每 1s | 每 333ms |
| CPU 影響 | goodFeaturesToTrack 1次/秒 | 3次/秒（Pixel 9a: +<15ms/秒） |
| 效果 | 點枯竭後 1s LOST | 333ms 即可回補 |

**ransacDistanceThreshold: 0.5 → 1.0**（保守版，非 v2.9.9 Traycer 建議的 2.0）

| 場景 | 舊閾值 | 新閾值 | 效果 |
|------|--------|--------|------|
| 靜止（median=2px） | 3.0px | 3.0px | 無改變（保守） |
| 輕微移動（median=6px）| 3.0px | 6.0px | 稍寬鬆 |
| 快速移動（median=20px）| 10px | 20px | 更寬鬆 |

**4.3 不修改項目**（v2.12.0 計劃）
- `targetFps`: 保持 15（Bitmap pipeline 下提高無意義）
- `featureROISize`: 保持 80（P1 建議 40-60，但需要與 P0 ImageProxy 管線配合才有意義）
- `maxLevel`: 保持 4（P3 建議 5-6，延後）

**可行性**: ✅ **可行（保守版）** — 2 個常數修改，易回滾
