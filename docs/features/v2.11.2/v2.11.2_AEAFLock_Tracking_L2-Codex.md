## 0. 結論（最佳方案）

**建議採用「最小改動 + 競爭條件保險」的 3-in-1 修正**，以同一個 atomic commit 進入 L3：

1. **Fix A（Bug A）**：在 `CameraViewModel.lockAEAF()` 進入 lock 模式前，**同步停止 Optical Flow tracking + 清除 trackedPoint state**，並在 Optical Flow callback 端加上**狀態 gate**，避免「停止後仍被 callback 重新寫回 focusPoint / trackedPointActive」。
2. **Fix B（Bug B）**：在 `LiveCameraSource.lockAEAF()` **移除 `isFocusSuccessful` gate**；只要 `future.get()` 正常返回就視為 lock action 已套用（但保留 log 記錄 `isFocusSuccessful` 供品質分析）。
3. **Fix C（Bug C）**：調整 `OpticalFlowConfig.DEFAULT` 的 `redetectionInterval` 與 `ransacDistanceThreshold`，以降低「點集枯竭」與「小動作過嚴剔除」造成的頻繁 LOST。

## 1. 問題回顧（從 L1 落地到代碼）

### Bug A：長按 B 卻鎖在 A（座標被覆蓋）

`setupOpticalFlowTracking()` 的 callback 會每幀更新 `focusPoint`；而 `lockAEAF()` 在呼叫 `cameraRepository.lockAEAF()`（suspend/async）期間，若 Optical Flow tracking 仍 active，就可能把剛設的 B 覆寫回 A。

**根因特徵**：ViewModel 端沒有「lock 模式優先」的排他策略，造成狀態競爭（race）。

### Bug B：lock 成功但無 3-phase 動畫

`LiveCameraSource.lockAEAF()` 把 `result.isFocusSuccessful == false` 視為失敗回傳，導致 ViewModel/UI 走失敗路徑（清除指示器、無動畫），但實務上 **AF 收斂失敗 != Lock action 未套用**。

### Bug C：Optical Flow 追蹤不穩定

DEFAULT 參數偏保守：
- `redetectionInterval=15`（點集補充太慢，LK 點集容易縮水到不足）
- `ransacDistanceThreshold=0.5`（小動作時實際 threshold 常落在 3px，對手持抖動偏嚴）

---

## 2. Fix A（最佳落地做法）

### 2.1 ViewModel：進入 lock 前「停追蹤 + 清 state」

在 `CameraViewModel.lockAEAF()`：
- 若 Optical Flow tracking 可能在跑（`trackedPointActive == true`），先：
  - `cameraRepository.stopOpticalFlowTracking()`（同步、立即停）
  - `_state.update { trackedPointActive=false, trackedPointLost=false, trackedPointQuality=0f(或維持), ... }`
- 同一個 `_state.update { ... }` 內同時清除 ML tracking（`trackedObjectId/trackedObjectType=null`），避免多段 update 造成 UI 短暫不一致。

### 2.2 Optical Flow callback：加 gate 防「停止後被寫回」

在 `setupOpticalFlowTracking()` 的 callback 開頭加入排他條件，建議優先序：

- **若目前處於 lock 狀態**（`lockPoint != null` 或 `isAEAFLocked == true`）→ 直接忽略 valid update（避免覆蓋 lock 指示器）
- **若目前 ML tracking 正在跑**（`trackedObjectId != null`）→ 忽略 valid update（避免兩種追蹤互相打架）
- **若 `trackedPointActive == false`** → 忽略 valid update（避免 stop 後被 callback 重新設回 true）
- invalid/lost 分支可保留（或只在 `trackedPointActive==true` 時處理一次），確保能正確 stop tracker 並清 UI

> 這個 gate 是 Fix A 的「保險絲」：即使 stop 與 callback 在極短窗口交錯，也不會再把 focusPoint 寫回錯誤座標。

---

## 3. Fix B（最佳落地做法）

在 `LiveCameraSource.lockAEAF()` 的 `future.addListener { ... }`：

- 改成：
  - `val result = future.get()` 成功 → `resume(Result.success(Unit))`
  - **另外 log**：`result.isFocusSuccessful`（供品質追蹤/回歸分析）
- 僅在 `future.get()` throw 或 camera 未初始化等情況才 `Result.failure`

**效果**：UI/動畫的成功回饋與「lock action 是否套用」對齊，不再被 AF 收斂品質誤判。

---

## 4. Fix C（最佳落地做法）

在 `OpticalFlowConfig.DEFAULT`（不改架構、只動常數）：

- `redetectionInterval: 15 → 5`
  - 以目前 tracker throttle（預設 15 FPS）估算：由 ~1 秒補點 → ~333ms 補點
  - 目標：減少點集縮水導致的 RANSAC LOST
- `ransacDistanceThreshold: 0.5 → 1.0`
  - 讓 adaptive threshold 在非靜止場景更寬鬆，降低手持抖動被當 outlier 的機率

## 5. 風險評估（含緩解）

| Fix | 風險 | 機率 | 影響 | 緩解/監控 | 回滾 |
|---|---|---:|---:|---|---|
| A | stop OF 後 callback 仍寫回 focusPoint（race） | 低 | 中 | **callback gate**（lockPoint/isAEAFLocked/trackedPointActive）+ lockAEAF 內先 stop 再 update | revert commit |
| A | 停掉 OF 造成「使用者以為還在追蹤」 | 低 | 低 | lock UI 本來就是排他模式；state 清除 trackedPointLost/quality 讓指示器一致 | revert commit |
| B | 回傳 success 但畫面其實不清晰（AF 未收斂） | 中 | 中 | log `isFocusSuccessful`；必要時後續版本新增「收斂品質」次級提示（不擋動畫） | revert commit |
| B | 真正 lock 失敗卻被當成功 | 低 | 高 | 僅在 `future.get()` 正常才 success；exception 仍走 failure | revert commit |
| C | CPU 增加（補點頻率提高） | 低-中 | 中 | 用 `OpticalFlowTracker` 的 `elapsedMs` log 做 P95 觀察；必要時把 interval 調回 10 或做裝置分級 | 單獨 revert 常數 |
| C | 閾值變寬鬆導致跟錯點（漂移） | 低-中 | 中 | `maxTrackingDistance` + `minQuality` 仍會擋；先採 1.0（非更激進值） | 單獨 revert 常數 |

## 6. 驗證計畫（L3 前後都適用）

### 6.1 手機實測（Pixel 9a）

1. **點 A（OF tracking 進行中）→ 長按 B**
   - 預期：黃框留在 B，不再被拉回 A
2. **暗景/低對比長按任意點**
   - 預期：黃框 + 3-phase 動畫必定出現（不再被 `isFocusSuccessful=false` 擋掉）
3. **Optical Flow 追蹤連續 10 秒**
   - 預期：LOST 次數下降、quality 更穩；redetection log 出現頻率更高
