## What（什麼問題）

> **功能認知更正（2026-02-18）**：依據 Pixel 9a 實機測試，釐清對焦追蹤 vs. AE/AF Lock 功能定義。
> 參考：`docs/features/v2.11.2/Pixel9_Focus-tracking-lock-function-analysis.md`

### 症狀一：基本對焦追蹤定點失效（focusOnPoint / tap-to-track）

用戶點擊螢幕：
- 對焦圖示顯示正常
- Optical Flow tracking 跟隨定點無效（指示器不隨主體移動）
- 對焦成功：正常進行 3-phase 機械咬合動畫

**Pixel 9a 預期行為**：對焦框應「黏著」主體在畫面上移動，當前框停在 tap 點不動。

### 症狀二：鎖定對焦（AE/AF Lock）— 確認正常

用戶長按螢幕：
- 對焦圖示顯示正常（Yellow 靜態框，不追蹤）
- 此為 Pixel 9a 標準行為（Lock = 靜態固定，參數鎖死），無需修復

## Why（根因分析）

### 根因 1 — stale `focusOnPoint()` coroutine 競爭條件（主因，影響鎖定追蹤）

**嚴重程度**: 🔴 Critical

`focusOnPoint()` 和 `lockAEAF()` 均使用 `viewModelScope.launch {}` 獨立啟動，**沒有任何取消機制**。

#### 競爭條件時序（focusOnPoint 失敗路徑）

```
t=0ms    用戶 tap A → focusOnPoint() coroutine 啟動
t=0ms    cameraRepository.focusOnPoint() → CameraX 開始嘗試對焦
t=300ms  CameraX 對焦失敗（暗景/逆光）→ focusSuccess=false
t=300ms  focusOnPoint() 進入失敗路徑：delay(500) 啟動
t=500ms  用戶長按 B → lockAEAF() 啟動
t=500ms  atomic update: focusPoint=Pair(Bx,By), isFocusing=true

t=800ms  ← stale focusOnPoint() delay(500) 到期！
         _state.update { focusPoint=null, focusSuccess=null, ... }
         → FocusIndicator 從畫面移除

t=826ms  CameraX lock 回傳成功 → _state.update { focusSuccess=true, isAEAFLocked=true }
         但 focusPoint 仍為 null（lockAEAF 成功路徑未重設 focusPoint）
         → FocusIndicator 不在 composition → LaunchedEffect 不執行 → 無動畫
```

#### 競爭條件時序（focusOnPoint 成功路徑，focusIndicatorFading 干擾）

```
t=0ms    用戶 tap A → 對焦成功 → focusSuccess=true → delay(1000) 啟動
t=500ms  用戶長按 B → lockAEAF() atomic update: focusPoint=Pair(Bx,By)
t=826ms  lock 成功 → focusSuccess=true（LaunchedEffect key: null→true 變化正確）
t=1000ms stale focusOnPoint() delay(1000) 到期 →
         _state.update { focusIndicatorFading=true }  ← 影響 stroke width（非致命）
         delay(500) 啟動...
t=1500ms 再次無動作（成功路徑不清除 focusPoint）← 此路徑相對安全

★ 成功路徑較安全，失敗路徑是主要殺手
```

**結論**: `lockAEAF()` 的成功 update 必須重設 `focusPoint = Pair(x, y)`（即使 stale coroutine 清除了它），**且** 應取消 stale `focusOnPoint()` job。

---

### 根因 2 — 座標系失配：imageWidth/imageHeight 為橫向解析度（影響 ML Kit 追蹤）

**嚴重程度**: 🔴 Critical

**調查發現**:
- Pixel 9a 的 ImageAnalysis ImageProxy 解析度：`1280×720`（橫向）
- `SmartCameraAnalyzer` 直接使用 `imageProxy.width=1280`, `imageProxy.height=720`
- `CoordinateTransformer` 以這組 imageWidth=1280, imageHeight=720 進行座標換算

**但 Pixel 9a 是直立（Portrait）使用**！在 Portrait 模式下：

```
Portrait PreviewView：寬=1080px, 高=2340px（~9:19.5 比例）
ML Kit 分析圖像：1280×720（橫向），旋轉 90° 後為 720×1280（直立）

CoordinateTransformer.contentToImage() 計算：
  imageX = (contentX / contentWidth) * imageWidth
         = (540 / 1080) * 1280
         = 640px  ← 基於 1280（橫向寬），錯誤！

正確應為：
  imageX = (contentX / contentWidth) * 720  （旋轉後的直立寬）
         = (540 / 1080) * 720
         = 360px
```

`imageWidth` 和 `imageHeight` 對應的是 **旋轉前** 的 sensor 原始方向，需考慮 `detectionResult.rotationDegrees` 做維度交換（90°/270° 旋轉時 width↔height 互換）。

**實際影響**:
- `findTappedTarget()` 座標轉換錯誤 → 點擊位置在 image space 偏移 → ML Kit hit test 失敗
- 用戶點擊人臉，但 image space 的命中點偏移到 bbox 之外 → 回傳 null → 誤判為 OF tracking

---

### 根因 3 — previewWidth/previewHeight 兩個來源不一致（影響 OF tracking + 鎖定對焦）

**嚴重程度**: 🟡 Medium

調查發現 **兩個不同的 size callback**：

| 來源 | 觸發方式 | 對應的尺寸 |
|------|---------|----------|
| `previewSize` (CameraScreen) | `PreviewViewportContainer.onSizeChanged` | 全容器尺寸（含 letterbox 區域） |
| `previewWidth`/`previewHeight` (ViewModel) | `CameraPreview.onSizeChanged` | PreviewView 內部尺寸（實際預覽面） |
| `cameraRepository.setPreviewSize` | `CameraUiEvent.SetPreviewSize` | OF tracking 用的尺寸 |

**長按/點擊的 viewWidth, viewHeight** 來自 `previewSize`（全容器），但 `previewWidth`/`previewHeight` ViewModel 屬性來自 CameraPreview（可能不同）。

若這兩個尺寸不一致，`focusOnPoint(x, y, viewWidth, viewHeight)` 傳入的 viewWidth/viewHeight 與實際的 PreviewView 尺寸不符，CameraX MeteringPoint 正規化計算錯誤。

---

### 根因 4 — lockAEAF 成功 update 未重設 focusPoint

**嚴重程度**: 🔴 High（獨立于根因 1 存在）

`lockAEAF()` 的成功路徑：
```kotlin
// 成功路徑（line ~960）
_state.update {
    it.copy(
        isFocusing = false,
        focusSuccess = true,
        isAEAFLocked = true
        // ← focusPoint 未重設！
    )
}
```

若 stale coroutine 在成功 update 之前已清除 `focusPoint=null`，lock 成功後指示器仍消失。
即使沒有 stale coroutine，若 focusPoint 因其他原因為 null，鎖定成功後也不會顯示指示器。

**修正**: 成功路徑應補充 `focusPoint = Pair(x, y)` 確保恢復。

## 潛在風險

### 風險 1：coroutine cancel 在 ML Kit 追蹤模式中途取消

若 `focusOnPoint()` 已成功啟動 ML Kit tracking（設定了 `trackedObjectId`），在 `lockAEAF()` 中 cancel 這個 job 時，tracking coroutine 的中段狀態（`isFocusing=true`，`trackedObjectId` 已設）可能殘留。

**緩解**: `lockAEAF()` 的 atomic update 已清除 `trackedObjectId=null, trackedObjectType=null`，cancel 後的殘留狀態會被 atomic update 覆蓋。

### 風險 2：rotation-aware 維度修正影響前鏡頭

前鏡頭在 Portrait 模式下 rotationDegrees 可能為 270°（而非 90°），維度交換邏輯需對應。現有 `isFrontCamera` flag 僅處理 X 鏡像，未處理旋轉維度。

**緩解**: L2 中明確確認 Pixel 9a 前後鏡頭的 rotationDegrees 值。

### 風險 3：previewSize 統一後 OF tracking 座標改變

OF tracking 用的座標通過 `cameraRepository.setPreviewSize` 傳遞，若統一後尺寸不同，OF 的追蹤點對應位置改變。需實機重新驗證 OF 追蹤準確性。
