## 根因分析（Root Cause）

### 雙管線座標空間衝突

系統存在兩個並行的 OF tracking 路徑，使用**不同解析度**的圖像：

| 路徑 | 圖像來源 | 解析度（1:1 模式） | 頻率 |
|------|----------|-------------------|------|
| `SmartCameraAnalyzer.analyze()` | ImageProxy (CameraX 分析流) | **1920×1920** | 2 FPS (Pixel 9a 500ms 節流) |
| `trackFromBitmap(bitmap)` | `LiveCameraSource.getPreviewStream()` 的 preview bitmap | **≤800px（約 720×720）** | ~28 FPS |

**衝突點**：
1. `imageWidth/imageHeight = 1920×1920` 由 `analyze()` 路徑設定
2. Fix G 用 `CoordinateTransformer` 將 screen=(698, 1042) 轉換為 image=(1242, 848) → 在 1920×1920 空間正確 ✅
3. `trackFromBitmap()` 將此座標傳入 `OpticalFlowTracker.startTracking(Point(1242, 848), imageWidth=1920, imageHeight=1920)`
4. 但實際 bitmap 是 ~720×720 → `x=1242 > 720` **超出邊界** ❌
5. OpenCV LK 在超出邊界的位置尋找特徵點 → 失敗或追蹤到錯誤特徵

### 數學驗證

```
Preview bitmap (getPreviewStream): ~720×720
Analysis image (SmartCameraAnalyzer): 1920×1920

Scale factor: 720/1920 = 0.375

Correct bitmap-space starting point:
  bitmapX = 1242 × 0.375 = 465.8
  bitmapY = 848 × 0.375 = 318.0

Actual (wrong) starting point fed to tracker:
  bitmapX = 1242 (OUT OF BOUNDS for 720-wide bitmap!)
```

## 解決方向（Candidate Fixes）

### 方案 A：trackFromBitmap() 路徑做座標空間縮放（最小 diff）

在 `trackFromBitmap()` 中，當 `isPendingInImageCoords=true` 時，將 analysis image 座標縮放至 bitmap 空間：

```kotlin
// In trackFromBitmap(), when applying pending image-coords:
val bitmapScaleX = bitmap.width.toFloat() / imageWidth.toFloat()
val bitmapScaleY = bitmap.height.toFloat() / imageHeight.toFloat()
val bitmapX = pendingTrackX * bitmapScaleX
val bitmapY = pendingTrackY * bitmapScaleY
val imagePoint = Point(bitmapX.toDouble(), bitmapY.toDouble())
// Also update imageWidth/imageHeight to bitmap dimensions for this session
```

同樣地，OF callback 回傳的 bitmap-space 座標也需反向縮放回 analysis image 座標，再由 CoordinateTransformer 轉換至 screen。

**優點**：修改範圍最小
**缺點**：需要在多處維護縮放因子，容易有新的不一致

### 方案 B：OF tracking 只使用 analyze() 路徑（統一單一管線）

移除 `observePreviewForOpticalFlow()` → `trackFromBitmap()` 路徑，完全依賴 `analyze()` 路徑的 ImageProxy 做 OF tracking。

**問題**：analyze() 在 Pixel 9a 節流至 2 FPS → tracking 不流暢（每 500ms 才更新一次）

**需要解決**：為 OF tracking 新增獨立的低延遲 ImageProxy 管線（不受 ML Kit 節流影響）

### 方案 C：OF tracking 使用獨立 ImageAnalysis 流（推薦）

新增第三個 ImageAnalysis 流，專用於 Optical Flow tracking：
- 解析度：中等（例如 640×480 或 720×720）
- 節流：無（每幀處理，~28 FPS）
- 不做 ML Kit（減少 CPU 負擔）

**優點**：座標空間統一、頻率高、與 ML Kit 完全獨立
**缺點**：需要額外的 CameraX UseCase，增加複雜度
