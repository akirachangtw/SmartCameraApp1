## 2) 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）

1. **`OpticalFlowTracker` 實作假設**
   - startTracking / processFrame 使用的座標系是否假設「輸入 frame 的寬高」即為座標空間。
   - tracker callback 回傳的點/框是否也是「該 frame 空間」。
2. **preview bitmap 的幾何假設**
   - `LiveCameraSource.getPreviewStream()` 產出的 bitmap 是否：
     - 固定正向（已旋轉至顯示方向）？

     - 實際尺寸是否會隨 1:1 / 4:3 / 裝置而改變（<=800px 只是上限）。

   - `screen -> image` 的 image 是指哪個 source（ImageProxy 1920²？sensor crop？）。
   - 是否支援從「bitmap-space」轉回 screen（或需要新增 transformer path）。
4. **節流來源**
   - Pixel 9a 2 FPS 是否為 `SmartCameraAnalyzer` 內部節流（500ms gate）或 MLKit block/backpressure 造成。
5. **同時綁定多個 UseCase 可行性**
   - 現況已綁定的 use cases：Preview + ImageAnalysis(ML) + ImageCapture？  
   - CameraX 版本、目標裝置的 stream 組合限制（特別是 1:1 / 4:3 會不會透過 ViewPort 造成額外 crop）。

## 3) 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）

1. **CameraX UseCase 組合風險（方案 C）**
   - 追加一個 ImageAnalysis 可能導致：
     - bindToLifecycle 失敗（IllegalArgumentException / stream combination not supported）
     - 某些裝置 fallback 到低解析/低 FPS
2. **座標轉換與裁切（最常見回歸點）**
   - 1:1 模式多半不是 sensor 原生比例，通常有 crop；  
     若 start 點用縮放但忽略 crop offset，仍可能「看似在框內但追不到目標」。
3. **Thread / backpressure**
   - `trackFromBitmap()` 若在 UI thread 或與 preview bitmap 取得同 thread，可能造成 UI jank 或 frame drop。
   - 多分析流同時運作時，backpressure strategy（KEEP_ONLY_LATEST / BLOCK_PRODUCER）會直接影響延遲與 CPU。
4. **模式切換（Live/Static/Debug、1:1/4:3）**
   - pending tracking start 的狀態機：切換模式或重綁 camera 時，舊的 pending 座標可能套用到新尺寸。
5. **權限與生命週期**
   - 重綁 UseCase / 新增 analyzer 流時，需確保 CameraProvider 與 lifecycle state 一致，避免 resume 時黑屏或 analyzer 未啟動。

## 4) 最小差異建議（Minimal diff approach：步驟化）

### A+（止血版，最小可交付修正）
**目標**：不改變 pipeline 架構，只修正「雙解析度導致 start point 越界」並把縮放集中管理，降低後續擴散。

**步驟**
1. **在 `SmartCameraAnalyzer.trackFromBitmap(bitmap)` 內建立「本次 OF session 的 frameSpec」**
   - 定義 `ofFrameWidth = bitmap.width`、`ofFrameHeight = bitmap.height`
   - 明確：`OpticalFlowTracker.startTracking()` 的 width/height 一律用 `ofFrameWidth/Height`
2. **套用 pending start 時做一次性轉換**
   - 若 pending 是 image(analysis) coords（1920²），轉到 bitmap coords：
     - `bx = pendingX * bitmap.width / analysisImageWidth`
     - `by = pendingY * bitmap.height / analysisImageHeight`
   - 並 **clamp** 到 `[0, w-1] / [0, h-1]`，避免邊界 LK 崩潰或回傳空特徵。
3. **統一 callback 出口**
   - 若 UI overlay/Focus 框是走 analysis image coords 再轉 screen：
     - callback 回來的 bitmap coords 必須反向轉回 analysis coords（或直接改 UI 走 bitmap->screen 轉換，但先別在 L2 承諾，交給 repo 現況決定）。
4. **把縮放因子集中成工具函式（避免散落）**
   - e.g. `AnalysisToOfBitmapMapper` / `CoordSpaceMapper`
5. **加入 debug log（可在 debug build 打開）**
   - 每次 startTracking 印：
     - pending 原座標、轉換後座標、bitmap 寬高、analysis 寬高、是否 clamp
6. **防呆：當 bitmap size 與 analysis size 未初始化時**
   - 不啟動 OF 或延遲一幀（避免拿到 0 或 stale 尺寸）。

> 注意：若 1:1/4:3 之間存在 crop offset，而不是純縮放，A+ 仍可能有「追蹤點偏移但不越界」。因此 L2 要求 Claude Code 驗證 CoordinateTransformer 與 ViewPort/crop 行為（見第 5 節）。

### C（長期解，進 L3 前的 L2 查證方向）
1. 查 repo 的 CameraX 綁定：是否使用 `UseCaseGroup` + `ViewPort`。
2. 試做（或至少設計）新增 `ImageAnalysis`（OF 專用）：
   - resolution: 640x480 / 720p（依裝置能力）
   - backpressure: KEEP_ONLY_LATEST
   - output format: YUV + 直接轉灰階 Mat（減少 bitmap 轉換）
3. 座標系統改為：**Tap(screen) → 對應到 OF analysis frame space**（需要新的 transformer：screen<->ofFrame）
4. 若可行，再考慮移除 trackFromBitmap path。

## 7) 回滾與降風險策略（Rollback/Feature flag）

1. **Feature Flag（建議）**
   - `ofCoordSpaceFixEnabled`（remote config 或 build config）
   - 可快速切回舊行為（即使舊行為有 bug，也能在緊急時避免新回歸影響其他模組）

   - 先保留原本 analyze path / preview bitmap path，但 **只修正 preview bitmap path 的座標**；避免牽動 MLKit 節流與其他偵測功能。
3. **快速回滾點**
   - commit 拆成 2 個 atomic commits：
     - Commit 1：座標轉換（A+）+ log（可回滾）
     - Commit 2：清理/重構（若有，獨立可回滾）
4. **Fail-safe**
   - 若轉換後起始點仍不合理（例如 NaN、bitmap w/h=0、點在極邊緣），直接不啟動 OF，並回到一般對焦框，不要進入 tracking 狀態（避免 UI 鬼畜）。
