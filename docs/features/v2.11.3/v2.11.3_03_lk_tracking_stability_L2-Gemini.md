# Level 2 進階分析與可行方案｜v2.11.3 LK Tracking Stability (Gemini)

## 1. 深度架構分析：真正導致追蹤失敗的連鎖反應

文件 `v2.11.3-03_lk_tracking_stability_L1.md` 提到的現象是完全正確的，但透過審閱程式碼 `OpticalFlowTracker.kt`，我們發現了 `maxDistancePerFrame` 造成的「延遲 (Lag)」會如何在數幀之內徹底摧毀追蹤：

在 `OpticalFlowTracker.kt` 中，`trackedCenter` 同時身兼 **兩個職責**：
1. **傳送給 UI 的視覺框中心**：因此施加了 `clampVelocity` (限制每幀移動不超過 `maxDistancePerFrame`，目前為 25px) 來防止視覺抖動 (Jitter)。
2. **重新偵測特徵點 (Redetection) 的 ROI 中心**：每 5 幀觸發一次 `detectFeatures`，以 `trackedCenter` 為中心，半徑 80px 的方塊來找特徵點。

**🚨 嚴重衝突場景 (快速移動 ~100px/frame)**：
1. **第 1 幀**：實體移動 100px。LK 演算法正確算出位移。但 `clampVelocity` 強制把中心點限制為移動 25px。此時**中心點落後特徵群 75px**。
2. **第 2~4 幀**：實體繼續移動，每移動一幀，落後差距再拉大 75px。
3. **第 5 幀 (災難發生)**：觸發 `detectFeatures`，準備補充點位。此時中心點已經落後真實主體高達 **300px**。但是 `detectFeatures` 的 ROI 半徑只有 80px！
4. **結果**：追蹤器在落後的背景位置上尋找新特徵點，直接導致**追蹤框從主體滑落，並死死釘在錯誤的背景上**（俗稱的 Drift）。

這意味著，如果在 v2.11.3-03 僅執行「方案 A：降低 `minQuality = 0.2f`」，我們確實能讓框不立刻消失 (LOST)，但會變成**框滑落到背景並釘死**，對使用者的感受可能比「直接消失」更差（False Positive）。

---

## 2. 最佳可行解決方案 (Best Feasible Solutions)

考慮到 v2.11.3 的 Hotfix 性質，我們不能對核心架構進行大規模重構（例如分離「視覺中心」與「邏輯中心」），我們必須用修改常數的方式在「追蹤黏著度」和「防抖動」之間取得黃金平衡。

### 終極推薦方案 (v2.11.3-03 升級版)：雙參數平衡調整

修改 `OpticalFlowConfig.kt` 的兩個參數：
1. **`minQuality = 0.2f`** (同原計畫，容許 RANSAC Pass 2 的較低 Inlier Ratio 存活)。
2. **`maxDistancePerFrame = 60f`** (放寬速度限制，將 25f 提高至 60f)。

**背後邏輯**：
*   在 640px 下採樣空間中，60px 的移動相當於原始 1920px 畫面中的 180px 位移，足以應付絕大多數手機快速平移的場景。
*   放寬 `maxDistancePerFrame` 能大幅減少「中心點落後」的累積量，確保在第 5 幀需重新取樣時，真正的主體**依然落在半徑 80px 的 ROI 範圍內**，從而抓到正確的點，延續追蹤生命週期。

> **替代微調方案 (如果 60f 抖動感明顯)**：
> 可考慮修改每幾幀重新偵測的頻率 `redetectionInterval = 3` (從 5 變成 3)。讓中心點即使落後，也能在落差還不大時及早把點補在主體上。但會增加 CPU 負載，相較之下，放寬速度限制是更優雅的解法。

## 3. 進階風險評估 (針對升級版方案)

| 評估面向 | 風險及說明 | 緩解措施 (Mitigations) |
| :--- | :--- | :--- |
| **視覺抖動 (Jitter) 增加** | **中低**：將 clamp 距離放寬至 60px，當場景背景極度複雜且反差大時，若 RANSAC 抓偏了一點，框的跳動幅度會從最高 25px 變成 60px，在畫面上看起來會稍微「活潑」。 | 依賴平滑濾波：如果發現太抖，可以在後續的 UI 層 (`SmartCameraAnalyzer` 等處) 針對傳出座標做簡單的 EMA (指數移動平均) 平滑，而不要在 LK 底層閹割物理距離。 |
| **追蹤誤判 (False Positive)** | **低**：由於放寬了 clamping，框會緊密跟隨物體，而不再輕易落後滑脫到背景，實際上**降低了**鎖死背景的嚴重 False Positive 發生率。 | RANSAC Outlier 過濾依然作用中，能保證抓取的是同方向移動的最大聚類。 |
| **性能損耗** | **無**：僅調整上限常數，無增加計算量。 | 無須特別緩解。 |

## 4. 給團隊的下一步行動建議

1. **修改程式碼**：在 `OpticalFlowConfig.kt` 修改上述的 `minQuality` 與 `maxDistancePerFrame` 兩大參數。
2. **實機測試 (重點驗證)**：
   * 在 Pixel 9a 安裝後，將手機快速甩動。
   * **重點觀察**：追蹤框是否能牢牢跟隨主體，**有沒有出現追蹤綠框滑落到背景上的現象**。
3. **建立技術債 (針對 v2.12.0)**：在 Tracker 類中徹底分離 `visualCenter` 與 `logicCenter`。內部 LK 計算與 ROI 擷取永遠使用無限制的真實 Median Center (`logicCenter`)，只有對外輸出給 UI 時才透過 `clampVelocity` 限制平滑輸出 (`visualCenter`)。這是未來能兼顧「抗抖動」與「不掉框」的唯一治本架構。
