## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）

1. **CameraX UseCase 組合與 Stream 重新協商**
   - 1:1/4:3 切換可能觸發重新 bind use cases，導致 HAL 選擇不同 stream config（解析度/FPS range），若選到高解析度但低 FPS 的 config，Preview 會真的掉到 <20。
2. **ImageAnalysis 解析度/長寬比設定方式**
   - 使用 `setTargetResolution`、`setTargetAspectRatio`、`ResolutionSelector` 的不同組合，可能造成：
     - 選到非預期解析度（如 1920×1920）
     - 不同鏡頭（前/後）行為不一致
     - Android 15 / CameraX 版本下選擇策略改變
3. **Thread/Executor 優先序與主執行緒負載**
   - 若 bitmap convert / OpenCV / MLKit 有任何步驟跑在 Main thread（或搶占與 CameraX 同一 executor），可能影響 UI 合成與 preview 顯示。
4. **記憶體壓力與 GC 抖動**
   - 1920×1920 ARGB bitmap 約 14MB/張（粗估 1920*1920*4），若每幀建立 bitmap（尤其還縮圖、copy），會造成 GC 頻繁與掉幀。
5. **模式切換時資源釋放/重建**
   - 1:1 <-> 4:3 來回切，若舊 analyzer / MLKit detector 未正確 close，會疊加負載（長時間使用才掉幀）。
6. **裝置差異**
   - Pixel 9a 的前/後鏡頭可用 stream config 可能不同；若用硬編 model 判斷 throttle（方案 C），容易造成後續機型維護風險。

## 4. 最小差異建議（Minimal diff approach：步驟化）

> 原則：先「釐清 FPS」→ 再「只動最小一條管線」→ 最後才做策略性調整（解析度/節流/併發）。

### Step 0 — 先把「FPS 指標」釐清（只加 log/overlay，不改行為）
1. 在 `CameraScreen.kt`（或 FPS 計算處）新增 debug log，標註：
   - FPS 計算是基於 `Preview` 還是 `ImageAnalysis.analyze()` callback
   - 取樣的 timestamp 來源（SystemClock? frame timestamp?）
2. 在 `SmartCameraAnalyzer.analyze()` 與 Guideline pipeline 各自印：
   - callback 間隔（incoming rate）
   - 真正處理完成率（processed rate）
   - imageProxy size（w/h/format/rotation）

**交付物**：一眼能看出「UI FPS」= preview or analysis。

### Step 1 — 若確認掉的是「分析 FPS」（高機率）
優先走 **方案 A（Guideline 縮圖）**，因為它：
- 不動 CameraX stream config（降低相容性風險）
- 直接砍 OpenCV 計算量與 bitmap 成本
- 對使用者感知（構圖線）容錯較高

實作要點（最小 diff）：
- 縮圖用可重用 buffer / 避免每幀 allocate（否則 GC 反而更糟）
- 先做「縮到固定上限（e.g. 960）」即可，不必做複雜動態策略

### Step 2 — 若 MLKit 仍是主要瓶頸，再評估方案 B（ImageAnalysis cap）
- 只針對 **MLKit 的 analysis use case** 限制解析度（例如 1080×1080 或 960×960）
- Guideline pipeline 若是另一條 analysis stream，視情況也 cap，但要避免影響 preview stream negotiation（需確認 binding 方式）

### Step 3 — 若確認掉的是「PreviewView 真 FPS」
- 暫停把心力放在 OpenCV/MLKit，改查：
  - Preview UseCase 在 1:1 是否被迫拉到高解析度或特定 stream
  - 是否能用 `ResolutionSelector` 選到「較低解析度但高 FPS」的 preview stream
  - 是否能避免 1:1 透過「裁切」達成，而不是要求方形輸出流（避免 HAL 降 FPS）

### Step 4 — 節流（方案 C）與背景低優先序（方案 D）放最後
- 節流是「接受分析更慢」，不是讓 preview 更順（除非分析真的在拖 preview）
- 背景低優先序要小心：若跟 CameraX executor 搶資源或造成延遲堆積，可能引入更多時序 bug

## 7. 回滾與降風險策略（Rollback/Feature flag）

1. **Feature Flag / Debug 開關**
   - 將「1:1 guideline 縮圖上限」做成可配置常數或 remote config（最少用 build config / debug menu），便於 A/B：
     - `GUIDELINE_MAX_SIZE = 960`（可改 720/1080）
2. **保留原路徑**
   - 縮圖策略用 if 分支包住，必要時可一鍵關閉回到原始 1920 流程。
3. **分階段合併**
   - 第一個 commit 只做「FPS 定義釐清 + log/overlay 標示」
   - 第二個 commit 才做縮圖/降解析度
4. **裝置特例避免 hardcode**
   - 方案 C 若要做，優先用「解析度/處理耗時」動態決策，避免 `Build.MODEL == Pixel 9a` 這種維護成本高的分支（除非確定是單機型 HAL bug）。
5. **出現精度回歸時的快速處置**
   - MLKit 精度下降：提高 cap（1080→1440）或只對 guideline 縮圖、不降 MLKit 解析度
   - 線條偵測不足：只針對 guideline 用較大上限（960→1080），並保留 4:3 不變
