## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）

Claude Code 需在 repo 內「找證據」驗證下列假設，否則 phase plan 的 gate 無法精確定義：

1. **CameraX 架構現況**
   - 是否存在相機管理抽象層（例如 `CameraManager/CameraController/UseCaseBinder`），或目前散落在 Activity/Fragment。
   - Preview / ImageAnalysis / ImageCapture 是否同時存在、是否會在模式切換時 bind/unbind。
2. **模式切換設計現況**
   - Live/Static/Debug 的狀態切換是否有明確狀態機（enum + reducer / state holder），或只是 if/else。
   - 切換時是否重用同一個 Analyzer/Executor；是否有 stop signal、queue drain、unbinding completion callback。
3. **效能量測現況**
   - 是否已有每幀 latency、FPS、drop frame、memory 指標（或至少有可擴充的 logging scaffold）。
   - 是否已有 debug overlay / log tag 規範 / 既有 benchmark 機制。
4. **OpenCV module 實際使用程度**
   - `opencv/` 模組是否已被 app 依賴（Gradle 依賴關係）、是否有 JNI、是否已在 analyzer 中跑 Mat 轉換。
5. **實機問題證據**
   - 是否已有「模擬器正常、實機翻車」的 logcat/stacktrace（特別是 `CameraControl not available`、黑屏、analysis 停止）。
6. **Feature flag/回滾機制**
   - 是否已有 remote config / BuildConfig flag / runtime toggle（debug menu）可用來切換新舊 pipeline、降級策略。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）

請 Claude Code 特別針對下列高風險區塊做 repo 追蹤與風險標註（最好能指出「目前在哪裡做、做得是否一致」）：

1. **CameraX UseCase 綁定/解除與生命週期**
   - bind/unbind 是否可能在非主執行緒觸發、或與 `LifecycleOwner` 不一致。
   - `ProcessCameraProvider.getInstance()` 的取得與重用是否正確；是否因多次 init 造成競態。
   - 前後台、旋轉、Fragment replace 時是否會重複 bind，導致黑屏或 analysis 停止。
2. **CameraControl 可用性與時序**
   - `camera.cameraControl` 的使用是否有 gate（例如必須在 bind 成功後、且相機 state ready）。
   - 模式切換/重新 bind 後仍沿用舊 `Camera` 參考，容易出現 `CameraControl not available`（實機更常見）。
3. **Analyzer/Executor/threading 競態**
   - 切換模式時是否確實停止 analyzer（包含：停止送 frame、停止背景 executor、清空 pending frame）。
   - 若使用 `STRATEGY_KEEP_ONLY_LATEST`，是否仍可能在切換期間拿到舊 frame callback。
4. **影像格式轉換與記憶體壓力**
   - YUV→RGB、Bitmap↔Mat 轉換是否每幀 allocate（高 GC、p95 latency 飆升）。
   - OpenCV Mat 是否正確釋放/重用（避免 native memory leak）。
5. **權限/裝置差異**
   - 10/11/13/14 的權限/前景服務/相機使用限制差異。
   - 不同 SoC / HAL 在 session 重建、zoom/focus 行為差異（模擬器通常無法覆蓋）。
6. **工具鏈導入風險（流程本身）**
   - CRLF/LF 警告可能造成腳本/JSON 解析或 lint 差異；需確認團隊在 Windows 環境的 git 設定或 `.gitattributes` 是否要補。

## 4. 最小差異建議（Minimal diff approach：步驟化）

> 原則：先建立可觀測、可回滾、可在實機重現/驗證的「門檻」，再逐步收斂模式切換與效能；避免一次大改架構。

### Step 0｜先把 v2.8.0 phase plan 變成「可執行 gate」
- 在 `docs/plan/` 確認 SSOT 檔名與章節固定（例如維持 `v2.8.0_development_phase_plan_L1.md`，新增 L2 版或補章節）。
- 明確定義每個 Phase 的「必交付物」：文件、log 指標、測試腳本、feature flag、回滾方式。

### Step 1｜Phase 0：觀測/基準線（最小侵入）
- 在現有 analyzer pipeline **外圍**加 instrumentation：
  - end-to-end latency（從 `analyze()` 進入到結果輸出/overlay 更新）
  - FPS（analysis callback rate、preview rate 若可）
  - memory（Java heap / native heap / RSS 擇一落地）
- 只做 debug build 啟用（避免影響 release），並提供統一 log tag/格式，利於 logcat grep。

### Step 2｜Phase 1：模式切換穩定性（只改「順序與 gate」，不先重構演算法）
- 固化模式切換流程：**先停舊（stop analyzer + unbind）→ 再 bind 新 use case → 相機 ready 後才允許 CameraControl 操作**。
- 針對 `CameraControl not available`：加入狀態 gate（例如 camera 綁定完成/active 後才 setZoom / focus），並避免沿用舊 camera reference。
- 將「切換按鈕連點」納入 UI debouncing 或 state lock（最小 diff：短時間內忽略第二次切換，或排隊處理）。

### Step 3｜Phase 2：OpenCV/轉換效能（若 v2.8.0 真的包含）
- 先用 Phase 0 的量測找瓶頸，再做 micro-optimizations：
  - buffer/mat 重用、避免每幀 new
  - 降低解析度或降低分析頻率（中階機降級策略）
- 透過 feature flag 控制新路徑，確保隨時可切回舊 pipeline。

### Step 4｜Phase 3：收斂與發布準備
- 把 device tier 建議、降級策略、已知限制寫入 release notes 模板（可由 hybrid_flow PR level 產出）。
- 將「必測實機腳本」固定成 checklist（避免靠記憶）。
