## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX analyzer 綁定/清除時序（模式切換 + 重綁）**
   - Phase 1 已新增 stop()/mutex，但 Phase 2 若改由 ViewModel 直接驅動 setAnalyzer，容易出現：
     - switchCamera / bindToLifecycle 時 analyzer 還在跑
     - clearAnalyzer 與 image.close() 時機錯誤造成卡住或 dropped frames（或 analyzer thread 積壓）

2. **Thread / Executor 選擇**
   - 若 analyzer 改回吃 ImageProxy，OpenCV 計算仍重，必須確認 analyzer 使用的 executor：
     - 不能在 main thread 跑 OpenCV
     - 也不能開太多 thread 造成 contention
   - 需檢視 `imageAnalysis.setAnalyzer(executor, analyzer)` 的 executor 來源與重用策略。

3. **影像方向、裁切、座標系對齊（overlay 跑版風險）**
   - Bitmap path 常見會有「已旋轉成直立」的結果；ImageProxy Y plane 是 sensor 座標 + rotationDegrees metadata。  
   - 若 GuidelineAnalyzer 內的線段座標直接拿來畫 overlay，可能出現：
     - 旋轉 90/270 沒處理
     - 前鏡頭鏡像沒處理
     - cropRect/targetResolution 不一致

4. **效能回歸：移除 RGBA→Gray 但引入其他 copy**
   - ImageProxy.toGrayMat() 若做了額外 copy / Mat allocation 不可控，或每幀 allocate 大 Mat，仍可能吃掉收益。
   - 若 ViewModel 原本 sample(100ms) 使得分析頻率較低，改成 analyzer 每幀跑會直接炸 CPU（需明確節流）。

5. **相機權限/生命週期**
   - 若 analyzer 綁定在某些生命週期點（onStart/onResume）與 UI 切換耦合，可能在權限重新授權/Activity 重建時出現 analyzer 未重綁或重複綁定。

## 4. 最小差異建議（Minimal diff approach：步驟化）
以 **Plan A（最小差異但走正確 ImageProxy path）**為主，核心是：**不要新增 ImageProxy Flow，不改 CameraInputSource 抽象；只把 guideline 分析從「Bitmap pipeline」搬回「ImageAnalysis Analyzer callback」**。建議步驟：

### Step 0｜加 Feature Flag（先讓兩條路徑可並存）
- 在 ViewModel（或 DI config）加：
  - `useImageProxyGuidelinePipeline: Boolean`
- 預設先 `false`，確保可快速回退。

### Step 1｜建立「結果回傳通道」不依賴 ViewModel 餵影像
- 若目前是 `GuidelineAnalyzer.analyzeBitmap()` 直接回傳 result：  
  - 改為 `GuidelineAnalyzer` 內部提供 `val results: StateFlow<GuidelineAnalysisResult?>` 或 callback（minimal diff：callback 通常更小）
- ViewModel 負責 collect results → 更新 UI state（這段通常原本就存在，只是輸入來源不同）。

### Step 2｜ViewModel 在 Live mode 啟用/停用 guideline 時，改為 set/clear analyzer
- 啟用 guideline：
  - 呼叫 `liveCameraSource.setPreviewStreamAnalyzer(guidelineAnalyzer)`（或既有 API）
- 停用 guideline / 離開 Live mode：
  - 呼叫 `liveCameraSource.clearAnalyzer()` 或走既有 stopPreview/awaitClose 清理路徑
- 重要：避免 ViewModel 同時又 collect PreviewBitmap Flow 又 setAnalyzer（雙管線並行會更慢）

### Step 3｜在 GuidelineAnalyzer 內做「節流」以取代 sample(100ms)
- 因 analyzer callback 可能是每幀進來，建議在 `analyze(image)` 裡加 timestamp gate（minimal diff、效果確定）：
  - `if (now - lastAnalyzeTime < 100ms) { image.close(); return }`
- 維持與舊 pipeline 相同的更新頻率，避免 CPU 突增。

### Step 4｜方向/鏡像對齊：先做到「不退步」
- 先以「結果座標仍以 analyzer 輸出影像座標」為準，ViewModel/UI 端做 mapping（若現有就是這樣）
- 必要時在 analyzer 端讀 `image.imageInfo.rotationDegrees` 與 camera facing，確保輸出座標與 overlay mapping一致
- 最小策略：先只處理 rotationDegrees，mirror 若現有 overlay 已處理就不要重複處理。

### Step 5｜保留 Bitmap path 作為 rollback
- 舊的 `observePreviewForGuidelineAnalysis()` 保留，但被 flag 控制不啟用。
- 等實機 A/B 數據確認後，再刪除或降級成 debug-only。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **Feature Flag 雙路徑並存**
   - `useImageProxyGuidelinePipeline`
     - `false`：舊路徑 `PreviewBitmap Flow + analyzeBitmap()`
     - `true`：新路徑 `ImageAnalysis setAnalyzer + analyze(ImageProxy)`
   - flag 切換需在「重新進入 Live mode」時生效，避免中途切換造成 analyzer/flow 同時運作。

2. **嚴禁雙管線同時跑**
   - ViewModel 要保證同一時間只啟用一條：
     - bitmap flow collect job（取消）
     - imageAnalysis analyzer（clear）

3. **安全停止**
   - 沿用 Phase 1：在任何會觸發 unbind/rebind（switchCamera、stopPreview、awaitClose）前呼叫：
     - `(analyzer as? GuidelineAnalyzer)?.stop()`
   - 新路徑中若要重新啟用 guideline，**建議 new 一個新的 GuidelineAnalyzer instance**（避免 stop 後無法恢復的狀態殘留；除非你也做了 restart())。

4. **快速回退判準**
   - 任一情況立即關 flag 回退：
     - overlay 跑版（rotation/mirror 不一致）
     - camera switching crash / 黑畫面
     - latency 未改善（Avg 下降 < 10ms）或 FPS 明顯下降（< 28 或 drop rate > 1%）
     - memory 出現持續成長趨勢

5. **降風險實作順序**
   - 先做「結果回傳通道 + flag + analyzer 節流」→ 再做 ViewModel 切換資料源  
   - 這樣即使最後 setAnalyzer 綁定不穩，仍可回到舊路徑且保留 instrumentation 方便比對。
