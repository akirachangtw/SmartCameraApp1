# v2.8.0_CameraViewModel_Issue｜Level 1 規劃摘要

## 1. 目標（Goal）
- 釐清並修正 **Guideline 分析管線在 CameraViewModel 內仍走 Bitmap → Gray Mat 轉換**所造成的效能瓶頸。
- 在 **不破壞既有 CameraX 綁定/模式切換穩定性**前提下，規劃 Phase 2 的最佳落地方式：**優先最小差異（minimal diff）**，並保留可回滾路徑。
- 建立清楚的 A/B 驗證方式，確認是否能將 RGBA→Gray 的 25ms overhead 移除（或顯著降低）。

---

## 2. 背景與問題（Why / What）
### 現況觀察（已驗證）
- v2.7.0 之後，**GuidelineAnalyzer 本身的 analyze(ImageProxy) 已可直接用 `ImageProxy.toGrayMat()`**（直接取 Y plane），理論上不需要 Bitmap 中間層。
- 但在實際 app 的 Guideline 分析路徑中，**CameraViewModel 仍存在一條 PreviewBitmap Flow → analyzeBitmap(bitmap)** 的路徑：
  - `PreviewBitmap Flow (已轉好的 Bitmap)`
    → `sample(100ms)`
    → `GuidelineAnalyzer.analyzeBitmap(bitmap)`
    → `Bitmap.toGrayMat()`（RGBA→Gray）← 目前確認為主要瓶頸（~25ms）
    → OpenCV Canny + Hough
- 因此「L2 報告假設舊架構」的前提不成立：  
  - 不是「CameraViewModel 直接把 analyzer 給 CameraInputSource 後，整體都走 ImageProxy」。  
  - 真正的問題是：**同一個 GuidelineAnalyzer 雖然支援 ImageProxy，但目前 ViewModel 呼叫的是 bitmap 路徑**。

### 核心問題定義
- **同一功能（Guideline analysis）存在雙路徑：ImageProxy path 與 Bitmap path；目前主要執行的是 Bitmap path，導致不必要的顏色空間轉換與延遲。**
- Phase 2 原目標是「ImageProxy → Mat」，但實務上要解的是：**CameraViewModel 如何不要再餵 Bitmap 給 GuidelineAnalyzer**。

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線耦合風險**  
   - 若為了拿 ImageProxy 改動 CameraInputSource 介面，可能牽動 bind/unbind、ImageAnalysis 設定、背壓策略（STRATEGY_KEEP_ONLY_LATEST）等。
2. **模式切換 / 重綁定競態（race condition）風險**  
   - v2.8.0 Phase 1 已加入 `GuidelineAnalyzer.stop()` 與 `bindMutex`，Phase 2 若新增/改動 analyzer 綁定流程，可能再引入「camera switching 時 analyzer 還在跑」的問題。
3. **效能回歸風險（反而變慢）**  
   - 即使移除 `Bitmap.toGrayMat()`，若引入新的 copy/format conversion 或增加 Flow/Channel overhead，可能抵銷收益。
4. **影像方向/裁切一致性風險**  
   - Bitmap path 可能已套用 rotation 或 mirror（前鏡頭），改走 ImageProxy Y plane 需確保座標系與 overlay 對齊不跑版。
5. **驗證不足導致誤判**  
   - 只看 GuidelineAnalyzer 的 latency 不夠；需要同時看 FPS/drop frame/memory，避免把壓力轉移到別處。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異優先）：保留現有架構，但讓 ViewModel 改走 ImageProxy Analyzer（以「綁定 analyzer」取代「餵 bitmap」）
目標：**不新增 CameraInputSource Flow，不引入新資料流抽象**，直接利用 CameraX ImageAnalysis 的 analyzer callback。

做法概念：
- CameraViewModel 不再 `observePreviewForGuidelineAnalysis()` 取 PreviewBitmap Flow 來做 OpenCV。
- 改為：在進入 Live mode（或 guideline 功能啟用）時，把 `GuidelineAnalyzer`（ImageAnalysis.Analyzer）交給 LiveCameraSource / CameraInputSource 去 setAnalyzer。
- ViewModel 只訂閱 analyzer 的結果（例如 analyzer 內部透過 callback / StateFlow 發結果），而不是餵入影像。

優點：
- 最接近「CameraX 正常用法」，減少多餘的 Bitmap pipeline。
- 直接吃 ImageProxy Y plane，理論上可拿到 Phase 2 收益。

缺點/前置條件：
- 需要確認目前架構是否允許「Analyzer 產出結果 → ViewModel/Usecase」這種回傳通道（可能要補一個 callback/flow）。
- 仍可能需要小幅調整 CameraInputSource API（但可嘗試只用既有 setAnalyzer 能力）。

### Plan B（保守且低風險）：維持 PreviewBitmap Flow，但移除 RGBA→Gray 成本（減少轉換而非重構）
目標：在不大改管線前提下，**降低 `Bitmap.toGrayMat()` overhead**。

可能方向（視既有工具而定）：
- 若 PreviewBitmap 是從 ImageProxy 轉來的，嘗試在轉 Bitmap 時「同步保留灰階 Mat / 或保留 Y plane ByteArray」提供給 GuidelineAnalyzer。
- 或在 `analyzeBitmap()` 內做更低成本的灰階取得（但 Bitmap 本質仍是 RGBA，效益有限）。

優點：
- 不動 CameraX bind/analyzer 生命週期，模式切換風險較低。
- 工時可控。

缺點：
- 可能只能部分改善，無法完全達到「直接用 Y plane」的最佳路徑。
- 長期仍存在「多一份 Bitmap pipeline」的 CPU/memory 成本。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### 功能正確性
- Live mode 進入後：
  - guideline overlay 正常顯示、更新頻率正常（不閃爍、不延遲過大）
  - 前/後鏡頭切換後 overlay 不跑位（特別注意 mirror/rotation）
- 模式切換（Live ↔ Static ↔ Debug 若有）連續操作 30 次不崩潰、不黑畫面。

### 效能指標（A/B 對照）
- **GuidelineAnalyzer latency**
  - Avg、P95（同場景、同裝置、同 sample interval 100ms）
  - 目標：Avg 顯著下降（預期可吃到 ~10–20ms 級別改善，取決於目前 25ms RGBA→Gray 的占比）
- **FPS / Drop frame**
  - FPS 平均值、Std Dev、Drop rate
  - 目標：FPS ≥ 28（中階機）、Drop rate < 1%
- **Memory**
  - Total PSS avg/max、Native heap 行為（是否持續成長）
  - 目標：無持續成長（3 分鐘 growth < 10MB 或呈 GC 週期）

- 模擬器：僅做功能 smoke test（CameraX/效能通常不具代表性）。

## 7. 回滾策略（Rollback）
- 加入 **feature flag**（建議在 ViewModel 或 data/source 層切換）：
  - `useImageProxyGuidelinePipeline = true/false`
- 回滾路徑：
  - 任何實機出現 overlay 跑版、camera switching crash、latency 未改善或 FPS 下降時：
    - 立即切回 `PreviewBitmap Flow + analyzeBitmap()` 舊路徑
- 原則：確保兩條路徑可以並存一段時間，用 A/B log 驗證後再刪除舊路徑。
