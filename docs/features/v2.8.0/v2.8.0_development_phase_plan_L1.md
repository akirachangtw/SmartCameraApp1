## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線風險（CameraX UseCase/生命週期）**
   - UseCase bind/unbind 時機不一致導致黑屏、analysis 停止、或 `CameraControl not available`（尤其模式切換/切回前景/旋轉）
   - 不同裝置 Camera HAL 行為差異導致「僅實機發生」
2. **模式切換風險（Live/Static/Debug）**
   - 切換時若重用同一個 Analyzer/Executor，可能造成：
     - 舊 pipeline 尚未 stop，新的 pipeline 已啟動（競態）
     - Zoom/AF/AE 狀態不一致或控制對象失效
3. **效能回歸風險（FPS/Latency/熱節流）**
   - 加入 OpenCV 或轉換流程（YUV->RGB、Mat 建立/釋放）可能使：
     - 分析延遲上升、GC 頻繁、記憶體尖峰
     - 中階機掉幀嚴重、過熱降頻導致「跑一段時間才變慢」
4. **工具鏈/流程風險（workflow 自動化導入）**
   - critical files 若被誤刪/誤忽略，會破壞規劃輸出與 PR 產出的一致性
   - Windows CRLF/LF 轉換警告可能造成腳本或設定檔差異（例如 JSON/MD 風格、CI lint）
5. **整合回歸風險（多檔案/多模組變更）**
   - app + opencv + tools + docs 同時變更，若缺乏 phase gate（驗證門檻），容易出現「能 build 但 runtime 崩」或效能悄悄退化。

## 5. 建議方案（Plan A / Plan B：最小差異優先）

### Plan A（建議｜最小差異、以 phase gate 推進）
以「v2.8.0 phase plan」為主線，拆成可控的增量里程碑，每個里程碑都具備：
- 明確輸入/輸出（文件、指標、可回滾）
- 實機驗證最低門檻（至少 1 台中階 + 1 台旗艦/或既有基準機）

建議 v2.8.0 可先規劃以下 Phase（可在後續 L2 再細化）：
1. **Phase 0：基準線與觀測能力**
   - 建立（或統一）效能 log 格式：avg/p95 latency、FPS、memory（至少 debug build 可用）
   - 定義測試情境：啟動、切換模式、前後台、旋轉、連續運行 5~10 分鐘
2. **Phase 1：模式切換穩定性**
   - 固定「切換狀態機」與 CameraX bind/unbind 順序（避免競態）
   - 把 CameraControl 相關操作（zoom/focus/exposure）集中到「相機可用」的狀態點執行
3. **Phase 2：OpenCV/分析管線效能（若 v2.8.0 目標包含）**
   - 針對最重的步驟做 micro-optimizations（重用 buffer、避免多次轉換、減少 Mat 配置）
   - 為中階機設定安全降級策略（降低解析度/降低分析頻率/ROI）
4. **Phase 3：收斂與發布準備**
   - 文件化 device tier 建議與 feature flag/降級策略
   - PR/Release notes 產出一致化（用 hybrid_flow PR level）

### Plan B（保守｜若 v2.8.0 需求不確定或風險過高）
- v2.8.0 先只做「工具化 + 觀測 + 修 bug（不動 pipeline 大架構）」：
  - 固化 Hybrid workflow 文件與 tasks（確保不再破壞）
  - 僅針對已知實機問題做防護（例如 CameraControl 可用性檢查、重試、狀態 gate）
- 將高風險的 pipeline 重構/效能大改延後到 v2.9.0，避免時程爆炸與回歸。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### 基本功能驗證
- 模擬器：
  - 能啟動、切換模式（Live/Static/Debug）、不 crash（僅作為基本煙霧測試）
- 實機（必做）：
  - 至少 2 台：1 台旗艦（或主力測試機）、1 台中階（最容易暴露效能/相機差異）
  - 測試腳本：
    1) 冷啟動進 Live → 觀察 preview/analysis 是否正常  
    2) Live ↔ Static 來回切 10 次（含快速連點）  
    3) 前景→背景→前景（含螢幕關閉再開）  
    4) 連續運行 5~10 分鐘（觀察是否逐漸掉幀/過熱/卡頓）  

### 效能指標（建議最低門檻，後續 L2 可調整）
- 分析延遲（ImageAnalysis pipeline end-to-end）
  - 旗艦：avg < 100ms（或專案既有目標）
  - 中階：avg < 130~150ms（依目前基準）
- 穩定性：
  - 連續運行期間無明顯 memory leak（RSS/heap 不持續爬升）
  - 無「切換後 analysis 停止」或 preview freeze

## 7. 回滾策略（Rollback）
- **Feature Flag / 開關式回滾（優先）**
  - 對模式切換新流程、OpenCV 新最佳化、降級策略等，提供可在 build variant 或設定中關閉的 flag
- **保留舊路徑**
  - 新 pipeline 以旁路方式接入（可切回舊 analyzer/舊轉換流程）
- **原子提交（atomic commits）**
  - 每個 phase 的變更可獨立 revert，不把「觀測 + 功能改動 + 重構」混在同一 commit
- **文件回滾**
  - `docs/plan/` 內保留每次決策版本（不要覆寫同名內容、或在檔案中記錄變更摘要）
