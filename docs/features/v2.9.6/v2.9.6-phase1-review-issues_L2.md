## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
### A. CameraX 旋轉一致性（Preview / ImageAnalysis / ImageCapture）
- 高風險：同時使用多個 rotation 來源（OrientationEventListener、Display rotation、ImageProxy rotationDegrees、sensor orientation）導致 **雙重旋轉**。
- 影響：預覽方向、AI 推論輸入方向、overlay 座標映射、最終照片 EXIF/像素方向互相打架。

### B. MediaStore + ExifInterface 相容性
- 高風險：不同 Android 版本/廠牌對 `ExifInterface(FileDescriptor)` 或對 MediaStore Uri 的 `rw` 存取支援差異。
- 影響：寫 EXIF 失敗、照片 metadata 損毀、甚至照片打不開（低機率但需防）。

### C. Thread/I/O 阻塞
- 高風險：寫 EXIF 是額外 I/O，若跑在主緒或與拍照 UI 同 thread，可能造成卡頓。
- 影響：拍照延遲增加、UI jank、連拍失敗率上升。

### D. 模式切換與共用儲存流程（推測）
- 若 Live/Static/Debug dump 共用 `saveBitmapToMediaStore()`，加入 EXIF 寫入可能影響其他輸出（例如 debug 需要無 EXIF 或 PNG）。
- 若前鏡頭鏡像/裁切也在 transformBitmap 做，改旋轉容易導致 **鏡像+旋轉矩陣次序錯誤**。

### E. 權限/Scoped Storage（Android 10+）
- 需確認 insert MediaStore 時的 `IS_PENDING` 流程與 reopen 行為，避免寫 EXIF 時 Uri 已 finalize/權限不足。

## 4. 最小差異建議（Minimal diff approach：步驟化）
### 4.1 先處理 EXIF Orientation（Plan A，最小 diff）
1) **在 LiveCameraSource（或拍照觸發點）凍結「拍照當下 rotation」**
   - 當 user press shutter（或 save action）時，取一個單一真值：  
     - 優先：`imageCapture.targetRotation`（Surface ROTATION enum）  
     - 或：當下 `display.rotation`（若 targetRotation 已跟 display 連動）  
   - 以參數傳入 repository：`saveBitmapToMediaStore(bitmap, rotation: Int, isFrontCamera: Boolean?)`

2) **維持現有 bitmap.compress 寫檔**
   - 不動現有 pipeline，先確保功能不回歸。

3) **寫檔成功後補寫 EXIF Orientation**
   - 嘗試：`openFileDescriptor(uri, "rw")` → `ExifInterface(fd.fileDescriptor)` → setAttribute(TAG_ORIENTATION, …) → saveAttributes()
   - Orientation mapping：由 `Surface.ROTATION_*` 轉 EXIF 常用值（1/3/6/8）。  
     - 注意：EXIF 的 6/8 代表 CW/CCW 90；需明確定義 LandscapeLeft/Right 對應。
   - 若寫入失敗：log error 並不中斷主流程（照片仍要可用）。

4) **只對 JPEG 生效**
   - 若存在 PNG/WEBP 或其他 debug 格式，避免誤寫。

5) **加最小 log**
   - 成功：記錄 uri + orientation value  
   - 失敗：記錄 exception + openFD mode + 是否 pending

### 4.2 預覽旋轉（先定位，後修）
1) **先加 debug log（不改行為）**
   - 每次 frame / 每次 orientation change：輸出  
     - `display.rotation`  
     - `imageProxy.imageInfo.rotationDegrees`  
     - `imageCapture.targetRotation`  
     - `sensorOrientation`  
     - 是否 front camera  
   - 目的：找出「多轉」發生在哪一層。

2) **確認 transformBitmap 的責任**
   - 若 transformBitmap 的輸出同時用於：  
     - (a) 顯示預覽 + (b) AI 推論  
     則修正需非常保守，避免 AI/overlay 全部位移。

3) **優先策略**
   - 原則：**預覽由 CameraX PreviewView 處理旋轉**；Analyzer pipeline 只做「必要的」旋轉以滿足模型輸入（若模型要求固定方向）。  
   - 若現在 transformBitmap 已經把 frame 旋轉到「看起來正」，而 PreviewView 又旋轉一次，就會多轉。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1) **單點改動集中在 repository**
- 將 EXIF 寫入封裝成 `writeExifOrientation(uri, orientation)` 私有方法；失敗不影響主流程。

2) **加開關（可選但建議）**
- 以 BuildConfig / remote config / 本地 flag：`ENABLE_EXIF_ORIENTATION_WRITE`
- 方便遇到特定機型寫入失敗時快速關閉。

3) **失敗降級行為**
- 若 `openFileDescriptor(uri,"rw")` 失敗：
  - 降級：只保留 JPEG 無 EXIF（維持現狀但不中斷）
  - 並打 log（包含 uri、Android 版本、exception type）

4) **預覽旋轉修正獨立提交**
- 與 EXIF 分 PR 或至少分 commit；若 overlay/推論錯位可快速 revert 該 commit，不影響 EXIF 修復。

5) **避免破壞檔案**
- 寫 EXIF 前後不要再次 recompress bitmap（避免畫質與檔案大小變動）
- 僅改 metadata；若 ExifInterface 寫入後檔案大小/校驗異常，要能立即停用 flag 回滾。
