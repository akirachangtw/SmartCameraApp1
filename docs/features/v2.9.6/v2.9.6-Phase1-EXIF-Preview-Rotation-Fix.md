# v2.9.6 Phase 1 實作計畫 - EXIF Orientation 與預覽旋轉修復

## 執行摘要

本計畫解決 v2.9.6 Phase 1 測試中發現的兩個關鍵問題：
1. **照片缺少 EXIF Orientation** - 照片缺乏方向 metadata，導致在相簿中顯示錯誤
2. **預覽雙重旋轉** - 裝置橫向時預覽旋轉不正確（多轉 90°）

**策略**：分階段漸進式修復，最小程式碼變更，明確回滾路徑。

---

## 已驗證假設（來自程式碼探索）

### ✅ MediaStore 可重新開啟寫入 EXIF
- 現行流程：`insert()` → `openOutputStream()` → `bitmap.compress()` → 回傳 Uri
- 可透過 `openFileDescriptor(uri, "rw")` 重新開啟寫入 EXIF
- 所有操作已在 `Dispatchers.IO` 執行
- **缺少**：`androidx.exifinterface:exifinterface:1.3.7` 依賴

### ✅ 可在拍照時取得 rotation
- `currentRotation` 是 LiveCameraSource 的 class property（line 212）
- OrientationEventListener 正確更新 currentRotation（Surface.ROTATION_0/90/180/270）
- `takePicture()` 可存取 currentRotation
- **缺口**：rotation 值目前未從 LiveCameraSource 傳遞至 saveBitmapToMediaStore()

### ✅ 預覽雙重旋轉根本原因已定位
- **根本原因**：`transformBitmap()` 使用 `imageProxy.imageInfo.rotationDegrees`（已反映 CameraX 內部旋轉處理）
- Activity 鎖定為 Portrait 模式（AndroidManifest.xml line 44）
- 當 targetRotation 更新時，rotationDegrees 改變（90° → 180°），導致 transformBitmap() 過度旋轉
- UI 層無額外旋轉（已確認）

## Phase 1: EXIF Orientation 修復

### 解決方案：新增 `getCurrentRotation()` 介面方法

**採用此方案的理由**：
- 最小侵入性 - 不改變現有 `takePicture()` 回傳型別
- 架構一致性 - 遵循 CameraInputSource 抽象介面模式
- 可測試性 - StaticImageSource 可回傳固定值
- 向後相容

### EXIF 映射策略：根據 rotation 動態映射

```
Surface.ROTATION_0   → EXIF Orientation 1 (Normal)
Surface.ROTATION_90  → EXIF Orientation 6 (Rotate 90° CW)
Surface.ROTATION_180 → EXIF Orientation 3 (Rotate 180°)
Surface.ROTATION_270 → EXIF Orientation 8 (Rotate 90° CCW)
```

**為何不固定為 EXIF=1**：不同拍攝方向應有正確的 EXIF 值，以獲得更好的第三方應用程式相容性。

```kotlin
/**
 * Write EXIF Orientation to saved JPEG
 * v2.9.6 Phase 1: EXIF Orientation support
 */
private fun writeExifOrientation(uri: Uri, rotation: Int) {
    val exifOrientation = when (rotation) {
        Surface.ROTATION_0 -> ExifInterface.ORIENTATION_NORMAL      // 1
        Surface.ROTATION_90 -> ExifInterface.ORIENTATION_ROTATE_90  // 6
        Surface.ROTATION_180 -> ExifInterface.ORIENTATION_ROTATE_180 // 3
        Surface.ROTATION_270 -> ExifInterface.ORIENTATION_ROTATE_270 // 8
        else -> ExifInterface.ORIENTATION_NORMAL
    }

    Log.d(TAG, "Writing EXIF Orientation: rotation=$rotation → exif=$exifOrientation")

    context.contentResolver.openFileDescriptor(uri, "rw")?.use { pfd ->
        val exif = ExifInterface(pfd.fileDescriptor)
        exif.setAttribute(ExifInterface.TAG_ORIENTATION, exifOrientation.toString())
        exif.saveAttributes()
        Log.i(TAG, "EXIF Orientation written successfully: $exifOrientation")
    } ?: run {
        Log.e(TAG, "Failed to open FileDescriptor for EXIF writing")
        throw Exception("Cannot open file descriptor for URI: $uri")
    }
}
```

## Phase 2: 預覽旋轉修復

### 解決方案：補償旋轉 + 鎖定 ImageAnalysis targetRotation

**根本原因已確認**：當裝置旋轉時，`imageProxy.imageInfo.rotationDegrees` 改變（90° → 180°），導致 `transformBitmap()` 應用旋轉兩次。

### 實作步驟

#### 2.1 新增診斷 Log（不改變行為）

**檔案**：`app/src/main/java/com/akirachang/ai/photographer/data/source/camera/LiveCameraSource.kt`

在 line 288-294（transformBitmap 呼叫前）：
```kotlin
val rotationDegrees = imageProxy.imageInfo.rotationDegrees

// v2.9.6 Phase 1: Diagnostic log for preview rotation issue
if (frameCount % 30 == 0L) {
    Log.d(TAG, "[Rotation Debug] currentRotation=$currentRotation, " +
        "rotationDegrees=$rotationDegrees, " +
        "isFront=$isFrontCamera, " +
        "frame=${rawBuffer.bitmap.width}x${rawBuffer.bitmap.height}")
}

val isFrontCamera = cameraSelector == CameraSelector.DEFAULT_FRONT_CAMERA
```

#### 2.2 收集診斷數據（需實機測試）

**測試步驟**：
1. 啟動 App（Portrait）→ 觀察 log `currentRotation=0, rotationDegrees=90`
2. 旋轉至 Landscape Right → 觀察 log `currentRotation=3, rotationDegrees=?`
3. 檢查預覽是否過度旋轉

**預期發現**：rotationDegrees 變化與 currentRotation 不一致

#### 2.3 修正 transformBitmap 邏輯（視診斷結果而定）

**檔案**：`app/src/main/java/com/akirachang/ai/photographer/data/source/camera/LiveCameraSource.kt`

取代 line 288-300：
```kotlin

// v2.9.6 Phase 1: Fix preview rotation issue
// Problem: When ImageAnalysis targetRotation is ROTATION_0 (locked for portrait UI),
// but device physically rotates, rotationDegrees changes unexpectedly.
// Solution: Use fixed rotation based on sensor orientation
val compensatedRotation = 90  // Fixed baseline for portrait-locked UI

Log.d(TAG, "[Rotation Fix] original=$rotationDegrees, using fixed=$compensatedRotation")

val isFrontCamera = cameraSelector == CameraSelector.DEFAULT_FRONT_CAMERA

val startTransform = System.nanoTime()
val outputBuffer = if (compensatedRotation != 0 || isFrontCamera) {
    transformBitmap(rawBuffer, compensatedRotation, isFrontCamera)
} else {
    rawBuffer
}
```

**替代方案（若固定旋轉無效）**：
使用基於 currentRotation 偏移的補償公式 - 需根據診斷 log 決定。

## 風險緩解

### 風險 1：EXIF 寫入在某些裝置失敗
**機率**：低 | **影響**：中（照片可用但方向錯誤）

**緩解措施**：
- 降級處理：catch exception，記錄 log 但不中斷儲存
- 可選：新增 feature flag `buildConfigField("Boolean", "ENABLE_EXIF_ORIENTATION", "true")`
- 多裝置測試：Pixel 9a + Android 10-13 裝置

**回滾方案**：設定 feature flag 為 `false`（若已實作）

### 風險 2：預覽修復破壞 AI overlay 對齊
**機率**：中 | **影響**：高（AI 功能失效）

**緩解措施**：
- Phase 1 與 Phase 2 完全分離
- 步驟 2.1 診斷 log 是修復前的必要步驟
- 保持 ImageAnalysis targetRotation 固定為 ROTATION_0（已在 line 678）
- 小步驟增量變更，立即測試

**回滾方案**：回復步驟 2.3 的 commit，保留診斷 log 供進一步分析

### 風險 3：效能回歸
**機率**：低 | **影響**：低

**緩解措施**：
- EXIF 寫入在 IO dispatcher 執行（已滿足）
- FileDescriptor 寫入速度快（< 10ms）
- 監控拍照延遲 < 500ms

## 可行性分析 (Feasibility Analysis)

### 整體可行性評估：高

本計畫採用標準 Android API (`ExifInterface`) 與 CameraX 官方建議作法（TargetRotation 控制），技術風險低，預期成效明確。

### 1. EXIF Orientation 修復 (Phase 1)
*   **技術可行性**: **高**
    *   `ExifInterface` 是 Android 處理 JPEG Metadata 的標準函式庫，相容性極佳（支援至 Android 5.0+）。
    *   在 `saveBitmapToMediaStore` 寫入 JPEG 後，透過 `contentResolver.openFileDescriptor` 重新開啟檔案進行 EXIF 編輯，是處理 Scoped Storage 的標準流程之一。由於我們剛寫入該檔案，擁有寫入權限，因此操作受阻機率極低。
    *   `Dispatchers.IO` 的使用確保了主執行緒不會被 I/O 操作阻塞。
    *   `getCurrentRotation` 的介面擴展模式符合現有的抽象層設計 (`CameraInputSource`)，不會破壞既有的依賴注入架構。

*   **潛在風險與應對**:
    *   **檔案鎖定 (File Lock)**: 極少數 OEM 裝置可能在寫入後立即鎖定檔案進行媒體掃描。應對：`try-catch` 包裹，若 EXIF 寫入失敗僅記錄 Log，不影響照片存檔成功與否（優雅降級）。
    *   **效能開銷**: 重新開啟檔案與寫入 EXIF 需極短時間（< 50ms），對使用者體驗（拍照卡頓）影響微乎其微。

### 2. 預覽旋轉修復 (Phase 2)
*   **技術可行性**: **中高**
    *   問題核心在於「UI 鎖定 Portrait」與「CameraX 自動旋轉補償」之間的衝突。
    *   解決方案的核心——鎖定 `ImageAnalysis.targetRotation` 為 `ROTATION_0`——強迫 CameraX 輸出的座標系與 UI 保持一致，這在邏輯上是完全正確的解決方向。
    *   `transformBitmap` 原本就是為了處理 Bitmap 轉正而存在，一旦輸入源（CameraX）的座標系固定，`transformBitmap` 的行為將變得可預測且穩定。

*   **潛在風險與應對**:
    *   **AI 座標系錯位**: 修改 `ImageAnalysis` 的旋轉可能會影響到依賴此串流的 `FaceDetector` 或 `ObjectDetector`。如果這些偵測器預期的是「已旋轉」的影像，我們可能需要同步調整偵測結果的座標映射。
        *   **應對**: Phase 2 強調「診斷優先」，先觀察 Log 確認數值變化，再實施修復。若發現 AI 框線錯位，需在 `SmartCameraAnalyzer` 中同步調整座標矩陣。
    *   **前鏡頭鏡像**: 前鏡頭的旋轉邏輯通常比後鏡頭複雜（涉及鏡像）。
        *   **應對**: 測試案例已包含前鏡頭測試，且 `transformBitmap` 已保留鏡像邏輯參數。

### 結論
此計畫技術上穩健，風險可控。建議優先執行 Phase 1 以解決最迫切的存檔問題，Phase 2 則在收集足夠診斷數據後實施，以確保 AI 功能不受影響。
