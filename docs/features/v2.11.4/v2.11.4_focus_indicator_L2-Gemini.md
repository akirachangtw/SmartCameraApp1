## 1. Bug 1: 有人臉時不會自動出現對焦框 (Saliency Score 座標系異常)

### 分析
L1 發現 `calculateSaliencyScore` 中混用了 ML Kit 回傳的影像原始座標 (Image Coordinates) 與螢幕座標 (Screen View Coordinates)，導致計算出的人臉比例 (Saliency Score) 極低，永遠達不到觸發閾值 (50)。

### 最佳可行方案 (Best Solution)
不能單純傳入 `detectionResult.imageWidth/Height`，因為裝置旋轉時，感光元件原始寬高 (640x480) 與實際預覽寬高比例可能顛倒。
- **作法**：應統一在**正規化後且已考慮旋轉 (Rotation) 的影像座標系**中計算面積。
- **具體實作**：
  建議直接從已考慮旋轉的 `CoordinateTransformer` (或 equivalent parameters) 取得 `effectiveImageWidth` 與 `effectiveImageHeight`。
  ```kotlin
  // 在計算 Score 前，確保寬高已根據 rotationDegrees 對調
  val effectiveWidth = if (rotationDegrees == 90 || rotationDegrees == 270) imageHeight else imageWidth
  val effectiveHeight = if (rotationDegrees == 90 || rotationDegrees == 270) imageWidth else imageHeight
  
  val score = calculateSaliencyScore(
      face.boundingBox, 
      true, 
      effectiveWidth, 
      effectiveHeight
  )
  ```
  在 `calculateSaliencyScore` 中以此為基準計算面積與中心點偏移，這樣能正確得出 ~75 的 Score。

### 風險評估 (Risk)
- **風險等級：低 (Low)。**
- Saliency Score 僅決定是否觸發「智能對焦 (Smart AF)」。如果參數計算錯誤最多只是如 Bug 1 導致不觸發，不至於造成閃退 (Crash)。只要確保分母 (effectiveWidth * effectiveHeight) 不為 0 即可。

## 2. Bug 2: 對焦框偶爾出現在錯誤位置 (TOCTOU Race Condition)

### 分析
`updateTrackedObjectPosition()` 執行在背景 (Background Thread)，當它準備更新 UI 狀態時，主執行緒 (Main Thread) 的「點擊對焦」可能已經先清空並更改了 `focusPoint`。背景更新隨後覆蓋了正確的點擊位置。

### 最佳可行方案 (Best Solution)
L1 提出的 StateFlow `update` 內 Atomic 檢查是正確且完美的防禦方式。
- **具體實作**：
  在 lambda 內直接比對目前的 `trackedObjectId` 是否仍是當初背景任務啟動時追蹤的 ID。如果已被清空 (null) 或是換成別的目標，則放棄更新。
  ```kotlin
  _state.update { current ->
      if (current.trackedObjectId != trackedId) {
          // 目標已改變或用戶手動點擊 (trackedObjectId 變為 null)，放棄更新
          return@update current
      }
      current.copy(focusPoint = Pair(screenX, screenY))
  }
  ```
- **額外補強**：如果還有其他非追蹤的 Auto-Focus 路徑也寫入 `focusPoint`，請確信所有 `_state.update` 均將「是否被用戶 Interrupt」的邏輯包含在內（優先權：手動點擊 > ML追蹤 > 被動偵測）。

### 風險評估 (Risk)
- **風險等級：低 (Low)。**
- Kotlin 的 `StateFlow.update` 保證原子性 (Atomicity)。在 update 內部檢查變數可有效解決 Race Condition，不會產生 Deadlock 且幾乎無效能損失。

## 3. Issue 3: 對焦框跟隨速度過慢 (Spring Animation Stiffness)

### 分析
v2.11.4 為了讓追蹤看起來有「平滑跟隨」的效果，將動畫從 `StiffnessHigh` 改成了 `StiffnessMedium`，結果延遲感過重，導致 UX 不佳。

### 最佳可行方案 (Best Solution)
- **作法**：恢復回較快的動畫反應，或者針對不同情境使用不同 AnimationSpec。
- **具體實作**：
  建議採用 L1 提到的 **Option A**：改回 `StiffnessHigh`。雖然 ML Kit 的 bbox 會有些微跳動，但使用者對「準確度」的主觀直覺高度依賴於「無延遲」。
  ```kotlin
  spring(dampingRatio = Spring.DampingRatioNoBouncy, stiffness = Spring.StiffnessHigh)
  ```
  *進階方案 (視後續迭代而定)*：若真的很在意跳動，可以對 ML Kit 收到的座標先過濾 (如：Kalman Filter / Exponential Moving Average)，UI 套用 `tween(50-80)`。但目前直接改回 `StiffnessHigh` 是最簡單有效的方案。

### 風險評估 (Risk)
- **風險等級：極低 (Minimal)。**
- 純粹為 UI 呈現層修改，完全不影響相機底層或對焦硬體邏輯。

## 4. Issue 4: EXIF 缺少曝光資訊 (ISO, 快門, 光圈)

### 分析
使用 `Bitmap.compress(JPEG)` 的儲存方式，會捨去來自 Camera HAL 的硬體 EXIF 資料。目前的寫入方法僅能補上軟體面的 TAG (如 Make, Model, DateTime)。

### 最佳可行方案 (Best Solution)
目前的架構（Bitmap 操作）**無法取得**硬體曝光參數，除非導入 `Camera2Interop` 從 `TotalCaptureResult` 中抽取出資訊再補寫入 API。
- **短期作法**：維持 v2.11.4 的實作，確保系統能正常寫入 Make、Model 與拍攝時間，以保證基礎照片排序正常運作。
- **長期作法**：
  推進 Roadmap 至 v2.12.0，從 CameraX 的 `ImageCapture.OnImageSavedCallback` (ImageProxy) 取得完整 EXIF，或是透過 Interop 取出 SENSOR_SENSITIVITY (ISO)、SENSOR_EXPOSURE_TIME 等參數，寫入 `ExifInterface` 屬性中。

### 風險評估 (Risk)
- **風險等級：無直接風險 (Known Limitation)。**
- 需要與核心開發者或使用者溝通這是底層實作路徑所致的暫時限制。不應在目前 v2.11.4 版本強行 Workaround (例如硬寫假數值或預估值)。

## 5. Issue 5: Auto Focus Throttle 驗證方法

### 分析
`AUTO_FOCUS_THROTTLE_MS = 2000ms` 防止過度頻繁觸發對焦。需要確保機制生效。

### 最佳可行方案 (Best Solution)
除了 L1 中提到的 Logcat 手動驗證，可在 ViewModel 層次撰寫簡單的 Unit Test。
- **Unit Test 概念**：
  連續推播三次大於 Threshold 面積的 Face Result（時間間隔 100ms），驗證 `cameraController.startFocusAndMetering()` 是否被 mock 且僅被呼叫 1 次。
- **實務驗證**：Logcat grep `Smart Subject Focus` 確認時間差。此為標準且有效的手動測試方法。

### 風險評估 (Risk)
- **風險等級：低 (Low)。**
- Throttle 若失效，影響的是對焦馬達反覆作動及耗電；Throttle 間距若太長 (例如 >5s)，則對於動態場景的適應力會變差。2000ms 是一個合理且標準的經驗值。

## 總結與執行建議 (Conclusion)

綜合評估後，**v2.11.4-01 迭代的修正方向可行且風險極低**。最大的變因在於**座標系轉換**的對應正確性。

1. **強烈建議**在修正 Bug 1 時，使用 `CoordinateTransformer` 取代的單純硬派入 `viewWidth` / `imageWidth`，確保即使轉向或各種 Crop Ratio 下計算都能保持一致。
2. Bug 2 的 StateFlow `update` 原子檢查是完美且必要的 Kotlin 最佳實踐，請直接合併進入核心代碼。
3. 動畫跟隨恢復 `StiffnessHigh` 作為 UX 補救方案優先執行。
