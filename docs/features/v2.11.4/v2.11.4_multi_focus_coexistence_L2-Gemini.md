**Date**: 2026-02-22

本文件基於對 `v2.11.4_multi_focus_coexistence_L1.md` 的深入解讀，針對自適應對焦框 (Adaptive Frame Size)、多點對焦顯示 (Multi-Focus Display)、防跳動 (Anti-Flicker) 以及實體 AE 鎖定 (AE Lock) 提出架構建議、最佳實踐方案 (Best Practices) 與風險評估 (Risk Assessment)。

## 1. Feature A: Adaptive Frame Size (對焦框自適應縮放)

### 分析
目前固定尺寸 (80.dp) 無法反映現實中被攝物體（如不同距離的人臉或不同大小的物件）的實體範圍。

### 最佳可行方案 (Best Solution)
- **架構銜接**：在 `updateTrackedObjectPosition` 中除了取出中心點，應一併取出 `boundingBox`。需要經過 `CoordinateTransformer` 由 Image 座標系轉換為 Screen 座標系，再更新至 UI State。
- **UI 渲染處理**：
  在 Compose 中，使用計算後的寬高繪製框，並嚴格加上尺寸約束 (Clamp)，防止偵測到極小或極大（佔滿螢幕）的意外 Bounding box 導致畫面突兀。
- **閾值設計**：L1 提及小於 40dp 忽略是一個極佳的防呆設計（40dp 也是 Material Design 推薦的最小觸控面積邊界）。最大值可限制為螢幕短邊的 80% (例如 120dp / 200dp 視設備而定)。

### 風險評估 (Risk)
- **風險等級：低 (Low)。**
- 純 UI 層改變與 State 單向流動，且不涉及 CameraX 的 metering 測光控制。確保 `CoordinateTransformer` 轉換 BBox 矩形時不要產生 out of bounds 錯誤即可。

## 2. Feature B: Multi-Focus Display (多對焦框共存)

### 分析
相機底層 HAL 本質上只吃一組 / 主要範圍的 metering point。因此多框共存純粹是「視覺 UI 層的呈現」，讓使用者知道「AI 有抓到這些臉」，但曝光/對焦仍以 Primary (通常是最高分或 User Tap) 為主。

### 最佳可行方案 (Best Solution)
- **資料模型重構 (Breaking Change)**：
  放棄單一 `focusPoint`，改用 `focusTargets: List<FocusTarget>`。這符合所有現代相機框架的走向。
- **權限與階級 (Hierarchy)**：
  `FocusTarget` 必須明確定義 `isPrimary` 屬性。
  唯一的 `isPrimary = true` 才允許送給 `CameraController.startFocusAndMetering`。
  其餘 (Secondary) 則在 UI 繪製為細框/半透明。
- **效能考量**：在 `autoFocusOnSalientTarget()` 當中如果一次湧入 10 張臉，只過濾出 Saliency Score 前 5 名轉換成 `FocusTarget` 即可。

### 風險評估 (Risk)
- **風險等級：中偏高 (Medium-High)。**
- 重大架構改動。所有原本存取 `_state.value.focusPoint` 的地方（包含 Optical Flow，Tap-to-focus，Cancel 邏輯）都需要遷移。
- **專案管理建議**：此項強烈建議遵循 L1 提到的**獨立分支或排至 v2.12.0**，以避免在 v2.11.4 的修補迭代中引入大量回歸問題 (Regression)。

## 3. Feature C: Anti-Flicker (防止對焦框跳動)

### 分析
框跳動的本質是使用者點擊 (Manual Tap) 與機器學習自動偵測 (Auto-Focus) 互搶同一個單點變數 `focusPoint`。

### 最佳可行方案 (Best Solution)
建立在 Feature B (多框共存) 的基礎上。
- **優先級覆蓋 (Override)**：
  當 `FocusTargetType == USER_TAP` 存在時，即使 ML Kit 傳來極高分的 Face Target，其 `isPrimary` 也會被強制降級為 `false`。
- **TTL (Time to Live)**：
  User Tap 應具備生命週期 (如 L1 建議的 5 秒)。使用者點擊五秒後，如果沒有再度互動或鎖定，系統自動將 `USER_TAP` 降級清空，主控權交還回 Auto-Focus 流程。

### 風險評估 (Risk)
- **風險等級：低 (Low)**（前提是 Feature B 已穩定實作）。
- 此為針對 State 的業務邏輯判斷，不會干涉到底層硬體機制。

## 4. Feature D: AE Lock 真實鎖定 (Camera2 Interop)

### 分析
`Controller.startFocusAndMetering` 裡頭的 `FLAG_AE` 意思是「告訴相機用哪裡來測光」，並不代表「鎖定當前光圈快門組合」。導致平移相機時曝光參數仍會自動漂移。

### 最佳可行方案 (Best Solution)
- **介入 Camera2Interop**：
  這是取得專業相機行為的唯一解。如 L1 規劃，於 `lockAEAF` 成功時，透過 `Camera2CameraControl` 注入 `CaptureRequest.CONTROL_AE_LOCK = true`。
- **AF 狀態維護**：
  根據實作經驗，`CONTROL_AE_LOCK` 是非常有效的，但需確保 `cancelFocusAndMetering` 執行時有呼叫 `clearCaptureRequestOptions()` 將狀態退回 HAL 預設。
- **實作建議**：
  這段邏輯可獨立包裝於 `LiveCameraSource.kt`，不用修改 UI 層。

### 風險評估 (Risk)
- **風險等級：低 (Low)。**
- 由於此功能完全封裝在底層 Source 中，且只有在使用 AE/AF Lock 長按時才會觸發，對一般自動拍照的 Regression 風險極小。非常適合在 v2.11.4 迭代中優先處理。

## 總結與 Roadmap 執行建議

根據業務需求複雜度與風險，強烈建議採納 L1 Plan 的分軌並行策略：

1. **優先執行 [v2.11.4-02] Feature D (AE Lock)**：
   因實作成本最低 (~6 行程式碼)，且解決了專業功能的核心問題。
2. **接續執行 [v2.11.4-03] Feature A (Adaptive Frame Size)**：
   只需單點修改 UI 與傳值，使單一框能縮放，增進 UX，為安全改動。
3. **戰略延後 Feature B & C (Multi-Focus)**：
   將 List 型態的 `focusTargets` 以及複雜的多點控制優先排入 **v2.12.0** 規劃中。這是涉及 ViewModel State 的 Breaking Change，在 v2.11 穩定版迭代中硬上容易導致難以追蹤的狀態衝突 (Race Condition) 與 Regression。
