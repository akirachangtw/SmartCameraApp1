# v2.11.4-06 Pinpoint FPS Bottleneck（L1：根因歸納與策略解法）

## 診斷摘要（來自 L0）

Traycer 的診斷指向：`LiveCameraSource.bindToLifecycle()` 內將同一個 `commonSelector` 同時套用到三個 UseCase（`Preview` / `ImageAnalysis` / `ImageCapture`）。在 **1:1** 模式下，`ResolutionFilter` 會挑選「最接近 **1920×1920**」的方形解析度，導致每幀 `ImageAnalysis` 收到約 **3.7MP** 的 `ImageProxy`；而 **4:3 / 16:9** 模式走 `AspectRatioStrategy`，CameraX 實際解析度約落在 **480×360（~0.17MP）** 等級。像素量級差異約 **~21×**，直接放大每幀的：

- YUV 轉換成本（YUV conversion）
- `transformBitmap()` 幾何/縮放轉換成本（bitmap transform）
- ML Kit / 其他模型推論成本（ML inference）

結論：FPS drop 在 1:1 模式並非「單一元件異常」，而是 **解析度選擇策略把分析管線推到高像素負載**，造成整條分析鏈路的每幀成本倍增。

---

## 最可能的問題根源（Probable Root Causes）

1. **分析用解析度選錯（Root cause #1 / Primary）**  
   1:1 模式把 `ImageAnalysis` 鎖到接近 1920×1920 的高解析度，導致每幀處理量暴增（~21× pixels）。

2. **UseCase 共用 selector，缺乏「畫質」與「分析成本」的分流（Root cause #2）**  
   `Preview`/`ImageCapture`（需要高畫質）與 `ImageAnalysis`（需要低延遲/高吞吐）採用同一選擇器，造成分析被迫跟著高畫質走。

3. **分析管線成本與像素線性相關，且包含多段重處理（Root cause #3）**  
   YUV→RGB、bitmap transform、ML 推論都會隨像素上升而近似線性（甚至超線性）增加；當解析度暴增，整體延遲與背壓（backpressure）會快速累積，導致掉幀/卡頓。

4. **既有「device optimal resolution」資訊未真正影響 selector（Root cause #4 / Config gap）**  
   `selectDeviceOptimalResolution()` 的結果僅用於日誌/診斷，沒有進入 `ResolutionSelector` 決策，使得配置意圖（target resolution）與實際分析輸入脫節。

---

## 策略性解決方案（3–5）

### 方案 1：分析用解析度分流（Preview/Capture 高解析度；Analysis 低解析度）

1. **Probable Cause Addressed**：#1、#2（1:1 分析解析度被拉到 1920×1920；selector 共用）。  
2. **Solution Category**：Graphics Pipeline Optimization / Engine Configuration（CameraX ResolutionSelector 分工）。  
3. **Expected Outcome**：把 1:1 的 `ImageAnalysis` 輸入降到最小可用方形（例如 480×480 或 720×720），使每幀像素處理量回落到與 4:3/16:9 相近等級，FPS 恢復到接近其它比例模式的水準。

高層策略要點：
- 為 `ImageAnalysis` 建立獨立 `analysisResolutionSelector`；1:1 時選「最小可用方形、且 ≥ 某門檻（例如 480px）」。
- `Preview` + `ImageCapture` 維持高解析度 selector，以保留 WYSIWYG 與輸出品質。
- `ViewPort` 維持 `Rational(1,1)`，用裁切一致性來對齊三個 UseCase 的視覺區域。

### 方案 2：在分析端做「輸入降採樣 / ROI 裁切」，將 ML 與轉換固定在小尺寸

1. **Probable Cause Addressed**：#3（多段 per-pixel 成本被高解析度放大）。  
2. **Solution Category**：Resource Management / ML Pipeline Optimization。  
3. **Expected Outcome**：即使某些機型/情境仍回傳較大 `ImageProxy`，也能把後續的 `transformBitmap()`、RGB 轉換與 ML 推論控制在固定的小輸入尺寸（例如 320–640 邊長），穩定降低 CPU/GPU 負載與延遲。

高層策略要點：
- 優先把 pipeline 變成「直接輸出到模型需要的輸入尺寸」，避免先做大圖轉換再縮小。
- 若模型只關心中央區域或特定 ViewPort 區，先做 ROI 裁切再縮放到模型輸入。

### 方案 3：加入分析吞吐控制（Backpressure/Frame Skipping/Adaptive FPS）

1. **Probable Cause Addressed**：#3（延遲堆積造成掉幀；分析跟不上相機幀率）。  
2. **Solution Category**：Resource Management / Engine Configuration。  
3. **Expected Outcome**：當分析耗時 > frame interval 時，透過「只保留最新幀」（keep-latest）或自適應跳幀，避免隊列累積造成 UI 卡頓與整體 FPS 下降，體感流暢度提升。

高層策略要點：
- 在 `ImageAnalysis` 使用合適的 backpressure 策略與 queue depth（以「最新幀」優先的互動體驗）。
- 依據最近 N 幀平均分析耗時動態調整分析頻率（例如只分析每 2/3/4 幀）。

### 方案 4：優化像素轉換與旋轉/縮放路徑（避免不必要的 bitmap work）

1. **Probable Cause Addressed**：#3（YUV 轉換 + transformBitmap 成本大）。  
2. **Solution Category**：Graphics Pipeline Optimization。  
3. **Expected Outcome**：在同樣的輸入解析度下，降低每幀 CPU 時間與記憶體壓力（GC/alloc），提升可持續 FPS，並降低熱節流（thermal throttling）風險。

高層策略要點：
- 降低每幀配置（allocation），重用 buffer/bitmap，減少 GC。
- 儘量在 YUV domain 或更低成本路徑完成必要的旋轉/鏡像/裁切（避免多次 bitmap copy/scale）。
- 視情況改用更高效的轉換實作（例如硬體加速或平台最佳化路徑）。

### 方案 5：讓「裝置最佳解析度」真正參與決策，並補齊可觀測性（Observability）

1. **Probable Cause Addressed**：#4（target resolution 只用於 log，未影響 selector；難以快速驗證）。  
2. **Solution Category**：Engine Configuration / Diagnostics。  
3. **Expected Outcome**：減少不同機型在 1:1 下出現意外高解析度的機率；同時用更精準的 logs/metrics 讓回歸測試能快速確認 `ImageAnalysis` 實際輸入尺寸，避免同類問題再次發生。

高層策略要點：
- 將 `selectDeviceOptimalResolution()`（或類似策略輸出）納入 selector 的 fallback/上限控制。
- 日誌統一打印：比例模式、各 UseCase 實際解析度、每幀分析耗時（ms）、掉幀率/隊列堆積指標。

---

## 建議優先順序（Minimal-risk → Highest impact）

1. 先做 **方案 1（selector 分流）**：最直接對準根因、侵入性低、效果預期最明確。  
2. 視成效補 **方案 3（吞吐控制）**：確保在極端機型/高負載場景仍能流暢。  
3. 再做 **方案 2 / 4**：把長期成本降下來，改善續航、溫控、穩定性。  
4. 最後補 **方案 5**：把配置意圖與可觀測性做扎實，降低回歸風險。
