## 2. Feature D — True AE Lock（v2.11.4-02）

### 狀態

**✅ 已實作，已安裝 Pixel 9a，待裝置驗證。**

實作位置：`LiveCameraSource.kt`（`lockAEAF()` success callback + `cancelFocusAndMetering()`）

### 4 份文件共識：完全一致

| 文件 | 風險評估 | 關鍵備註 |
|------|----------|---------|

| Codex L2 | LOW（已確認） | 強調 `clearCaptureRequestOptions()` 全域搜尋確認安全（無其他 interop 用途） |
| Gemini L2 | LOW | 完全封裝在 `LiveCameraSource.kt`，只有長按才觸發，對 Regression 影響最小 |
| Traycer L2 | LOW（~6 行） | 已實作；風險主要是 UseCase rebind 重置問題 |

### 主要共識點

1. **根本原因已確認**：`FocusMeteringAction.FLAG_AE` 只設定測光區域，不寫 `CONTROL_AE_LOCK=true`。Camera2 實機 log 明確顯示 `AE_LOCK=false` 全程（ISO 29→669，+2207%）。

2. **修正方式已確認**：
   - **Lock**：在 `startFocusAndMetering()` success callback 後，`Camera2CameraControl.addCaptureRequestOptions(CONTROL_AE_LOCK=true)`
   - **Unlock**：`cancelFocusAndMetering()` 完成後，`Camera2CameraControl.clearCaptureRequestOptions()`

3. **`clearCaptureRequestOptions()` 安全性**：全域搜尋確認（Codex 明確記錄），repo 內無其他 `addCaptureRequestOptions` 或 `clearCaptureRequestOptions` 使用點。清除不會影響其他功能。

4. **範圍封裝良好**：僅改 `LiveCameraSource.kt` 2 個函式，~6 行，不觸碰 ViewModel / UI / CameraUiState。

5. **必須在 Release 生效**：所有文件均強調 `CONTROL_AE_LOCK` 實作不能只在 DEBUG 模式運作（現有 Camera2 CaptureResult logging 在 DEBUG guard 內，但 AE Lock 本身必須在 release 生效）。

### 已知風險（需驗證後排除）

| 風險 | 來源 | 狀態 |
|------|------|------|
| UseCase 重綁定可能重置 AE_LOCK | Claude L2, Traycer L2 | 實機驗證中 |
| 拍照 pipeline AE 行為（Preview lock ≠ Capture lock） | Claude L2 | 需拍照實測 10 張 |
| 連續 lock/unlock ≥20 次穩定性 | Claude L2 | 壓力測試項目 |

## 3. Feature A — Adaptive Frame Size（v2.11.4-03）

### 4 份文件共識與關鍵分歧

**共識**：Feature A 可行，風險 LOW-MEDIUM，適合 v2.11.4-03 實作。

**關鍵分歧 — Traycer 的 P0-2 依賴警告**：

> Traycer L2 明確指出：Roadmap 文件標注 P2-1（Adaptive Frame Size）**依賴** P0-2（PreviewViewportContainer）。P0-2 排入 v2.12.0。若 v2.11.4-03 在 PreviewViewportContainer 完成前實作，bbox 轉換使用現有 `CoordinateTransformer`（v2.11.3 已驗證），技術上可行，但 **v2.12.0 整合 PreviewViewportContainer 後必須重新驗證 Overlay 邊界**。

其他 3 份文件（Claude L2、Codex L2、Gemini L2）未提及此依賴，均視為 LOW 風險直接可行。

### 決策：Feature A P0-2 依賴評估

**結論：在 v2.11.4-03 先行實作，但加入明確的技術債記錄。**

**理由**：
1. `CoordinateTransformer.imageToScreen()` 已在 v2.11.3 完整驗證（包含 rotation-aware dimension swap），**單框 bbox 轉換不依賴 PreviewViewportContainer**。
2. PreviewViewportContainer（P0-2）的主要目的是「Overlay 容器座標一致性」，對多框場景影響更大（Feature B）。單框 Adaptive Size 的風險有限。
3. v2.12.0 整合 PreviewViewportContainer 後，需執行 **Overlay 邊界回歸測試**（已加入 §7 驗證清單）。

**技術債記錄**：
```
// TODO(v2.12.0): Re-verify Adaptive Frame Size overlay bounds after
// PreviewViewportContainer (P0-2) integration. Current impl uses
// CoordinateTransformer directly (v2.11.3 verified, single-frame).
// See: v2.11.4_multi_focus_coexistence_L2-Synthesis.md §3
```

### 最佳可行方案（4 份文件彙整）

**修改 3 個檔案，最小 diff：**

#### 3.1 `CameraState.kt` — 新增狀態欄位

Traycer L2 + Codex L2 共同建議（兩份最具體）：

```kotlin
// 新增至 CameraUiState（Codex: focusBoundingBox Rect? / Traycer: focusFrameWidth/Height Float）
// 採用 Traycer 方案（已轉換至 dp 的 Float，更適合 Compose 直接使用）
focusFrameWidth: Float = 48f,   // dp，預設值 = 最小 clamp
focusFrameHeight: Float = 48f,  // dp
isAutoFocused: Boolean = false   // 區分 auto-focus vs user-tap 觸發（Traycer）
```

> **Codex 替代方案**（`focusBoundingBox: Rect?`）：保留 screen-space Rect，在 Compose 層再做 dp 換算。兩者皆可行，選 Traycer 方案因 Float dp 在 Compose 直接使用更簡潔。

#### 3.2 `CameraViewModel.kt` — 計算邏輯

```kotlin
// 新增函式（Traycer 具體公式 + Gemini clamp 建議）
private fun calculateAdaptiveFrameSize(
    boundingBox: android.graphics.Rect,
    density: Float
): Pair<Float, Float> {
    val widthDp = (boundingBox.width() * 0.8f) / density
    val heightDp = (boundingBox.height() * 0.8f) / density
    // Clamp: min=48dp (Traycer), max=120dp (Traycer) / max=200dp (Gemini, device-dependent)
    // 統一採用 48-120dp（保守，避免過大框佔滿螢幕）
    return Pair(
        widthDp.coerceIn(48f, 120f),
        heightDp.coerceIn(48f, 120f)
    )
}
```

**忽略閾值**（全文件一致）：
- screen-space bbox < **40dp × 40dp** → 不觸發對焦，不更新 frame size
- 依據：40dp = Material Design 最小觸控面積（Gemini 明確引用）

**呼叫時機**：
- `autoFocusOnSalientTarget()` 觸發對焦前：計算並 `_state.update { focusFrameWidth, focusFrameHeight, isAutoFocused=true }`
- `updateTrackedObjectPosition()` 中每幀 bbox 更新同步更新 frame size

#### 3.3 `CameraScreen.kt` — FocusIndicator 尺寸動畫

```kotlin
// 取代固定 80.dp（Traycer 具體方案）
val animatedWidth by animateFloatAsState(
    targetValue = focusFrameWidth,
    animationSpec = spring(
        dampingRatio = Spring.DampingRatioMediumBouncy,
        stiffness = Spring.StiffnessLow
    )
)
val animatedHeight by animateFloatAsState(
    targetValue = focusFrameHeight,
    animationSpec = spring(
        dampingRatio = Spring.DampingRatioMediumBouncy,
        stiffness = Spring.StiffnessLow
    )
)
// Canvas 繪製改用 halfWidth = animatedWidth.dp / 2
```

### 回滾策略

- bbox 為 null 或計算結果 fallback：直接使用固定 **80dp**（Codex 明確建議）
- 若 bbox 轉換有問題：可單獨 revert `CameraScreen.kt` 的尺寸參數，不影響 state 邏輯

## 4. Feature B+C — Multi-Focus + Anti-Flicker（評估）

### 4 份文件共識：MEDIUM-HIGH 風險，建議移至 v2.12.0

| 文件 | 建議 | 原因 |
|------|------|------|
| Claude L2 | 未直接評估 B+C | （Feature D 專用文件，未涉及） |
| Codex L2 | 移至 v2.12.0（或過渡版） | `CameraUiState` breaking change + Thread concurrency HIGH |
| Gemini L2 | **強烈建議**移至 v2.12.0 | v2.11.x = bugfix/stability，breaking state change = regression risk |
| Traycer L2 | 移至 v2.12.0 | 依賴 PreviewViewportContainer（P0-2）先完成 |

### Codex「過渡版本」提案（Step 3 Transition）

Codex L2 提出一個獨特的折中方案：**不做 `focusTargets` breaking change，先加 `salientCandidates: List<FocusTargetCandidate>` 作為 UI-only overlay**。

**核心概念**：
- Primary 仍維持現有 `focusPoint + focusBoundingBox` 鏈路（不破壞 OF/lock/tap）
- 新增 `salientCandidates`：只是 UI 用的 secondary 候選者清單，不影響 metering 狀態
- UI 另外畫 secondary candidates（細框 alpha 0.5，最多 5 個）
- 風險從 HIGH 壓低至 **MEDIUM**

**評估**：
- 優點：可以在 v2.11.4-NN 中先交付「多框視覺」，且不破壞架構
- 缺點：引入兩套並行的 focus 狀態表示（`focusPoint` + `salientCandidates`），形成技術債，在 v2.12.0 仍需完整遷移

### 最終建議：明確版本分派

**決定：Feature B+C 全部移至 v2.12.0，不實作過渡版。**

**決策依據**：
1. **v2.11.x 策略邊界**（MEMORY.md 確認）：v2.11.x = Bug Fix / 穩定性，v2.12.0 = 新功能。Multi-Focus 屬於新功能，不符合 v2.11.x 定義。
2. **Codex 過渡版技術債成本高**：兩套並行 focus 狀態表示，v2.12.0 遷移複雜度未降低反而增加。
3. **Traycer 依賴警告**：PreviewViewportContainer（P0-2）是多框 Overlay 正確座標的必要前提，P0-2 在 v2.12.0 才完成。
4. **Gemini 最直接**：「在 v2.11 穩定版迭代中硬上容易導致難以追蹤的 Race Condition 與 Regression」。

### v2.12.0 執行前置條件順序

Feature B+C 在 v2.12.0 的正確執行順序（Traycer 明確定義）：

```
v2.12.0 執行順序（嚴格遵守）：

Step 1. PreviewViewportContainer (P0-2)
        ← 確保 Overlay 座標基礎，所有 FocusIndicator 座標正確
        ← 這是 Step 2+ 的必要前提

Step 2. FocusTarget 資料模型
        ← 新建獨立檔案，不破壞現有 state
        ← data class FocusTarget, enum FocusTargetType, FocusTargetState

Step 3. CameraState.kt 遷移
        ← focusPoint: Pair<Float,Float>? → focusTargets: List<FocusTarget>
        ← 遷移所有 focusPoint 引用（需全域搜尋確認引用點）

Step 4. CameraViewModel.kt 重構
        ← autoFocusOnSalientTarget(): 收集所有 score > 閾值候選者
        ← focusOnPoint(): 建立 FocusTargetType.USER_TAP 條目（5 秒 override）
        ← OF tracking: 只追蹤 isPrimary=true 的目標

Step 5. CameraScreen.kt — FocusIndicatorLayer()
        ← 多框渲染：Primary（2.5dp, alpha 1.0）/ Secondary（1.0dp, alpha 0.5）
        ← 上限 top 5，stable key = trackingId
```

**Anti-Flicker（Feature C）在 Step 4 自然解決**：USER_TAP 條目獨立，auto-focus 候選者不覆蓋 user tap，天然防止框跳動。
