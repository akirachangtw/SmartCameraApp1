# v2.11.4-06 (L1) — Planning Summary: Long-Press Lock Delay & Dark Preview After Unlock

This L1 plan builds on the L0 analysis (`v2.11.4-06_Analyzing_App_Bugs_Lock_Delay_Dark-L0.md`) that points to **CameraX Camera2Interop capture request options being replayed into a new session** after lifecycle transitions, with `clearCaptureRequestOptions()` sometimes landing **before** the HAL session is actually active.

---

## Objectives

- **Bug 1:** Eliminate the intermittent ~5-second delay on subsequent long-press AE/AF lock after the first use, especially after screen lock/unlock and foreground/background transitions.
- **Bug 2:** Eliminate the dark camera preview immediately after screen unlock (ensure exposure is not “frozen” across session rebuild).
- Make behavior deterministic across lifecycle events by ensuring **thread safety**, **single ownership**, and **correct sequencing** of camera/session operations.

## Working Hypotheses (from L0)

- **Bug 1 delay:** Stale `CONTROL_AF_MODE=OFF` (and related focus/meters state) can survive across session recreation. When the user triggers the next lock/metering action, the system effectively waits for a timeout window consistent with the default focus/metering auto-cancel (~5s).
- **Bug 2 dark preview:** Stale `CONTROL_AE_LOCK=true` can be replayed into the new session, freezing AE at the previous scene’s ISO/shutter state until reconvergence.
- Root risk is a **race**: lifecycle-driven unbind/rebind and app “unlock” actions occur while the camera is inactive or the new capture session is not yet configured, so clears/updates can be dropped or no-op.

---

## Bug 1 — Diagnostic Strategy (Pinpoint the Exact Cause)

### 1) Reproduction Matrix (make intermittency measurable)

Create a small matrix and record outcomes (delay present? exact latency ms?):

- Device(s): Pixel 9a (noted in L0), at least one slower/older device.
- Screen lock/unlock paths:
  - Lock screen via power button → unlock.
  - App background via Home → return via Recents.
  - Rotate screen (if applicable) / configuration change.
- App states:
  - Immediately after cold start.
  - After first lock/unlock cycle.
  - After several repeated cycles (10–20).

Success criteria for diagnostics: reduce “it happens sometimes” to a **repeatable sequence** with timestamps and session identifiers.

### 2) Lifecycle + Camera Session Timeline Logging (single correlated trace)

Add structured logs (timestamped, single-line) and correlate across:

- `CameraScreen` lifecycle (`ON_START`, `ON_RESUME`, `ON_PAUSE`, `ON_STOP`).
- `LiveCameraSource.bindToLifecycle()` entry/exit, and “camera bound” markers.
- Camera session readiness markers:
  - First `CaptureResult` (or first frame / first session callback).
  - Any session state callbacks (configured, closed, failed) if available.
- Lock/Unlock events:
  - User long-press event → `LockAEAF` dispatch.
  - `lockAEAF()`, `startFocusAndMetering()`, `cancelFocusAndMetering()`, `clearCaptureRequestOptions()`.
- Camera2Interop state application:
  - When `addCaptureRequestOptions()` is called and with which key options (AE_LOCK / AF_MODE / focus distance / metering regions).
  - When `clearCaptureRequestOptions()` is called and whether the camera/session is active.

**Key output goal:** a deterministic timeline proving whether:
1) `clearCaptureRequestOptions()` is invoked while the camera is inactive, or
2) invoked before the first active session/frame, or
3) invoked correctly but options are still replayed later.

### 3) Thread/Handler/Queue Diagnostics (prove delayed execution vs. HAL delay)

To separate “callback queued late” from “HAL took 5 seconds”:

- Tag logs with **thread name** and **Coroutine dispatcher** (if coroutines are used).
- Record queue/dispatch timing:
  - Time from long-press → `LockAEAF` handled.
  - Time from `startFocusAndMetering()` call → focus callback completion/cancel.
- Inspect active jobs/handlers:
  - Count or list pending coroutines / timers / delayed runnables tied to lock/unlock, especially after resume.
- Use Android Studio profiling (as needed):
  - **CPU profiler**: verify no main-thread stall around the 5s window.
  - **Memory profiler**: verify no accumulation of listeners/controls across resume.

If the 5-second interval is observed even when callbacks execute promptly, it strengthens the “camera state machine / focus action timeout” hypothesis rather than an app-side queue delay.

### 4) Camera2-Level Observability (if needed)

If logs are insufficient:

- Add debug logging of relevant `CaptureResult` keys around the period:
  - `CONTROL_AF_STATE`, `CONTROL_AE_STATE`, `CONTROL_AE_LOCK`, `CONTROL_AF_MODE`.
- Verify whether the session ever sees `AF_MODE=OFF` after resume and before the next long-press action.

## Bug 1 — High-Level Solution Options

### 1) Resource Management (release/reacquire correctly across lifecycle)

Primary goal: ensure Camera2Interop settings are cleared **only when they can reach an active session**, and that session-bound resources don’t leak across pauses.

- **Defer clears to “session ready”:**
  - Convert `clearCaptureRequestOptions()` calls into a *deferred action* that executes after session readiness (e.g., first `CaptureResult` callback / first frame).
  - Use a one-shot flag (e.g., `pendingClearOnNextFrame`) to ensure the clear runs exactly once after rebind.
- **Ensure session-aware cleanup:**
  - If `cancelFocusAndMetering()` is called while camera is inactive, store intent (deferred clear) rather than calling no-op interop APIs.
- **Single owner of camera control:**
  - Centralize Camera2Interop control application/clear into one component (e.g., `LiveCameraSource`) to avoid “multiple places issuing clears” with no guarantees.

### 2) State Management (robust lock/unlock state machine)

Primary goal: prevent app state from diverging from HAL state and prevent lifecycle transitions from leaving the system in a half-locked state.

- Implement an explicit **AE/AF Lock State Machine** with:
  - States like `Unlocked`, `LockRequested`, `Locked`, `UnlockRequested`, `Suspended(inactive session)`.
  - A monotonic “generation/session id” to discard stale callbacks from older sessions.
- Make all lock/unlock operations **idempotent**:
  - Calling unlock multiple times should be safe and should not depend solely on a UI flag like `isAEAFLocked`.
- Align ViewModel state with camera session lifetime:
  - Reset or recompute “locked” flags on session recreation.
  - Avoid guards that skip unlock when the HAL might still be dirty.

### 3) Event Handling (prevent duplicate/delayed callbacks)

Primary goal: ensure there’s no duplicate listener registration or delayed callback execution that triggers late clears or replays old state.

- Verify registration/deregistration symmetry:
  - Camera session callbacks, capture callbacks, lifecycle observers, and gesture listeners should be registered once and removed deterministically.
- Ensure lock/unlock events are serialized:
  - Use a `Mutex`/single-thread executor or a “camera command queue” so `LockAEAF`, `UnlockAEAF`, `bindToLifecycle`, and cancel/clear cannot interleave unpredictably.
- Add “debounce” or “drop stale” policy:
  - If multiple lock/unlock events arrive during resume, process only the most recent relevant command for the current session generation.

## Bug 2 — Diagnostic Strategy (Dark Preview After Screen Unlock)

### 1) Session State + Exposure Timeline

Log/trace exposure-related behavior across unlock:

- Lifecycle transitions and session recreation markers (same as Bug 1).
- When `CONTROL_AE_LOCK` is set/cleared.
- Any HDR/exposure compensation re-application (e.g., `pendingExposureIndex`) and its timing relative to session readiness.

Outcome to confirm: dark preview corresponds to `AE_LOCK=true` (or AE state not converging) on early frames after resume.

### 2) Preview Rendering / Surface Attachment Checks

Confirm the preview path is intact and not rendering stale/detached buffers:

- Log `SurfaceTexture`/`SurfaceView` attachment lifecycle events (created/destroyed/available size).
- Verify camera preview is producing frames (first frame timestamp vs. resume).
- Identify if the darkness is “no frames / stale frame” vs. “frames but underexposed”.

### 3) Camera2 CaptureResult Inspection (targeted)

If needed, inspect capture results immediately after resume:

- `CONTROL_AE_LOCK`, `CONTROL_AE_STATE`, `SENSOR_EXPOSURE_TIME`, `SENSOR_SENSITIVITY`, `CONTROL_AWB_STATE`.
- Validate that AE is allowed to run and converge after unlock.

## Bug 2 — High-Level Solution Options

### 1) Camera Re-initialization (resume/re-configure correctly)

Primary goal: ensure camera session is restored into a known-good baseline on resume/unlock.

- Use the same “deferred-to-first-frame” mechanism to:
  - Clear Camera2Interop options after session is active.
  - Re-apply only intentional, current-session settings after the clear.
- Ensure session rebuild sequencing is explicit:
  - Bind → wait for session ready → clear stale options → apply desired options (HDR/exposure comp, etc.).

### 2) Exposure/Brightness Settings (AE/AWB correctness)

Primary goal: guarantee exposure locks and compensation are consistent.

- On session resume:
  - Explicitly set `CONTROL_AE_LOCK=false` (or clear options) before applying exposure compensation.
- Ensure “HDR persistence” logic (`pendingExposureIndex`) does not run before the clear completes.
- Add guardrails:
  - If AE is locked but app state says unlocked, force unlock on the next active frame.

### 3) Surface Management (preview surfaces are correct)

Primary goal: ensure the preview surface is attached and receiving frames in the new session.

- Validate surface lifecycle handling:
  - If surface is recreated on unlock, ensure camera is reconfigured to target the new surface.
- Ensure no stale surface references are used after pause/stop.
- If using `SurfaceTexture`, ensure buffer size and default orientation are reasserted after resume if needed.

## Cross-Cutting Architecture & Refactoring Considerations

### Lifecycle-aware camera control

- Introduce a single **Lifecycle-aware Camera Controller** abstraction that owns:
  - Bind/unbind
  - Session readiness signals
  - Camera2Interop option application/clear
  - Lock/unlock command queue
- Prefer a “session-ready signal” primitive:
  - e.g., a `CompletableDeferred` that completes on first `CaptureResult`, tied to a session generation id.

### Thread safety & command serialization

- Enforce a single execution context for camera commands:
  - e.g., a dedicated coroutine dispatcher/executor for camera operations.
- Every command includes a `sessionGeneration` to avoid applying to the wrong session.

### Single source of truth

- Keep ViewModel/UI state as “intent and UI display”, but make the camera controller authoritative for:
  - What is actually applied to the camera session
  - When it is safe to apply/clear options

## Roadmap (High-Level)

1) **Instrument & reproduce**: add lifecycle/session/interop logs + reproduction matrix until the race is proven with timestamps.
2) **Stabilize sequencing**: implement “deferred clear on first active frame” and command serialization; ensure idempotent lock/unlock.
3) **Harden state**: add session generation + state machine; remove or adjust guards that can skip required unlock/clear actions.
4) **Validate**:
   - Re-run reproduction matrix (10–20 cycles) and ensure lock latency is stable and preview brightness is correct.
   - Confirm no duplicate callbacks/listeners and no resource accumulation across lifecycle transitions.

---

## Acceptance Criteria

- **Bug 1:** Long-press lock responsiveness remains consistent (<~200ms to start lock command handling, no 5s timeout behavior) after repeated screen lock/unlock and background/foreground cycles.
- **Bug 2:** Preview brightness is correct immediately after unlock; AE/AWB converge normally without being frozen by stale locks.
- No regressions in:
  - Manual focus/lock flows
  - HDR/exposure persistence behavior
  - App stability across lifecycle transitions
