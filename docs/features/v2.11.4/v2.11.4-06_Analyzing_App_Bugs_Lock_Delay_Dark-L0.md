Bug 1 — ~5-Second Delay on Subsequent Long-Press Lock Operations
Symptoms & Trigger
After the first lock/unlock cycle, every subsequent long-press lock takes ~5 seconds to respond. The delay reappears after screen unlock or foreground/background transitions, and only a full app restart clears it.

Root Cause Analysis
The evidence points to stale Camera2 interop options (CONTROL_AE_LOCK=true + CONTROL_AF_MODE=OFF) surviving across the screen-lock/unlock lifecycle, causing the camera HAL to be in a frozen AF state when the next lock attempt begins.

The ~5-second delay matches the default FocusMeteringAction auto-cancel duration (set to 5 seconds in focusOnPoint() at line 645 of LiveCameraSource.kt). When AF_MODE=OFF is still active from the previous session, startFocusAndMetering() must wait for the HAL to time out the stale metering action before it can converge.

Bug 2 — Dark Camera Preview After Screen Unlock
Symptoms & Trigger
The preview appears noticeably dark immediately after the phone screen is unlocked.

Root Cause Analysis
The evidence points to CONTROL_AE_LOCK=true surviving into the new camera session after screen unlock, causing the AE algorithm to be frozen at the exposure values from the moment the screen was locked (which may have been in a dark environment or with a different scene).

Key code locations:

LiveCameraSource.kt lines 1151–1163 — The clearCaptureRequestOptions() on bind is the intended fix, but it is called immediately after cameraProvider.bindToLifecycle(). At this point, the underlying CameraCaptureSession may not yet be configured, meaning the Camera2 interop clear is a no-op. The AE_LOCK option then gets re-applied by CameraX's internal option replay mechanism.
LiveCameraSource.kt lines 1186–1192 — pendingExposureIndex is reapplied after rebind (for HDR persistence). If AE_LOCK is still active when this runs, the exposure compensation is applied on top of a locked AE state, which can produce an incorrect (dark) exposure.
LiveCameraSource.kt lines 747–771 — lockAEAF() explicitly sets CONTROL_AE_LOCK=true via Camera2CameraControl.addCaptureRequestOptions(). CameraX's Camera2CameraControl stores these options and replays them on every new capture session, including after a rebind — unless clearCaptureRequestOptions() is called successfully on an active session.

# Phase Breakdown

## Task 1: Bug 1 Fix: Guarantee Camera2 Interop Options Are Cleared on Active Session After Screen Unlock

Fix the ~5-second AE/AF lock delay after screen unlock in `d:\MyDocuments\DevSources\AndroidStudioProjects\SmartCameraApp1\app\src\main\java\com\akirachang\ai\photographer\data\source\camera\LiveCameraSource.kt`:

- Move the `clearCaptureRequestOptions()` call (currently at line ~1157) to **after** the first `CaptureResult` callback fires (i.e., inside `setSessionCaptureCallback.onCaptureCompleted`), so the clear is guaranteed to reach an active HAL session.
- Add a one-shot `pendingClearOnNextFrame: Boolean` flag; set it `true` in `bindToLifecycle()`, consume and clear it inside `onCaptureCompleted` before the `logAeAfState` guard.
- In `cancelFocusAndMetering()` (`LiveCameraSource.kt` lines 826–843), verify that `addCaptureRequestOptions(AF_MODE=CONTINUOUS_PICTURE)` + `clearCaptureRequestOptions()` are only called when `::camera.isInitialized` and the camera session is active; otherwise set `pendingClearOnNextFrame = true` as a deferred fallback.


## Task 2: Bug 2 Fix: Prevent AE_LOCK from Persisting into New Camera Session (Dark Preview After Unlock)

Fix the dark preview after screen unlock caused by `CONTROL_AE_LOCK=true` surviving into the new camera session:

- In `d:\MyDocuments\DevSources\AndroidStudioProjects\SmartCameraApp1\app\src\main\java\com\akirachang\ai\photographer\data\source\camera\LiveCameraSource.kt`, use the same `pendingClearOnNextFrame` one-shot flag (introduced in Bug 1 fix) to also explicitly set `CONTROL_AE_LOCK=false` via `addCaptureRequestOptions` on the first active frame after rebind, before releasing the flag.
- In `d:\MyDocuments\DevSources\AndroidStudioProjects\SmartCameraApp1\app\src\main\java\com\akirachang\ai\photographer\presentation\camera\CameraScreen.kt`, consider also firing `UnlockAEAF` on `ON_PAUSE` (in addition to `ON_STOP`) to reset `isAEAFLocked` state earlier, so `unlockAEAF()` in `CameraViewModel.kt` does not skip the cancel due to the `!isAEAFLocked` guard when the state is already stale.
- Ensure `pendingExposureIndex` reapplication in `bindToLifecycle()` (line ~1189) runs **after** the deferred clear completes, to avoid applying HDR exposure on top of a locked AE state.
