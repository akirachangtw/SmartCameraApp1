## 2) 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
1. **現況對焦 UI 資料流**：`focusPoint` 的單點狀態是唯一 UI 依據，且所有「顯示框 / 動畫 / 狀態」都綁在這個欄位上。需由 repo 搜尋 `focusPoint` 的讀寫點數量與用途驗證。
2. **ML Kit detection 結果**：目前 `updateTrackedObjectPosition()`（或等效函式）確實拿得到 `boundingBox` 與 `trackingId`，且每幀都可用於 secondary targets 的更新。需檢視 ViewModel/Analyzer 的資料結構確認。
3. **CoordinateTransformer 的 API**：存在穩定可用的 `imageToScreen()` 或等效方法，可將 image-space `Rect`/`RectF` 轉成 screen-space，且支援目前 PreviewView/viewport 裁切模式。需確認 transformer 是否提供「Rect 轉換」或僅提供「Point 轉換」。
4. **OF tracking 只追 primary**：目前 OF pipeline 假設 single target，且其輸出會回寫到 focusPoint（或類似）。需確認 OF 結果寫回的欄位與觸發時機，避免與 multi-target state 互相覆寫。
5. **CameraX metering 單點限制**：你們的 `focusOnPoint()` / `startFocusAndMetering()` 只支援單點，multi-focus 只做 UI 多框即可（Primary 送 metering）。需確認現有 CameraX code path 是否有「每幀重新 metering」或「自動切 primary 會觸發 metering」機制。
6. **AE Lock interop 清除行為**：`clearCaptureRequestOptions()` 是否會清除除了 AE_LOCK 之外的其他 interop 設定（例如 session callback、其他 request option）。需由 repo 搜尋 Camera2Interop 使用點與實機 log 驗證。

## 3) 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **State breaking change（HIGH）**  
   `CameraUiState.focusPoint -> focusTargets` 會導致：
   - Compose 重組路徑改變、所有 focus indicator 呼叫點需要遷移
   - 可能牽涉到 lock/unlock、tap、autofocus job、OF job 的同步與取消
2. **Thread / concurrency（HIGH）**  
   - `autoFocusOnSalientTarget()` 可能在 analyzer thread / coroutine 中高頻更新  
   - user tap 事件在 main thread  
   - 兩者同時更新 `focusTargets` 時，若非單一 reducer/atomic update，容易造成「框閃爍、順序抖動、primary 判定不穩」。
3. **CameraX Preview / Viewport（MEDIUM-HIGH）**  
   多框需要依賴「正確的 screen-space mapping」。如果 preview 有 crop / scaleType / rotation，bbox 轉換稍有不一致就會造成框漂移。雖然你標註 CoordinateTransformer v2.11.3 已驗證，但 multi-rect 轉換會放大問題。
4. **模式切換（Live / Static / Debug）（MEDIUM）**  
   - Debug capture callback（Camera2Interop session callback）只掛在 Preview builder，需確認 static mode 或其他 use case 組合不會因 interop callback 造成不可預期差異。
5. **效能（MEDIUM）**  
   - 多框繪製 N 個 indicator + 各自動畫（spring/tween）可能增加 Compose 負擔  
   - 每幀更新 list（尤其若未做 stable key / diff）會造成 GC / jank。
6. **AE/AF Lock 行為一致性（MEDIUM）**  
   - 你已觀察到 lock 後 AF 也可能退化；multi-focus 若引入更多狀態，lock state 的 UI priority（黃框）必須穩定且不被 secondary 覆蓋。

## 4) 最小差異建議（Minimal diff approach：步驟化）
### 建議路線：先「不破壞 focusPoint」完成 80% 視覺目標，再決定是否進 v2.12.0 做完整重構

**Step 0（先決條件）**：全域搜尋確認 interop options 沒有其他用途  
- 若 `clearCaptureRequestOptions()` 會清空其他需求，改為「只 clear AE_LOCK」的方式（若 Camera2Interop API 不支援 selective clear，就必須建立「集中管理 interop options」的 wrapper，這會放大範圍 → 更偏 v2.12.0）。

**Step 1（v2.11.4-02 / Feature D）**：AE Lock 真鎖定完成並實機驗證  
- 維持你現在的最小 diff，先拿到 `AE_LOCK=true` 與 `AE_STATE=LOCKED` 的 log。

**Step 2（v2.11.4-03 / Feature A）**：Adaptive Frame Size（不改 State 結構）  
- 在 `CameraUiState` 先只加 `focusBoundingBox: Rect?`（你提的方案）  
- UI 仍然只畫一個框，但尺寸依 bbox adaptive（48–120dp clamp + <40dp ignore）。  
- 這一步可以獨立驗證 CoordinateTransformer 的 rect mapping 正確性。

**Step 3（v2.11.4-NN 候選 / Multi-focus Phase 1 的「最小風險替代版」）**  
> 不做 `focusTargets` breaking change；先做「多框 overlay（secondary-only）」作為過渡版

- 增加一個欄位：`salientCandidates: List<FocusTargetCandidate>`（僅 UI 用，非核心對焦 state）  
- Primary 仍維持 `focusPoint + focusBoundingBox` 既有鏈路，避免影響 OF/lock/tap。  
- UI 另外畫 secondary candidates（細框 alpha 0.5，最多 5 個），但不影響 metering、不影響 primary state。  
- 這能先滿足「多人臉多框共存」的視覺期待，且把風險壓到 MEDIUM。

**Step 4（v2.12.0 / 正式 Feature B Phase 2 + C）**  
- 再把 state 正式升級到 `focusTargets`，並做 user tap override timer、anti-flicker、primary arbitration、與 OF 僅追 primary 的規則。

## 7) 回滾與降風險策略（Rollback/Feature flag）
1. **Feature flag（強烈建議）**
   - `enableMultiFocusOverlay`：只影響 UI overlay（secondary frames），預設 false（或 debug only），確保 v2.11.x 不會因新 UI 邏輯影響穩定版。
   - `enableTrueAeLock`：若遇到特定機型 HAL 相容性問題可關閉（Pixel 9a 已支援，但為保險）。
2. **回滾路徑**
   - Feature D：回滾僅需移除 `addCaptureRequestOptions(CONTROL_AE_LOCK)` 與 `clearCaptureRequestOptions()` 兩段（最小 diff、易 revert）。
   - Feature A：保留原本固定 80dp path，bbox 為 null 時 fallback 固定 size。
   - Multi-focus：優先採用「不改 state」的過渡版；若出問題可直接關 flag 或移除 overlay composable，不影響核心對焦。
3. **避免 breaking change 進 v2.11.x**
   - `focusTargets` 這種 state 重構若要做，**建議放 v2.12.0**；v2.11.4 僅做可逆、可關閉、可快速 revert 的改動。
4. **資料結構穩定性**
   - 即使做 overlay list，也要確保 Compose 使用 stable key（例如 trackingId）與 top-N deterministic sort，避免每幀順序抖動造成「視覺閃爍」假象。
