這個「需要點擊 2 次才能解鎖」的問題，其實是一個**「UI 狀態回饋 (UI Feedback) 與底層相機重新測光 (Re-metering) 時間差」**所造成的 UX (使用者體驗) 錯覺。

這個問題的分析非常精確。如同您所述： 第 1 次點擊，底層確實已經送出 cancelFocusAndMetering() 解除了 Lock 狀態，但緊接著又送出了 startFocusAndMetering() 去做新的「點擊位置自動對焦 (Refocus)」。

相機 HAL 收到新的測光要求後，會開始改變鏡頭焦距並重新計算曝光 (AE SEARCHING)，這個過程物理上需要大約 0.5 ~ 1.5 秒 才能穩定 (CONVERGED)。

而在這 1 秒內，預覽畫面看起來還是跟鎖定的時候一樣暗或一樣亮（因為它正在努力調光），使用者就會有種「剛剛的點擊是不是沒反應？」的錯覺，進而急躁地按了第 2 次。

針對這個 UX 問題，我提出以下 3 個可行方案 (Solutions)：

方案 1：解鎖時只做 Cancel，不強制 Refocus (解開就好，交給連續對焦)
邏輯：當系統處於 AE/AF_LOCKED 狀態時，如果使用者點擊畫面，我們只執行 cancelFocusAndMetering() 讓相機回到「連續自動對焦與測光 (Passive/Continuous Mode)」，不要緊接著呼叫 startFocusAndMetering 去對點擊的位置對焦。 優點：

相機硬體馬上接管，畫面會隨著相機移動而平順地調整亮度。
沒有刻意把焦點「黏」在使用者點擊的地方，感覺比較像是「解除束縛」。
程式碼修改極小（在 ViewModel 或 Screen 層判斷 if (isLocked) { unlock() } else { focusOnPoint() }）。 缺點：
使用者點這一下，焦點並不一定對在手指按的地方 (因為它只是解鎖並回到連續自動模式)。
方案 2：加入短暫的「解鎖過渡 UI」或「觸覺回饋」 (UX 引導)
邏輯：維持現狀（解鎖 + 立即對原本按下的位置對焦），但給予使用者強烈的「已經收到指令」的提示。 實作方式：

視覺：第 1 次點擊解鎖時，原本的「黃色鎖定框」瞬間變成一個「正在跑的特效框（例如閃爍的白框或淺藍框）」或短暫顯示一個「Unlocked」的小 Toast / Icon 消失動畫。
觸覺 (Haptic Feedback)：在點擊解鎖的瞬間觸發輕微震動 (HapticFeedbackConstants.CONTEXT_CLICK 或 VIRTUAL_KEY)。 優點：使用者收到明確回饋，知道系統在做事，就不會去點第 2 次。 缺點：如果底層對焦/測光還是很慢（例如在極暗環境），畫面依舊需要時間恢復。
方案 3：強制先重置 (Reset/Passive) 延遲一小段時間再 Refocus
邏輯：點擊解鎖當下送出 cancelFocusAndMetering()，等候大約 200ms（讓 HAL 完全確認模式切回 Passive 後），再送出 startFocusAndMetering()。 優點：可以確保 CameraX 內部狀態乾淨，不會產生您發現的 superseded (即第二次 cancel 取消第一次) 覆蓋現象，讓 Log 更乾淨。 缺點：增加了人為延遲，體驗反而可能變鈍。而且並不能真正縮短物理測光需要的 ~1 秒鐘。

最佳可行方案建議：
綜合評估後，強烈建議採用【方案 1 結合方案 2 的觸覺回饋】。

實作思路： 在 CameraScreen 或 CameraViewModel 處理 onTap 事件時區分狀態：

kotlin
fun onTapToFocus(x: Float, y: Float) {
    if (uiState.isAeAfLocked) {
        // 解鎖邏輯：
        // 1. 給予觸覺回饋 (Haptic)
        // 2. 僅觸發 unlock() / cancelFocusAndMetering()
        // 3. 讓相機回到全自動模式 (不會有死黏在特定點的感覺)
        cameraRepository.unlockAEAF() 
    } else {
        // 一般對焦邏輯：
        cameraRepository.focusOnPoint(x, y)
    }
}
這樣做，第一次點擊的語意就是「解鎖」，畫面黃框消失，相機開始全螢幕自動尋找對焦點與曝光；如果使用者真的對畫面上的某個特定物件不滿意，他才會再點擊第 2 次（這時候的語意才是「對焦在這個點上」）。這種手感與多數原生相機的體驗最為接近。
