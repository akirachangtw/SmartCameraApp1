# Level 1 規劃摘要：unlock_fix_concurrent_cancel

## 1. 目標（Goal）
修復 **AE/AF Lock 解鎖失效**問題：使用者點擊解鎖後 UI 雖已解除（黃框消失），但相機 HAL 仍維持 `AE_LOCK=true` 與 `AF_MODE=OFF`，導致預覽持續過暗、無法重新對焦。目標是在 **快速連點解鎖**等競態情境下，仍能 **確實執行 Camera2 interop cleanup**，讓相機回到可自動曝光/自動對焦狀態。

---

## 2. 背景與問題（Why / What）
### 使用者可見現象（Pixel 9a 實機確認）
- 長按 Lock 後：黃色框出現，且 `CONTROL_AE_LOCK=true + CONTROL_AF_MODE=OFF` 設定正確。
- 點擊解鎖後：黃色框消失（ViewModel state reset），但預覽仍鎖定：
  - 畫面偏暗（exposure=16.6ms, ISO=29 固定不變）
  - 無法重新對焦
  - 連點 5 次仍無法解鎖

### Logcat 根因（21:25:04-05，出現 3 次）
```
E/LiveCameraSource: java.util.concurrent.ExecutionException:
    CameraControl$OperationCanceledException: Cancelled by another cancelFocusAndMetering()
    at LiveCameraSource$cancelFocusAndMetering$2$1.run(LiveCameraSource.kt:804)
```

### 錯誤鏈（已定位）
1. 使用者快速點擊 → 多次並行觸發 `cancelFocusAndMetering()`
2. CameraX 行為：後一次 cancel 會取消前一次 Future
3. `future.get()` 拋 `OperationCanceledException`
4. 例外被 catch → **try block 後段 cleanup（clearCaptureRequestOptions）被略過**
5. `CONTROL_AE_LOCK=true + CONTROL_AF_MODE=OFF` 殘留在 HAL
6. UI 顯示已解鎖，但 HAL 未解 → 預覽暗/對焦失效（功能性故障）

### 目前程式碼結構問題（LiveCameraSource.kt ~798-825）
- `future.get()` 與 `clearCaptureRequestOptions()` 在同一個 try 區塊
- cleanup 排在 `future.get()` 後方 → **任何例外都會阻止 cleanup 執行**
- 形成「非致命 cancel 例外 → 變成致命狀態殘留」的錯誤放大器

## 4. 風險清單（Risks）
1. **相機管線競態風險**：調整 cleanup 時序若處理不當，可能造成：
   - cancel 尚未完成即清除 options，造成短暫閃爍/曝光跳動
   - AF 模式回復時機不一致，導致下一次對焦/追蹤行為不穩定
2. **模式切換風險（推測）**：若 unlock 同時碰到 rebind use cases / 前後鏡切換，可能出現：
   - request options 被清掉後又被其他流程覆寫（需確認權責與順序）
3. **效能回歸風險（低，但需列）**：
   - 在 listener callback 最前段做 cleanup，可能增加少量 Camera2 interop 呼叫頻率（尤其快速點擊時）
4. **行為改變風險**：將 `OperationCanceledException` 視為非致命，可能掩蓋其他真正錯誤（需明確只針對「Cancelled by another cancelFocusAndMetering」類型降級處理）

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（最小差異、首選）
**核心原則：cleanup 必定執行（at-least-once），且不依賴 future.get() 成功。**

調整 `cancelFocusAndMetering()` 內部結構：
- 將 **Camera2 interop cleanup**（包含 `clearCaptureRequestOptions()` + 回復 `CONTROL_AF_MODE` 至 `CONTINUOUS_PICTURE` 等）移到：
  - `addListener { ... }` callback 的**最開頭**，並確保即使後續 `future.get()` 拋例外也不影響 cleanup
- `OperationCanceledException: Cancelled by another cancelFocusAndMetering()`：
  - 視為**非致命**：因為「另一個 cancel 呼叫」的 cleanup 會覆蓋狀態，當前這次應可視為成功/可忽略
- 例外處理策略：
  - 仍記錄 log（建議降級為 warn/ info），避免誤判為 crash 級錯誤
  - 但流程需回報「已完成解鎖必要步驟」的結果（依現有 API 回傳/狀態設計決定）

預期效果：
- 不論使用者連點幾次，只要任一 cancel listener 被執行到，就會清掉 HAL 殘留鎖定參數，恢復自動 AE/AF。

### Plan B（保守加固，仍維持小改）
在 Plan A 基礎上，增加**去重/節流**避免並行 cancel：
- 方式 1（較小侵入）：在 `LiveCameraSource` 內保存一個 `AtomicBoolean` / 狀態旗標，若 cancel 進行中則忽略後續請求
- 方式 2（更完整但稍大）：用單一序列化 executor / coroutine mutex，確保 `cancelFocusAndMetering()` 不會並行

適用時機：
- 若 Plan A 修完仍出現「短時間大量 cancel」造成其他副作用（例如閃爍/狀態跳動），再上 Plan B。
