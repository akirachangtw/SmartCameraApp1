## Bug 1：有人臉時不會出現對焦框 — L2 深入分析

### 1.1 影像尺寸確認

透過程式碼追蹤確認實際值：

```
SmartCameraAnalyzer.kt:363:
    imageWidth = imageProxy.width    // sensor 原始 landscape 寬 = 640
    imageHeight = imageProxy.height  // sensor 原始 landscape 高 = 480
    rotationDegrees = 90°            // portrait 模式

ML Kit bboxes 座標空間：ROTATED 後（upright portrait）
    effectiveImageWidth  = rawImageHeight = 480
    effectiveImageHeight = rawImageWidth  = 640
```

**CoordinateTransformer 已正確處理**（`updateContentBounds()` 有相同 swap 邏輯）：
```kotlin
// updateContentBounds() 現有正確邏輯：
val (effectiveImageWidth, effectiveImageHeight) = if (rotation == 90 || rotation == 270) {
    rawImageHeight to rawImageWidth  // 480 to 640 ← 正確
}
```

**`calculateSaliencyScore()` 缺少此 swap**：
```kotlin
// 現有錯誤：傳入 previewWidth=1080, previewHeight=2340（螢幕尺寸）
val score = calculateSaliencyScore(face.boundingBox, true, viewWidth, viewHeight)
```

### 1.2 Score 數值對比

| 場景 | 修改前 score | 修改後 score | 閾值 50 |
|------|-------------|-------------|---------|
| 小臉（100×150 in 480×640, 邊緣位置） | ~38 | ~58 | ✓ 過 |
| 中臉（150×200, 略偏） | ~43 | ~68 | ✓ 過 |
| 大臉居中（200×300, 中心） | ~48 | ~76 | ✓ 過 |
| 理論最小可偵測臉 | ~35 | ~52 | ✓ 過 |

修改後所有常見人臉場景均超過 50 閾值。

## Bug 2：對焦框偶爾定在錯誤位置 — L2 深入分析

### 2.1 真實根因（L1 推測 TOCTOU 不準確）

**L1 推測**（錯誤）：background thread 與 main thread 的 state update race
**L2 確認根因**：`lastManualTapTime` 在 **coroutine 內部設定**，存在時序漏洞

#### 執行緒模型確認

```kotlin
// observePreviewForAnalysis()
.onEach { bitmap ->
    val detectionResult = analyzeImageWithMLKit()  // 內部 withContext(Default) 暫停 ~48ms
    // 暫停期間 Main thread 空閒，其他 coroutine 可執行
    updateTrackedObjectPosition(detectionResult)   // Main thread，無暫停點，atomic
    autoFocusOnSalientTarget()                     // Main thread，同步執行
}
.launchIn(viewModelScope)  // Dispatchers.Main
```

#### 競爭時序（導致 Bug）

```
時間軸（所有代碼在 Main thread 執行）：

t=-48ms: onEach 呼叫 analyzeImageWithMLKit() → 暫停（切至 Dispatchers.Default）

t=0:     用戶點擊牙線盒 → focusOnPoint(tap_x, tap_y, isUserTap=true)
         → focusJob?.cancel()（取消舊 job）
         → focusJob = viewModelScope.launch { /* coroutine A */ }
              ← 注意：此時 coroutine A 只是「排隊等待」，尚未執行！
         → focusOnPoint() 函數 return

t=0.1ms: ML Kit 分析完成 → onEach coroutine 在 Main thread 恢復
         → updateTrackedObjectPosition()
              val trackedId = state.trackedObjectId  // = face_A（coroutine A 還沒更新它！）
              計算 face_A 的 screenX, screenY
              _state.update { focusPoint = (face_x, face_y) }  ← 框跑到臉上 ⚠️
         → autoFocusOnSalientTarget()
              canAutoFocus 檢查：
                (now - lastManualTapTime) > 5000ms
                lastManualTapTime 仍是「舊值」！（coroutine A 還沒更新它！）
                → true → auto-focus 觸發！
              → focusOnPoint(face_screen_x, face_screen_y, isUserTap=false)
                   → focusJob?.cancel()  ← 取消 coroutine A！
                   → focusJob = launch { /* coroutine B (auto-focus) */ }

t=1ms:   coroutine A 被取消，lastManualTapTime 永遠不被更新
         coroutine B 執行：focusPoint = (face_screen_x, face_screen_y)
         結果：對焦框固定在臉上，用戶點擊無效  ← BUG

間歇性原因：只有 ML Kit 分析在「tap 觸發後、coroutine A 首行執行前」恰好完成時才發生
（~0.1ms 視窗，機率約 1-5%，符合「偶爾出現」描述）
```

### 2.2 修改方案（可行）

**方案 A（建議）**：將 `lastManualTapTime` 移至 coroutine **外部**設定

```kotlin
private fun focusOnPoint(x: Float, y: Float, viewWidth: Int, viewHeight: Int, isUserTap: Boolean = true) {
    focusJob?.cancel()
    // ✅ Fix Bug 2: 移至 launch{} 外部，確保 autoFocusOnSalientTarget 看到最新時間戳
    if (isUserTap) {
        lastManualTapTime = System.currentTimeMillis()
    }
    focusJob = viewModelScope.launch {
        try {
            // ❌ 移除此行（已移至外部）：
            // if (isUserTap) { lastManualTapTime = System.currentTimeMillis() }
```

此修改消除競爭視窗：
- `lastManualTapTime` 在 `focusJob?.cancel()` 之後立即設定（同步）
- `onEach` 恢復並執行 `autoFocusOnSalientTarget()` 時，看到最新的 `lastManualTapTime`
- `canAutoFocus` 為 false（在 5s 阻擋期內）→ 不觸發 auto-focus ✓
- `updateTrackedObjectPosition()` 的 `focusPoint` 設定問題仍在，但 coroutine A 不會被取消，最終 tap 座標會覆蓋 ✓

**方案 B（補強）**：在 `autoFocusOnSalientTarget()` 不使用 `focusOnPoint()` 的取消機制

```kotlin
// 在 autoFocusOnSalientTarget() 中，改為直接檢查而非依賴 cancel：
if (!canAutoFocus || isUserTapRecentlyQueued) return
```

但需要 `isUserTapRecentlyQueued` 旗標，較複雜。**建議僅用方案 A**。

**方案 C（額外補強，可選）**：在 `updateTrackedObjectPosition()` 的 state.update 中再次確認 trackedId

```kotlin
// 現有（line 810）：
_state.update { it.copy(focusPoint = Pair(screenX, screenY)) }

// 補強（防止在狀態已被 focusOnPoint 更新後覆蓋）：
_state.update { current ->
    if (current.trackedObjectId != trackedId) return@update current
    current.copy(focusPoint = Pair(screenX, screenY))
}
```

方案 A 是必要修正，方案 C 是防禦性補強，**建議 A+C 一起實作**。

### 2.3 風險評估

| 風險項 | 評估 | 緩解 |
|--------|------|------|
| 移動 lastManualTapTime 至 launch 外 | VERY LOW：只影響設定時序，語意不變 | - |
| lastManualTapTime 的 thread safety | LOW：Main thread only，無跨執行緒 | viewModelScope = Main |
| 方案 C 的 return@update 語法 | VERY LOW：Kotlin 標準 StateFlow pattern | - |
| 回歸：OF tracking 的 focusOnPoint 呼叫 | LOW：`isUserTap=false` 不更新 lastManualTapTime（正確） | 無需改動 |

## Fix 3：對焦框跟隨速度 — L2 深入分析

### 3.1 動畫參數確認

| 動畫 Spec | 約等效過渡時間 | 用戶感受 |
|-----------|-------------|---------|
| `Spring.StiffnessHigh` (10,000 N/m) | ~100-150ms | 快速追蹤，有輕微彈性 |
| `Spring.StiffnessMedium` (1,500 N/m) | ~350-500ms | 平滑流暢（目前，過慢） |
| `tween(80)` | 80ms 線性 | 近即時（適合 ML Kit 高頻更新） |
| `tween(0)` | 即時 | 無動畫（跳躍感） |

ML Kit bbox 更新頻率：~10 FPS（100ms 間隔，`sample(100)` 決定），
→ 動畫時間應 ≤ 100ms 才不會讓指示器「追不上」

### 3.2 修改方案（可行）

**方案 A（建議）**：恢復 `StiffnessHigh`（已在 v2.11.1 驗證）

```kotlin
// CameraScreen.kt FocusIndicator()
// 修改前（v2.11.4）：
animationSpec = if (isTracking) {
    spring(dampingRatio = Spring.DampingRatioNoBouncy, stiffness = Spring.StiffnessMedium)
} else {
    tween(0)
}

// 修改後：
animationSpec = if (isTracking) {
    spring(dampingRatio = Spring.DampingRatioNoBouncy, stiffness = Spring.StiffnessHigh)
} else {
    tween(0)
}
```

animatedX 和 animatedY 各一行，共 2 行修改。

**方案 B（備選）**：區分 ML Kit tracking vs OF tracking 的速度

```kotlin
val isMLKitTracking = state.trackedObjectId != null
val isOFTracking = state.trackedPointActive

animationSpec = when {
    isMLKitTracking -> tween(80)          // ML Kit：近即時
    isOFTracking    -> spring(stiffness = Spring.StiffnessHigh)  // OF：快速彈性
    else            -> tween(0)           // 靜態：無動畫
}
```

但 FocusIndicator 目前只接收 `isTracking` boolean，需修改簽名。**優先採用方案 A**，方案 B 留 v2.12.0 精細調整。

### 3.3 風險評估

| 風險項 | 評估 | 緩解 |
|--------|------|------|
| StiffnessHigh 在 OF tracking 是否過快 | LOW：OF 位置更新頻率約 30 FPS，100ms spring 合理 | - |
| 與 scale animation 的視覺衝突 | VERY LOW：position 和 scale 是獨立 Animatable | - |
| 回歸：AE/AF Lock 黃框位置跳躍 | VERY LOW：Lock 時 isTracking=false → tween(0)，不受影響 | - |
