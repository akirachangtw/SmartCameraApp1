## Bug 1: AE/AF 解鎖需要兩次點擊 (Double Click to Unlock)

### L2 Technical Tasks
1. **Module & Functions**:
   - `CameraScreen.kt` (UI Layer): 審查 `onTapToFocus` (或處理觸控事件的 Modifier) 的觸發條件與頻率。
   - `CameraViewModel.kt`: 檢查 `unlockAEAF()` 被呼叫後的 State 轉換邏輯。確認是否有路徑在 `isAeAfLocked == true` 時，不僅呼叫了 `unlock`，緊接著又呼叫了 `focusOnPoint`。
   - `LiveCameraSource.kt`: 確保 `cancelFocusAndMetering` 被執行時，確實能完全重置 Focus Engine。
2. **State Machine Adjustments**: 在 ViewModel 實作嚴格的 XOR 邏輯：
   ```kotlin
   if (state.isLocked) {
       unlock() 
       // **任務**: 確保沒有後續的 focus() 呼叫
       return 
   } else {
       focusOnPoint()
   }
   ```

### Technical Feasibility & Complexity
- **Feasibility: High**. 這是純邏輯與 ViewModel 狀態機流轉的問題，不涉及複雜的底層硬體操作。
- **Complexity: Low**. 透過明確的 `if-else` 分支即可解決。

### Potential Risks or Side Effects
- **Risk**: 如果使用者真的想要「解鎖並立刻對焦到新位置」，硬性擋下第二次 `focusOnPoint` 可能會讓使用者覺得沒對到新目標。
- **Mitigation**: 依賴連續被動對焦 (Passive Focus)。解鎖後，相機會自然接管回到自動尋找焦點。若使用者對被動找的焦點不滿意，他們自然會點下第二次 (這時 State 已解鎖，就變成正確的 Explicit Focus)。

### Suggested Alternative Approaches
- **UX Haptic Feedback**: 在 `unlock()` 發生的當下，加入短暫的震動 (`HapticFeedbackConstants.CONTEXT_CLICK`)，給予使用者明確的「解鎖成功」體感回饋，緩解視覺上因為 `AE SEARCHING` 時間差造成的「錯覺」。

### Logging & Debugging Areas
- **Breakpoints**: 設在 `CameraViewModel.kt` 的 `onTap` 處理函數。
- **Logcat Tags**:
  - `Log.d("UserAction", "Tap received, isLocked=${state.isLocked}")`
  - 觀察 `LiveCameraSource` 是否在短時間內連續收到 `cancelFocusAndMetering` 與 `startFocusAndMetering`。

## Bug 2: 螢幕關閉再開啟後，AE/AF 鎖定對焦框延遲 (Focus Box Delay After Screen Off/On)

### L2 Technical Tasks
1. **Module & Functions**:
   - `LiveCameraSource.kt`: 這是 CameraX `UseCase` 綁定 (`bindToLifecycle`) 的核心。
   - Android Lifecycle Observer: 檢視 `ON_STOP` / `ON_START` 對 Camera State 的影響。
2. **Event Sequence & Cleanup Compensation**: 
   - **任務**: 實作「最終一致性清理 (Eventual Consistency Cleanup)」。當 `cancelFocusAndMetering` 拋出 `OperationCanceledException` (尤其是由於 `Camera is not active` 引起時)，設置一個 `pendingCleanupRequired = true` 的 Flag。
   - **任務**: 在 `LiveCameraSource` 的 `bindToLifecycle` (或 Camera 成功啟動的 callback `cameraState.type == CameraState.Type.OPEN`) 中，檢查此 Flag，若為 True，則立即發送 `clearCaptureRequestOptions()` 掃除前一次 Lifecycle 殘留的 HAL 參數，然後設為 False。

### Technical Feasibility & Complexity
- **Feasibility: Medium-High**. CameraX 在 Lifecycle 轉場時非常積極地管理 Session，但在被強迫 Unbind 時，開發者自定義的 Camera2Interop Token 確實容易成為「孤兒參數」。
- **Complexity: Medium**. 需要準確捕捉 Camera 啟動完畢的時間點（避免在 Session 尚未建立時調用 CameraControl 導致新的 Exception）。

### Potential Risks or Side Effects
- **Risk**: 若在 Camera 剛啟動的非常初期 (例如 First Frame 產出前) 強制下發 `CaptureRequest`，可能會干擾 CameraX 自帶的 Initial 3A (Auto Exposure, Auto Focus, Auto White Balance) 收斂過程。
- **Mitigation**: 確保在 `CameraState.Type.OPEN` 且具有有效 `Surface` 的情況下，再執行補償清理。

### Suggested Alternative Approaches
- **Force Unconditional Cleanup on Bind**: 不管前一次是怎麼死的，只要 `bindToLifecycle` 被呼叫，預設就呼叫一次 `clearCaptureRequestOptions()` 及重設為 Continuous Picture 模式，保持乾淨的啟動狀態。這比維護一個 Pending Flag 更健壯 (Robust)。

### Logging & Debugging Areas
- **Breakpoints**: `ProcessLifecycleOwner` (或對應的 Activity/Fragment Lifecycle) 的 `onStop` 與 `onStart`。
- **Logcat Tags**:
  - `Log.d("CameraLifecycle", "Bind completed. Doing compensation cleanup.")`
  - `Log.w("CameraInterop", "Exception caught: ${e.message}")` (用來確認 Screen off 時的 Exception 種類)

## Bug 3: AE/AF 鎖定後預覽模糊 (Blurry Preview after Focus Lock - Pixel 9a Specific)

### L2 Technical Tasks
1. **Module & Functions**:
   - `LiveCameraSource.kt` (`lockAEAF` 函數): 處理 Camera2 Interop 的 `CaptureRequestOptions`。
2. **Camera2 API interaction**:
   - 目前實作可能設置了 `CaptureRequest.CONTROL_AF_MODE = CameraMetadata.CONTROL_AF_MODE_OFF` 來達成長按鎖定。
   - **任務**: 在 Pixel 9a 上，當 `AF_MODE` 切成 `OFF` 時，鏡頭馬達可能會失去驅動力並回歸無限遠 (Infinity) 或預設休眠位置。
   - **任務**: 利用 `CameraCaptureSession.CaptureCallback` 或現有的 `AE/AF Debug Callback`，在 `AF_STATE` 達到 `FOCUSED_LOCKED` 的瞬間，擷取 `CaptureResult.LENS_FOCUS_DISTANCE`。
   - **任務**: 在設定 `AF_MODE_OFF` 的同一個 `addCaptureRequestOptions` Builder 中，將剛才抓到的距離強塞回去：`setCaptureRequestOption(CaptureRequest.LENS_FOCUS_DISTANCE, extractedDistance)`。

### Technical Feasibility & Complexity
- **Feasibility: Medium**. Camera2 API 允許手動控制對焦距離，但需要判斷裝置是否支援手動對焦 (Capability: `REQUEST_AVAILABLE_CAPABILITIES_MANUAL_SENSOR`)。幸運的是，Pixel 9a 一定支援。
- **Complexity: High**. 捕捉 `LENS_FOCUS_DISTANCE` 是一個異步過程。必須等待 Metering Action 處於 `CONVERGED`/`LOCKED` 的那個特定 Frame 的 `CaptureResult`，才能取得準確數值，這需要撰寫一個狀態監聽器。

### Potential Risks or Side Effects
- **Risk (Device Quirks)**: 強迫寫入 `LENS_FOCUS_DISTANCE` 可能在某些 OEM 上被忽略，或導致底層 Driver Crash。
- **Risk (Precision)**: Float 精確度問題，寫入的距離跟馬達實際停留位置可能有微小落差，導致鎖定瞬間畫面「抖動」一下。

### Suggested Alternative Approaches
- **Alternative (Safe Strategy - Plan B)**: 不要使用 `CONTROL_AF_MODE_OFF` 來鎖定焦距！改為維持 `AF_MODE = AUTO` (或 `CONTINUOUS_PICTURE`)，但是透過 CameraX 的 `FocusMeteringAction` 將測光區域 (Metering Region) **縮到極小**，並告訴相機這就是唯一焦點。
  只要不重新觸發 `startFocusAndMetering` 且關閉場景變化偵測 (若硬體支援)，多數現代手機在 AUTO 下也能穩定保持焦點。這避開了 Pixel 9a 特有的 `AF_OFF` 漂移 Bug。

### Logging & Debugging Areas
- **Dumpsys**: `adb shell dumpsys media.camera` 觀察 Pixel 9a 相機 HAL 在鎖定時到底接收了什麼 Request。
- **Logcat Tags**:
  - `Log.i("FocusDebug", "Focus locked. Captured Distance: $focusDistance")`
  - 紀錄鎖定前後連續 10 個 Frame 的 `LENS_FOCUS_DISTANCE` 變化，以證實漂移現象。

## L2 總結與執行建議 (Summary & Next Steps)

根據上述架構分析，三個 Bug 的處理策略非常明確，建議依照 L1 所列的優先序進行：

1. **Bug 2 (Lifecycle & Cleanup)**: 最優先解決。實作「不管任何情況進入重新綁定 (`bindToLifecycle`) 時，無條件呼叫一次 Camera2Interop Cleanup」，這將終結一切跨生命週期的狀態殘留鬼影。
2. **Bug 3 (Pixel 9a AF 漂移)**: 這關乎核心的 Lock 品質。強烈建議先嘗試替代方案 (Alternative Plan B) — **不使用 `AF_MODE_OFF`**，而是單純依賴 `CONTROL_AE_LOCK = true` 配上 `FocusMeteringAction` 的狀態鎖定。若真會跑焦，再實作高成本的 `LENS_FOCUS_DISTANCE` 捕捉與手動寫入策略。
3. **Bug 1 (Double Click to Unlock)**: 修改 UI State Machine 的 if-else 邏輯，並強烈建議補上 `Haptic Feedback (震動回饋)` 以抹平日經暗光環境下的 1 秒測光體感延遲。這個變更最簡單，但極大幅度改善 UX。
