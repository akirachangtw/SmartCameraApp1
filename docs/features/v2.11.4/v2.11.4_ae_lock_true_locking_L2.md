# Level 2｜可行性檢視備忘錄（給 Claude Code 檢視 repo 用）
主題：`ae_lock_true_locking`（Focus scope: **Feature D only**）

---

## 1. 可行性結論（可行 / 不可行 / 需調整）
**可行（建議以最小 diff 方式修正）**。

理由：根因已確認為 **CameraX `FocusMeteringAction.FLAG_AE` 只設定 AE metering 區域，不會寫入 Camera2 的 `CONTROL_AE_LOCK`**。  
解法是以 **Camera2 Interop 的 `Camera2CameraControl.addCaptureRequestOptions()` 寫入 `CONTROL_AE_LOCK=true`**，且在取消鎖定時用 `clearCaptureRequestOptions()` 清除，屬於局部、可回滾、可驗證的修正。

1. **目前 `lockAEAF()` 已成功呼叫 `startFocusAndMetering()`**，且 callback success 時代表 metering region 設定完成（但尚未 AE lock）。
2. 專案 camera provider 實作使用的是 **CameraX + camera2 interop 可用**（目前 diff 已 import `Camera2CameraControl`, `CaptureRequestOptions`）。
3. `cancelFocusAndMetering()` 目前是正確的「解除」入口（UI/VM flow 會走到這裡），因此 **unlock 行為可集中在此**。
4. `cameraControl` / `cameraInfo` 在 `LiveCameraSource` 中可取得到對應的 `Camera2CameraControl.from(camera.cameraControl)`（需由 repo 實際物件生命週期驗證）。
5. 裝置支援 `CONTROL_AE_LOCK`（多數支援，但仍需在少數 device 上容錯；至少要做到「不崩潰、可 fallback」）。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX UseCase 生命週期/重綁定**  
   - 若 Preview/Analysis 重建或重新 bind，先前透過 `addCaptureRequestOptions()` 設定的 AE_LOCK 可能失效或持續（取決於 CameraX internal session）。需要確認重新 bind 時是否會帶著舊 options 或需要重設。
2. **模式切換 / UI state 與鎖定狀態不同步**  
   - 若 UI 顯示「已鎖定」但 `AE_LOCK` 尚未成功寫入（或寫入失敗），會造成誤導。建議至少 log/telemetry 可辨識。
3. **Thread / callback 時序**  
   - `startFocusAndMetering()` success callback 觸發後再寫 `AE_LOCK=true` 是合理時序，但仍可能遇到 race（例如立刻 cancel）。需確保 cancel 時 clear options 能覆蓋。
4. **與 AF lock / existing control options 互動**  
   - `clearCaptureRequestOptions()` 會清掉所有透過 interop 設的 request options；若專案其他地方也用 interop 設定（例如 NR, edge, etc），會被清掉 → 需 repo 搜尋確認是否只有 AE/AF lock 使用。
5. **ImageCapture / 拍照 pipeline 的 AE 行為**  
   - Preview session AE_LOCK=true 不代表 ImageCapture 的 capture request 一定鎖定（CameraX 可能另外發 capture request）。但多數情況下 cameraControl options 能影響 capture template；需實機驗證「拍照曝光不飄」。

## 4. 最小差異建議（Minimal diff approach：步驟化）
1. **只改 `LiveCameraSource.kt` 的兩個函式**（Feature D only）  
   - `lockAEAF()`：在 `startFocusAndMetering()` 的 success callback 後，加入：
     - `val c2 = Camera2CameraControl.from(camera.cameraControl)`
     - `c2.addCaptureRequestOptions(CaptureRequestOptions.Builder().setCaptureRequestOption(CaptureRequest.CONTROL_AE_LOCK, true).build())`
   - `cancelFocusAndMetering()`：在取消 metering 完成後，加入：
     - `Camera2CameraControl.from(camera.cameraControl).clearCaptureRequestOptions()`
2. **錯誤處理必須非致命**  
   - interop 呼叫包 try/catch，失敗只 log，不要中斷 UI flow（避免「點一下鎖定 app 直接壞掉」）。
3. **避免影響非 DEBUG 行為**  
   - 目前已有 DEBUG CaptureResult logging，可保留；但 AE_LOCK 實作不應只在 DEBUG，必須在 release 生效。
4. **不改動 ViewModel / UI state machine**  
   - 保持現有 lock/unlock 行為一致，僅讓它「真的鎖 AE」。
