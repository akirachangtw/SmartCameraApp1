## 1. 根本原因深入分析 (Root Cause Analysis)

使用者回報了兩個嚴重現象：
1. **AE/AF Lock 鎖定後無法正常解鎖** (連點失效，黃框消失但預覽仍暗)。
2. **手機螢幕解鎖後，AE/AF Lock 狀態異常** (黃框消失、曝光與對焦失效、延遲)。

根據 L1 文件的 Logcat 證據，這兩個現象的根源都指向了同一個問題：**CameraX `cancelFocusAndMetering` 的非同步操作與 Camera2Interop 狀態清理的競態條件 (Race Condition)**。

### 1.1 競態點：並發的 Cancel 請求
目前的程式碼架構將 Camera2Interop 的清理邏輯 (`clearCaptureRequestOptions`) 放在了 `future.get()` 之後：
```kotlin
// 問題程式碼結構情境：
val future = cameraControl.cancelFocusAndMetering()
future.addListener({
    try {
        future.get() // <-- 如果被另一個 cancel 取消，這裡會拋出 OperationCanceledException
        
        // --- 災難發生點 ---
        // 以下清理代碼因為上面的 Exception 而被跳過！
        camera2Control.clearCaptureRequestOptions()
        // ...
    } catch (e: Exception) {
        Log.e(TAG, "Cancel failed", e)
    }
}, executor)
```
- **連擊解鎖時**：使用者點擊第一次，產生 Future A。快速點擊第二次，產生 Future B。CameraX 會因為 B 的出現，強制取消 (Cancel) Future A。此時 A 的 `future.get()` 拋出 `OperationCanceledException`，導致 A 的清理代碼沒被執行。而 B 如果也因為某些原因（例如 UI 快速重繪）被拋棄，就會導致相機 HAL 永遠殘留著 `CONTROL_AE_LOCK=true`。
- **螢幕解鎖/生命週期重建時**：當螢幕關閉又打開，CameraX 的 UseCase 會經歷解綁 (unbind) 與重綁 (rebind)。在此過程中，舊的 Focus 操作會被 CameraX 底層強制 Cancel。這同樣會觸發上述的 `OperationCanceledException`，攔截了我們自己清理 `AE_LOCK` 的邏輯。UI 狀態（ViewModel）因為生命週期重建而重置（所以看不到黃框），但相機硬體 (HAL) 卻因為清理代碼沒掃到，依然處於鎖定狀態。

## 2. 最佳可行方案 (Best Solution)

針對這個問題，我們必須採取 L1 提到的 **Plan A (最小差異優先)** 並加上 **Plan B 的狀態防護**的綜合解法。我們必須保證：**無論 CameraX 的 Future 是成功、失敗、還是被取消，Camera2 的參數清理 (Cleanup) 絕對必須被執行 (At-Least-Once Guarantee)。**

### 2.1 實作細節

修改 `LiveCameraSource.kt` (或實際控制 CameraControl 的類別) 中的解鎖邏輯：

```kotlin
fun unlockAEAF() {
    // 1. 立即清理 Camera2 Interop 狀態 (保證執行，完全不依賴 Future 結果)
    @OptIn(ExperimentalCamera2Interop::class)
    val camera2Control = Camera2CameraControl.from(cameraControl)
    camera2Control.clearCaptureRequestOptions()
    
    // 2. 呼叫 CameraX 的取消測光
    val future = cameraControl.cancelFocusAndMetering()
    
    // 3. 處理 Future 結果 (僅作 Logging 或 UI 同步使用)
    future.addListener({
        try {
            future.get()
            Log.d(TAG, "Focus and metering cancelled successfully.")
        } catch (e: java.util.concurrent.ExecutionException) {
            val cause = e.cause
            if (cause is androidx.camera.core.CameraControl.OperationCanceledException) {
                // 這是預期內的行為 (被其他 Cancel 覆蓋或生命週期變化)，記錄即可，不當作 Error
                Log.w(TAG, "Focus/Metering cancel operation was superseded: ${cause.message}")
            } else {
                Log.e(TAG, "Error cancelling focus and metering", e)
            }
        } catch (e: Exception) {
            Log.e(TAG, "Unexpected error during cancel", e)
        }
    }, ContextCompat.getMainExecutor(context))
}
```

### 2.2 方案優勢
- **無條件清理**：把 `clearCaptureRequestOptions()` 及相關的參數反轉放在 `cancelFocusAndMetering` 呼叫或 Future 監聽之外/源頭。只要呼叫了 unlock 意圖，立即解除連動於 Camera2Interop 的硬體鎖。
- **解決螢幕解鎖問題**：由於硬體鎖已經被強制作廢，即使 CameraX 底層因為 Screen UI 重建而拋出 Cancel Exception，也不會影響到曝光的自由度。
- **優雅降級 Exception**：明確捕捉 `OperationCanceledException` 並將其視為 Warning (非致命)，避免誤導 Debug 過程。

## 3. 風險評估 (Risk Assessment)

### 3.1 相機管線錯位風險 (Camera Pipeline Synchronization Risk)
- **風險等級：低 (Low)**
- **說明**：先送出 `clearCaptureRequestOptions` 再呼叫 `cancelFocusAndMetering`，這兩者對 Camera HAL 來說都會轉譯成下一個 Frame 的 `CaptureRequest`。因為 CameraX 實際上也是在同一個 request queue 裡塞東西，這兩步緊接著呼叫並不會造成明顯的 Frame tearing 或曝光閃爍。

### 3.2 效能回歸風險 (Performance Regression)
- **風險等級：極低 (Minimal)**
- **說明**：即使使用者因為連點在一秒內觸發了 5 次解鎖，呼叫 5 次 `clearCaptureRequestOptions` 的開銷也極小，不會造成 Main Thread 阻塞或相機掉幀。

### 3.3 UI 狀態不一致風險 (UI State Drift)
- **風險等級：無 (None / Resolves existing issue)**
- **說明**：原先的 Bug 正是 UI (黃框消失) 和 HAL (依舊鎖定) 不對齊。採用此 Best Solution 後，只要 ViewModel 清除 Yellow Box 狀態的同時觸發此函數，HAL 就會保證解鎖，強迫兩者對齊。

## 4. 接下來的執行步驟 (Next Steps)

1. **定位目標檔案**：前往負責封裝 `CameraControl` 的層級 (通常為 `LiveCameraSource.kt` 或等價的元件)。
2. **重構 解鎖 / Cancel 方法**：將所有放入 `CaptureRequest.Builder` 的鎖定參數（如 `CONTROL_AE_LOCK = true`）的反向清理操作，移出 `future.get()` 的 `try-catch` 保護傘之下。
3. **優化 Exception 處理**：過濾掉 `OperationCanceledException`，只印 Warning，不阻礙任何狀態機的流轉。
4. **驗證與使用者確認**：編譯新版本並執行實機測試，要求在 Pixel 9a 上以「螢幕重啟」及「瘋狂連點」兩種極端條件確認預覽畫面與曝光是否迅速恢復正常。
