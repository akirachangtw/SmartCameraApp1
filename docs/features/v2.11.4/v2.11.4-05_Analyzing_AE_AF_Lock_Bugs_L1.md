# AE/AF Lock Bugs — L1 Planning Summary (High-Level)

本文件根據 L0 初步分析（`v2.11.4-05_Analyzing_AE_AF_Lock_Bugs_L0.md`）整理成 L1 高層次調查/解法規劃摘要，聚焦在策略性步驟與可落地的 investigation areas。

## L1 策略總覽（共通）

- **解耦 UI 與硬體狀態**：UI 只反映 `ViewModel state`；硬體參數（CameraX/Camera2 interop）的清理由 `LiveCameraSource` 以「可重入、可延後補償」方式保證最終一致，特別是 lifecycle/power 造成 `camera inactive` 的情境。
- **以狀態機 + 事件序列統一 3 個問題**：用同一視角檢視 `Lock → Unlock → Rebind(可能) → Next Lock/Focus` 的轉換點，在每個關鍵轉換處加上可觀測的 log/trace（專案已有 AE/AF debug callback 基礎可用）。

---

## Bug 1：AE/AF 解鎖需要兩次點擊（double click to unlock）

### 1) Key Areas of Investigation

- **ViewModel 解鎖分支是否 fall-through**：檢查 `focusOnPoint()` 在 `isAEAFLocked=true` 時是否還會繼續觸發後續對焦/取消流程，導致使用者感覺需要第二次點擊才「真的解鎖」。
- **UI 手勢與 lock state 的時序**：確認 `onTap` / `onLongPress` 的事件序列在解鎖瞬間不會立即觸發下一個 focus 動作或再次 cancel。

### 2) Solution Categories

- **UI event listener 行為修正**：避免同一次 tap 同時被當作「解鎖」與「對焦」。
- **狀態機 / 視覺回饋調整**：解鎖時提供明確的視覺狀態變化（例如 focus indicator 清空或短暫間隙），但避免引入新的 race。

### 3) High-Level Fix Strategy

- **明確規格化：locked 時 tap 只做 unlock**：locked 狀態下 tap 只執行 `unlock` 並立即 return；下一次 tap 才是 explicit point focus。
- **用最小 UI state 變更確保「已解鎖」可感知**：例如解鎖時清空 `focusPoint`，必要時加入短 delay 作為視覺間隙（以不引入競態為原則）。

## Bug 2：螢幕關閉再開啟後長按 AE/AF Lock 導致對焦框延遲

### 1) Key Areas of Investigation

- **Power/Lifecycle 觸發 unlock 的條件與時機**：`ON_STOP` / 背景化時是否觸發 `UnlockAEAF`，以及 `unlockAEAF()` 是否在「未鎖定」時仍會擾動 HAL（需確認 guard 覆蓋所有路徑）。
- **`cancelFocusAndMetering()` 在 camera inactive 時的例外與清理時序**：區分不同 `OperationCanceledException` 成因，特別是 `Camera is not active` 類型是否導致清理延後到下一次操作才生效。
- **Rebind 後是否需要補償式 cleanup**：`bindToLifecycle()` 綁定成功後是否應防禦性執行 `clearCaptureRequestOptions()`，避免殘留 interop options 造成下一次 lock/focus 延遲。

### 2) Solution Categories

- **狀態機邏輯強化**：將 unlock 與 camera lifecycle state 做更條件化的控制，避免背景/螢幕 off 時的無效硬體操作。
- **Camera API 呼叫/清理策略重構**：把 cleanup 做成「可延後、可重試、最終一致」。
- **Power management flow 釐清**：釐清 screen off/on 期間的 unbind/rebind 與手勢事件先後，以避免 race。

### 3) High-Level Fix Strategy

- **把 cleanup 從一次性改成最終一致**：若遇到 `camera inactive` 導致取消或清理無法完成，記錄 `pending cleanup`，在 `bindToLifecycle()` 重新綁定成功後立即補做清理。
- **避免 ON_STOP/背景期間擾動 HAL**：將「觸發 unlock」與「camera 是否 active」整合進同一條狀態機判斷，減少回前景後第一個 lock 的延遲與不確定性。

## Bug 3：AE/AF 鎖定後預覽模糊（Pixel 9a；AF_MODE=OFF 造成鏡頭漂移）

### 1) Key Areas of Investigation

- **`CONTROL_AF_MODE=OFF` 的副作用**：在 `lockAEAF()` 鎖定時設定 `AF_MODE=OFF` 是否造成某些裝置（Pixel 9a）在後續 capture request 週期中把鏡頭位置重置（例如漂移到 infinity）。
- **是否能凍結 focus distance**：專案已有 `CaptureResult.LENS_FOCUS_DISTANCE` 的讀取能力（debug callback），可用於量化「鎖定前後」鏡頭距離變化並作為 fix 的輸入值。
- **裝置/driver 差異**：確認這是 Camera HAL/driver 行為差異，並為裝置特定策略預留落點（feature flag / device profile / fallback policy）。

### 2) Solution Categories

- **Camera API call 調整**
  - 方案 A：維持 `AF_MODE=OFF`，但同步下發 `LENS_FOCUS_DISTANCE` 以凍結鏡頭位置。
  - 方案 B：避免 `AF_MODE=OFF`，改用較少 device-quirk 的 AF 策略（例如 AUTO/CONTINUOUS + 適當的 trigger/region）以提高跨裝置穩定性。
- **Driver interactions debugging**：用 debug logging 把 `focusDistance / AF_STATE` 的變化時點與漂移相關性釐清。

### 3) High-Level Fix Strategy

- **觀測→固定 的兩段式策略**
  1. 在 lock 成功回調（或 lock 前後）讀取 `LENS_FOCUS_DISTANCE`（收斂值）。
  2. 依裝置行為選擇 A/B：要嘛在 `AF_OFF` 同步凍結距離，要嘛切回較安全的 AF mode 策略。
- **建立裝置策略矩陣並記錄**：將 Pixel 9a 的行為與選定策略整理成可追溯文件（v2.11.4 docs），並保留未來擴充到其他裝置的結構。

---

## 建議處理順序（降低互相干擾）

1. **Bug 2（lifecycle/power 下的清理一致性）**：先把「回前景後第一個操作延遲」這種系統性不確定因素消除。
2. **Bug 3（device/driver + interop option 穩定性）**：在穩定的 lifecycle/cleanup 基礎上調整 lock 參數策略，降低誤判。
3. **Bug 1（UI 規格與視覺回饋收斂）**：最後收斂產品體感與操作規格，確保行為一致且不被前兩者競態影響。
