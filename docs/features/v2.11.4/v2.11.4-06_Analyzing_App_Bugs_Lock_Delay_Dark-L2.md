## Bug 1: Intermittent 5-Second Delay in Long-Press Unlock

This bug is primarily caused by stale HAL states surviving session recreation and race conditions between app-side commands and CameraX lifecycle events.

### 1. Feasibility of Resource Tracking
**Goal:** Detect resource leaks, dangling listeners, or blocked threads.
*   **Technical Feasibility (High):** Modern Android development tools make this highly feasible.
*   **Methods & Granular Breakdown:**
    *   **Android Studio Profilers:** Use the **Memory Profiler** to take heap dumps before and after a lifecycle transition (screen off -> screen on). Look for accumulated instances of `GestureDetector`, `CameraCaptureSession.CaptureCallback`, or custom `Runnable` objects.
    *   **Coroutine/Thread Diagnostics:** Enable Coroutine debug logging (`-Dkotlinx.coroutines.debug`). Create custom log tags that inject `Thread.currentThread().name` for every Camera2Interop call.
    *   **Handler Tracking:** If using `Handler`, dump the `MessageQueue` using `Looper.getMainLooper().dump(LogPrinter(Log.DEBUG, "MainLooper"), "")` upon `onResume` to detect stuck or heavily delayed callbacks.
*   **Resource Impact:** Very Low for logging/debugging. Heap dumps briefly pause the app but are only used in development.
*   **Side Effects:** Verbose logging in production could impact performance; ensure diagnostic logs are guarded by `BuildConfig.DEBUG`.

### 2. State Machine Refinement
**Goal:** Prevent the app state from diverging from the actual camera HAL state.
*   **Technical Feasibility (High):** Kotlin `StateFlow` within a `ViewModel` is the perfect modern architecture for this.
*   **Granular Breakdown:**
    *   Define a robust enum: `enum class AeAfLockState { UNLOCKED, LOCK_REQUESTED, LOCKED, UNLOCK_REQUESTED, SUSPENDED }`.
    *   **Transitions:**
        *   `UNLOCKED` -> User long presses -> `LOCK_REQUESTED`.
        *   CameraX `Future` completes successfully -> `LOCKED`.
        *   App goes to background (`ON_PAUSE`/`ON_STOP`) -> Force transition to `SUSPENDED`.
        *   App resumes (`ON_START`) -> Transition from `SUSPENDED` to `UNLOCKED` (and queue a mandatory hardware cleanup).
    *   *Crucial Variable:* Introduce a `sessionGenerationId` (an `Int` or `UUID`) that increments every time `bindToLifecycle` is called. Any callbacks holding an older `sessionGenerationId` must be immediately discarded.
*   **Resource Impact:** Negligible (state variables reside in memory).
*   **Side Effects:** UI might momentarily reflect an `UNLOCKED` state upon resume while the camera is still spinning up, but this is accurate to the hardware intent.

### 3. Event Listener Management
**Goal:** Prevent accumulation or incorrect firing of UI and camera listeners across lifecycle bounds.
*   **Technical Feasibility (High):** Standard Android lifecycle management practices apply.
*   **Granular Breakdown:**
    *   **UI Gestures:** Register touch listeners/GestureDetectors in `onResume` and nullify/remove them in `onPause`. Do not rely solely on View instantiation.
    *   **Camera Callbacks:** If using `Camera2CameraControl.addCaptureRequestOptions` combined with a custom `CaptureCallback`, ensure `clearCaptureRequestOptions()` is called reliably on `onStop`.
    *   **ViewModel Interactivity:** Use `repeatOnLifecycle(Lifecycle.State.STARTED)` in Compose or Fragments to collect state. This guarantees that UI events are only processed when the UI is actively visible, automatically pausing collection when the app is backgrounded.
*   **Resource Impact:** Positive. Reduces memory leaks and wasted CPU cycles handling events in the background.

### 4. Concurrency Handling
**Goal:** Prevent race conditions between `LockAEAF`, `UnlockAEAF`, and `bindToLifecycle`.
*   **Technical Feasibility (Medium-High):** Requires careful handling to avoid deadlocking the main thread or camera thread.
*   **Granular Breakdown:**
    *   **Mutex / Single-Threaded Dispatcher:** Create a dedicated single-threaded Coroutine dispatcher (`Executors.newSingleThreadExecutor().asCoroutineDispatcher()`) or use a `Mutex` in a `CoroutineScope` owned by the `LiveCameraSource`. All hardware operations (`startFocusAndMetering`, `clearCaptureRequestOptions`) must be posted to this queue.
    *   **Avoid Main Thread Blocking:** Never call `.get()` on a CameraX `ListenableFuture` on the Main Thread. Always use `.addListener()` or convert it to a suspending function using `await()`.
    *   **Atomic Flags:** For immediate checks (e.g., "Is a cleanup pending?"), an `AtomicBoolean(pendingCleanup)` is highly efficient and thread-safe without needing lock overhead.
*   **Resource Impact:** Very Low. Single-thread executors have minimal overhead.
*   **Side Effects:** Hardware commands will execute strictly sequentially. This prevents races but means command $N$ must wait for command $N-1$ to complete.

## Bug 2: Dark Camera Preview After Screen Unlock

This bug occurs because the HAL remembers `CONTROL_AE_LOCK = true` (and potentially weird ISO/Shutter values) from the previous session, but the app UI thinks it is unlocked.

### 1. Camera Re-initialization Robustness
**Goal:** Guarantee a known-good baseline on resume.
*   **Technical Feasibility (High):** CameraX handles the surface lifecycle, but Interop requires explicit management.
*   **Granular Breakdown (Sequence of API Calls):**
    1.  `ON_START` triggered.
    2.  `ProcessCameraProvider.unbindAll()` (ensure a clean slate).
    3.  `camera = ProcessCameraProvider.bindToLifecycle(...)`.
    4.  **Crucial Step:** Do *not* immediately apply options. Wait for the camera state to be `OPEN`. Observe `camera.cameraInfo.cameraState`.
    5.  Once `OPEN` (or on the first frame callback), execute `Camera2CameraControl.clearCaptureRequestOptions()`. This flushes out any residual `AE_LOCK` or `AF_MODE_OFF`.
    6.  *Only after* the clear completes, re-apply user-intended persistent settings (like dynamic Exposure Compensation / EV).
*   **Resource Impact:** Low. `unbindAll` and `bindToLifecycle` are standard CameraX operations.
*   **Side Effects:** A very brief flicker might be observed as the camera transitions from its cached hardware state to the flushed state, but this is vastly preferable to a permanently dark screen.

### 2. Exposure/Brightness Control
**Goal:** Specify which parameters to flush and which to restore.
*   **Technical Feasibility (High):** Uses standard Camera2 metadata keys.
*   **Granular Breakdown:**
    *   **Parameters to FORCE CLEAR (via `clearCaptureRequestOptions`):**
        *   `CaptureRequest.CONTROL_AE_LOCK` (Must revert to `false`).
        *   `CaptureRequest.CONTROL_AF_MODE` (Must revert to CameraX's defaults, usually `CONTINUOUS_PICTURE`).
        *   `CaptureRequest.LENS_FOCUS_DISTANCE` (Must be released back to auto).
    *   **Parameters to RESTORE (via CameraX APIs if possible, or Interop):**
        *   Exposure Compensation (EV): Use `CameraControl.setExposureCompensationIndex()`. This is safer than manually tweaking `SENSOR_SENSITIVITY` (ISO) and `SENSOR_EXPOSURE_TIME` via Interop, heavily reducing OEM-specific quirks.
*   **Alternative / Safer Approach:** Whenever possible, avoid overriding `CONTROL_AE_LOCK` manually. If lock is needed, rely solely on `FocusMeteringAction` with `FLAG_AE`. If manual Camera2 Interop is absolutely required for a specific device (like Pixel 9a), isolate that logic behind a device-specific feature flag.

### 3. Surface Re-attachment
**Goal:** Ensure the preview surface is correctly piped to the new capture session.
*   **Technical Feasibility (High):** Standard behavior of `PreviewView`.
*   **Granular Breakdown:**
    *   When using Jetpack Compose's `AndroidView` for `PreviewView` (or standard XML), ensure the `Preview.SurfaceProvider` is linked *before* calling `bindToLifecycle`.
    *   ```kotlin
        val preview = Preview.Builder().build().also {
            it.setSurfaceProvider(previewView.surfaceProvider)
        }
        cameraProvider.bindToLifecycle(lifecycleOwner, cameraSelector, preview, imageCapture)
        ```
    *   **Confirmation:** The darkness is highly likely *not* a surface detachment issue. If the surface were detached, the screen would typically be black or frozen on the last frame, not "dark/underexposed" (which implies a live feed with terrible AE parameters). Focus efforts on Step 1 & 2.

## Conclusion & Suggested Refinements

The L1 plan is structurally sound but needs to prioritize **CameraState Observation** over time-based delays. 

**Refined Architecture Recommendation:**
Do not rely on catching `OperationCanceledException` to trigger cleanups. Instead, adopt a **Reactive Camera Controller**:
1.  Wrap the CameraX `Camera` instance in a repository/controller.
2.  Expose the `CameraInfo.cameraState` as a Kotlin `Flow`.
3.  When the app resumes, a collection on this flow detects the transition to `CameraState.Type.OPEN`.
4.  This triggers an automatic `clearCaptureRequestOptions()`, completely independently of whatever UI buttons the user is pressing. This explicitly decouples the lifecycle-recovery logic from the user-intent logic, solving both Bug 1's delay and Bug 2's dark screen elegantly.
