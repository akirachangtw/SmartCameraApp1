# Level 2 可行性檢視備忘錄（給 Claude Code 檢視 repo 用）
主題：**unlock_fix_concurrent_cancel**

## 1. 可行性結論（可行 / 不可行 / 需調整）
**需調整（Plan A 不建議照提案「無條件 add 再 clear」原樣落地）**。

理由摘要：
- `clearCaptureRequestOptions()` 的語意是「清空 interop 覆寫」，**不保證**會把 AF mode 明確帶回 `CONTINUOUS_PICTURE`（多數情況會回到 CameraX 內部預設/3A 狀態，但遇到并發、rebind、或 CameraX 內部 state machine 切換時，結果可能不穩定）。
- 在 `future.get()` 前就操作 Camera2 interop options，可能與 `cancelFocusAndMetering()` 的內部流程競態，導致：
  - option 覆寫在下一個 request 才生效（或被內部 request 覆蓋），行為不可預期；
  - 或把你剛 set 的 `CONTINUOUS_PICTURE` 立刻清掉，等同沒做。
- `OperationCanceledException` 降級為 success 在「使用者體感與狀態機」層面大多可接受，但要配合**狀態校正**與**日志**，避免呼叫端誤以為已回 auto mode。

建議方向：
- 把「解除 AE_LOCK / AF_MODE_OFF」視為主要目標：**先 clear interop options，再（必要時）明確 set AF 連續模式**，並將 `OperationCanceledException` 視為「已無需等待的終態」而非錯誤；但要加上 rebind / isBound / cameraId 檢查與冪等保護。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX 內部 3A 狀態機競態（高）**
   - `cancelFocusAndMetering()` 本身會驅動內部 pipeline；同時呼叫 Camera2 interop option（set/clear）可能造成 request ordering 不確定，特別是在快速切換、連點、或 tracker 自動 refocus 情境。

2. **MainExecutor 不代表跨 Listener 全序（中高）**
   - `ContextCompat.getMainExecutor(context)` 雖在主執行緒串行跑 runnable，但「哪個 runnable 先被 post」取決於各 future 完成時間與 post 時機。
   - 若存在多個 future listener（或多次 cancel），**不能**假設 listener 會依呼叫順序執行。

3. **clearCaptureRequestOptions() 的語意落差（中高）**
   - clear 只移除你透過 interop 加的覆寫；CameraX 接下來會怎麼設 AF mode，依 use case 組合與當下 3A 狀態而定。
   - 因此「clear 後必回 CONTINUOUS_PICTURE」屬於不可靠假設。

4. **rebind / camera close 對舊 cameraControl 的安全性（中）**
   - 多數情況下舊 control 呼叫會失敗並回傳 failed future 或丟例外；但是否「一定不 crash」需以 CameraX 版本與實機行為驗證。
   - 特別要避免在 listener 裡對已失效 control 做多次 interop 呼叫，造成連鎖例外。

5. **呼叫端狀態機誤判（中）**
   - 若把 `OperationCanceledException` 當 success，但實際 AF/AE 尚未回 auto（或 camera 已 rebind），可能導致 UI 顯示「已解鎖」但實際拍照/追蹤仍用 lock 狀態。

## 4. 最小差異建議（Minimal diff approach：步驟化）
> 目標：修正「并發 cancel 導致 OperationCanceledException」同時，確保 AE/AF lock 覆寫被移除；避免引入更多競態。

**建議採用的最小 diff（比 Plan A 更可控）**：

1. **在 listener 內：優先處理例外分類，不要讓 OCE 變致命**
   - `future.get()` 包在 try/catch：
     - `OperationCanceledException`：記錄 warn，**視為可接受終態**（因為 cancel 的語意本來就是「不需要結果」）；繼續走清理流程並 `resume(success)`。
     - 其他 Exception：`resume(failure)`。

2. **清理 interop options 的動作改成「冪等且容錯」**
   - 保留你現有的 `clearCaptureRequestOptions()`，但不要假設一定成功；失敗只 warn（現在你已是這樣做）。

3. **是否需要「明確設回 CONTINUOUS」：改成條件式，不要 set+clear 連打**
   - 不建議「先 set CONTINUOUS 再 clear」這種互相抵消的 sequence。
   - 若你要「保險」：在 clear 之後**再 add 一次** `CONTROL_AF_MODE=CONTINUOUS_PICTURE`（且不要再 clear），但這會重新引入 interop 覆寫，需確認不會干擾 CameraX 自動 AF 行為。
   - 更保守：clear 即可；並在下一次正常對焦流程（或 camera rebind 完成）由 CameraX 自行回到合適 AF mode。

4. **加上 camera instance guard（避免舊 control callback 誤清新 camera 狀態）**
   - 在進入 `cancelFocusAndMetering()` 時 capture 一個 token（例如 `val cameraInstanceId = currentCameraBindId` 或 `val cameraHash = camera.hashCode()`）。
   - listener 觸發時先檢查 token 是否仍一致；不一致則只做安全結束（resume success 或直接 return，避免操作已過期 control）。

5. **避免 continuation 重複 resume**
   - 在 listener 與外層 catch 之間加保護（例如 `val resumed = AtomicBoolean(false)`），或改用 `runCatching` + `if (continuation.isActive)` 檢查。

### 對「L2 關鍵問題」的直接回答（供 Claude Code 審核時對照）
1. **add + clear 連續呼叫是否安全？**  
   通常不會 crash，但在語意上互相抵消、且與 CameraX request pipeline 可能競態；不建議「無條件連打」作為最小風險方案。

2. **MainExecutor 單執行緒是否保證多 listener 執行順序？**  
   不保證「依呼叫順序」，只保證「在主線程串行執行」。完成時間不同會改變入隊順序。

3. **clear 後是否確實恢復 CONTINUOUS_PICTURE 預設？**  
   不保證。clear 只移除 interop 覆寫；後續 AF mode 由 CameraX/3A 狀態機決定，裝置差異存在。

4. **OCE 降級 success 對呼叫者是否安全？**  
   多數情境可（cancel 本就不需結果），但要加上狀態校正/日志與 token guard，避免「誤以為已回 auto」的錯覺。

5. **rebind 發生時，對舊 cameraControl clear 是否安全（不 crash）？**  
   多數情況是失敗/丟例外而非 crash，但需做 try/catch + token guard，避免在 listener 裡連續操作失效 control 造成連鎖錯誤。
