# v2.11.4-06 Pinpoint FPS Bottleneck（L2：可行性評估與執行步驟）

基於 [L1：根因歸納與策略解法](v2.11.4-06_Pinpoint_FPS_Bottleneck-L1.md) 所提出的策略解決方案，本文件進行了深入的可行性與影響力評估，並決策出最優先的實作項目與其 L2 細節步驟。

---

## 1. 深入評估 (Critical Feasibility and Impact Assessment)

### 方案 1：分析用解析度分流（Preview/Capture 高解析度；Analysis 低解析度）
1. **Technical Feasibility:** **High** 
   * CameraX 架構原生支援對不同的 UseCase 注入獨立的 `ResolutionSelector`。實作上僅需修改 UseCase 的建構邏輯，將原本共用的 Selector 拆分。
2. **Estimated Performance Impact:** **High** 
   * 這是目前最關鍵的瓶頸。將 1:1 模式的輸入像素量從 ~3.7MP (1920x1920) 降至與其他比例相近的 ~0.23MP (例如 480x480)，處理量減少約 93%，預期對 FPS 與延遲的改善將極為顯著。
3. **Required Effort/Resources:** **Small** 
   * 約需 1-2 天的開發與跨機型測試時間。主要變更集中於 `LiveCameraSource` 的設定區塊。
4. **Potential Risks/Side Effects:** 
   * 分析用解析度若設定過低，可能導致 ML Kit (如：文字、人臉或物件追蹤) 無法準確辨識細節。需確認 ML 模型的最低輸入解析度要求（通常 480p 左右即可滿足大多數即時檢測需求）。

### 方案 2：在分析端做「輸入降採樣 / ROI 裁切」，將 ML 與轉換固定在小尺寸
1. **Technical Feasibility:** **Medium** 
   * 需在 `ImageAnalysis.Analyzer` 內介入影像處理管線，進行幾何運算（裁切）與縮放。自己實作高效的 YUV/Bitmap 縮放具一定複雜度。
2. **Estimated Performance Impact:** **Medium-High** 
   * 能有效減輕 ML 推論的負載，但依然需在 CPU 端承受大尺寸 YUV 轉 RGB 或初步讀取的記憶體開銷，改善幅度不如直出低解析度（方案 1）。
3. **Required Effort/Resources:** **Medium** 
   * 約需 3-5 天。包含撰寫高效能的裁切與縮放演算法（需處理旋轉矩陣），並對齊前後座標系統。
4. **Potential Risks/Side Effects:** 
   * CPU based 的大圖降採樣仍會導致 garbage collection (GC) 壓力與 CPU 高負載，尤其在高影格率下可能造成卡頓。

### 方案 3：加入分析吞吐控制（Backpressure / Frame Skipping / Adaptive FPS）
1. **Technical Feasibility:** **High** 
   * CameraX 內建 `STRATEGY_KEEP_ONLY_LATEST`，且在 Analyzer 實作自定義的「節流閥 (Throttle) / 跳幀策略」程式碼很直觀。
2. **Estimated Performance Impact:** **Medium** 
   * 不會加快單幀的處理速度，但能避免佇列堵塞（Queue back-up），確保 UI main thread 流暢並維持預覽畫面（Preview）的 FPS 不掉幀。
3. **Required Effort/Resources:** **Small** 
   * 約需不到 1 天。程式碼變動極小。
4. **Potential Risks/Side Effects:** 
   * 幀率過低時，追蹤框或分析結果的更新會產生視覺延遲（Lag / Jitter），框線可能跟不上移動中的物體。

### 方案 4：優化像素轉換與旋轉/縮放路徑（避免不必要的 bitmap work）
1. **Technical Feasibility:** **Low-Medium** 
   * 需引入如 libyuv (JNI/NDK) 或 Vulkan/OpenGL 等硬體加速方案來取代原生的 Bitmap 操作。
2. **Estimated Performance Impact:** **Medium** 
   * 減少 CPU 使用率和記憶體頻寬，但依然是在處理龐大的資料量，無法根本解決 1920x1920 的巨量像素問題。
3. **Required Effort/Resources:** **Large** 
   * 需數週開發時間，涉及跨端 (C++/Java) 介接，並帶來顯著的維護負擔與裝置相容性測試成本。
4. **Potential Risks/Side Effects:** 
   * 引入 NDK 庫會增加 APK 體積與 Crash 風險。硬體加速路徑在不同 OEM 手機上的行為可能不一致。

### 方案 5：讓「裝置最佳解析度」真正參與決策，並補齊可觀測性
1. **Technical Feasibility:** **High** 
   * 補充 Logs 與 Metrics 以觀測目前解析度。調整 `selectDeviceOptimalResolution()` 做為 Fallback 也是 CameraX 表層 API。
2. **Estimated Performance Impact:** **Low** 
   * 主要價值在於防禦性設計與未來除錯，對當下 FPS 無直接提升效果。
3. **Required Effort/Resources:** **Small** 
   * 約 1-2 天。整合效能追蹤埋點與 Log 輸出。
4. **Potential Risks/Side Effects:** 
   * 若演算法估算錯誤，可能會在部分高階機型上限縮了本可執行的更高解析度。

---

## 2. 優先方案決策 (Prioritization)

根據評估，**方案 1** 具備最高收益與最低風險，直指效能崩潰的物理根因（像素數量暴增）。**方案 3** 則可作為方案 1 的保險與防禦機制，確保在極端低階裝置上的穩定流暢度，且實作成本極低。

**優先級：方案 1 > 方案 3**

---

## 3. L2 具體執行步驟 (Actionable L2 Steps)

### 優先項目 1：實作分析用解析度分流 (Analysis Resolution Separation)

**目標**: 將 `ImageAnalysis` 的目標解析度在 1:1 模式下限制於 480×480 到 720×720 的級別，而 `Preview` 和 `ImageCapture` 維持既有高解析度。

1. **定位目標區塊**: 
   * 開啟相機管理模組（如 `LiveCameraSource.kt` 或負責 `ProcessCameraProvider.bindToLifecycle` 的類別）。
   * 尋找目前的 `ResolutionSelector` 實例（目前是 `Preview`, `ImageCapture`, `ImageAnalysis` 共用）。
2. **建立專屬 Analysis Selector**:
   * 新增一個變數 `analysisResolutionSelector`。
   * 根據當前 Aspect Ratio 進行條件判斷：
     * 若為 **4:3 或 16:9**：可以繼續使用 `AspectRatioStrategy` (系統會預設給一個較低的 480p 或 720p 組合)。
     * 若為 **1:1**：由於 1:1 經常被預設關聯到極大的正方形尺寸，需強制介入。使用 `ResolutionStrategy` 並傳入指定的 `Size` (例如 `Size(480, 480)` 或稍微大一點的 `Size(720, 720)` 視 ML 需求而定)。
     * 搭配 `FallbackRule`，例如：`ResolutionStrategy(Size(480, 480), ResolutionStrategy.FALLBACK_RULE_CLOSEST_HIGHER)` (確保不過度模糊)。
3. **保留高品質 Selector**:
   * 原本的 `commonSelector` 或 `previewCaptureSelector` 維持不變，繼續套用在 `Preview.Builder()` 和 `ImageCapture.Builder()`。
4. **繫結至 UseCase**:
   * 在 `ImageAnalysis.Builder()` 中，呼叫 `.setResolutionSelector(analysisResolutionSelector)`。
5. **維護視角一致性 (ViewPort)**:
   * 確保 `ViewPort` 的設定（`ViewPort.Builder(Rational(1, 1), displayRotation)`）依然應用於整個 `UseCaseGroup`。CameraX 會自動從高解析度 Preview / Analysis 中各自裁切出 1:1 的有效區塊供你使用，維持所見即所得。
6. **驗證**:
   * 切換至 1:1 模式，在 `Analyzer.analyze(image: ImageProxy)` 印出 `image.width` 與 `image.height`，確認已被壓縮到設定的尺寸區間 (例如 480x480)。

### 優先項目 2：加入分析吞吐控制與跳幀保護 (Backpressure & Throttle)

**目標**: 防止 ML 分析時間超過相機出幀時間，導致隊列積壓、主執行緒背壓和體感卡頓。

1. **強制最新幀策略**:
   * 在建立 `ImageAnalysis` 實例處，確保使用：`.setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)`。
   * 這會讓 CameraX 在分析器忙碌時自動丟棄舊幀，不排入隊列。
2. **實作 Analyzer 層級的主動節流閥 (Adaptive Throttle)**:
   * 在實作 `ImageAnalysis.Analyzer` 的類別中，新增變數紀錄上次分析時間：`private var lastAnalyzedTimestamp = 0L`。
   * 定義最大分析頻率常數：`private val MIN_FRAME_INTERVAL_MS = 66L` (約 15 FPS，適用於耗時的 ML 操作)。
3. **過濾過密集的幀**:
   * 於 `analyze(image: ImageProxy)` 的最開頭進行攔截：
     ```kotlin
     val currentTimestamp = System.currentTimeMillis()
     if (currentTimestamp - lastAnalyzedTimestamp < MIN_FRAME_INTERVAL_MS) {
         image.close() // 必須關閉
         return
     }
     lastAnalyzedTimestamp = currentTimestamp
     ```
4. **驗證**:
   * 在低階手機或開啟高負載的 ML 模組下，觀察是否 UI 滑動、按鈕與相機預覽皆不再發生遲滯與卡頓。
