# v2.11.4 Multi-Focus Coexistence — L1 Plan

**Date**: 2026-02-22
**Version**: v2.11.4 (planning for v2.11.5 or v2.12.0)
**Device**: Pixel 9a (59131JEBF17244)
**Branch**: feature/camera-core-v2.11.0

---

## 1. Background (What / Why)

v2.11.4-01 Pixel 9a 實測發現，目前對焦系統與專業相機行為有 3 項結構性差距：

| # | 現況 | 專業相機期待（Pixel 9 / iPhone / Sony Alpha） |
|---|------|----------------------------------------------|
| A | 對焦框**固定尺寸**，不隨主體大小改變 | 框的長寬隨 bounding box 縮放 |
| B | 永遠只顯示**單一框**（最高 saliency 候選者） | 多人臉 / 多物件 → 多框共存 |
| C | 點擊物件後 auto-focus 搶 focusPoint → **框來回跳動** | 使用者 tap 目標與 auto-focus 目標各自獨立顯示 |

這 3 項不是 Bug（saliency score / race 已修正），而是**架構層面的單焦點限制**。

---

## 2. Scope (影響範圍)

### 2.1 需修改的核心架構

| 層級 | 現況 | 目標 |
|------|------|------|
| **State** | `focusPoint: Pair<Float,Float>?`（單一點） | `focusTargets: List<FocusTarget>`（多點） |
| **ViewModel** | `autoFocusOnSalientTarget()` 選最高分 1 個 | 所有超過閾值的候選者都加入 |
| **UI** | `FocusIndicator()` 只渲染 1 個 | `FocusIndicatorLayer()` 渲染多個，各自獨立動畫 |
| **CameraX** | `focusOnPoint()` 對最高分目標發送 metering | 主要 metering 仍對最高分（硬體限制），但 UI 多框 |

### 2.2 新增資料模型

```kotlin
data class FocusTarget(
    val id: Int,                          // ML Kit trackingId or user-tap ID
    val position: Pair<Float, Float>,     // Screen-space center
    val boundingBox: Rect?,               // Screen-space bbox (for adaptive sizing)
    val type: FocusTargetType,            // FACE / OBJECT / USER_TAP
    val isPrimary: Boolean,               // Highest saliency = gets CameraX metering
    val saliencyScore: Float,
    val state: FocusTargetState           // FOCUSING / LOCKED / TRACKING / FADING
)

enum class FocusTargetType { FACE, OBJECT, USER_TAP }
enum class FocusTargetState { FOCUSING, LOCKED, TRACKING, FADING }
```

### 2.3 不觸碰範圍

- `CoordinateTransformer`（v2.11.3 已驗證）
- RANSAC / logicCenter / trackedCenter 架構
- `OpticalFlowConfig` 參數
- CameraX metering 底層 API（硬體只支援單一 metering point）
- AE/AF Lock 行為（已驗證一致）

## 3. Feature A — Adaptive Frame Size（框尺寸隨 bbox 縮放）

### 3.1 問題分析

目前 `FocusIndicator` 用固定 `size = 80.dp` 繪製。ML Kit 回傳的 `boundingBox` 資訊未傳遞到 UI 層。

### 3.2 方案

1. `updateTrackedObjectPosition()` 中已有 `face.boundingBox` / `obj.boundingBox`
2. 將 bbox 轉換至 screen-space（使用 `CoordinateTransformer`）後存入 state
3. `FocusIndicator` 接收 bbox width/height，繪製時以此決定框尺寸
4. 設定 min/max clamp（避免過小或過大的框）

### 3.3 最小尺寸閾值（忽略過小人臉）

```
建議：bbox screen-space 面積 < 40×40 dp → 忽略（不顯示框）
依據：40dp ≈ 手指觸控最小區域，小於此的人臉在手機上幾乎無法辨識
```

### 3.4 預估改動

| 檔案 | 改動 |
|------|------|
| `CameraUiState` | 新增 `focusBoundingBox: Rect?` |
| `CameraViewModel.kt` | `updateTrackedObjectPosition()` 傳遞 screen-space bbox |
| `CameraScreen.kt` | `FocusIndicator()` 接收 bbox 尺寸 |

## 4. Feature B — Multi-Focus Display（多框共存）

### 4.1 問題分析

目前架構是 **single focusPoint** → `autoFocusOnSalientTarget()` 只保留 1 個最高分候選者。
使用者 tap 也寫入同一個 `focusPoint` → auto-focus 與 user tap 互相覆蓋 → 框跳動。

### 4.2 方案

**Phase 1：UI 多框（Low Risk）**
- State 改為 `focusTargets: List<FocusTarget>`
- `autoFocusOnSalientTarget()` 收集**所有** score > 閾值的候選者
- UI 渲染每個 `FocusTarget` 各自獨立的 `FocusIndicator`
- CameraX metering 仍只對 `isPrimary=true` 的目標發送（硬體限制）

**Phase 2：User Tap 獨立（Medium Risk）**
- User tap 建立 `FocusTargetType.USER_TAP` 條目，不與 auto-focus 搶同一 slot
- Auto-focus 候選者不覆蓋 user tap 目標
- User tap 目標有獨立的 5 秒 override 計時器

### 4.3 多框視覺規則（參考 Sony Alpha / Canon R 系列）

| 條件 | 視覺 |
|------|------|
| Primary（最高分 / user tap） | Cyan 粗框（2.5dp），full alpha |
| Secondary（其他候選者） | Cyan 細框（1.0dp），alpha 0.5 |
| Locked（AE/AF Lock） | Yellow 粗框，full alpha |
| 過小（< 40dp） | 不顯示 |
| 超過 5 個候選者 | 只顯示 top 5（避免畫面雜亂） |

### 4.4 預估改動

| 檔案 | 改動 | 風險 |
|------|------|------|
| `CameraUiState` | `focusPoint` → `focusTargets: List<FocusTarget>` | HIGH（breaking change） |
| `CameraViewModel.kt` | 重構 auto-focus + tracking + user tap 管理 | HIGH |
| `CameraScreen.kt` | `FocusIndicatorLayer()` 渲染 N 個 indicator | MEDIUM |
| 所有讀取 `focusPoint` 的位置 | 遷移至 `focusTargets` API | MEDIUM |

## 5. Feature C — Anti-Flicker（防止框跳動）

### 5.1 問題分析

框在 user tap 目標和 auto-focus 人臉之間跳動，因為兩者寫入同一 `focusPoint`。

### 5.2 方案（依賴 Feature B）

Feature B 實作後，user tap 和 auto-focus 各有獨立 `FocusTarget`，天然解決跳動問題。

額外防護：
- `autoFocusOnSalientTarget()` 不對已有 `USER_TAP` 目標的 trackingId 發起 auto-focus
- User tap override 期間（5 秒），auto-focus 候選者降為 secondary 顯示，不搶 CameraX metering

# Feature D — AE Lock 真正鎖定（Camera2 CONTROL_AE_LOCK）

**發現日期**: 2026-02-22
**觸發事件**: Camera2 CaptureResult debug logging（v2.11.4-01 方法 A 驗證）

---

## D.1 問題描述

**現象**：長按觸發 AE/AF Lock 後，曝光參數（ISO / exposure time）仍持續變化。
將手機從明亮環境移至暗環境，ISO 從 29 飆升至 669（23 倍），exposure 從 4ms 升至 60ms。

**Camera2 debug log 證據（2026-02-22 Pixel 9a 實測）**：

```
17:58:02  [AE/AF Debug] AF_STATE=FOCUSED_LOCKED, AE_STATE=SEARCHING, AE_LOCK=false, ISO=29,  exposure=9.997ms,  focusDist=2.746
17:58:04  [AE/AF Debug] AF_STATE=FOCUSED_LOCKED, AE_STATE=CONVERGED, AE_LOCK=false, ISO=29,  exposure=4.123ms,  focusDist=4.781
17:58:11  [AE/AF Debug] AF_STATE=FOCUSED_LOCKED, AE_STATE=SEARCHING, AE_LOCK=false, ISO=43,  exposure=20.003ms, focusDist=3.259  ← 開始漂移
17:58:13  [AE/AF Debug] AF_STATE=PASSIVE_FOCUSED, AE_STATE=CONVERGED, AE_LOCK=false, ISO=56,  exposure=9.998ms,  focusDist=2.346  ← AF 也釋放
17:58:22  [AE/AF Debug] AF_STATE=PASSIVE_SCAN,   AE_STATE=SEARCHING, AE_LOCK=false, ISO=412, exposure=30.001ms, focusDist=4.725
17:58:23  [AE/AF Debug] AF_STATE=PASSIVE_SCAN,   AE_STATE=SEARCHING, AE_LOCK=false, ISO=614, exposure=60.002ms, focusDist=2.461
17:58:30  [AE/AF Debug] Logging DISABLED — returned to auto mode
```

**關鍵指標**：
- `AE_LOCK=false` — **全程 false**，AE 從未被鎖定
- `AE_STATE` 在 `SEARCHING` / `CONVERGED` 間持續震盪（表示 HAL 仍在自動調光）
- `AF_STATE` 從 `FOCUSED_LOCKED` 退化為 `PASSIVE_FOCUSED` → `PASSIVE_SCAN`（AF 也自動釋放）
- ISO 變化：29 → 669（**+2207%**），exposure：4ms → 60ms（**+1400%**）

---

## D.2 根本原因

**CameraX `FocusMeteringAction.FLAG_AE` ≠ Camera2 `CONTROL_AE_LOCK=true`**

| API | 作用 |
|-----|------|
| `FocusMeteringAction.FLAG_AE` | 設定 **AE metering region**（告訴 HAL 從哪個區域測光） |
| `CONTROL_AE_LOCK = true` | **凍結曝光參數**（停止 HAL 調整 ISO / shutter） |

`FLAG_AE` 只影響測光區域，不凍結參數。真正的曝光鎖定必須透過 Camera2 `CONTROL_AE_LOCK`。

同樣地，AF 鎖定也需要 `CONTROL_AF_MODE = AF_MODE_AUTO`（在 focus 完成後維持）。CameraX 的 `FLAG_AF` 在 metering 完成後可能由 HAL 切回 passive mode。

---

## D.3 修正方案

### 核心修正（2 個 API 呼叫）

**Lock 時**（在 `FocusMeteringAction` callback 成功後呼叫）：

```kotlin
@OptIn(ExperimentalCamera2Interop::class)
Camera2CameraControl.from(cameraControl)
    .addCaptureRequestOptions(
        CaptureRequestOptions.Builder()
            .setCaptureRequestOption(CaptureRequest.CONTROL_AE_LOCK, true)
            .build()
    )
```

**Unlock 時**（在 `cancelFocusAndMetering()` 後呼叫）：

```kotlin
@OptIn(ExperimentalCamera2Interop::class)
Camera2CameraControl.from(cameraControl).clearCaptureRequestOptions()
```

### 修改位置

| 檔案 | 位置 | 修改 |
|------|------|------|
| `LiveCameraSource.kt` | `lockAEAF()` callback 成功路徑 | 加 `addCaptureRequestOptions(CONTROL_AE_LOCK=true)` |
| `LiveCameraSource.kt` | `cancelFocusAndMetering()` callback 成功路徑 | 加 `clearCaptureRequestOptions()` |

**不需要修改**：`CameraViewModel.kt`、`CameraScreen.kt`、`CameraUiState`
