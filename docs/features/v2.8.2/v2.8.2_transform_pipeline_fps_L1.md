# Level 1 規劃摘要：v2.8.2_Transform_pipeline_FPS

## 1. 目標（Goal）
- **主要目標**：在 **Sony XQ-BT52（SD690 / Android 12）** 上，將 Live camera pipeline 的實際 FPS 由 **~19–20 提升至 ≥ 26 FPS**（不降低畫質/功能為前提，允許「可控降級」作為備案）。
- **次要目標**：
  - 讓 **Transform** 階段（旋轉/縮放/鏡像/overlay/composition analysis 等）時間更穩定，降低抖動（例如從 8–31ms 收斂）。
  - 維持既有成果：**YUV→RGB 平均 5.4ms（RS）**、**0 dropped frames**、無 crash。

---

## 2. 背景與問題（Why / What）
- v2.8.2 Phase C 已成功把 **YUV 轉換**優化到平均 **5.4ms**（RS GPU/高度優化 fallback），相較 Phase B-1（39.6ms）提升 **7.3x**。
- 但整體 FPS 仍只有 **~19–20（目標 ≥ 26）**。從 timing log 可見瓶頸轉移到 **Transform**：
  - `Transform=8–31ms` 波動很大
  - 單幀總耗時約 `YUV(5.4) + Transform(8–31) = 13–36ms`
  - 以最差 36ms 計算，理論上限約 27 FPS，實測 peak 24.3，吻合「Transform 成為新瓶頸」的推論
- Transform 可能包含：
  - Canvas drawBitmap + Matrix（旋轉/鏡像/位移）與可能的縮放
  - composition analysis / overlay 繪製
  - UI 更新（含 Compose recomposition 或 bitmap 顯示端的成本）
  - 額外 bitmap buffer 管理（pool acquire/release、in-flight queue）造成的記憶體/GC/同步成本

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
1. **相機管線風險（CameraX / ImageAnalysis）**
   - 調整 backpressure 或解析度可能改變 frame delivery 行為，導致分析頻率下降或延遲上升。
2. **模式切換風險（前後鏡 / 旋轉 / 重綁定）**
   - Transform 若改為「條件式跳過」或「不同路徑」，可能引入 front camera 鏡像方向錯誤、rotation 不一致、或 rebind 後 analyzer 未正確恢復。
3. **效能回歸風險（FPS / 延遲 / 抖動）**
   - 為了減少 Transform 成本而改變 buffer 生存週期，可能造成更多拷貝、GC、或鎖競爭，反而讓 FPS 更差或抖動更大。
4. **記憶體與資源風險**
   - BitmapPool 若 key 爆炸（多尺寸輸出）會造成池化失效、記憶體上升；in-flight queue 若釋放時機不對可能造成暫存堆積。
5. **RenderScript 未來相容性（既知風險延伸）**
   - 本次焦點是 Transform，但若方案牽涉 RS / GPU API，需留意 Android 未來版本移除 RS 的風險。
6. **視覺正確性風險**
   - 任何「避免旋轉/避免建立新 bitmap」的優化，都可能造成畫面裁切、拉伸、鋸齒、透明底色處理錯誤（PorterDuff CLEAR）或 overlay 對不齊。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
> 原則：**先減少 Transform 的工作量與頻率（不改架構）**，再考慮 GPU/並行化等較大改動。

### Plan A（最小差異 / 優先）
A1. **把「旋轉/鏡像」盡量移到顯示層或 CameraX 設定，降低每幀 bitmap transform**
- 優先檢查能否透過：
  - `PreviewView` / 顯示層的 transform（例如 View 層 matrix）
  - CameraX target rotation / setTargetRotation（或 use case 配置）
- 目標：讓 `transformBitmap()` 在大多數情境變成「不需要產生新 bitmap」（或至少不需要 Canvas draw）。
- 風險：需要確認前鏡 mirror 與 rotation 的視覺一致性；不同裝置 sensor orientation 可能不一致。

A2. **Transform 條件化與降頻（Decimation）**
- 若 Transform 內含 composition analysis / overlay，考慮：
  - overlay 每幀更新，但 analysis **每 N 幀**更新一次（例如 2~3 幀一次）
  - 或 analysis 與 overlay 拆開：analysis 降頻，overlay 使用上次結果
- 目標：把 Transform 平均時間與最差時間壓下來（尤其是 30ms 尖峰）。

A3. **固定輸出尺寸策略，避免 BitmapPool 因旋轉導致多尺寸 key**
- 目前旋轉後輸出可能改變寬高（用 mapRect + ceil），會引入更多 bitmap 尺寸組合。
- 最小差異作法：將輸出 **固定為同一尺寸**（例如保持 720x720），旋轉以「填滿/裁切」策略處理，避免 pool 分裂。
- 目標：減少 acquire 分配與 pool miss，降低抖動。

A4. **精簡 Canvas pipeline（同尺寸快速路徑）**
- 若 degrees 是 90/270 且固定方形輸入（720x720），可以走更簡化的矩陣與繪製設定（少做 mapRect/ceil/clear）。
- 目標：縮短 Transform 基礎成本、減少波動。

### Plan B（較大改動 / 備案）
B1. **GPU-based Transform（OpenGL ES / Vulkan / Android Graphics Pipeline）**
- 把旋轉、縮放、鏡像、overlay 合併到 GPU render pass，CPU 僅做最小工作。
- 代價：架構改動較大、需要新增渲染管線與更多裝置相容性測試。

B2. **並行化 pipeline（double-buffer / producer-consumer）**
- 將 YUV convert、Transform、analysis 分成不同 stage，做更明確的佇列與背壓控制。
- 代價：同步與 buffer ownership 複雜度上升，模式切換風險提高。

## 7. 回滾策略（Rollback）
- 使用 **feature flag / runtime switch** 回退 Transform 優化路徑：
  - 例：`ENABLE_FAST_TRANSFORM`（或沿用既有 config 機制）
- 保留舊 `transformBitmap()` 實作一段時間（或以策略模式切換）。
- 若改動牽涉 CameraX rotation/display transform：
  - 保留原本「CPU Canvas 旋轉」路徑作 fallback（確保方向正確優先於效能）。
- 回滾驗收：回到 v2.8.2 現況（YUV 5.4ms、FPS 19–20、穩定）即可視為安全回退。
