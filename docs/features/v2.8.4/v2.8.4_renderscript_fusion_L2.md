# v2.8.4_renderscript_fusion｜Level 2 可行性檢視備忘錄（給 Claude Code）

## 1. 可行性結論（可行 / 不可行 / 需調整）
**需調整（條件式可行）**  

RenderScript 做 **YUV→RGB + Transform（rotation/mirror）fusion** 在技術上可行，但是否能穩定達成 **21ms → 7–10ms** 需要先用 repo 現況與實測 profiling 證實「瓶頸確實集中在 YUV→RGB + Transform 且存在可被 fusion 消掉的 copy / pass」。  
另外 RS 已 deprecated，專案的 **targetSdk / minSdk / 既有 RS 依賴狀況** 會直接影響落地方式（support mode、打包設定、裝置相容與維護成本）。因此建議以 **Plan A profiling + 最小改動的 RS intrinsic/既有轉換優化** 作為 Gate；通過 Gate 才進入 fusion kernel。

## 2. 關鍵假設（Assumptions：哪些需由 repo 或 log 來驗證）
需由 Claude Code 透過 code search、執行 log、trace 來確認：

1. **目前 21ms/frame 的分佈**

   - 需驗證：是否已有分段計時（例如 `measureTimeMillis`、`Trace.beginSection`、perf logger）。

2. **目前 YUV→RGB 的實作路徑**
   - 假設：當前不是已經「單 pass + 零 copy」；存在中間 Bitmap / ByteBuffer 拷貝。
   - 需驗證：使用 CPU（自寫 converter / libyuv）還是 RenderScript intrinsic（如 `ScriptIntrinsicYuvToRGB`），或 GPU shader。

3. **Transform（rotation/mirror/crop/resize）目前在哪裡做、做幾次**
   - 假設：Transform 發生在 RGB 後、且至少一次額外 pass（例如先轉 RGB 再 rotate/mirror，再 resize）。
   - 需驗證：是否透過 Matrix/Bitmap、OpenGL、或自寫像素搬移。

4. **CameraX 設定與 backpressure**
   - 假設：Analyzer 可能被阻塞（造成掉幀），或 queue 堆積。
   - 需驗證：`ImageAnalysis.Builder.setBackpressureStrategy()` 是否為 `STRATEGY_KEEP_ONLY_LATEST`；`setOutputImageFormat` 是否為 `YUV_420_888`；Analyzer executor/threading。

5. **模式切換（Live / Static / Debug）是否共用同一 pipeline**
   - 假設：共用同一轉換 API；fusion 會影響 debug 中間輸出。
   - 需驗證：模式入口、共用的 converter/transform service 是否單例、是否可插拔。

6. **RenderScript 在專案中的現況**
   - 假設：專案可能已有 `app/src/main/rs/` 或既有 RS 管線與 Allocation 管理。
   - 需驗證：Gradle 是否啟用 renderscript support mode / 相關依賴；是否已有 RS Context lifecycle（建立/釋放）。

## 3. 高風險點（High-risk areas：CameraX Preview/ImageAnalysis/模式切換/Thread/權限）
1. **CameraX ImageAnalysis 執行緒阻塞**
   - RS kernel dispatch 若同步等待回傳、或 Allocation copy 回 CPU，可能使 Analyzer thread 卡住 → FPS 更低。
   - 需檢查：Analyzer executor 是否單執行緒；是否在 `analyze(image)` 內做重工作且未快進快出。

2. **YUV_420_888 plane/stride/pixelStride 相容性**
   - 高風險：不同裝置 pixelStride 可能為 1 或 2；rowStride 不等於 width。
   - fusion kernel 若假設 contiguous 會導致色偏/錯位。

3. **前鏡頭 mirror + rotation 座標映射**
   - CameraX `imageProxy.imageInfo.rotationDegrees` + 裝置 orientation + 前鏡頭鏡像規則容易出現「Preview 正確但 Analysis 反了」。
   - overlay 對齊（偵測框）也會因此回歸。

4. **模式切換資源釋放（RS Context/Allocation 泄漏）**
   - Live → Static / Debug 切換若未關閉 RS、Allocation 未 destroy，可能出現記憶體持續上升、黑屏、或 GPU resource leak。

5. **RenderScript deprecated 的長期風險**
   - 新裝置/新 driver 表現不可預期；targetSdk 提升後可能需要額外調整打包或改走替代方案。
   - 若專案有「長期維護」要求，需保留 fallback 且避免 RS 成為唯一路徑。

6. **輸出格式與 AI 前處理耦合**
   - fusion 若直接輸出 RGB ByteBuffer（或 RGBA），必須與模型 input tensor layout、normalization、stride 完全一致；否則會導致準確率下降（功能回歸但不易察覺）。

## 4. 最小差異建議（Minimal diff approach：步驟化）
> 目標：先「量到」再「合併」，全程可 fallback、可逐步上線。

1. **先做 Profiling 插樁（不改演算法）**
   - 在 Analyzer pipeline 內對以下段落加上統一的 timer/Trace：
     - acquire image → YUV→RGB → Transform → resize/crop → preprocess → inference → postprocess → render/overlay
   - 產出每段 avg / P95（至少 logcat），作為 Gate。

2. **整理出單一「FrameProcessor interface」做可插拔**
   - 不改外部呼叫，只把內部實作抽成：
     - `DefaultProcessor`（現況）
     - `RsFusionProcessor`（新）
   - 用 feature flag 決定用哪個 Processor。

3. **先做「RS 非 fusion」版本（若 repo 目前是 CPU）**
   - 低風險路徑：先替換成 RS intrinsic 的 YUV→RGB（或沿用 repo 既有 RS），Transform 保持原樣。
   - 驗證：確認 RS 對特定裝置是否已經省下主要成本、且沒有色偏。

4. **再做「半 fusion」：Transform 先移入同一個 pass 的 resize/crop（若可）**
   - 若目前存在 resize/crop pass，可嘗試把 rotation/mirror 融合進該 pass（不一定 RS kernel）。
   - 這一步常能省一次 bitmap copy / buffer pass，且比自訂 RS kernel 風險低。

5. **最後才進入 RS 自訂 fusion kernel（B 方案）**
   - 僅在 profiling 證實：YUV→RGB + Transform 確為最大宗，且中間 copy 明確可被消除時進行。
   - kernel 輸出先以 **RGBA_8888**（或專案現行最相容）降低整合難度，再視模型需求改成 RGB planar/packed。

## 7. 回滾與降風險策略（Rollback/Feature flag）
1. **Feature flag（硬性要求）**
   - `rsFusionEnabled`：預設 **false**
   - 支援 runtime 切換（至少在 app 啟動時可由設定/remote config 決定）
   - 可加裝置黑名單：model + sdk + vendor

2. **保留原路徑（不移除、不覆寫）**
   - 原本 YUV→RGB 與 Transform 實作完整保留
   - 新增的 fusion processor 走「旁路」插入，不破壞既有 API

3. **失敗即降級（Fail-open）**
   - RS 初始化失敗 / kernel compile 失敗 / allocation mismatch：
     - 自動切回 DefaultProcessor
     - 並記錄一次性事件 log（避免一直噴）

4. **Debug 可觀測性**
   - 即便 fusion 取消中間 buffer，也要能輸出關鍵診斷資訊：
     - rotationDegrees、mirror flag、input/output size、rowStride/pixelStride
   - 若專案有 Debug 顯示中間圖：提供「抽樣輸出」機制（例如每 N 幀輸出一次）避免影響效能。

5. **灰度策略**
   - 先只對 1–2 款測試機型開啟（白名單），確認穩定後再擴大
   - 發現任一機型色偏或 FPS 下降：立即 remote 關閉
