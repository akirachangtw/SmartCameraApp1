# v2.8.4_renderscript_fusion｜Level 1 規劃摘要

## 1. 目標（Goal）
- 將即時影像處理總耗時由目前約 **21ms/frame** 降至 **7–10ms/frame**。
- 將即時推流/分析 FPS 由目前 **19–20 FPS** 提升到 **≥ 26 FPS**（以中高階實機為主）。
- 以「最小差異」為原則：先確認瓶頸與可達成幅度，再決定是否投入高風險的 RenderScript 自訂 kernel。

---

## 2. 背景與問題（Why / What）
- 目前管線中存在 **YUV → RGB 轉換** 與 **Transform（旋轉 + 鏡像）** 的分段處理，推測包含：
  - 多次 memory copy / buffer 讀寫
  - CPU 與 GPU / 或不同處理階段間的同步成本
  - 旋轉/鏡像在 RGB 後做造成額外成本
- 使用者補充的 Plan B 構想：  
  **RenderScript YUV+Transform Fusion**：把 YUV→RGB 與 Transform 合併成單一 RenderScript kernel，嘗試達成「GPU 端到端處理」，減少中間 buffer 與多次 pass。
- 挑戰：RenderScript 已被官方 deprecated（雖仍可用 Support mode/既有裝置），自訂 kernel 複雜且容易踩到：
  - YUV 格式差異（YUV_420_888 的 plane/stride/pixelStride）
  - 裝置 GPU/driver 差異造成的效能不穩或錯色
  - 與 CameraX 管線整合、模式切換相容性

## 4. 風險清單（Risks：含相機管線/模式切換/效能回歸）
### 相機管線 / 正確性風險
- **YUV_420_888 plane/stride/pixelStride 處理錯誤**導致：
  - 色偏（綠/紫）
  - 影像撕裂、鋸齒、行列錯位
- **旋轉/鏡像座標映射錯誤**：前鏡頭鏡像、90/270 度在不同裝置 orientation 行為不一致。
- **與 CameraX 取 frame 節奏衝突**：若 RS kernel 導致阻塞 Analyzer thread，可能反而掉幀/堆積 backpressure。

### 模式切換風險（Live / Static / Debug）
- Live 與 Static 若共用同一轉換 API，fusion 可能導致：
  - Debug（顯示中間結果）失去中間輸出（因為 pass 被合併）
  - 切換模式時資源（RS Context/Allocation）未釋放造成 memory leak 或黑屏
- 不同模式的旋轉/鏡像規則若目前分散在多處，fusion 容易把「規則」寫死在 kernel，造成行為不一致。

### 效能回歸 / 相容性風險
- RenderScript **deprecated**：未來 targetSdk / 新裝置支援與行為不確定。
- **GPU/driver 差異**：某些裝置可能比原本更慢（kernel compile、cache、driver optimization 不同）。
- **能耗/溫控**：FPS 提升但功耗上升導致降頻，長時間反而回落。
- **開發成本高**：自訂 RS kernel debug 困難，迭代時間長。
- **fallback 複雜度**：需要保留原 pipeline 當退路（多路徑維護成本上升）。

## 5. 建議方案（Plan A / Plan B：最小差異優先）
### Plan A（優先｜最小差異、先把可達收益榨乾）
目標：在不引入高風險 fusion 前，先確認「21ms」的主要來源與可用的低風險優化。
- A1. 重新盤點時間分佈（Profiling / Trace）
  - 分段量測：YUV→RGB、Transform、Resize/Crop、AI 前處理、模型推論、後處理、render。
- A2. 減少中間 buffer 與 copy（不改演算法）
  - 盡量重用 ByteBuffer / Allocation / Bitmap（若目前有頻繁 new）
  - 確認 ImageAnalysis 的 backpressure strategy（KEEP_ONLY_LATEST 等）是否正確
- A3. 如果目前 YUV→RGB 是 CPU 路徑：優先替換為既有低風險 GPU/加速方案（若專案已具備）
  - 例如：沿用既有 RenderScript intrinsic / 或現有的轉換 util（視 repo 現況）
- A4. 先確認 transform 是否真的需要在 RGB 後做
  - 若 AI input 允許，研究「在縮放/裁切時順便處理旋轉/鏡像」的方式（仍維持同一處理框架，不一定要 fusion kernel）

**Plan A 成功標準**：不引入 fusion kernel，也能把總耗時拉到可接受區間（例如 12–15ms），或至少確認「fusion 的理論上限與必要性」。

---

### Plan B（高風險｜RenderScript YUV+Transform Fusion）
目標：合併 YUV→RGB + rotation+mirror 成單一 RS kernel，減少 pass 與中間記憶體往返，衝刺 7–10ms。
- B1. 設計單一 kernel 輸入/輸出
  - Input：YUV_420_888 的 Y/U/V planes（需處理 stride/pixelStride）
  - Output：RGB(A) buffer（或直接符合後續 AI input 的 layout）
- B2. 在 kernel 內完成座標映射
  - 依 rotation（0/90/180/270）+ mirror（front camera）計算 src(x,y) → dst(x,y)
- B3. 與現行 pipeline 的介面保持一致（重要）
  - 外部 API 盡量不變，只在內部切換實作（避免大範圍改動）
  - 以 feature flag 控制（例如 `rsFusionEnabled`）
- B4. 保留 fallback
  - fusion 失敗或某些裝置效能差時可回退 Plan A 路徑

**Plan B 進入條件（建議）**：Plan A profiling 證明 YUV→RGB + Transform 佔比是主因，且 fusion 理論上能省下多次 pass / copy（可預期至少省 8–12ms）。

## 6. 驗證方式（How to verify：模擬器/實機/效能指標）
### 功能正確性
- 旋轉/鏡像一致性測試：
  - 後鏡頭：0/90/180/270（依裝置旋轉）
  - 前鏡頭：mirror on/off（若有設定）
  - 比對：Preview 畫面、AI 偵測框位置（overlay 對齊）
- 色彩正確性：
  - 觀察是否有綠紫偏色、亮度異常、邊緣撕裂
  - 以固定場景（色卡/室內白牆/高對比邊緣）做 A/B 對照

### 效能指標（必要）
- FPS：
  - 目標：≥ 26 FPS（穩定 60 秒區間的平均與 P95）
- Latency：
  - 目標：7–10ms/frame（針對「轉換+transform」段落與 end-to-end）
- 資源：
  - CPU/GPU 使用率趨勢（至少觀察是否因 GPU 飆高造成熱降頻）
  - 記憶體：避免持續上升（leak）與 GC 尖峰

### 測試環境建議
- 模擬器：只做基本功能 sanity（不作為效能依據）
- 實機：至少兩級裝置（旗艦 / 中階），各跑 3 次、每次 60–120 秒
- 需同時驗證 Live / Static / Debug（若專案有這些模式）

## 7. 回滾策略（Rollback）
- 以 **feature flag** 包裝新路徑（預設關閉或灰度開啟）：
  - `rsFusionEnabled=false` → 走原本穩定路徑（Plan A / 既有 pipeline）
- 保留原本 YUV→RGB 與 Transform 兩段實作，不做破壞式移除。
- 若上線後發現特定裝置異常：
  - 可在遠端設定/本地白名單關閉 fusion（若專案支援 remote config）
  - 或以裝置型號/SDK 版本黑名單回退
- 回滾驗收：關閉 flag 後，功能與 FPS 回到 v2.8.3/現況水準且無額外 crash。

## 8. 是否需要 Level 2 可行性檢視（Yes/No + 理由）
**Yes，需要 Level 2。**  
理由：
- 涉及 CameraX / ImageAnalysis 即時管線與效能（符合 Checklist Level 2 條件）。
- RenderScript 自訂 kernel 屬高風險變更，且 RS 已 deprecated，需要確認：
  - repo 目前是否已使用 RS、是否已有既有 Allocation/Context 管理
  - 目前 YUV→RGB 與 Transform 的實作細節（stride、buffer 格式、API 介面）
  - 目標裝置與 minSdk/targetSdk 對 RS 支援狀況
  - 是否存在更低風險替代（例如現有 GPU shader / Intrinsics / NDK libyuv 等）
- 變更很可能會動到多個檔案與模式切換路徑，需先做影響面盤點與最小 diff 設計。
