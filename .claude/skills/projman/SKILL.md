# projman

## Mission

讓「原定成果」在多階段、多張 Ticket 後仍可對照：局部完成不等於原始功能完成。
本 Skill 只維護**一份耐久成果文件**與其中**一張階段成果表**。
它不是 code review、不是驗證 gate、不是 Ticket 流程；不建立 Ticket，不碰 Registry、lifecycle、hooks、`ticket-author` 或 Android 產品程式。

## Invocation

```text
$ARGUMENTS
```

第一個非空白 token 為 `MODE`，只接受下列三值：

```text
/projman base   [topic 或 @需求來源 與需求文字]
/projman update [成果文件路徑 或 修訂內容]
/projman align  [成果文件路徑 或 階段 ID]
```

`MODE` 缺少或不在上述三值 → 只顯示上列用法後停止，不猜測模式、不開始工作。
其餘參數、當前訊息與 `@file` 為 payload。

## 節奏

由使用者直接呼叫，或依使用者明確指示由模型呼叫；align 在階段成果點執行。不得自動掛到每張 Ticket 完成、每次對話、交接或小修改；階段中的問題照常說明處理，不因此自行啟動 `align`。`base` 也不是小修正的必要前置。

`update` 只在**真實修訂**（需求增補、澄清、規格修訂、Bug 揭露基準缺漏）出現時使用，不為驗證而製造修訂。被某治理條款呼叫時的行為見〈被治理條款呼叫時（行為契約）〉專節；本檔不定義、不啟用任何條款。

## 成果文件

### 成果文件定位規則

位置決定順序：

1. 使用者指定 → 沿用（含明確指定的 `archive/` 內歷史文件）。指定須來自使用者於**當前對話**的明示；被治理條款自動呼叫時，執行端自行於引數或 payload 指名的路徑**不算**使用者指定，且不得藉此覆寫第 2 項的作廢清單。
2. 已有對應成果文件 → 更新同一份，不建平行副本。判定只看結構標記：`grep -rl "^## 階段成果表" plans/ --exclude-dir=archive` 命中且議題相符的檔案才算候選（檔名不限；一般 roadmap／規劃文件沒有此標題，不算候選）。**票前綴只是可選定位線索、不是資格**；舊文件缺票前綴、缺議題識別欄不因此排除。自動搜尋一律排除 `archive/` 目錄，**使用者明確指定該路徑者除外**。
3. 都沒有 → 新建 `plans/roadmap/<議題全名>-outcomes.md`（檔名以**議題全名**開頭，例 `projman-outcomes.md`；同議題已有有效文件先沿用）。
4. 零個或多個候選無法唯一判定 → 說明並詢問一次（對話正文，列出候選），不猜測、不建立平行副本。

不得放在 `tmp/`、`.tmp/` 或其他暫存目錄。定位只用 `grep`／`ls`／`git`，不新增工具或腳本。

### 文件結構

**新格式（建議；新建一律採用）**：

```markdown
# <議題名稱> Outcomes

## 基準
- project_key：<工具 project 鍵>　project_label：<專案顯示名>
- topic_key：<議題穩定識別>　topic_label：<議題顯示名>
- 票前綴：<可選>
- 專案目標：
- 最小成功場景：
- 不可默默刪減的核心能力：
- 規格／架構約束：
- 非目標：
- 假設（尚未確認的技術或依賴）：
- 目前階段：<階段 ID>
- 最近 align：<日期> <HEAD 全雜湊> <本次檢查的階段 ID 清單>（無則「無」）

## 階段成果表
| ID | 階段 | 成果 | 已驗收 | 約定 | 達成度 | 狀態 |
| --- | --- | --- | --- | --- | --- | --- |

## 明細
### <ID>
- 預期功能與規格：
- 驗收方式與必要前提：
- 實際成果與證據：
- 落差與下一步：
- 最近 align：<日期> <HEAD40> 範圍 <ID>（固定單行；從未 align 寫「無」）

## 已確認變更
| 日期 | 變更前 | 變更後 | 影響 | 使用者確認 |
| --- | --- | --- | --- | --- |
```

「已確認變更」僅在有使用者已確認的變更時才新增列，簡短一行即可。

**量化規則**：

- `已驗收`、`約定` 是各列獨立的**整數數值來源**。`約定` 值域＝正整數或 `—`；`0` 不合法。`達成度` 若顯示屬**衍生呈現**＝`round(100×已驗收/約定)%`（.5 進位），須與計數一致，不得另行維護。
- `約定` 為正整數的列：`已驗收`＝`—` 表示**未盤點**（`達成度`＝`—`、`狀態`＝`未盤點`），不得寫 `0`；`0` 專指**已盤點且零項通過**。
- `約定`＝`—` 表示該列無約定項：`已驗收`＝`—`、`達成度`＝`—`、`狀態`＝`無約定`，不計比例。
- `狀態` 值域＝`未盤點｜符合｜部分符合｜不符合｜未驗｜尚不具備驗收條件｜無約定`；`無約定` **只用於** `約定`＝`—` 之列，與缺必要前提的 `尚不具備驗收條件` 分開。
- **不計跨階段平均、不設總計列或總百分比**；次要成果不得抵銷核心缺口（每個 ID 各自計數）。
- ID 不編入票名、票號或票數；不重用、不改名；新增項目以新 ID 追加。階段與票可多對多，拆票或加修補票不構成改基準的理由。

**舊 5 欄格式（相容；不再作為新建範本）**：`## 階段成果表` 下單表五欄 `階段／成果 ID｜預期功能與規格｜驗收方式與必要前提｜實際成果與證據｜落差與下一步`，基準區以單行散文記 `最近 align`。舊文件不強制遷移。

**格式辨識**：`## 階段成果表` 下表頭含 `已驗收` 與 `約定` 欄 → 新格式；表頭含 `預期功能與規格` 欄 → 舊 5 欄格式；兩組標記同時存在或皆無 → **無法辨識**，不寫入、說明並詢問一次。

## base

依使用者需求整理並寫入成果文件：專案目標、最小成功場景、不可默默刪減的核心能力、必要規格／架構約束、非目標、初步階段與目前階段。

階段劃分規則：

- 依**可驗收成果**劃分，不依週數或 Ticket 數量；一個階段可含多張 Ticket。
- 每階段必須寫清楚「做完後能展示或驗證什麼」，並落在「預期功能與規格」「驗收方式與必要前提」兩欄。
- 沒有獨立成果的工作留在所屬階段內，不硬拆里程碑。階段數按需求決定。
- 尚未確認的技術或依賴寫進「假設」，並在驗收前提中標明；不為填表而新增架構或規格。
- 新建文件採新格式：`約定` 項數依需求列明；初始 `已驗收`＝`—`、`狀態`＝`未盤點`（`約定`＝`—` 之列為 `無約定`）。明細「實際成果與證據」填「未開始」，**已知已有進度者填「待首次盤點」**（不一律寫未開始，也不預填符合）；「落差與下一步」填「—」。

新建文件寫入後依〈寫入與保存〉核對與保存（無 HEAD 版本，V1、V3 不適用）。

重新執行 `base`（文件已存在）：

- `base` 不修訂也不重設既有成果、不建立平行副本；先讀既有文件，需求或驗收修訂改用 `update`、成果判定改用 `align`（核心縮減、新成本、新權限或交付取捨仍須先列「變更前／變更後／影響」並取得使用者確認，見〈update〉與〈路線與規格調整〉）。
- 需求本身有歧義、無法唯一推導的產品取捨 → 以對話正文一次問清，不自行挑選。

## update

標準化修訂既有成果文件。**輸入**＝真實需求增補、澄清、規格修訂，或 Bug 揭露的基準缺漏；**一般修補不自動新增成果**；**不為驗證而製造修訂**。

行為：

- 保留既有 ID、有效證據與未受影響內容。
- 新增成果不繼承完成狀態：新列 `已驗收`＝`—`、`狀態`＝`未盤點`（`約定`＝`—` 之新列為 `無約定`）；既有列增加 `約定` 時 `已驗收` 不增，`達成度`／`狀態` 重新依量化規則衍生。
- 任何分母（`約定`）變動須在「已確認變更」有同次一列（日期、變更前後、影響、依據）。
- 核心縮減、新成本、新權限或交付取捨：須先列差異並取得使用者明確確認。
- 舊格式文件**不主動遷移**，僅在使用者明示要求時遷移，且遷移須保留全部原需求、ID 與證據。
- **手動 `update` 遇文件未追蹤或 dirty**：寫前檢查、來源證明、略過與保存一律依〈寫入與保存〉第 1 項（手動與自動一致，不另設授權）。來源已證明時，以寫前**完整讀取**的現值為修訂起點與 V1／V3 基準，保留未受影響內容，並在對話列精簡摘要（ID 集合、各 ID 的 `約定`），寫後以指令輸出對照該摘要；不新增快照檔。不含合併衝突標記（`<<<<<<<`／`>>>>>>>`）只是格式前提，不構成來源證明；含衝突標記 → 不寫入，說明並詢問一次。

**完整性核對**（寫入後 MUST 執行；以下指令為說明文字，不是 repo 內腳本；`DOC` 為成果文件路徑；awk 欄位一律寫 `$(n)` 形式以避免與 skill 引數替換混淆；任一不過 → 回報並修正，不宣稱完成）：

```bash
# 共用：抽出 `## 階段成果表` 下各列第一欄 ID（新舊格式皆可）
ids() { awk -F'|' '/^## /{s=(index($(0),"## 階段成果表")==1)} s && /^\| /{gsub(/^ +| +$/,"",$(2)); if ($(2)!="ID" && $(2)!="階段／成果 ID" && $(2) !~ /^-+$/) print $(2)}'; }
```

- **V1** ID 集合保留（舊有 ID 不得消失；輸出為空＝通過）。基準前提：僅當文件已追蹤且寫入前 `git status --short -- "$DOC"` 為空時，`git show HEAD:"$DOC"` 才等於寫入前狀態；未追蹤或 dirty 時改以上述對話摘要為基準：
  ```bash
  comm -23 <(git show HEAD:"$DOC" | ids | sort) <(ids < "$DOC" | sort)
  ```
- **V2** 摘要表 ID 與明細 `### <ID>` 互為子集（新格式；輸出為空＝通過）：
  ```bash
  comm -3 <(ids < "$DOC" | sort) <(awk '/^## /{s=(index($(0),"## 明細")==1)} s && /^### /{print $(2)}' "$DOC" | sort)
  ```
- **V3** 分母不無聲變動（新格式；逐 ID 比對 `約定`，任一差異須對應「已確認變更」新列；基準前提同 V1）：
  ```bash
  den() { awk -F'|' '/^## /{s=(index($(0),"## 階段成果表")==1)} s && /^\| /{for(i=2;i<=NF;i++)gsub(/^ +| +$/,"",$(i)); if ($(2)!="ID" && $(2) !~ /^-+$/) print $(2)"="$(6)}'; }
  diff <(git show HEAD:"$DOC" | den | sort) <(den < "$DOC" | sort)
  ```
- **V4** 計數與衍生一致（新格式；輸出為空＝通過）：`約定` 須為正整數或 `—`；`已驗收`≤`約定`；`—` 與 `0` 不混；`達成度`＝`round(100×已驗收/約定)%`；`約定`＝`—` 時 `已驗收`／`達成度` 皆 `—` 且 `狀態`＝`無約定`；`無約定` 不得用於 `約定` 為正整數之列；`已驗收`＝`—` 時 `達成度`＝`—` 且 `狀態`＝`未盤點`；已驗收為整數時 `狀態` 不得為 `未盤點`；`狀態` 須屬上述量化規則之七值集合，值域外輸出違規列：
  ```bash
  awk -F'|' '/^## /{s=(index($(0),"## 階段成果表")==1)} s && /^\| /{for(i=2;i<=NF;i++)gsub(/^ +| +$/,"",$(i)); id=$(2); if(id=="ID"||id ~ /^-+$/)next; a=$(5); d=$(6); p=$(7); st=$(8); bad=""; if(st !~ /^(未盤點|符合|部分符合|不符合|未驗|尚不具備驗收條件|無約定)$/){bad="狀態須屬七值集合"} else if(d=="—"){if(a!="—"||p!="—"||st!="無約定")bad="約定為—時須已驗收=達成度=—且狀態=無約定"} else if(d !~ /^[1-9][0-9]*$/){bad="約定須為正整數或—"} else if(st=="無約定"){bad="無約定只用於約定為—"} else if(a=="—"){if(p!="—"||st!="未盤點")bad="已驗收為—時須達成度=—且狀態=未盤點"} else if(a !~ /^[0-9]+$/||a+0>d+0){bad="已驗收須為整數且不得超過約定"} else if(st=="未盤點"){bad="已驗收為整數時狀態不得為未盤點"} else if(p!=(int(100*a/d+0.5) "%")){bad="達成度與計數不一致"} if(bad)print id": "bad}' "$DOC"
  ```
- **V5** 摘要表無總計／平均列（輸出為空＝通過）：
  ```bash
  awk -F'|' '/^## /{s=(index($(0),"## 階段成果表")==1)} s && /^\| /{if($(2) ~ /平均|總計|合計|Total/)print $(0)}' "$DOC"
  ```
- **V6** 表格欄數逐行一致（輸出為空＝通過；反引號內與 `\|` 的豎線不計），並依 `/mdlint` Rule G／H 檢查表格格式：
  ```bash
  awk '/^\|/{l=$(0); gsub(/\\\|/,"",l); gsub(/`[^`]*`/,"",l); n=gsub(/\|/,"|",l); if(inb && n!=c)print NR": 欄數"n"≠"c; if(!inb){inb=1;c=n}; next} {inb=0}' "$DOC"
  ```

對舊 5 欄文件僅適用 V1、V6；V2–V5 不適用（須在回報中明寫）。

## align

使用時點：實作已到約定的階段成果點、可以檢查該階段功能。**可驗收不等於會通過**；功能可檢查即可執行，不必先保證通過。

流程：

1. 找到成果文件（依〈成果文件定位規則〉；找不到或多候選無法唯一判定 → 說明並詢問一次，不自行建立新文件、不猜測）。
2. 確認本次階段：payload 指定者優先，其次「目前階段」；仍不明確 → 詢問一次。
3. 依該階段「預期功能與規格」與「驗收方式」取證，範圍只限本階段與受影響的核心成果，不全量重查歷史。
4. 依格式辨識結果回填同一份文件（寫入集合見下），寫後依〈寫入與保存〉核對與保存。
5. 在對話直接回報（見〈直接回報〉），不只說文件已更新。

**回填邊界（寫入集合；依格式辨識結果）**：

- **舊 5 欄格式**：只更新本次實際檢查 ID 之列的「實際成果與證據」「落差與下一步」，以及基準區「最近 align」（單行散文，沿用；缺該行時不新增）。**per-ID 錨點**寫在該列「實際成果與證據」格內，固定格式 `align: <日期> <HEAD40> 範圍 <ID>`：表格格內不得換行，該段以 `；` 分隔附於格尾、同格恰一段（既有者原位更新、不重複追加），不得含 `|`。可用 `grep -oE 'align: [0-9]{4}-[0-9]{2}-[0-9]{2} [0-9a-f]{40} 範圍 [^；| ]+' "$DOC"` 定位。基準區「最近 align」**只作摘要**，不作任何 ID 的錨點。
- **新格式**：明細中該 ID 的「實際成果與證據」「落差與下一步」「最近 align（單行）」；摘要表中**本次實際檢查之 ID** 的 `已驗收`（僅由證據支持的整數，不得超過 `約定`；`約定`＝`—` 之列不寫整數）、`達成度`（衍生）、`狀態`；基準區 `最近 align` 摘要行。
- **兩種格式皆不得改動**：`約定`、預期功能與規格、驗收方式與必要前提、不可默默刪減的核心能力、ID／階段／成果名稱、「已確認變更」列。這些只能經使用者確認的 `update` 修改（見〈路線與規格調整〉）。

**每 ID 範圍與錨點**：只更新本次實際檢查的 ID；**不消費其他階段尚未檢查的交付**。每個 ID 的 `最近 align` 記日期、HEAD 全雜湊、檢查範圍。從未 align 的 ID 以成果文件首次提交為預設錨點（文件尚未提交則用建立當下 HEAD）；舊格式以該列證據格內 `align:` 行的 HEAD40 為該 ID 錨點，**沒有列內記錄的 ID 視為從未 align**，不因全域摘要行更新而視為已檢查：

```bash
git log --diff-filter=A --follow --format=%H -- "$DOC" | tail -1   # 首次提交（預設錨點）
git log --oneline <錨點>..HEAD                                      # 僅協助列示候選交付
```

`git log` 只協助列示候選交付：不作資格條件、不代替功能證據，不以提交前綴或目錄排除將 docs-only 或規則型成果整類排除。

**直接回報**（對話正文，非只說文件已更新）：

1. 單項結果：ID、`狀態`、`已驗收／約定`、一行證據與限制。
2. 各階段 `已驗收／約定` 計數（**不給跨階段平均或總百分比**；`無約定` 列不計入計數與比例，另列其 ID）。
3. 主要缺口。
4. 下一步。
5. 真正需要使用者決策的事項（無則寫「無」）。

摘要必須回答：

- 原定成果是什麼。
- 現在實際能做什麼。
- 證據支持到哪裡。
- 是否有缺口、縮水或方向偏移。
- 下一步怎麼處理。

判斷用語（不新增評分系統）：
`符合` / `部分符合` / `不符合` / `未驗` / `尚不具備驗收條件`。
- 每個階段列只寫**一個**判斷，放在「落差與下一步」欄開頭，格式「判斷：X — 理由」；證據寫在「實際成果與證據」欄，不另寫判斷。
- 驗收所需前提不存在 → 判 `尚不具備驗收條件`；已完成的局部工作只作為帶標記的證據寫入證據欄，不另判 `部分符合`。
- 前提具備時：局部完成判 `部分符合` 並列出缺的部分。
- 任一核心成果不是 `符合`，階段整體就不得判 `符合`。
- 新格式摘要表的 `狀態` 另有 `未盤點`（`已驗收`＝`—`）與 `無約定`（`約定`＝`—`，不計比例）兩值，定義見〈文件結構〉量化規則。

### 證據規則

- 功能證據優先；檔案存在、Ticket CLOSED、commit 存在都不能代替功能證據。
- 證據標記分開寫：`[已執行]` 實際跑過並有結果（寫明指令／裝置／結果）、`[靜態]` 讀碼或讀設定推得、`[文件]` 文件或他人敘述、`[未驗]` 並附原因。只有 `[已執行]` 可寫「已驗證」。
- 證據**來源**與**證明範圍**分開：文件、ledger、測試、完整場景不互相升格（例：ledger 登記事件不證其中調用的真實性；單元測試不等於整體功能；round 通過不提升證據強度）。
- 精確數字須可定位核對（檔案:行號或指令）；搜尋未命中只限本次檢查範圍，不得宣稱全域不存在。
- mock／stub／模擬器不替代要求真實整合（如實機、真實服務）的驗收，須明寫「僅 stub 層通過」。
- 無法執行 → 寫「未驗」與原因，不推定成功或失敗。
- 舊證據可沿用並註明日期與來源；相關實作、依賴或環境之後有變動 → 標「待重驗」。
- 已決事項先重用；結果清楚就退出，不反覆修表。
- 未來階段尚未實作，不判為當前階段失敗；局部實作不得宣稱完整功能完成；前提具備時判「部分符合」並列出缺的部分，缺必要前提時依上列優先判「尚不具備驗收條件」。

### 尚不具備驗收條件

原定驗收需要某必要前提（例如實機驗收但設備未到貨）而前提不存在時：

- 判斷為 `尚不具備驗收條件`，寫明缺少的前提。
- 在「落差與下一步」提出解除阻礙或調整安排的下一步。
- 討論、下單、準備工作不得改稱驗收通過；可先做的前提內檢查只能如實標註其範圍（如「僅模擬器」）。
- 不為了通過而自行降低原階段規格；不因缺前提而做無意義的全量審查。

### 最終覆蓋確認

使用時點：本輪最後一張票的 `close` 結果已知後，或向使用者給出議題最終交付總結前；使用者手動下令或被治理條款呼叫皆同。目的：確認成果表已涵蓋最新交付與審查結論，**不是**逐票重跑，也不是新增驗收。

1. 「最後一張票」依計畫、成果缺口、待續工作與交付意圖綜合判斷；**Registry 無 OPEN 票不構成完成**。非最後一張票不做覆蓋確認（階段點 align 照常依〈align〉使用時點）。
2. 只讀取證：比對成果文件各 ID 自其錨點之後的新交付與審查結論（含 `close` 的 reviewer 結論、Registry checkpoint 中審查方的處置），不新增付費呼叫，預設不新增本地建置或測試。
3. 有新證據 → 以 align 處理有新證據的 ID（範圍＝這些 ID），依〈寫入與保存〉核對、保存並直接回報；無新證據 → 回報「已涵蓋、無需重跑」，不寫入、不提交；有必要功能或驗收缺口尚未開票 → 於最終報告揭露，**不自行開票或開新工作**。
4. 「close 結果已知後」限本次呼叫鏈實際執行了 close；已收束重入（`lifecycle ∈ {REVIEW, CLOSED}` 且走 `RETURN`）不經 Step 11 觸發，不改變 Transition Table 該列對 closeout 的處置。「向使用者給出最終交付總結前」為不經 Step 11 的獨立觸發，重入情形下亦可執行，僅讀取票務事實，不寫 Registry、不重做 closeout。覆蓋確認及其保存不是 Ticket 收束，不帶票前綴，不再觸發另一輪 align（不遞迴）。

## 寫入與保存（base／update／align 共同）

成果文件 `<doc>` 的建立與內容異動**只經** base／update／align；不得繞過 Projman 直接寫入。實際 Projman 呼叫內，依模式與授權使用既有編輯工具（Edit／Write 等）寫入該文件屬正常路徑。既有文件不得以 `base` 繞過修訂紀錄或重設成果（需求或驗收修訂用 `update`，成果判定用 `align`）。三模式、手動呼叫與被治理條款呼叫共用下列順序與同一保存授權；不 push、不空提交、不夾帶他檔、不繞過權限／hook／安全限制，不新增腳本、鎖、資料庫或狀態檔。

1. **寫前檢查**（單次觀察；以**目前內容**為寫前基準，完整讀取，不要求先提交或還原）：
   - `<doc>` 不存在（base 新建）或已追蹤且 `git status --short -- <doc>` 為空：直接進第 2 項。
   - `git status --short -- <doc>` 非空（dirty、未追蹤或 staged）：先判來源。**來源已證明**須**同時**成立三項，缺一即視為來源不明：①**實際呼叫紀錄**——可指出先前 Projman 呼叫的 `Skill` tool_use；②**寫入紀錄**——可指出該呼叫對本文件的寫入 tool_use；③**內容識別**——目前 `git hash-object -- <doc>` 等於該呼叫報告所記之寫後 blob id。**blob 相等只輔助識別內容，不得單獨採認**：內容相同但缺可對應的呼叫或寫入紀錄，仍不採認。同 session 以報告與 transcript（取得方式同〈被治理條款呼叫時〉第 6 項）對應；跨 session 僅在該 session transcript 可唯讀取得且含①②時比照，取不到即不明。日期、格式、錨點吻合**不構成**來源證明。
   - `<doc>` 有 staged 變更（`git diff --cached --quiet -- <doc>` 非 0）：index 版（`git rev-parse :<doc>`）與工作樹版**各自**須滿足上列三項（二版相同視為同一版；工作樹版回到 HEAD 內容而 index 版不同者，依③自然判為不明）才屬先前 Projman 產物，涵蓋 base 的 `git add` 成功、`git commit` 失敗後的合法恢復；任一版本不滿足，即含額外來源不明內容。不採 hunk 或臨時 index 方案。
   - 來源已證明 → 進第 2 項；來源不明、含額外不明內容、或已知並行修改（同檔另有 session 正在修改）→ **不寫入、不提交**，回報「回填未完成（略過：來源不明／並行）」＋dirty 路徑。**手動 `update` 亦同**（手動與自動一致）：來源不明時略過，使用者可先自行提交或還原其既有異動再呼叫。
2. **寫入**：只動 `<doc>` 單檔；本次無修改（只有先前產物待保存）則不寫入，直接進第 3 項。
3. **核對**（完整性核對 V1–V6，定義見〈update〉；任一必要檢查不過 → 於該模式邊界內至多修一次，仍不過則不保存）。依模式與格式適用：舊 5 欄僅 V1、V6；新格式的 `update`、`align`：V1–V6，其中 `update` 的 V3 差異若有同次「已確認變更」列，屬**合法差異、不算失敗**，`align` 的 V3 須為空（align 不得改 `約定`）；`base`（一律建立新文件）無 HEAD 版本：V2、V4、V5、V6（V1、V3 不適用）。**V1／V3 基準**：已知來源 dirty（含先前 `update` 已改 `約定`、附「已確認變更」列但尚未保存者）時，三模式的基準皆為**寫前目前內容**（完整讀取之現值或摘要），不是 HEAD；其餘情形沿用 V1 說明（已追蹤且寫前乾淨用 HEAD）。只有先前產物待保存而本次無寫入時，依**先前產物的模式**對目前內容（相對 HEAD）核對。
4. **保存**（任一 git 查詢、寫入或核對失敗，依實際階段回報，不假報「無差分」）：
   - 先判追蹤狀態：`git ls-files --error-unmatch -- <doc>` exit 0＝已追蹤、exit 1＝未追蹤、其他非 0＝查詢失敗。**不得**以 `git status --short -- <doc>` 空輸出直接把新建或未追蹤文件判為無差分（被 ignore 的未追蹤檔 status 亦為空）。
   - 已追蹤：寫後 `git status --short -- <doc>` 為空 → 不提交，回報「無差分」；非空 → 進下列 commit。
   - 未追蹤（含 base 新建，以及先前產物尚未 add）：先 `git check-ignore -q -- <doc>`——exit 1（未被忽略）→ `git add -- <doc>`（限此路徑）後進下列 commit；exit 0（被忽略）→ 不強制 add、不改 ignore，內容寫入與核對已成功者回報「已回填未提交」＋路徑＋原因（被 ignore）；`git add` 失敗 → 同樣回報「已回填未提交」＋原因。
   - 保存階段的 git 查詢（`ls-files`／`check-ignore`／`status`）本身失敗而無法判定 → 不提交、不判無差分：回填與核對已成功者回報「已回填未提交」＋原因；寫入或核對未完成者回報「回填未完成」。
   - `git commit -o -m "[PROJMAN-SYNC] <摘要>" -- <doc>`：`-o` 只取 `<doc>`，他檔 staged／unstaged 不受影響；摘要註明模式與範圍，併入先前呼叫產物時一併註明。成果文件不要求寫入該提交自己的 hash，不為補 hash 製造補交。
   - **已被拒絕的提交不自動重試**：先前報告載明該提交被使用者、權限系統或 Claude Code PreToolUse hook 拒絕者，後續 Projman 呼叫不因再次被呼叫即重試，仍回報「已回填未提交」＋原因；僅該次使用者明示要求保存時才再嘗試。git 自身 hook（如 commit-msg）失敗屬提交失敗、非拒絕，下一次呼叫可依第 1 項（來源已證明）處理一次，不成重試迴圈。
5. **回報**（對話正文）：依實際進度擇一，輸出字面（非 verdict／receipt 枚舉）——「未完成呼叫」：Skill 不可用、權限被拒或呼叫未完成，不寫、不改道寫檔；「回填未完成」：寫前略過（來源不明／並行）、必要核對失敗，或寫入未完成，附路徑與原因（核對失敗時修改保留於工作樹，不還原）；「已回填未提交」：回填**與核對均成功**而保存（add／commit）失敗、被拒、被 ignore 而不強制 add，或保存階段 git 查詢失敗，附 dirty 路徑與原因，保留修改、不還原、不重試迴圈；「已提交」：commit 成功，附 hash。另有「無差分」（僅限已追蹤檔且寫後 status 為空，如實說明，不屬「已提交」）。呼叫或回填未完成時不得聲稱已回填。**每次寫入完成後**於報告記錄寫後 `git hash-object -- <doc>` 的 blob id（報告文字，無新檔案或狀態庫），供第 1 項後續比對。
6. **殘留續作與已知限制**：來源已證明且先前產物待保存時，下一次任一 Projman 呼叫（含最終覆蓋確認）依第 1–4 項處理（單次，不成迴圈），被明確拒絕者除外；Gate 路徑上後續票 Step 4.5 遇該 dirty 回報 Scope 汙染時，以呼叫 Projman 完成保存為已授權自修策略。來源不明者維持 Scope 汙染，終點依 `.claude/rules/ssot-governance.md` §Autonomous Engineering Gate。已知限制：寫前乾淨與 blob 比對皆為單次觀察、不排除並行寫入；殘留 dirty 異動可能被下一張票的廣域提交帶走；寫入或 `git add` 之後、報告記錄寫後 blob id 之前中斷者（session 結束或崩潰），下次呼叫第 1 項③無可對照之 blob，依來源不明略過（fail-closed），須使用者自行提交或還原後再呼叫；Projman 提交（含手動呼叫與上述 Step 4.5 自修）若發生於他票開工後、收束前，會落在該票的 `DIFF_REF..DIFF_END` 內，該票的範圍檢核（`qa` Step 0、`sv` Files Changed）會列出此成果文件，處置：保留該票完整交付範圍（`DIFF_REF` 起點不縮短、不漏早期或晚期變更）；固定 `DIFF_END` 只阻止其後無關提交進入，**不能**移除已混入範圍內的 Projman 提交；該中途產物按既有具名 payload 排除方式處理（票面 conf `EXCLUDED_PAYLOAD` 或 sv_report `## Excluded Payload`，仍須列於 Files Changed，並符合該方式所需授權）；無合法處理方式時回報範圍混入，不縮短起點、不隱藏 payload；本節不新增工具或流程，不改 `qa`／`sv`；本節為模型契約，無機械後盾。

## 被治理條款呼叫時（行為契約）

本節只描述被某治理條款呼叫時的行為；本 Skill 不定義、不啟用該條款，也不驗證自動鏈。手動呼叫時本節不適用。

1. **候選集合與定位回報**：候選集合＝〈成果文件定位規則〉的輸出（含作廢清單排除）。先依**當前任務／議題**取相關候選（沿用條款的歸屬訊號），**不以全域候選數或全域排除數作判準**；唯一合理候選才執行。本議題原本無候選且無明示成果目標 → 不執行、不輸出；本議題相關候選被作廢清單排除而無其他合法候選，或使用者已明示應使用的成果文件卻找不到 → 回報「定位未完成」（不選回被排除的文件、不宣稱已涵蓋、不建立或處置其他成果文件，作廢排除數為零亦同）；有候選但不能唯一歸屬 → 以一行揭露歧義並列出候選，不猜測、不建立平行副本。此為判讀契約，非機械後盾。不複製、不改寫定位邏輯。
2. **只消費既有證據**（被收束票的 sv_report、commit、收束敘事、既有測試輸出）；不新增付費呼叫；預設不新增本地建置或測試，僅用唯讀命令（`git`／`grep`／`ls`）；需要新執行的項目標「未驗」並寫原因。
3. **寫前檢查**：依〈寫入與保存〉第 1 項（來源證明、staged、略過）；只寫該一份成果文件，不改其他檔案、產品需求、Registry 或 lifecycle。
4. **保存**：依〈寫入與保存〉第 4 項；所呼叫之條款授予的單檔保存即該項（前綴 `[PROJMAN-SYNC]`），且只含本次產物。
5. **失敗處置**：依〈寫入與保存〉第 5 項四態與無差分字面；不回滾原票、不還原檔案、不重試迴圈、不開 Gate incident，不回頭視為原票或下一張票未收束；已知限制見〈寫入與保存〉第 6 項。
6. **回報項目與紀錄**：呼叫來源、Skill 實際呼叫、回填差分（`git diff --stat` 與各 ID 前後 `已驗收`）、結果摘要、保存結果、**Claude Code session id 與依序工具呼叫**。取得方式：session id＝環境變數 `CLAUDE_CODE_SESSION_ID`；工具序列＝`~/.claude/projects/<專案目錄>/<session-id>.jsonl` 內依序的 `tool_use`（唯讀 `python -X utf8 -I` 讀取）。任一取不到 → 該欄寫 `UNAVAILABLE`，不得事後編造，不得以記憶補寫；不新增日誌系統。
7. **自動／手動判別**：同一回合內、收束寫入完成後、沒有新的使用者訊息、就呼叫了 `Skill(projman)` 者，可**候選**記為「自動」並附上列證據；需使用者另外下令者記為「手動」（證明 align 可用，不算自動觸發驗證）；僅在文件自填「自動」、或只找到成果文件的提交，皆不足以升級。若成果文件存在對應的自動觸發驗證項（本議題為 `PM2-E`），將上列內容寫入其明細並標「自評，待審查確認」，由審查方確認；無法核對或未觸發 → 該項維持未驗。
8. **不遞迴**：被條款觸發的 align 不是 Ticket 收束，不再觸發另一次 align。
9. 漏跑僅得稱「可能於後續相關收束時補判」。

## 路線與規格調整

- 某條技術路線失敗，不等於原始成果不可行。先考慮既有能力、可逆替代方案與低成本實驗。
- 沒有官方文件不等於不可行；有未知就標明為假設，能安全驗證時採最小實驗，不虛構能力、不保證成功。
- `align` 可提出修正建議，**不得自行縮小核心需求**使現況看起來符合；發現落差就如實記為落差。
- 核心功能縮減、新成本、新權限或交付承諾改變：列明變更前後與影響，等使用者確認；確認後才改表，並於「已確認變更」簡短記錄。

## 第二方複核

成果文件與摘要須自足：另一個模型或使用者只讀文件，就能看出原定成果、實際證據層級與落差。證據欄寫明指令、檔案或來源，不寫「已確認」這類無出處斷言。
