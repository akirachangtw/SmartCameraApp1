# projman

## Mission

讓「原定成果」在多階段、多張 Ticket 後仍可對照：局部工作完成不等於原始功能完成。
本 Skill 只維護**一份耐久成果文件**與其中**一張階段成果表**。
它不是 code review、不是驗證 gate、不是 Ticket 流程；不建立 Ticket，不碰 Registry、lifecycle、hooks、`ticket-author` 或 Android 產品程式。

## Invocation

```text
$ARGUMENTS
```

第一個非空白 token 為 `MODE`，只接受：

```text
/projman base  [topic 或 @需求來源 與需求文字]
/projman align [成果文件路徑 或 階段 ID]
```

`MODE` 缺少或不在上述兩值 → 只顯示上列用法後停止，不猜測模式、不開始工作。
其餘參數、當前訊息與 `@file` 為 payload。

## 節奏

只由使用者在階段成果點手動呼叫。不得自動掛到每張 Ticket 完成、每次對話、交接或小修改；階段中的問題照常說明處理，不因此自行啟動 `align`。`base` 也不是小修正的必要前置。

## 成果文件

位置決定順序：

1. 使用者指定 → 沿用。
2. 已有對應成果文件 → 更新同一份，不建平行副本。判定只看結構標記：`grep -rl "^## 階段成果表" plans/` 命中且 topic 相符的檔案才算（檔名不限；一般 roadmap／規劃文件沒有此標題，不算候選）。
3. 都沒有 → `plans/roadmap/<topic>-outcomes.md`。
4. 多個候選無法唯一判定 → 詢問一次（對話正文，列出候選）。

不得放在 `tmp/`、`.tmp/` 或其他暫存目錄。

### 文件結構（單一文件、單一表）

```markdown
# <Topic> Outcomes

## 基準
- 專案目標：
- 最小成功場景：
- 不可默默刪減的核心能力：
- 規格／架構約束：
- 非目標：
- 假設（尚未確認的技術或依賴）：
- 目前階段：<階段 ID>
- 最近 align：<日期> <階段 ID> <判斷>（無則「無」）

## 階段成果表
| 階段／成果 ID | 預期功能與規格 | 驗收方式與必要前提 | 實際成果與證據 | 落差與下一步 |
| --- | --- | --- | --- | --- |

## 已確認變更
| 日期 | 變更前 | 變更後 | 影響 | 使用者確認 |
| --- | --- | --- | --- | --- |
```

「已確認變更」僅在有使用者已確認的變更時才新增列，簡短一行即可。

## base

依使用者需求整理並寫入成果文件：專案目標、最小成功場景、不可默默刪減的核心能力、必要規格／架構約束、非目標、初步階段與目前階段。

階段劃分規則：

- 依**可驗收成果**劃分，不依週數或 Ticket 數量；一個階段可含多張 Ticket。
- 每階段必須寫清楚「做完後能展示或驗證什麼」，並落在「預期功能與規格」「驗收方式與必要前提」兩欄。
- 沒有獨立成果的工作留在所屬階段內，不硬拆里程碑。階段數按需求決定。
- 尚未確認的技術或依賴寫進「假設」，並在驗收前提中標明；不為填表而新增架構或規格。
- 「實際成果與證據」初始填「未開始」，「落差與下一步」填「—」。

重新執行 `base`（文件已存在）：

- 不得無聲覆蓋原目標與核心能力。先讀既有文件，只補充或調整使用者此次明示的部分。
- 需要縮減、移除核心成果時：先列「變更前／變更後／影響」，等使用者確認後才改；確認後於「已確認變更」記一行。
- 需求本身有歧義、無法唯一推導的產品取捨 → 以對話正文一次問清，不自行挑選。

## align

使用時點：實作已到約定的階段成果點、可以檢查該階段功能。**可驗收不等於會通過**；功能可檢查即可執行，不必先保證通過。

流程：

1. 找到成果文件（依「成果文件」位置規則；找不到或多候選無法唯一判定 → 說明並詢問一次，不自行建立新文件、不猜測）。
2. 確認本次階段：payload 指定者優先，其次「目前階段」；仍不明確 → 詢問一次。
3. 依該階段「預期功能與規格」與「驗收方式」取證，範圍只限本階段與受影響的核心成果，不全量重查歷史。
4. 回填**同一份文件的同一張表**，並更新「最近 align」。
5. 在對話給短版成果摘要與初判。

回填邊界：`align` 只寫「實際成果與證據」「落差與下一步」與「最近 align」。**不得改動**「預期功能與規格」「驗收方式與必要前提」「不可默默刪減的核心能力」；這些只能經使用者確認的變更修改（見「路線與規格調整」）。

摘要必須回答：

- 原定成果是什麼。
- 現在實際能做什麼。
- 證據支持到哪裡。
- 是否有缺口、縮水或方向偏移。
- 下一步怎麼處理。

判斷用語（不新增評分系統）：
`符合` / `部分符合` / `不符合` / `未驗` / `尚不具備驗收條件`。
- 每個階段列只寫**一個**判斷，放在「落差與下一步」欄開頭，格式「判斷：X — 理由」；證據寫在「實際成果與證據」欄，不另寫判斷。
- 驗收所需前提不存在 → 判 `尚不具備驗收條件`；已完成的局部工作只作為帶標記的證據寫入證據欄，不另判 `部分符合`。
- 前提具備時：局部完成判 `部分符合` 並列出缺的部分。
- 任一核心成果不是 `符合`，階段整體就不得判 `符合`。

### 證據規則

- 功能證據優先；檔案存在、Ticket CLOSED、commit 存在都不能代替功能證據。
- 證據標記分開寫：`[已執行]` 實際跑過並有結果（寫明指令／裝置／結果）、`[靜態]` 讀碼或讀設定推得、`[文件]` 文件或他人敘述、`[未驗]` 並附原因。只有 `[已執行]` 可寫「已驗證」。
- mock／stub／模擬器不替代要求真實整合（如實機、真實服務）的驗收，須明寫「僅 stub 層通過」。
- 無法執行 → 寫「未驗」與原因，不推定成功或失敗。
- 舊證據可沿用並註明日期與來源；相關實作、依賴或環境之後有變動 → 標「待重驗」。
- 未來階段尚未實作，不判為當前階段失敗；局部實作只能寫成「部分符合」並列出缺的部分，不得宣稱完整功能完成。

### 尚不具備驗收條件

原定驗收需要某必要前提（例如實機驗收但設備未到貨）而前提不存在時：

- 判斷為 `尚不具備驗收條件`，寫明缺少的前提。
- 在「落差與下一步」提出解除阻礙或調整安排的下一步。
- 討論、下單、準備工作不得改稱驗收通過；可先做的前提內檢查只能如實標註其範圍（如「僅模擬器」）。
- 不為了通過而自行降低原階段規格；不因缺前提而做無意義的全量審查。

## 路線與規格調整

- 某條技術路線失敗，不等於原始成果不可行。先考慮既有能力、可逆替代方案與低成本實驗。
- 沒有官方文件不等於不可行；有未知就標明為假設，能安全驗證時採最小實驗，不虛構能力、不保證成功。
- `align` 可提出修正建議，**不得自行縮小核心需求**使現況看起來符合；發現落差就如實記為落差。
- 核心功能縮減、新成本、新權限或交付承諾改變：列明變更前後與影響，等使用者確認；確認後才改表，並於「已確認變更」簡短記錄。

## 第二方複核

成果文件與摘要須自足：另一個模型或使用者只讀文件，就能看出原定成果、實際證據層級與落差。證據欄寫明指令、檔案或來源，不寫「已確認」這類無出處斷言。
本 Skill 不自動呼叫其他模型，不新增第三個模式；專案方向複核不等同正式 code review 或驗證 gate。

## 邊界

不修改：`ticket-author`、正式 Ticket 模板、Registry 與票據 lifecycle、全域啟動規則、交接規則與 hooks、Android 產品程式。
不建立正式 Ticket。除成果文件外不寫入其他檔案。
