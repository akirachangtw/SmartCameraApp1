# Projman 成果圖譜協議

版本：v1.0
日期：2026-10-22
用途：Perplexity 上游需求整理、Projman 提示詞編譯與跨對話交接。
執行入口：Claude Code 的 Projman Skill（base／update／align）。
原則：需求要完整，方法不必重教。圖譜是需求與成果的對應，不是新增系統。

## 1. 角色與邊界

- 使用者：確認目標、核心功能、範圍與產品取捨。
- Perplexity：整理需求、比較選項、指出遺漏與歧義，編譯可獨立使用的提示詞；不冒稱已呼叫本機 Skill、寫入 repo 或完成驗收。
- Projman：實際建立或修訂單一成果文件、整理 ID／階段／約定子項，依當前規則核對、保存與回報。
- base 建立基準；update 執行已確認的真實修訂；align 依證據回填現況，不改需求或降低驗收條件。
- 所有 outcomes 內容異動都須實際經 Projman。Skill 內可依授權使用既有編輯工具，其他流程不得繞過入口代寫。
- 本協議不建立正式票、不變更 Registry 或 lifecycle，不新增資料庫、hook、腳本或第二套流程。

## 2. 成果圖譜

```text
議題與目標
  └─ 使用情境
      └─ 功能需求
          └─ 階段成果（P1／P2……）
              └─ 可驗收子項（約定）
                  └─ 實際證據與缺口（後續 align）
```

不另建平行追蹤矩陣。需求、成果與證據的關係保留在同一份成果文件。
階段用 P；版本用 V。階段依可展示／可驗收成果劃分，不依票數或週數。

## 3. 情境與模式選擇

功能狀態與成果文件狀態分開判斷：

| 開發情境 | 沒有有效成果基準 | 已有有效成果基準 |
| --- | --- | --- |
| 全新功能 | base 建立 | 確認是否同議題；沿用，不重建 |
| 既有功能不足、追加能力 | base 整理已確認原需求與本次增補 | update 修訂同一份 |
| 只想知道目前做到哪裡 | 先建立必要基準，不從實作反推需求 | align 依證據盤點 |

不存在有效基準才用 base。已有基準不得以 base 重設成果；新需求不必然代表新議題。
無法唯一定位時，先澄清，不猜測、不建立平行副本、不選回已確認錯誤的舊表。

## 4. 需求輸入

使用自然語言即可，不強制 YAML 或逐欄填表。已在本次對話確認的內容可以直接整合，不重問。

### 4.1 必要內容

1. 議題：專案、議題名稱與開發情境。
2. 問題與目標：目前的問題，以及完成後使用者能做到什麼。
3. 使用情境：誰在何時使用，如何開始，期望如何結束。
4. 功能需求：必要行為、可觀察結果與重要例外。此部分應較詳細。
5. 核心與範圍：不可刪減能力、非目標及已確認限制。

每項功能應足以回答：
- 誰在什麼情況下需要它？
- 系統或 AI 必須實際做什麼？
- 什麼結果表示該功能達成？
- 哪些失敗、拒絕或缺席情況不能假裝成功？

不要求每項都寫技術方案、程式位置或測試命令。只有會影響功能邊界的重要例外才需展開。

### 4.2 有資料才提供

- 既有成果文件的本地位置。
- 已確認的階段。
- 已有能力、交付回報、執行證據與已知限制。
- 已確認決策、僅供建議的方案及待決事項。

未知可寫未知，不為填表猜測。需求不足以界定成果時，集中詢問真正缺少的產品語義；可唯一推導的整理工作自行完成。

### 4.3 既有功能增補必補的差異

```text
原定目標：
目前能做：
目前不足：
本次新增或改變：
必須保留的原行為：
不處理：
```

沒有舊基準時，依已確認原需求與本次增補建立完整基準；無法確認的既有承諾列待確認，不從實作猜測。
已有基準時，保留既有 ID、有效證據與未受影響需求；只修訂本次受影響部分。

## 5. 需求轉成果的規則

- 以使用者可觀察成果分組，不照檔案、Ticket、測試名稱或程序清單拆表。
- 每列有清楚功能邊界與可驗收子項，不遺漏、不重複計入核心需求。
- 技術方法與需求分開；替換技術路線不得無聲降低成果。
- 原有需求草案或成果表可作輸入：核對與標準化，不必刪掉重寫，也不可機械照抄。
- 檢查每項已確認核心需求是否有對應成果。缺漏就明示，不無聲刪減、不自行新增功能。
- 歷史交付與現有實作只作進度線索，不用來反推或縮小需求。
- base 的已驗收初始為「—」、狀態為「未盤點」。有進度者記「待首次盤點」，不因 CLOSED 預填完成。
- update 新增項目不繼承完成狀態；分母或需求修訂記錄已確認變更。
- align 分清靜態、隔離案例與真實行為證據，不把票結案、豁免或檔案存在當成完整功能證明。
- 不為建表新增測試、付費呼叫、票或治理程序。

## 6. 「約定」與進度的意思

「約定」是一列成果中，已明確列出的可驗收子項總數，是該列達成度的分母。
不是 1～5 分評等，不是難度、優先序、票數、天數或模型信心，也沒有最多五項的限制。

例：共同保存有五項明列要求：
1. 手動 update 修改後保存。
2. 手動 align 修改後保存。
3. base 新建文件可保存。
4. 單檔保存不夾帶其他修改。
5. 保存失敗如實回報，不假稱成功。

則約定＝5。若核對後只有其中三項有符合要求的證據，已驗收＝3，達成度＝60%。
剩餘兩項須分清尚未實作、已實作未驗或缺前提，不能由百分比推定。

| 已驗收 | 約定 | 達成度 | 解讀 |
| --- | --- | --- | --- |
| — | 5 | — | 尚未盤點，不代表零項完成 |
| 0 | 5 | 0% | 已盤點，沒有任何子項被接受通過；原因須看明細 |
| 3 | 5 | 60% | 五項約定中三項已驗收，不是工時完成60% |
| 5 | 5 | 100% | 本列約定均已驗收，不代表所有其他列或全部情境通過 |
| — | — | — | 無約定，不計比例 |

百分比由計數推導，不另行主觀維護。子項不是等工時或等重要性；關鍵缺口不得被其他子項抵銷。
一個子項包含多個必要條件時，必須滿足該子項要求才整項計入，不自行給半項。
不要把每個句子拆成一項湊數，也不要把互不相關功能塞在一項；採最少且完整的功能粒度。
每個分母須可對應明細中的具體子項，不能先填數字再補內容。
約定變動只能經已確認的 update；align 不得自行減少分母來提高達成度。
不計跨階段總平均或總百分比。

## 7. 提示詞編譯與交接

交付內容須可獨立使用，帶入已整理的需求、決策與限制，不只寫「依前文」或一個議題名稱。
不要求使用者重新教 Skill 如何編號、計數、核對、保存；只補本次特有要求。

- 外部材料先由 Perplexity 消化；Claude 交接只放整理後內容。
- 交付 Claude 的 prompt、摘要或文件，不包含外部服務名稱、外部文件檔名、讀取紀錄、存取協議或「不要求存取」旁註。
- 保留執行必需的本地程式、設定、成果及產物路徑。
- 沒有實際本地 receipt，不宣稱已呼叫 Skill、寫檔、提交或驗收。
- 本協議是需求整理與提示詞規範，不代表已修改 Skill。

## 9. 範例二：既有功能不足，追加能力

以下是供 Claude 執行的模式選擇指令，不是新增 Projman 模式；先定位文件，再實際呼叫 base 或 update。

```text
/projman base <議題名稱>
專案：
既有成果文件：<有則填；尚無則明示沒有>
開發情境：既有功能增補

原定目標：
<議題原本要達成什麼>

目前能做：
<已知能力，區分實際證據與交付回報>

目前不足：
<具體情境下做不到什麼，造成什麼影響>

本次增補需求：
1. <新增／改變的行為與預期結果>
2. <重要例外與限制>

必須保留：
<原有需求、相容行為、資料或操作方式>

不處理：
<本次排除事項>

已確認決策：
<已採納的變更前後與交付取捨>

待確認：
<沒有則寫無>

先定位有效成果基準：
- 尚無：實際呼叫 Projman base，依已確認的原需求
  與本次增補建立完整成果表。
- 已有：實際呼叫 Projman update，修訂同一份，
  保留原 ID、有效證據與未受影響內容。

不因增補另建平行文件，不從實作推定全部原需求，
新增能力不繼承完成狀態。
本次不執行 align，不重新測試、不開票；
依現行 Projman 規則核對、單檔保存並如實回報。
```

## 10. 完成回報與退出

回報只需包含：
1. 實際呼叫的模式、成果文件位置。
2. 階段、成果分組與約定數，以及必要需求差異。
3. 已確認變更或真正待決事項。
4. 核對、保存結果與限制。

沒有實際執行，不宣稱已落盤。基準建立或修訂完成即退出，不自動啟動 align、開票或實作。
後續 align 依使用者指令或已生效的正常收束規則執行，不為填表製造新場景。
